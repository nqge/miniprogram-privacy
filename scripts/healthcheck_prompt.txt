运行 bash /root/.openclaw/workspace/scripts/healthcheck.sh。

**只在有 FAIL 时通知**：
- 若输出里 FAIL=0 → 一句话汇报「巡检通过 PASS=N」即可，不要贴全部输出
- 若有 FAIL → 贴出失败项和原因，并写进 memory/YYYY-MM-DD.md

**当前 FAIL 的 28 类含义**（由 `scripts/gen_healthcheck_instruction.py` 从 healthcheck.sh 自动生成，**不要手写**）：
（以下是「可处理」类的含义；E 类明文凭证、M 类 provider 韧性属长期项，
已在脚本里自动归入「等你」组，不触发告警）
- A 飞书 token / GitHub 额度（认证 5000 次/小时）/ 嵌入代理
- B gateway / embed-proxy / log-cleanup.timer / quick-health.timer
- C 索引完整性 + Embeddings 可用
- D announce 型必须 delivered=True（这是曾经静默失效的环节）
- E GIT_CREDENTIALS.md / gh hosts.yml（**需牛哥哥本人吊销重签，不要自己改**）
- F 「每日学习」/「每日反思」小节是否重复（**查全部每日笔记文件**，不只今天 —— 只查重复不查缺失，缺失可能是合法的）
- G 本地与远端一致
- H 真实跑一次记忆检索 + API
- I 茶馆蒸馏进度 + 队列自洽性
- J L1 经验库活跃度 + 每条经验是否都能被检索到
- K 根目录整洁度
- L SESSION-STATE 头部日期
- M 只有一个 provider 时，fallback 全在同一账号下 → provider 级故障时兜底无效
- N 单个记忆文件 > 300KB / 索引块垄断 > 60% / memory/ 目录 > 200MB
- O MEMORY.md 与 L1 主库声明的条目数是否与实际文件数一致
- P 某个每日笔记里的小节日期晚于文件名（跨零点写错文件）
- Q cron 指令里的 FAIL 含义清单是否与 healthcheck.sh 的实际组数一致（防过期手册）
- R cron 任务超时余量：某任务最近因超时失败（脚本 0.2s 但 agent turn 跑了 300s，时间全耗在 LLM 推理）→ 提高该任务 timeoutSeconds；手写的 timeout 值彼此不可比
- S 连续性入口的「当前状态」是否过期
- T cron 指令里会写每日笔记/跑长脚本的任务，是否都带了【跨日提醒】和【等待方式】
- U cron 实测耗时 vs 超时余量：最近一次超过 70% → FAIL；最近 3 次递增且超 50% → WARN（巡检一周长了 11 倍，这个趋势原本没人看得见）
- V 会话里的长 poll(指令说了但没照做的信号)
- W 【V】判据自身的单测(防判据本身是坏的)
- W2 cron 投递判据单测(E55：本该发什么)
- W3 小节长度判据单测(2026-11-03 加:正则盲区)
- X 巡检脚本自己的解析器自检(防断言装死)
- Y 外部 API 的响应延迟(不只是能不能通)
- Z 压缩后重注入的上下文预算（防红线被截掉）
- 附加：**systemd 配置漂移**（单元 enabled / 脚本存在 / 关键指令真正生效 / 定时器调度 / 敏感文件权限）
- 附加：**quick-health 的 OnFailure 告警链路是否生效**（用 systemctl show 取值，不 grep 文件）

**排查提示**：
- 静默失败优先排查「触发→执行→落盘→投递」每一段，别只看状态字段
- 每周 3、6、9、12 会各多一个小节（写入前先看今天有没有）
- 若 FAIL 项是「明文凭证」类 → 那是**长期项**（等牛哥哥吊销 PAT），
  不要为了消警告去删凭证文件，那会打断他的工作流
