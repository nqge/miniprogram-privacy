# 2026-11-21（周六）

## 08:10 —— 心跳：抓到【D】组的「陈旧快照」假故障

### 巡检结论

07:00 巡检 `PASS=86 FAIL=0 WARN=5`，灾备审计 `PASS=19 FAIL=0`。
两个「等你」长期项（额度充值、fallback 同账号）状态不变，等牛哥哥决策。

但**有一个 WARN 我不接受**：

```
⏳ 等你 daily-reflection 运行失败（lastRunStatus=error，原因：额度耗尽(API rate limit，需充值)）
```

它在报告里被列为**当前故障**。查下去发现：**这是 6 天前的陈旧快照**。

### 根因：数据源换了，但断言还在读旧源

2026-11-16 起 `daily-learning` / `daily-reflection` 改由 **systemd 闸门触发**
（cron 里 `enabled=False`，只作为被触发的目标）。

而【D】组读的是 `/root/.openclaw/cron/jobs.json` —— 这份文件**迁移后再没被写过**：

```
daily-reflection: enabled=False | lastRunAt=None | lastRunStatus=error
```

`lastRunStatus` 还停在迁移前最后一次 cron 运行的结果。硬证据：

| 证据 | 值 |
|---|---|
| 最后一次 cron 运行 | **2026-11-15 07:03**（status=error，额度耗尽，耗时 217s） |
| 迁移日 | **2026-11-16** |
| cron 里的 `nextRunAtMs` | 2026-11-22 07:00 —— 但 `enabled=False` → **永远不会触发** |
| systemd timer | `OnCalendar=Sun *-*-* 07:00` → 首跑 **明天 07:00** |

→ 所以这条「故障」既**过期 6 天**，又**还没到新路径的首次执行**。

### 为什么会漏

判据里的守卫：

```python
if run_status is None and not st.get("lastRunAtMs"):
    print(f"WARN {name} 尚未运行过（新建任务，等待首次执行）")
    continue
```

`run_status` 是**陈旧的 `error`**（不是 `None`）→ 守卫**永远不触发** →
判据把 6 天前的失败当成「刚发生」。

### 讽刺点：两个组读的是**两套数据源**

- 【G2】组读 `memory/gate-history.jsonl`（**活的**）→ 报的是真实闸门行为
- 【D】组读 `cron/jobs.json`（**冻的**）→ 报的是历史残留

**同一个 job，两组用不同真相源** → 一组准、一组假，而且没人发现。

### 附带发现

`daily-reflection` 是**周频**（`0 7 * * 0`）→ `systemctl list-timers` 显示 `LAST = -`
（从未跑过）**是正常的**，不是故障。我一开始差点误判成「timer 坏了」。

→ **定时器刚建 + 周频 + 今天不是周日** = 三重巧合，
   看 `LAST=-` 之前必须先确认 `OnCalendar` 表达式。

### 落地（08:20 完成）

#### 1. 修【D】组：识别陈旧快照，改读活的闸门历史

`scripts/check_cron_delivery.py` 新增 3 个函数 + 迁移日常量：

| 函数 | 作用 |
|---|---|
| `_read_gate_history()` | 读 `memory/gate-history.jsonl`（**活的**真相源），坏行跳过 |
| `_gate_records_for(history, job)` | 按 job 名过滤（兼容 `-gate` 后缀） |
| `_gate_result_is_failure(rec)` | `error` → 故障；`blocked`/`skipped` → **闸门正常工作**，不算故障 |
| `_stale_snapshot_info(job, history, env, job_id)` | 判定「cron 已 disabled + 迁移后没在 cron 跑」→ 陈旧快照 |

判定条件（三条同时成立才算陈旧）：
① cron 任务 `enabled=False` ② cron 侧最后运行早于 **2026-11-16**（迁移日）
③ → 改读闸门历史判定，**不再把旧快照当当前故障**

**输出对比**：

```
落地前：⏳ 等你 daily-reflection 运行失败（lastRunStatus=error，原因：额度耗尽(API rate limit，需充值)）
落地后：✅ PASS daily-reflection cron 快照已陈旧（cron 最后运行 2026-11-15，
        闸门最后记录 无记录）→ 按活的闸门历史判定，非当前故障（E81）
```

#### 2. 新增巡检组【W7】（E81 判据单测）

`scripts/test_e81_stale_snapshot.py` —— **23 个用例**，import 真身不抄判据。

**双向覆盖**（E80 的教训：加过滤 = 把判据改弱，必须两边都断言）：
- ✅ 真阳性：陈旧快照 → **不**报当前故障
- ✅ 真阴性：闸门 `error` → **要**报；`blocked` → 不报；cron 仍 enabled → 走原路径
- ✅ **注入自检**：改判据 → 结果**必须**跟着变（防「注入空转、测试全绿但什么都没测」）
- ✅ 真实场景复现：直接用真的 job id 拉 cron 运行历史

#### 3. 顺带挖出第二个真 bug：**缓存失效范围不够 → 陈旧 FAIL 被永久缓存**

修完上面那个，跑巡检却仍报：

```
FAIL L1 经验库有经验检索不到 -- 结果: 81/81 条经验可被检索
```

**两个事实互相矛盾**。查缓存 `/tmp/openclaw/l1_verify_cache.json`：

```json
{"fp": "dcb443...", "rc": 1, "line": " 结果: 81/81 ...", "fails": ["❌ FAIL E81 不在主库里"]}
```

→ 缓存的是**中间状态**（E81 独立文件已建、主库还没同步那一刻）的 FAIL。
→ 而**指纹只覆盖 `L1-entries/E*.md`**，同步主库只改主库文件、
  **独立文件一个字节没动** → 指纹不变 → **陈旧 FAIL 无限期缓存**。

**修法（两处）**：
1. 指纹扩到**所有会改变结论的文件**：独立文件 + `L1-experience-library.md` + `MEMORY.md`
2. `verify_l1_retrieval.py` 的**结果行必须扣掉 misses** ——
   原来 hits 只数结构通过数，不扣失败 → 才会出现「81/81 可被检索」+「FAIL E81 不在主库里」

→ 这条本身就是 E81 的**第二个实例**：**派生数据会过期，缓存也会过期**，
   而且**过期的方式很隐蔽**（指纹没覆盖到真正会变的那部分）。
