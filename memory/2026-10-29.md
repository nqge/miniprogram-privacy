### 元认知（很小但值得记）
- **「无新内容」不等于「任务失败」** —— 巡检类任务最容易被误判成「没干活」。
  脚本跑完、队列干净、产出为空 → 这就是**正确完成**。

  多一次调用就多一次 gateway 状态读写，多一分出错面。
- **等待方式**：本轮 `exec(yieldMs=10000)` → 后台 → `process(poll, timeout=10000)`，
  一次就拿到结果（20s 的脚本，1 次 poll 命中）→ 印证 E35 规则：
  **poll 要短、要多次，别一次等满**。

  **dump core** → 只能按文件名精确匹配导入

**采用的方案**：`scripts/memory_batch_search.mjs`
- 一次 Node 进程，复用同一个 memory manager，串行跑完所有查询
- **三个坑（都实测踩过）**：

- **必须有等价性自检**（否则断言装死）：`node scripts/memory_batch_search.mjs --self-test`

## 🫀 2026-10-29 10:31 心跳 —— 修掉【D】组的硬编码常数（+ 一次自伤）

**上下文**: 健康 · Compactions 0

### 起因
上一轮收尾时记的 TODO：【D】组的 PASS 计数是**硬编码 6**（`PASS + 6 - cron_fail`），
那是 2026-10-26 手写的快照值 —— 断言数一变它就悄悄错了，且**没人看得见**（巡检照样报绿）。

### 改法
改成**按实际输出的 PASS 行数计**：`cron_pass_count=$(printf '%s\n' "$cron_out" | grep -c '^PASS')`
→ 从源头消除「常数过期」这类漂移，以后加断言不用记得回来改数。

### ⚠️ 我自己踩的坑：改这段时**误删了渲染循环**
第一次编辑把 `while IFS= read -r line; do case ... done <<< "$cron_out"` 整段连带删掉了
（我以为那段在 oldText 里，实际它在上面一行）→ 【D】组的 8 行输出**全没了**。

**症状**：全量体检 PASS 从 75 掉到 69、WARN 从 5 掉到 2 —— **数字变小了，但没人报警**，
因为「少了一组断言」和「断言全过」在计数上无法区分。

**怎么发现的**：跑完 10:01 那轮改动的体检 → PASS=69 WARN=2，与改动前的 75/5 对不上，
于是 stash 一下对比：stash 后 75/5，pop 后 69/2 → 锁定是我的改动引入的。

**教训**：
> **PASS 总数变小 ≠ 断言变严了，也可能只是「有几组没跑」。**
> 改巡检脚本后**必须对比改动前后的计数**，差值对不上就是出了问题。
> —— 这正好是 E53「快照管不住退化」的另一个变种：这里连快照都没有了。

  → **74 才是真值**，原来的 75 本身就是那个硬编码常数虚增出来的 ✅
