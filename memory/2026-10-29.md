**为什么不一致**：cron 那次跑完之后，工作区又产生了新 commit（10-28 白天/晚间的工作），
所以「全绿」是**当时**的快照，**不是现在的状态**。
→ **状态字段描述的是「任务跑完那一刻」，不是「用户现在得到的结果」**（老教训，第三次撞上）

### 真正的洞：连续 3 次 cron 超时
查 `openclaw cron runs --id 480555ac...` 发现历史：
| runAt | duration | status |
|---|---|---|
| 10-27 00:00 | 300071ms | error: cron: job execution timed out |
| 10-27 00:45(手动) | 600021ms | error: cron: job execution timed out |
| 10-27 01:00 | 600015ms | error: cron: job execution timed out |
| 10-27 03:00 | 47185ms | ok |
| 10-28 03:00 | 151153ms | ok (PASS=19) |

**超时的是「等」不是「跑」** —— 脚本本身只要 **0.164 秒**，

### 元认知（很小但值得记）
- **「无新内容」不等于「任务失败」** —— 巡检类任务最容易被误判成「没干活」。
  脚本跑完、队列干净、产出为空 → 这就是**正确完成**。
  反面风险是：为了「留点痕迹」硬写一篇学习笔记，把空内容包装成洞察。
- **空队列时 `--mark-distilled` 是无害的空操作，但仍应跳过** ——
  多一次调用就多一次 gateway 状态读写，多一分出错面。
- **等待方式**：本轮 `exec(yieldMs=10000)` → 后台 → `process(poll, timeout=10000)`，
  一次就拿到结果（20s 的脚本，1 次 poll 命中）→ 印证 E35 规则：
  **poll 要短、要多次，别一次等满**。

### 6) 体检提速：103s → 54s（真正的瓶颈不是 CLI）

**先 profile 再优化**（我差点犯「凭直觉改」的错）：
- 把 25 个 python 块逐个计时 → PY8 占 21s，**但那不是最大头**
- 量 `verify_l1_retrieval.py` → **77 秒**（占体检 80%）→ 真正的瓶颈

**根因**：`openclaw memory search` 每次要起一个 Node 进程
- 实测：CLI **4.85s/次**，其中 embedding 只要 **0.36s** → 其余全是 Node 启动 + 插件注册
- 17 条经验要查 17 次 → **78 秒**

**试过并否决的方案**：
- ❌ **并行 4 路**：**86.9s，比串行 78.4s 还慢** —— 2 核机上并发只抢 CPU
  （与 TOOLS.md 里「8 并发零加速、18 个慢 3 倍」的记录一致）
- ❌ 遍历导入 dist 下所有 .js 来找导出：**触发 CLI 副作用**（"Memory index updated"）+
  **dump core** → 只能按文件名精确匹配导入

**采用的方案**：`scripts/memory_batch_search.mjs`
- 一次 Node 进程，复用同一个 memory manager，串行跑完所有查询
- **三个坑（都实测踩过）**：
  1. 打包后 export 名被压成单字母（search-manager 导出 `n`/`r`/`t`，
     `n` 才是 getMemorySearchManager）→ **不能靠名字猜**，只能挨个试
  2. `new URL('file://' + absPath)` 把绝对路径当 host → 要用 `pathToFileUrl()`
  3. `pathToFileUrl()` 返回的是**字符串**，再 `.href` 就成了 `undefined`
     → `import(undefined)` 报 "Cannot find package 'undefined'"（最迷惑的一个）
- **必须有等价性自检**（否则断言装死）：`node scripts/memory_batch_search.mjs --self-test`
  → 逐条比对 path + score → PASS
