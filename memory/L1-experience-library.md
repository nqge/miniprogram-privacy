## 🔧 排查方法论


### E1：区分「失败」和「没触发」
> 本条讲：**区分「失败」和「没触发」**

**场景**：定时任务没产出结果。
**陷阱**：看到没产出就归因为「任务失败了」→ 去查日志、查错误码 → 什么都查不到 → 记为「已知残留项」。
**岔路口**：先查 **cron runs 历史**（有没有触发记录）→ 有记录 = 失败（查日志）；没记录 = 没被调度（改频率/查调度器）。
**证据**：2026-10-26，`daily-learning` 10-24/10-25 零产出。查 runs 历史发现
**10-19 之后到 10-26 之间零次触发** —— 不是失败，是根本没跑。


### E2：口径不一致的对比会产生假告警
> 本条讲：**口径不一致的对比会产生假告警**

**场景**：比对「本地 vs 远端」文件数。
**陷阱**：一边用 `find`（含运行时垃圾如 `__pycache__`），另一边用 `git ls-tree`（只含被追踪文件）→ 报「漏文件」。
**岔路口**：**先确认两边用同一口径**，再判断差异是否真实。
**证据**：2026-10-26，`backup_audit` 报「scripts/ 远端 8 < 本地 9」，实测 `git ls-files` 两边完全一致。


### E3：清理想删旧文件，先确认判龄信号本身有效
> 本条讲：**清理想删旧文件，先确认判龄信号本身有效**

**场景**：清理按时间轮转的日志。
**陷阱**：用 `mtime` 判断「文件多旧」→ 规则永不触发，而且**看起来一直在正常工作**。
**岔路口**：先验证判龄信号本身（打印每个文件的实际年龄）；轮转方式与文件系统行为不符时，
**唯一可靠信号通常是文件名里的槽位标识**。
**证据**：2026-10-26，OpenClaw 日志轮转**按大小不按天** → 同一槽位跨天追加 → `mtime` 永远新鲜
→ `-mtime +7` 规则一次都没触发过。


### E4：涉及「默认值/协议/常量」的结论，必须查源码或实测
> 本条讲：**涉及「默认值/协议/常量」的结论，必须查源码或实测**

**场景**：判断某个配置项的默认行为。
**陷阱**：读文档或凭印象 → 写进记忆文件 → 下个会话当成已验证事实继承。
**岔路口**：`grep` 源码里的常量定义 / 直接实测。
**证据**：2026-10-26 两次栽在这上面 ——
① 「agentTurn 型 cron 默认 timeout 是 30s」实为 **360s**（30s 是 `apply.runtime` 搜索路径的值）
② 「远端提交已添加 `bin/requirements.txt`」实为**文件根本没提交**。


### E5：提交说明 ≠ 文件真的存在
> 本条讲：**提交说明 ≠ 文件真的存在**

**场景**：判断某个修复是否生效。
**陷阱**：读 commit message 里的「已添加/已修复」就当作事实。
**岔路口**：`git ls-tree` / `git show --stat` 落到**文件层面**核实。
**证据**：2026-10-26，远端 `ad8098d` 声称「添加 bin/requirements.txt」→ `git ls-tree origin/main bin/` 只有脚本。

## 📏 工程取舍


### E6：状态字段 ≠ 用户得到的结果
> 本条讲：**状态字段 ≠ 用户得到的结果**

**场景**：任何「自动化是否正常工作」的判断。
**陷阱**：只看 `status=ok` / `enabled` / `consecutiveErrors=0` → 绿色一片，实际功能全死。
**岔路口**：沿着 **触发 → 执行 → 落盘 → 投递 → 用户看到** 逐段取证，每段单独断言。
**证据**：2026-10-26 一天内四个例子——
① 记忆检索 `enabled` 但 Embeddings unavailable（**从 3 月起就没工作过**）
② 飞书投递 `status=ok` 但结果从未送达
③ 学习笔记不报错但周频让 4/8 天根本不触发
④ 茶馆摘要稳定落盘但 4/15 讨论从未被提炼


### E7：定时器保证触发频率，不保证信息增量
> 本条讲：**定时器保证触发频率，不保证信息增量**

**场景**：设计周期性任务。
**陷阱**：把「每 4 小时跑一次」当成「每 4 小时有新东西」→ 重复产出、浪费存储。
**岔路口**：落盘前与上一份比对，内容相同则跳过。
**证据**：2026-10-26，茶馆 0039 与 0040 两份摘要**全文 1671 行、diff 仅 4 行**（99.8% 相同）。


### E8：纯脚本任务不该用 agent 型 cron
> 本条讲：**纯脚本任务不该用 agent 型 cron**

**场景**：让定时器执行一个 shell 脚本。
**陷阱**：agent 型 cron 为了跑一个 20ms 的脚本，消耗 261 秒的模型往返。
**岔路口**：需要判断的用 agent 型；纯脚本用 systemd timer。
**证据**：2026-10-26，`log-cleanup` 改成 systemd oneshot → **261s → 21ms**。


### E9：收集、存储、加工是三件事
> 本条讲：**收集、存储、加工是三件事**

**场景**：构建「信息采集」类系统。
**陷阱**：把「收集」当成终点 → 数据进磁盘，但从未影响判断。
**岔路口**：加工环节要独立存在（待办清单 + 进度断言），否则收集系统只是**浪费磁盘的订阅服务**。
**证据**：2026-10-26，茶馆 monitor 忠实收集 95 条讨论，**4/15 未被提炼**。


### E10：同一文件里的多个同类小节会指数膨胀
> 本条讲：**同一文件里的多个同类小节会指数膨胀**

**场景**：让 agent「在已有小节内追加」而非覆盖。
**陷阱**：频繁触发 + 追加语义 = 每次跑一次多一节。
**岔路口**：明确规定「每天只允许 1 个小节，已有则**替换/精炼**」；长度写成硬约束并自检。
**证据**：2026-10-26，一天堆出 **6 个学习小节、单节 3365 字**（约束是 100-200 字）——
典型的「反刍」。


### E11：新增断言必须做注入故障验证
> 本条讲：**新增断言必须做注入故障验证**

**场景**：写检查脚本（巡检、校验器）。
**陷阱**：脚本跑出 PASS=20 就认为它有效 —— 它可能内含一个**永远抓不到故障**的分支。
**岔路口**：注入故障（停服务 / 造分歧 / 造未蒸馏）→ 确认它真会 FAIL → 恢复。
**证据**：2026-10-26，9 组断言里 **4 组写完后自己坏过**；
且第一版【I】组把蒸馏稿也算进搜索范围，一直**误判 PASS** ——
**检查自己产出的文件，等于没检查**。

## 🧭 认知与判断


### E12：落盘 ≠ 送达
> 本条讲：**落盘 ≠ 送达**

**场景**：把待办、结论、选项单交给用户。
**陷阱**：写进文件就以为「做完了」→ 文件存在反而带来虚假的安全感。
**岔路口**：每个待办问一句「**他怎么知道？**」—— 答不上来就是没做。
**证据**：2026-10-26，`待决策选项单.md` 在磁盘上躺了 6 周，**从未进入用户视野**。


### E13：机制缺口比单点故障更值得修
> 本条讲：**机制缺口比单点故障更值得修**

**场景**：同时发现多个「功能其实早就是死的」。
**陷阱**：逐个修完就收工 → 下个月同样的问题换个马甲再来。
**岔路口**：修完一个，追问「**为什么现有机制没抓到它**」，把那条断言补进每日巡检。
**证据**：2026-10-26 发现的四个故障，**没有一个**是被原有机制抓到的。


### E14：风险描述不能靠记忆，要靠实测
> 本条讲：**风险描述不能靠记忆，要靠实测**

**场景**：评估某个凭证/配置的风险等级。
**陷阱**：沿用之前的描述 → 用户基于错误前提做优先级判断。
**岔路口**：涉及权限/额度/影响范围时，**实测**（查 scope、查实际权限），不要只复述「是不是明文」。
**证据**：2026-10-26，classic PAT 原记录是「明文落盘」，实测 scopes 含
`admin:org` / `delete_repo` / `admin:enterprise` → 实际是**账号完全控制权**。


### E15：对外收敛 ≠ 对内收敛
> 本条讲：**对外收敛 ≠ 对内收敛**

**场景**：判断某件事该不该做。
**陷阱**：把「用户不在场」当成「可以无限期做」→ 内部学习、笔记、维护一起停掉。
**岔路口**：区分**对外动作**（要克制）和**对内动作**（零成本、不打扰，照常）。
**证据**：2026-10-21 的反思（当时定规矩）→ 10-24/10-25 两天 memory 零文件（规矩失效）。


### E16：低触发频率的机制没有容错
> 本条讲：**低触发频率的机制没有容错**

**场景**：把某个每日任务调成每周/每月以「省资源」。
**陷阱**：低频 = 每次失败就是整周空白，且**空白期往往正是无人注意的时候**。
**岔路口**：频率是**容错参数**，不是省钱旋钮。
**证据**：2026-10-26，daily-learning 周频 → 10-24/10-25 零文件。


### E17：检索的最小单位是「块」，不是「条」——短章节会被切碎稀释
> 本条讲：**检索的最小单位是「块」，不是「条」——短章节会被切碎稀释**

**场景**：新建知识库 / 经验库 / 笔记体系；任何「写下来了但搜不到」的现象（沉淀一条新经验时）。
**陷阱**：验证「文件存在、条目数对、mtime 新」就宣布完成 → 内容**写完即死**。
更隐蔽的一层：检索按 token 切块（`chunking.tokens=200`），**切在条目中间时标题和「场景」被切走**；
短小节夹在两个长小节之间时，标题与正文分处两块，**两块都不以这条内容开头** → 向量被邻段平均掉，
搜原文措辞也排不进去。检索到的是**语义残片**，不是你的条目。
**岔路口**：① 建完立刻拿**原文措辞**检索一次，排不进前列就重写标题/措辞（命中分数是硬指标，不是感觉）；
② 关键条目**首行重复标题关键词**（本文件的 `> 本条讲：` 约定即为锚点），让条目在任意切块下都自洽；
③ 独立条目**拆成独立文件**，彻底摆脱邻段稀释（最有效，见下方证据）。
**证据**：2026-10-26 建立 L1 库（16 条）→ 用原文措辞搜「区分『失败』和『没触发』」，
L1 排第 1（**0.6554**）→ 但新增 E17 后搜「沉淀 验收标准 检索命中」，**E17 所在块没进前 6**；
查库见其被切成 20-45（开头是反思）与 41-57（开头无标题）两块 →
补标题锚点后仍被邻段稀释 → **拆成独立文件 `memory/daily-notes-index.md` 后直连余弦 0.5457 排第 1**
（同查询下旧写法为「未进前 6」）。

### E18：记住了 ≠ 不再踩，要改结构
> 本条讲：**记住了 ≠ 不再踩，要改结构**

**场景**：任何「我刚犯过这个错」「我刚记录过这条教训」的场合。
**陷阱**：把教训写进笔记 / 记忆文件就当解决了 → 同样的错误换个场景再来，
而且因为「我已经记过了」，反而不会再警惕。
**岔路口**：凡是**已经踩过一次**的错误，要改的不是记忆而是**结构**：
- 长文本（尤其含反引号、`>`、`$`）→ 写进文件，用 `--message "$(cat file)"` 引用，不要裸放命令行
- 危险字符 → 用 heredoc（`<< 'EOF'`）而非拼接字符串
- 路径 → 提取成变量，不重复手写
**证据**：2026-10-26 12:15，我给 cron 改指令时在命令行里写了反引号和 `>`：
- 反引号 → **命令替换** → `memory/YYYY-MM-DD.md` 被当命令执行
- `>` → **输出重定向** → `memory/daily-notes-index.md` 被当输出目标
- 两个文件路径**从指令里消失**，而命令**「成功」返回了 JSON**（无报错）
讽刺的是：我 20 分钟前刚把这条写进 E17 那一节的上下文里（「检查自己产出的文件等于没检查」）。
→ **记教训是最弱的改进步骤，改结构才是。**


### E19：bash 里嵌套 heredoc + 命令替换会吞掉变量
> 本条讲：**bash 里嵌套 heredoc + 命令替换会吞掉变量**

**场景**：在 shell 脚本里用 `$(...)` 包一个 heredoc（python 代码），再把结果放进变量。
**陷阱**：变量**静默变成空串**，不报错、不中断。表现是「写进去了，但值是 0/空」。
**岔路口**：把 python 代码抽成**独立脚本文件**，用 `python3 script.py "$arg"` 调用，
不要在 shell 里内嵌 heredoc。需要多参数就全部走命令行参数。
**证据**：2026-10-26 12:20，给 healthcheck.sh 加「自动更新 SESSION-STATE 巡检现状行」时：
```bash
GROUPS=$(python3 - "$SELF" << 'PYEOF'
...
PYEOF
)
NEWLINE="... ${GROUPS} 组断言 ..."
```
`bash -x` 显示 `GROUPS=12` 紧接着 `NEWLINE='... 0 组断言 ...'` —— **变量被吞**。
我试了固定路径（怀疑 BASH_SOURCE 空）、花括号、多字节字符、heredoc 改写，
**换了四种写法都是 0**，直到把 python 抽成独立脚本 `scripts/update_state_status.py` 才通。
**排查耗时超过 10 分钟，且过程中输出一直是「成功」** —— 静默失败最难查的就是这种。

### E20：验证的对象错了，结论就全错
> 本条讲：**验证的对象错了，结论就全错**

**场景**：想证明「某个机制能工作」。
**陷阱**：验证了**你想验证的东西**，而不是**实际生效的东西**。
**岔路口**：先问「**真正生效的是哪个？**」，再去验证它。

**同一类问题的三种形态**（2026-10-26 一天内连中三次）：

| 我验证的 | 实际生效的 | 症状 |
|---|---|---|
| 手动 `cron run` 成功 | 定时调度 | 从没真正无人值守跑过 |
| 交互 shell 里跑通 | systemd 环境 | PATH 缺 pnpm、`systemctl --user` 报 unknown |
| 文件里有 `OnFailure=` 这行字 | 指令真的生效 | 注释里也有这行字，grep 看着正常 |

**证据**：2026-10-26
1. 08:00 巡检我以为是自动跑过，实际是我自己手动触发的，还写成「无人值守下真实生效」
2. 30 分钟巡检第一版在 shell 里测过，systemd 下直接挂两项（PATH + XDG_RUNTIME_DIR）
3. 为了加一行 `ExecStartPost` 重写了整个 `.service`，把 `OnFailure=` 真实指令弄丢 ——
   **但注释里还留着这行文字**，所以 grep 能搜到，看起来一切正常，
   而故障时告警单元**完全不被触发**。

**怎么破**：验证时先确认「**我看到的东西就是系统用的东西**」。
- 指令是否生效 → `systemctl show -p <Prop> --value`（不是 grep 文件）
- 定时是否触发 → 找**真实的定时运行样本**（看 sessionId、时间和手动触发区分开）
- 状态是否正常 → 问「**实际运行的是谁**」（`/proc/<pid>/environ` 的 PATH）

**延伸**：**时间线是因果的证据**。09:02 失败 / 09:19 修 / 09:19 之后全成功 ——
这三条排在一起，因果关系不需要解释。如果只看「现在是 ok」，无法排除是偶然。

### E21：修症状 ≠ 修类
> 本条讲：**修症状 ≠ 修类**

**场景**：修完一个 bug。
**陷阱**：把「这个具体问题」修好就收工 → 同一类的下一个问题照样会静默发生。
**岔路口**：修完立刻问「**这一类风险还有哪些地方没覆盖？**」，
用一个检查**覆盖整类**，而不是每次出一处补一处。

**证据**：2026-10-26
我修了「重写 .service 把 `OnFailure=` 弄丢」这个**症状**（恢复指令 + 加一条断言），
但没问「『配置文件里的东西 ≠ 实际生效的东西』这一类风险覆盖到了吗」——
换个单元、改个路径，同样会静默失效。
于是又做了 `scripts/check_unit_drift.py`，把这一类系统性覆盖：
单元 enabled / 脚本存在 / 关键指令生效 / 解释器存在 / 定时器调度 / 敏感文件权限。

**怎么破**：
1. 修完先问「这是**个案**还是**一类**？」
2. 是类 → 找一个能**同时覆盖多个实例**的检查点
3. 新检查点**必须做注入故障验证**（否则它自己可能有盲区）

**代价对比**：个案修复 = 一次；类覆盖 = 一次 + 一个检查脚本，
但**同类问题再也不会复发**。

### E22：知道 ≠ 会做到
> 本条讲：**知道 ≠ 会做到**

**场景**：刚学会了一条经验。
**陷阱**：以为「我已经知道这条了」→ 写东西时**根本没想起它** → 犯了刚学过的错。
**岔路口**：知识要变成行为，得靠**机制**（可检查的约定），不能靠「我记得有这么回事」。

**证据**：2026-10-26 下午
我下午把 E17（「检索的最小单位是块，不是条」）写进经验库，
理由是「别把短小节塞进长文档」——
**然后我自己就把 19 条短经验全塞进了一个长文档**，
结果 19 条里有 **4 条检索不到**（E4/E6/E7/E9），写的时候完全没察觉。

**这不是讽刺，是机制问题**：
- 知道 → 需要**能被触发的条件**（比如「新增经验必须写进 L1-entries/」这个可检查的约定）
- 会做到 → 需要**自动验证**（`scripts/verify_l1_retrieval.py` 每天查一遍）
- 靠「我记得」→ **必然复发**

**怎么破**：每写一条经验，问「**这条要成立，需要什么条件？那个条件怎么保证？**」
如果答案是「我会记得」，那就**还没做完**。

### E23：担心要用实测替代想象
> 本条讲：**担心要用实测替代想象**

**场景**：发现一个疑似风险。
**陷阱**：凭想象推演出一个可怕的后果 → 记成「高危」→ 但**从没验证过**。
**岔路口**：**先量，再判**。担心本身不产生价值，**实测出来的结论才产生价值**。

**证据**：2026-10-26
我担心「GitHub token 进了记忆库 → 会被检索出来 → 通过飞书发出去」。
**实测**：`main.sqlite` 的 chunks 里完整 token 数 = **0**（只有 `ghp_` 前缀）。
**担心不成立。**

但**同一次实测**找到了另一个**更实际**的问题：
会话日志目录 755、6 个含完整 token 的文件是 644（全局可读）——
这个比「token 被检索出去」**更可能真的出事**。

**怎么破**：
- 担心 → 变成一条**可执行的检查**（查 sqlite / 查权限），而不是留在脑子里
- 实测结论可能推翻担心，**也可能指向另一个更真的问题**（这次就是）
- **两边都要做**：担心的不成立 = 排除一个风险；实测发现新的 = 找到一个风险

### E24：跑两遍不只是浪费，是会引入竞态
> 本条讲：**跑两遍不只是浪费，是会引入竞态**

**场景**：某个脚本被调用了两次（自己调自己，或两个入口各跑一次）。
**陷阱**：只是「慢一点」→ 忽略了两次读到的**是不同时间点的状态**。
**岔路口**：两次执行之间状态可能已经变了 → **结果可能不一致**。

**证据**：2026-10-26
`alert_dedup.py` 会自己再跑一遍 `quick_health.py`，
导致每次成功巡检实际跑两遍（8 秒 → 16 秒）。
**更要紧的是竞态**：
「第一次 FAIL、第二次 PASS」会让 dedup 误判为**已恢复** →
**发一条假的恢复通知，同时丢掉真实的故障**。

**修法**：`quick_health.py` 把结果写到 `logs/quick-health-result.json`，dedup **读它**。
效果：~14 秒 → ~7 秒，且状态与实际**严格一致**。

**怎么破**：修性能问题时顺手问一句「**这两次跑的结果可能不一致吗**」——
答案是「会」，那就不只是性能问题了。

### E25：发现问题时先问「这个真的需要对方参与吗」
> 本条讲：**发现问题时先问「这个真的需要对方参与吗」**

**场景**：发现一个问题，准备丢给对方。
**陷阱**：默认「这需要对方」→ 写成待办 → **其实自己就能修** → 风险一直挂着。
**岔路口**：写下待办之前，先花两分钟问：**真的需要对方吗？**

**证据**：2026-10-26
我发现 `openclaw-gateway.service` 里明文写着 `OPENSUBTITLES_PASSWORD`，
直接写进「残留项 · 需你重新申请密钥」。
**下一轮复核才发现**：
那两个凭据**没有任何代码在用**（tools/scripts/skills 全扫过，零引用）——
根本不用重新申请，**`chmod 600` 就完事了**。

**另一个例子**：PAT 残留项。
我原本只准备写「等你吊销」，但复核发现**权限加固、精确摸底、加断言防复发**
这些**我现在就能做**（而且做完才该找你 —— 剩下的才是真正需要你的）。

**怎么破**：
- 「需要对方参与」是**需要证据的判断**，不是默认状态
- 典型的不需要对方：权限、路径、配置、脚本、断言、文档
- 典型的需要对方：账号会话、付费、破坏性操作、影响对方工作流、方向决策
- **判断错了的代价是 asymmetric**：错判为「需要对方」= 风险挂着；
  错判为「自己能做」= 顶多多花两分钟

### E26：告警链路自身的失败模式，是「读到了上次的成功结果」

> 本条讲：**告警链路读到的可能是上次的成功结果 —— 故障时告警被静默吞掉**

**场景**：想证明「故障时告警真的会发出去」。

**陷阱**：OnFailure 处理器读巡检结果文件。
脚本如果**在写这个文件之前**就崩了/被 kill/超时，
文件里留的还是**上一次成功运行**的结果 → 处理器读到「无故障」→ **告警被静默吞掉**。

> 恰恰发生在系统最坏的时候 —— 而且**看起来一切正常**。

**岔路口**：
1. 注入崩溃 → 手动触发 OnFailure → 看告警单元说了什么
2. 观察它读的是**哪一次**运行的结果 → 定位到「时间错位」
3. 修复要两层：
   - **新鲜度校验**（结果文件超过 N 分钟 → 不信，自己重跑）
   - **running 标记**（开跑前写标记，跑完删掉；标记还在 = 没跑完 = 失败）

**关键**：只用「新鲜度」**不够** —— 崩溃发生在写文件前时，
旧文件可能只有 1 分钟前写的，看起来很新鲜。
必须靠 running 标记才能区分「刚成功」和「崩了」。

**成果**：
- 修好后 4 条路径全部验证：正常成功 / 检查项失败 / 崩溃在写文件前 / 文件陈旧
- 端到端走真实 systemd OnFailure 链路验证：`code=0 msg=success` ✅

**延伸**：这条其实是 E12「落盘 ≠ 送达」的**镜像版** ——
E12 讲「执行了不等于送达了」，E26 讲「读取了不等于读的是对的东西」。
两者都是**中间产物被误当作结论**。

### E27：两处结论同时错，根因通常是「测量环境不同」

> 本条讲：**两处结论同时错，根因通常是「测量环境不同」—— 先问是不是在测同一个东西**

**场景**：复核另一个会话（或过去的自己）写在共享文档里的实测结论。

**陷阱**：两边都「测过了」，数看起来也有依据，但**测的不是同一个东西**。
这次的实例：
- A 会话测「`--log-level warn` flag 有没有效」时，**环境变量还没配**
- B 会话（我）复核时，**环境变量已经配上了**
- 于是 flag 的效果被环境变量**盖住** → 看起来像「flag 无效」
- 而在**裸环境**单独测 flag，它完全有效（-100%）

同样地，「每次 CLI 调用都会重新注册全部插件」这个归因也是错的 ——
实测 CLI 调用产生 **0 行**，真实来源是 **agent session 启动**（同一秒成簇 16 行）。

**岔路口**：
1. 发现结论冲突时，**先问「两边测的是同一个环境吗」**，而不是先判断谁对
2. **构造「裸环境」单独测**：`env -u OPENCLAW_LOG_LEVEL ...`
3. 对照表要分维度量（动作 × 产生量），不要只测一个动作
4. 跨会话共享的文档（TOOLS.md / 运维笔记）**必须复核** ——
   写错的结论会一直复制下去

**证据**：2026-10-26 21:35，裸环境 3 次 CLI 调用：
默认 60630 字节 → 带 `--log-level warn` = 0 字节；
`openclaw cron list` × 5 → 0 条 Registered 行；
agent session 启动 → 同一秒 16 条。

**关键判断**：环境变量的价值不在于「比 flag 强」，
而在于**它能作用于非 CLI 的进程** —— 也就是 agent session 启动、systemd 单元这些
真正产生噪音的地方。flag 只在显式带 flag 的那一次调用里有效。

### E28：长期项和真故障混在一起，等于让信号失效

> 本条讲：**长期项和真故障混在一起，等于让「今天有没有故障」这个信号彻底失效**

**场景**：巡检里加了一条「客观存在、但要等别人才能解决」的断言。

**陷阱**：那条断言每天都会 FAIL →
1. 巡检从此**永久 exit 1** → 告警链路每次都触发 → 每次都被去重抑制 → 纯消耗
2. 更糟：**真故障出现时，它和长期项并列在同一个列表里** → 报告里两个 FAIL 并列，
   长期项把真故障的注意力带走了
3. 「今天有没有故障」这个信号**彻底失效** —— 永远是「有」

**岔路口**：
1. 给失败项**分类**：「可处理 — 现在就该修」 vs 「等用户 — 长期项」
2. 分类后：长期项**仍然全部报出来**（信息不丢），但
   - **退出码只看可处理项** → 服务该 success 就 success
   - **告警只对可处理项触发** → 长期项静默
   - 报告里两组分开显示，一眼看出哪些要动、哪些在等
3. 关键：**别把长期项「静音」成看不见** —— 那是另一种形式的信号失效。
   要静默的只是**通知**，不是**记录**

**证据**：2026-10-26 22:35，加了【M】Provider 韧性断言后：
只有长期项 → exit 0、不告警 ✅；注入真故障 → exit 1、告警发出 ✅；
每日报告分成「可处理 / 等牛哥哥」两组 ✅

**延伸**：这是 E6「状态字段 ≠ 用户得到的结果」的**变体** ——
E6 讲「状态绿着但功能死了」，E28 讲「状态红着但这个红不代表你的动作」，
两者都是**信号与含义脱节**。

### E29：断言的第一版阈值很可能是假警报 —— 先问「正常时它长什么样」

> 本条讲：**断言的第一版阈值很可能是假警报 —— 先问「正常时它长什么样」**

**场景**：2026-10-26 23:15，加了一条记忆库体检断言：
「单个文件占索引块数 > 25% → FAIL」。

理由听起来很硬：索引 215 块，某文件占 100 块（46%），「会稀释检索」。
但断言一加上就报 FAIL —— 而**当天其实没有任何问题**。

**陷阱**：我凭「直觉上的不均衡」设阈值，**没先量过「正常状态」长什么样**。
更关键的是——我后来去查了那个文件的内容：

```
搜「日志清理脚本形同虚设 38M」
  1. 0.8963 memory/2026-10-26.md
  2. 0.8679 memory/2026-10-26.md
  3. 0.7123 memory/2026-10-26.md
```

**4 块全在那个文件里，检索完全正常。**
那个文件是 15 小时连续工作的产物，里面是**真实且唯一的操作知识**
（日志清理脚本失效、技能仓库停滞、茶馆摘要去重…）—— 它**合法地**就该占 30-40%。

→ 我差点把「忙碌的一天」当成「故障」来报。

**岔路口**：
1. 加任何「规模类」断言前，先问：**「正常时它长什么样？」**
   - 样本：其他天分别是 1-8 块 → 今天的 35-46% 是**离群值，但不是错误**
   - 一个离群值不等于一个故障
2. 阈值要对着**真实故障**设，不是对着**我的不适感**设
3. 真故障长什么样？→ **两个可验证的特征**：
   - ① **没有上限**（memory/ 目录原本**完全没有任何体积限制**，
     而 `/tmp/openclaw` 日志有 50MB/200MB 上限 —— 对比才看得出缺口）
   - ② **开始垄断检索**（把别的文件挤掉）
   → 据此重设：单文件 > 300KB FAIL、占比 > 60% FAIL、目录 > 200MB WARN
4. **双方向验证**（这是必须的）：
   - 当前真实状态 → 全 PASS（不假警报）
   - 注入 400KB 文件 → 正确 FAIL（不漏报）

**证据**：重写后
- 真实状态（35% 占比、64KB 笔记）→ **3 项全 PASS** ✅
- 注入 400KB 文件 → **正确 FAIL** ✅
- 25% 阈值已废弃，并在注释里写明**为什么废弃**（防止以后有人「优化」回去）

**同时修掉的真实问题**：
今天笔记里有一段 748 行的**原始茶馆摘录**，而那些内容**已经完整存在**于
`memory/teahouse-digest-2026-10-26.md` → 纯重复存储。
已删除（105KB → 64KB，索引 215 块 → 179 块），只留蒸馏结论 + 指针。

**延伸**：这是 E28 的**反面教材** —— E28 讲「别把长期项静音成看不见」，
E29 讲「别把正常状态报成故障」。两者是同一件事的两面：
**信号必须和它要表达的含义对齐**，多报和少报一样有害。

### E30：队列型状态只加不减 = 每次运行都在重复劳动

> 本条讲：**队列型状态只加不减 = 每次运行都在重复劳动**

**场景**：茶馆监控每 4 小时跑一次，拉取新讨论 → 写入「待蒸馏清单」→ agent 蒸馏成知识。
看起来是完整的流水线。

**陷阱**：2026-10-27 凌晨发现，`memory/teahouse-todo.json` 的 `pending` 队列里
**永远躺着同样 4 条**（#135/#138/#134/#154）—— 它们在 11:30 就已经蒸馏完了。

根因：`prompt_distillation()` **只追加，从不移除**。
```
for i in fresh:
    if n in known: continue
    existing["pending"].append(...)     # 只加
# 全函数没有一句从 pending 里删东西
```
→ 蒸馏完成后**没有任何机制**把条目移出队列 → 每 4 小时重新蒸馏同样 4 条。

**为什么巡检没发现**：健康巡检的【I】组是**间接**判定的 ——
它查「编号是否出现在某篇 memory 笔记里」，出现就报 PASS。
但它**从不检查队列本身**，所以：
- 巡检报「茶馆内容已全部蒸馏」✅
- 而队列里明明还挂着 4 条 ❌
**两个状态互相矛盾，巡检只信了对自己有利的那个。**

**岔路口**：
1. 任何「待处理队列」必须配一个**出队**路径，且出队和入队一样显式
2. 蒸馏完成的条目 → 移到 `distilled` 列表（保留编号/标题，便于追溯）
3. **`distilled` 列表也要限量**（默认 50）—— 否则只是把「只增不减」换了个字段
4. 巡检要查**队列本身的自洽性**：
   `pending ∩ distilled == ∅`（同一议题不能既待处理又已蒸馏）
5. 修的时候顺手检查：**我查的字段对吗？**
   → 我一开始查 `seen_ids`（GitHub REST 的 10 位 id）以为没去重，
   实际去重键是 `seen_numbers`（议题号）→ **4 条都在里面**
   → 差点得出「修复会被 4 小时后推翻」的错误结论

**证据**：
- 修前：`pending` 恒为 4 条，每 4 小时重蒸馏一遍
- 修后：端到端跑真实监控 → 「无新内容」，`pending` 保持 0，`distilled` 4 条
- 巡检自洽性：注入「#135 同时在两个列表」→ **正确 FAIL** ✅；正常态 → PASS ✅

**延伸**：这跟 E29 是同一类问题 —— **状态字段和真实情况脱节**。
E29 讲「别把正常报成故障」，E30 讲「别让队列状态骗过自己」。
共同点：**光看一个状态字段不够，要交叉验证**。

### E31：只在指令里写「要记得做」= 把 bug 交给人的记性

> 本条讲：**只在指令里写「要记得做」= 把 bug 交给人的记性**

**场景**：2026-10-27 01:10，修完 E30（茶馆待办队列只加不减）之后，
我意识到自己的修复**留了个洞**：

```
cron 指令: "蒸馏完成后，把已蒸馏的议题编号标记掉"
           python3 scripts/teahouse_monitor.py --mark-distilled <编号>
```

**陷阱**：E30 的根因就是「**出队这一步靠人记得做**」。
我把这一步写进了 cron 指令 —— 但那**还是靠 agent 记得执行**。
指令是提示，不是机制。agent 忘了、或者跑歪了、或者指令被别的段落盖住，
bug 原样复发。

而且更糟：**巡检查不出来**。我原来的【I】组逻辑是：
```
still = [pending 里没出现在任何笔记的条目]
if still: FAIL        # 真未蒸馏 → 该报
else:      PASS        # 已出现在笔记里 → 报 PASS，但【不清理】
```
→ 「已蒸馏但没出队」这个 E30 的 bug 状态，**恰好落在 PASS 分支**里。
巡检说「一切正常」，而 bug 就在那儿。

**岔路口**：
1. **凡是「队列出队」类动作，必须有机制兜底，不能只靠指令**
   → 巡检自愈：检测到「pending 里的条目已出现在笔记里」→ **主动移出队列**
   → 出队不再依赖任何人记得做
2. **自愈和告警要分开**：
   - 「已蒸馏但没出队」→ **自愈**（本来就是对的，只差个出队动作）
   - 「真未蒸馏」→ **FAIL 告警**（真的需要人做事）
   → 自愈**绝不能掩盖真问题**：注入一个笔记里不存在的编号 → 仍必须 FAIL
3. **自愈之后要重新读盘**：自愈刚改过文件，继续用内存里的旧数据
   → 会报出「刚自愈完又说矛盾」的假 FAIL（我自己就踩了这个）

**证据**（双向都验了）：
- 注入 E30 原始 bug 状态（#135 已蒸馏但仍在 pending）
  → 「自愈：1 条已蒸馏但未出队 → 已移入 distilled [135]」，pending 归 0 ✅
- 注入真未蒸馏条目（#999，笔记里不存在）
  → **仍 FAIL**「茶馆有 1 条讨论未蒸馏」✅（自愈没掩盖真问题）
- 注入「#135 同时在两个列表」→ 正确 FAIL ✅
- 正常态 → PASS ✅

**⚠️ 我自己在这条上犯的错（值得记）**：
自愈逻辑第一版把 `still`（=**没**出现在笔记里的）当成了「已蒸馏」，
方向完全搞反 → 注入 #135 后自愈了 **0 条**。
**「still / healed」这类反直觉的命名最容易把逻辑写反** ——
变量名要能自解释，否则不如改成 `not_in_notes` / `in_notes`。

**延伸**：这是 E20「验证的对象错了」的**升级版** ——
E20 讲「验证了脚本却没验证指令」，E31 讲「**改了指令却没改机制**」。
两者共同点：**别把「正确性」寄托在某个人/某个 agent 会记得执行上**。

### E35：任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」

> 本条讲：**任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」**

**场景**：2026-10-27 凌晨，巡检报「backup-audit 运行失败（超时）」。
脚本本身只要 **0.18 秒**。

**我走的弯路（三次错误假设）**：
1. 「timeoutSeconds 太紧」→ 提到 600 → **还是超时**
2. 「模型限流 / 上下文溢出」→ 直连 API 测：3 个模型全 200、1.1–2.6 秒 → 不成立
   → 构造 1.16M token 请求：HTTP 200 但 **61.5 秒** → 也不是它
3. 「和我的会话抢同一账号配额」→ 我停手后再测，API 依然快 → 不成立

**真根因**：`process(action='poll')` **每次都阻塞满 timeout**。
```
CALL 19:28:11 (timeout: 120000) → CALL 19:30:12   = 121.0s
CALL 19:30:12 (timeout: 180000) → CALL 19:34:40   = 268.0s
CALL 19:34:40 (timeout: 240000) → CALL 19:36:41   = 121.0s
```
3 次 poll ≈ 510 秒 → 必然撞上 job 超时。
**慢的从来不是任务，是「等法」。**

**关键教训 —— 调超时前必须先分清两类失败**：
| 症状 | 真正含义 | 正确动作 |
|---|---|---|
| 任务**本身**耗时长 | 任务慢 | 调大 timeout ✅ |
| 任务很快但**轮询**耗时长 | 等待方式慢 | **改等待方式** ❌ 调 timeout 只是把问题推后 |

**岔路口**：
1. **超时失败时，先单独量脚本耗时**（`time bash xxx.sh`）——
   0.18 秒 vs 600 秒超时 = 明显不是「任务慢」
2. **别用长 timeout 的 poll 等后台任务**：poll 的 timeout 是**上限**，
   实际会等满 → 用**短 timeout 多次 poll**（如 10-15s）而不是一次 120s
3. **会话里的 120s 停顿就是信号**：我自己那轮有 **140 次 120 秒级停顿** ——
   每个都是一次「等满」的工具调用
4. **timeoutSeconds 仍然是必要的兜底**（300 → 600），
   但它是**第二道**防线，不是第一道 —— 第一道是「别等满」

**证据**：
- 脚本 0.18s，job 超时 300s → 差 1600 倍 → 立刻排除「任务慢」
- 直连 API 全 200 / 1.1–2.6s → 排除限流
- 1.16M token 请求 HTTP 200 / 61.5s → 排除上下文溢出（那也是我一开始的怀疑）
- poll 调用间隔 = 请求 timeout + 1s（121.0s / 268.0s / 121.0s）→ **决定性证据**

**延伸**：这是 E29「先问『正常时它长什么样』」的**时间维度版本** ——
E29 讲「别把正常报成故障」，E35 讲「**别把等待慢当成任务慢**」。
两者共同点：**症状和原因之间隔着一层「怎么观测的」**。

### E37：并行不一定更快 —— 先看瓶颈是不是 CPU

> 本条讲：**并行不一定更快 —— 先看瓶颈是不是 CPU**

**场景**：2026-10-27 06:00，发现巡检要跑 **252 秒**，其中
`verify_l1_retrieval.py` 占 **174.7 秒（69%）** —— 它对 36 条 L1 经验
逐条调 `openclaw memory search`，每次起一个 Node 进程。

**直觉**：36 次独立调用 → 开 8 个线程并行 → 应该快 8 倍。

**实测（这台机器只有 2 个 CPU 核）**：
| 方式 | 数量 | 耗时 |
|---|---|---|
| 串行 | 1 个 | 6.6s |
| 并发 | 8 个 | **55s**（≈ 8×6.6s，**零加速**） |
| 并发 | 18 个 | **6m18s**（比 18 个串行的 119s **慢 3 倍**） |

→ **并行不但没加速，反而慢 3 倍。**
原因：`openclaw memory search` 的成本是 **Node 进程启动**（CPU 密集），
2 核上并发只加剧上下文切换。

**岔路口**：
1. **并行前先问「瓶颈是不是 CPU」**：
   - 瓶颈是**等待 I/O**（网络、磁盘）→ 并行有效
   - 瓶颈是 **CPU**（进程启动、计算）→ 并行只会更慢
   - 判断方法：`user` 时间 ≈ `real` 时间 → CPU 密集
   （我的实测：`user 5m21s / real 3m54s` → 纯 CPU 密集）
2. **真正的解法不是「怎么等」，是「要不要等这么多」**：
   → 拆成**两层**：
   - **第 1 层（全量、零成本）**：结构检查 ——
     独立文件存在 · 首行有「本条讲：**关键词**」· 主库里有对应条目
     → 这一层能抓到 E17 那类「写了但结构上检索不到」的绝大多数成因
   - **第 2 层（抽样、有成本）**：真实检索 ——
     最近 6 条全查 + 存量每 1/4 抽 1 条
3. **抽样必须轮转，不能固定**：
   固定抽样 → 抽不到的那 58% 可能 **21 天**才被查到
   → 改成**按天轮转起点** → 任何一条最多等 **3 轮**（3 天）
   （用 `datetime.now().strftime("%j") % SAMPLE_EVERY` 做 offset）

**证据**:
| 项 | 改前 | 改后 |
|---|---|---|
| verify_l1 耗时 | 174.7s | **67s** |
| 整个巡检 | 252s | **102s** |
| 结构检查覆盖 | 0（全靠检索） | **36/36 全量** |
| 真检索覆盖 | 36/36 | 14/36（**但轮转保证 3 天内全覆盖**） |

**注入验证**: 删掉 E30 的首行关键词 → **结构检查当场 FAIL** ✅

**延伸**：这是 E35「慢的是等法不是任务」的**下一层** ——
E35 讲「别用长 poll 等满」，E37 讲「**别以为并发就是答案**」。
两者合起来：**先问「时间花在哪」，再决定是「换等法」还是「少等」。**
