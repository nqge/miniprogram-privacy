## 🔧 排查方法论


### E1：区分「失败」和「没触发」
> 本条讲：**区分「失败」和「没触发」**

**场景**：定时任务没产出结果。
**陷阱**：看到没产出就归因为「任务失败了」→ 去查日志、查错误码 → 什么都查不到 → 记为「已知残留项」。
**岔路口**：先查 **cron runs 历史**（有没有触发记录）→ 有记录 = 失败（查日志）；没记录 = 没被调度（改频率/查调度器）。
**证据**：2026-10-26，`daily-learning` 10-24/10-25 零产出。查 runs 历史发现
**10-19 之后到 10-26 之间零次触发** —— 不是失败，是根本没跑。


### E2：口径不一致的对比会产生假告警
> 本条讲：**口径不一致的对比会产生假告警**

**场景**：比对「本地 vs 远端」文件数。
**陷阱**：一边用 `find`（含运行时垃圾如 `__pycache__`），另一边用 `git ls-tree`（只含被追踪文件）→ 报「漏文件」。
**岔路口**：**先确认两边用同一口径**，再判断差异是否真实。
**证据**：2026-10-26，`backup_audit` 报「scripts/ 远端 8 < 本地 9」，实测 `git ls-files` 两边完全一致。


### E3：清理想删旧文件，先确认判龄信号本身有效
> 本条讲：**清理想删旧文件，先确认判龄信号本身有效**

**场景**：清理按时间轮转的日志。
**陷阱**：用 `mtime` 判断「文件多旧」→ 规则永不触发，而且**看起来一直在正常工作**。
**岔路口**：先验证判龄信号本身（打印每个文件的实际年龄）；轮转方式与文件系统行为不符时，
**唯一可靠信号通常是文件名里的槽位标识**。
**证据**：2026-10-26，OpenClaw 日志轮转**按大小不按天** → 同一槽位跨天追加 → `mtime` 永远新鲜
→ `-mtime +7` 规则一次都没触发过。


### E4：涉及「默认值/协议/常量」的结论，必须查源码或实测
> 本条讲：**涉及「默认值/协议/常量」的结论，必须查源码或实测**

**场景**：判断某个配置项的默认行为。
**陷阱**：读文档或凭印象 → 写进记忆文件 → 下个会话当成已验证事实继承。
**岔路口**：`grep` 源码里的常量定义 / 直接实测。
**证据**：2026-10-26 两次栽在这上面 ——
① 「agentTurn 型 cron 默认 timeout 是 30s」实为 **360s**（30s 是 `apply.runtime` 搜索路径的值）
② 「远端提交已添加 `bin/requirements.txt`」实为**文件根本没提交**。


### E5：提交说明 ≠ 文件真的存在
> 本条讲：**提交说明 ≠ 文件真的存在**

**场景**：判断某个修复是否生效。
**陷阱**：读 commit message 里的「已添加/已修复」就当作事实。
**岔路口**：`git ls-tree` / `git show --stat` 落到**文件层面**核实。
**证据**：2026-10-26，远端 `ad8098d` 声称「添加 bin/requirements.txt」→ `git ls-tree origin/main bin/` 只有脚本。

## 📏 工程取舍


### E6：状态字段 ≠ 用户得到的结果
> 本条讲：**状态字段 ≠ 用户得到的结果**

**场景**：任何「自动化是否正常工作」的判断。
**陷阱**：只看 `status=ok` / `enabled` / `consecutiveErrors=0` → 绿色一片，实际功能全死。
**岔路口**：沿着 **触发 → 执行 → 落盘 → 投递 → 用户看到** 逐段取证，每段单独断言。
**证据**：2026-10-26 一天内四个例子——
① 记忆检索 `enabled` 但 Embeddings unavailable（**从 3 月起就没工作过**）
② 飞书投递 `status=ok` 但结果从未送达
③ 学习笔记不报错但周频让 4/8 天根本不触发
④ 茶馆摘要稳定落盘但 4/15 讨论从未被提炼


### E7：定时器保证触发频率，不保证信息增量
> 本条讲：**定时器保证触发频率，不保证信息增量**

**场景**：设计周期性任务。
**陷阱**：把「每 4 小时跑一次」当成「每 4 小时有新东西」→ 重复产出、浪费存储。
**岔路口**：落盘前与上一份比对，内容相同则跳过。
**证据**：2026-10-26，茶馆 0039 与 0040 两份摘要**全文 1671 行、diff 仅 4 行**（99.8% 相同）。


### E8：纯脚本任务不该用 agent 型 cron
> 本条讲：**纯脚本任务不该用 agent 型 cron**

**场景**：让定时器执行一个 shell 脚本。
**陷阱**：agent 型 cron 为了跑一个 20ms 的脚本，消耗 261 秒的模型往返。
**岔路口**：需要判断的用 agent 型；纯脚本用 systemd timer。
**证据**：2026-10-26，`log-cleanup` 改成 systemd oneshot → **261s → 21ms**。


### E9：收集、存储、加工是三件事
> 本条讲：**收集、存储、加工是三件事**

**场景**：构建「信息采集」类系统。
**陷阱**：把「收集」当成终点 → 数据进磁盘，但从未影响判断。
**岔路口**：加工环节要独立存在（待办清单 + 进度断言），否则收集系统只是**浪费磁盘的订阅服务**。
**证据**：2026-10-26，茶馆 monitor 忠实收集 95 条讨论，**4/15 未被提炼**。


### E10：同一文件里的多个同类小节会指数膨胀
> 本条讲：**同一文件里的多个同类小节会指数膨胀**

**场景**：让 agent「在已有小节内追加」而非覆盖。
**陷阱**：频繁触发 + 追加语义 = 每次跑一次多一节。
**岔路口**：明确规定「每天只允许 1 个小节，已有则**替换/精炼**」；长度写成硬约束并自检。
**证据**：2026-10-26，一天堆出 **6 个学习小节、单节 3365 字**（约束是 100-200 字）——
典型的「反刍」。


### E11：新增断言必须做注入故障验证
> 本条讲：**新增断言必须做注入故障验证**

**场景**：写检查脚本（巡检、校验器）。
**陷阱**：脚本跑出 PASS=20 就认为它有效 —— 它可能内含一个**永远抓不到故障**的分支。
**岔路口**：注入故障（停服务 / 造分歧 / 造未蒸馏）→ 确认它真会 FAIL → 恢复。
**证据**：2026-10-26，9 组断言里 **4 组写完后自己坏过**；
且第一版【I】组把蒸馏稿也算进搜索范围，一直**误判 PASS** ——
**检查自己产出的文件，等于没检查**。

### E39：共享账号就是共享配额 —— provider 变慢比 provider 挂掉更隐蔽
> 本条讲：**provider 变慢比 provider 挂掉更隐蔽 —— 共享账号就是共享配额**

**场景**：2026-10-27 06:30 心跳。查 `daily-learning` 为何 362s / timeout 420s（余量仅 16%），
翻会话时间分布发现**有一次单次 LLM 调用等了 353 秒** —— 不是在等工具。

**陷阱**：把「只有一个 provider」只理解成一重后果（**挂了兜底无效**）。
真实还有第二重：**provider 变慢 → 所有任务一起变慢**。
这一重**不报错、不告警**，只表现为「时间莫名变长」——
每个任务单独看都「没超时」，最难归因。

**根因**：所有任务共用**同一个 MiniMax 账号**。
关键线索：353 秒那段时间（19:05–19:11 UTC）**正是 backup-audit 超时失败的时段**，
两者是**互相抢同一份配额**，不是各自慢。
实测同账号 6 并发：单发 **1.8s** → 最慢 **7.0s（3.9 倍）**。

**岔路口**：
1. **第二个 key 的价值不是「容灾冗余」，是「拆开共享配额」** ——
   两把 key = 两个独立配额桶，慢的那把只拖慢用它的那批任务
2. **退化分两类**：**挂掉**有 error、容易发现；**变慢**无 error、最难发现，
   却恰恰先吃掉超时余量 → 要给「慢」配耗时观测，不能只配错误率
3. **并发变慢要区分成因**：E37 是**本地 CPU** 瓶颈（并行更慢）；
   本条是**远端配额**排队（本地快但远端慢）
4. **发现长尾耗时先查「时间重叠」**：慢调用区间与其他任务失败区间若重叠
   → 不是那个任务自己慢，是**它们在抢同一份资源**

**证据**：单次 LLM 调用最长等待 **353s**；6 并发最慢 **7.0s**（3.9 倍）；
巡检 420s 预算只剩 16% 余量。已把并发实测数字写进【M】长期项断言注释，
让「等第二个 key」带上**具体代价**而非一句「兜底无效」。

**延伸**：E28 讲「长期项和真故障混在一起会让信号失效」，
E39 讲「**同账号多任务是隐形的长期项**」——
它表现为「大家都变慢了」而不是「某一项坏了」，
永远排不进故障列表，只能靠实测并发延迟才能看见。

### E40：验收用的测量，必须跑在真实负载上
> 本条讲：**验收用的测量，必须跑在真实负载上**

**场景**：2026-10-27 07:00。今晚所有改动第一次**无人值守**验收。
跑之前的前置检查写「巡检 ~102s / timeout 600s，余量充足 ✅」，
但 07:00 真实 cron 跑完实测 **298.4s** —— **差了近 3 倍**。
前置检查没测错东西，它测的是**另一个工作负载**。

**陷阱**：用「我手动跑一次」的数字给**定时任务**定超时预算。
两者的负载不同，差多少事先不知道：
- 手动跑：交互会话里跑，缓存热、抽样轮转到轻的一天、有人在旁边盯着
- 真实 cron：无人值守、缓存冷、按 `%j % 4` 轮转到不同抽样位置、还要和别的任务抢配额

→ **手动测出的耗时是定时任务耗时的下界，不是它的估计值。**
更糟的是它**给出一个自信的具体数字**（102s），比不给数字更危险。

**根因**：`verify_l1_retrieval.py` 的抽样量**按天轮转**
（`offset = %j % SAMPLE_EVERY`，存量每 4 条抽 1 条 + 最近 6 条全查）。
轮转设计的初衷是「保证任何一条最多等 3 轮就被真检索一次」——
**它保证了覆盖的公平，却让每天的负载不一样**。
于是「昨天测的耗时」根本不能代表「今天这一轮」的耗时。

**岔路口**：
1. **别拿手动测的耗时给定时任务定预算** —— 要么在**最重的一轮**上测，
   要么直接看**真实 cron run 的历史耗时**（run 记录里有真实值）
2. **抽样/轮转的设计要同时管「覆盖」和「负载」** —— 覆盖公平 ≠ 负载恒定；
   负载浮动就得给预算留**最坏情况的余量**，而不是平均情况
3. **最重的负载要能被识别出来** —— 抽样量随天变化时，
   「今天这轮为什么慢」要能从数据里看出来，不能靠人记得今天轮转到哪
4. **验收要验收「被验收的那一份」** —— 手测的样本 ≠ 线上跑的样本；
   这和 E23「担心要用实测替代想象」、E26「读到上次的成功结果」同族：
   **验证的对象错了，结论就全错（E20）**

**证据**：前置检查记录「~102s，余量充足」；同一套脚本 07:00 真实 cron 实测
**298.4s**（timeout 600s，余量 50%）。差 2.9 倍，**同一天、同一套脚本**。

**延伸**：E35 讲「任务超时 ≠ 任务慢 —— 先量等待方式再调超时值」，
E37 讲「并行不一定更快」，本条讲**测量的样本本身**——
E35/E37 都在追问「时间花在哪」，本条追问的是「**你测的是哪一次运行**」。

## 🧭 认知与判断


### E12：落盘 ≠ 送达
> 本条讲：**落盘 ≠ 送达**

**场景**：把待办、结论、选项单交给用户。
**陷阱**：写进文件就以为「做完了」→ 文件存在反而带来虚假的安全感。
**岔路口**：每个待办问一句「**他怎么知道？**」—— 答不上来就是没做。
**证据**：2026-10-26，`待决策选项单.md` 在磁盘上躺了 6 周，**从未进入用户视野**。


### E13：机制缺口比单点故障更值得修
> 本条讲：**机制缺口比单点故障更值得修**

**场景**：同时发现多个「功能其实早就是死的」。
**陷阱**：逐个修完就收工 → 下个月同样的问题换个马甲再来。
**岔路口**：修完一个，追问「**为什么现有机制没抓到它**」，把那条断言补进每日巡检。
**证据**：2026-10-26 发现的四个故障，**没有一个**是被原有机制抓到的。


### E14：风险描述不能靠记忆，要靠实测
> 本条讲：**风险描述不能靠记忆，要靠实测**

**场景**：评估某个凭证/配置的风险等级。
**陷阱**：沿用之前的描述 → 用户基于错误前提做优先级判断。
**岔路口**：涉及权限/额度/影响范围时，**实测**（查 scope、查实际权限），不要只复述「是不是明文」。
**证据**：2026-10-26，classic PAT 原记录是「明文落盘」，实测 scopes 含
`admin:org` / `delete_repo` / `admin:enterprise` → 实际是**账号完全控制权**。


### E15：对外收敛 ≠ 对内收敛
> 本条讲：**对外收敛 ≠ 对内收敛**

**场景**：判断某件事该不该做。
**陷阱**：把「用户不在场」当成「可以无限期做」→ 内部学习、笔记、维护一起停掉。
**岔路口**：区分**对外动作**（要克制）和**对内动作**（零成本、不打扰，照常）。
**证据**：2026-10-21 的反思（当时定规矩）→ 10-24/10-25 两天 memory 零文件（规矩失效）。


### E16：低触发频率的机制没有容错
> 本条讲：**低触发频率的机制没有容错**

**场景**：把某个每日任务调成每周/每月以「省资源」。
**陷阱**：低频 = 每次失败就是整周空白，且**空白期往往正是无人注意的时候**。
**岔路口**：频率是**容错参数**，不是省钱旋钮。
**证据**：2026-10-26，daily-learning 周频 → 10-24/10-25 零文件。


### E17：检索的最小单位是「块」，不是「条」——短章节会被切碎稀释
> 本条讲：**检索的最小单位是「块」，不是「条」——短章节会被切碎稀释**

**场景**：新建知识库 / 经验库 / 笔记体系；任何「写下来了但搜不到」的现象（沉淀一条新经验时）。
**陷阱**：验证「文件存在、条目数对、mtime 新」就宣布完成 → 内容**写完即死**。
更隐蔽的一层：检索按 token 切块（`chunking.tokens=200`），**切在条目中间时标题和「场景」被切走**；
短小节夹在两个长小节之间时，标题与正文分处两块，**两块都不以这条内容开头** → 向量被邻段平均掉，
搜原文措辞也排不进去。检索到的是**语义残片**，不是你的条目。
**岔路口**：① 建完立刻拿**原文措辞**检索一次，排不进前列就重写标题/措辞（命中分数是硬指标，不是感觉）；
② 关键条目**首行重复标题关键词**（本文件的 `> 本条讲：` 约定即为锚点），让条目在任意切块下都自洽；
③ 独立条目**拆成独立文件**，彻底摆脱邻段稀释（最有效，见下方证据）。
**证据**：2026-10-26 建立 L1 库（16 条）→ 用原文措辞搜「区分『失败』和『没触发』」，
L1 排第 1（**0.6554**）→ 但新增 E17 后搜「沉淀 验收标准 检索命中」，**E17 所在块没进前 6**；
查库见其被切成 20-45（开头是反思）与 41-57（开头无标题）两块 →
补标题锚点后仍被邻段稀释 → **拆成独立文件 `memory/daily-notes-index.md` 后直连余弦 0.5457 排第 1**
（同查询下旧写法为「未进前 6」）。

### E18：记住了 ≠ 不再踩，要改结构
> 本条讲：**记住了 ≠ 不再踩，要改结构**

**场景**：任何「我刚犯过这个错」「我刚记录过这条教训」的场合。
**陷阱**：把教训写进笔记 / 记忆文件就当解决了 → 同样的错误换个场景再来，
而且因为「我已经记过了」，反而不会再警惕。
**岔路口**：凡是**已经踩过一次**的错误，要改的不是记忆而是**结构**：
- 长文本（尤其含反引号、`>`、`$`）→ 写进文件，用 `--message "$(cat file)"` 引用，不要裸放命令行
- 危险字符 → 用 heredoc（`<< 'EOF'`）而非拼接字符串
- 路径 → 提取成变量，不重复手写
**证据**：2026-10-26 12:15，我给 cron 改指令时在命令行里写了反引号和 `>`：
- 反引号 → **命令替换** → `memory/YYYY-MM-DD.md` 被当命令执行
- `>` → **输出重定向** → `memory/daily-notes-index.md` 被当输出目标
- 两个文件路径**从指令里消失**，而命令**「成功」返回了 JSON**（无报错）
讽刺的是：我 20 分钟前刚把这条写进 E17 那一节的上下文里（「检查自己产出的文件等于没检查」）。
→ **记教训是最弱的改进步骤，改结构才是。**


### E19：bash 里嵌套 heredoc + 命令替换会吞掉变量
> 本条讲：**bash 里嵌套 heredoc + 命令替换会吞掉变量**

**场景**：在 shell 脚本里用 `$(...)` 包一个 heredoc（python 代码），再把结果放进变量。
**陷阱**：变量**静默变成空串**，不报错、不中断。表现是「写进去了，但值是 0/空」。
**岔路口**：把 python 代码抽成**独立脚本文件**，用 `python3 script.py "$arg"` 调用，
不要在 shell 里内嵌 heredoc。需要多参数就全部走命令行参数。
**证据**：2026-10-26 12:20，给 healthcheck.sh 加「自动更新 SESSION-STATE 巡检现状行」时：
```bash

...
PYEOF
)
NEWLINE="... ${GROUPS} 组断言 ..."
```
`bash -x` 显示 `GROUPS=12` 紧接着 `NEWLINE='... 0 组断言 ...'` —— **变量被吞**。
我试了固定路径（怀疑 BASH_SOURCE 空）、花括号、多字节字符、heredoc 改写，
**换了四种写法都是 0**，直到把 python 抽成独立脚本 `scripts/update_state_status.py` 才通。
**排查耗时超过 10 分钟，且过程中输出一直是「成功」** —— 静默失败最难查的就是这种。

### E20：验证的对象错了，结论就全错
> 本条讲：**验证的对象错了，结论就全错**

**场景**：想证明「某个机制能工作」。
**陷阱**：验证了**你想验证的东西**，而不是**实际生效的东西**。
**岔路口**：先问「**真正生效的是哪个？**」，再去验证它。

**同一类问题的三种形态**（2026-10-26 一天内连中三次）：

| 我验证的 | 实际生效的 | 症状 |
|---|---|---|
| 手动 `cron run` 成功 | 定时调度 | 从没真正无人值守跑过 |
| 交互 shell 里跑通 | systemd 环境 | PATH 缺 pnpm、`systemctl --user` 报 unknown |
| 文件里有 `OnFailure=` 这行字 | 指令真的生效 | 注释里也有这行字，grep 看着正常 |

**证据**：2026-10-26
1. 08:00 巡检我以为是自动跑过，实际是我自己手动触发的，还写成「无人值守下真实生效」
2. 30 分钟巡检第一版在 shell 里测过，systemd 下直接挂两项（PATH + XDG_RUNTIME_DIR）
3. 为了加一行 `ExecStartPost` 重写了整个 `.service`，把 `OnFailure=` 真实指令弄丢 ——
   **但注释里还留着这行文字**，所以 grep 能搜到，看起来一切正常，
   而故障时告警单元**完全不被触发**。

**怎么破**：验证时先确认「**我看到的东西就是系统用的东西**」。
- 指令是否生效 → `systemctl show -p <Prop> --value`（不是 grep 文件）
- 定时是否触发 → 找**真实的定时运行样本**（看 sessionId、时间和手动触发区分开）
- 状态是否正常 → 问「**实际运行的是谁**」（`/proc/<pid>/environ` 的 PATH）

**延伸**：**时间线是因果的证据**。09:02 失败 / 09:19 修 / 09:19 之后全成功 ——
这三条排在一起，因果关系不需要解释。如果只看「现在是 ok」，无法排除是偶然。

### E21：修症状 ≠ 修类
> 本条讲：**修症状 ≠ 修类**

**场景**：修完一个 bug。
**陷阱**：把「这个具体问题」修好就收工 → 同一类的下一个问题照样会静默发生。
**岔路口**：修完立刻问「**这一类风险还有哪些地方没覆盖？**」，
用一个检查**覆盖整类**，而不是每次出一处补一处。

**证据**：2026-10-26
我修了「重写 .service 把 `OnFailure=` 弄丢」这个**症状**（恢复指令 + 加一条断言），
但没问「『配置文件里的东西 ≠ 实际生效的东西』这一类风险覆盖到了吗」——
换个单元、改个路径，同样会静默失效。
于是又做了 `scripts/check_unit_drift.py`，把这一类系统性覆盖：
单元 enabled / 脚本存在 / 关键指令生效 / 解释器存在 / 定时器调度 / 敏感文件权限。

**怎么破**：
1. 修完先问「这是**个案**还是**一类**？」
2. 是类 → 找一个能**同时覆盖多个实例**的检查点
3. 新检查点**必须做注入故障验证**（否则它自己可能有盲区）

**代价对比**：个案修复 = 一次；类覆盖 = 一次 + 一个检查脚本，
但**同类问题再也不会复发**。

### E22：知道 ≠ 会做到

**场景**：刚学会了一条经验。
**陷阱**：以为「我已经知道这条了」→ 写东西时**根本没想起它** → 犯了刚学过的错。
**岔路口**：知识要变成行为，得靠**机制**（可检查的约定），不能靠「我记得有这么回事」。

**证据**：2026-10-26 下午

### E24：跑两遍不只是浪费，是会引入竞态
> 本条讲：**跑两遍不只是浪费，是会引入竞态**

**场景**：某个脚本被调用了两次（自己调自己，或两个入口各跑一次）。
**陷阱**：只是「慢一点」→ 忽略了两次读到的**是不同时间点的状态**。
**岔路口**：两次执行之间状态可能已经变了 → **结果可能不一致**。

**证据**：2026-10-26
`alert_dedup.py` 会自己再跑一遍 `quick_health.py`，
导致每次成功巡检实际跑两遍（8 秒 → 16 秒）。
**更要紧的是竞态**：
「第一次 FAIL、第二次 PASS」会让 dedup 误判为**已恢复** →
**发一条假的恢复通知，同时丢掉真实的故障**。

**修法**：`quick_health.py` 把结果写到 `logs/quick-health-result.json`，dedup **读它**。
效果：~14 秒 → ~7 秒，且状态与实际**严格一致**。

**怎么破**：修性能问题时顺手问一句「**这两次跑的结果可能不一致吗**」——
答案是「会」，那就不只是性能问题了。

### E25：发现问题时先问「这个真的需要对方参与吗」

**场景**：发现一个问题，准备丢给对方。
**陷阱**：默认「这需要对方」→ 写成待办 → **其实自己就能修** → 风险一直挂着。
**岔路口**：写下待办之前，先花两分钟问：**真的需要对方吗？**

**证据**：2026-10-26

### E26：告警链路自身的失败模式，是「读到了上次的成功结果」

> 本条讲：**告警链路读到的可能是上次的成功结果 —— 故障时告警被静默吞掉**

**场景**：想证明「故障时告警真的会发出去」。

**陷阱**：OnFailure 处理器读巡检结果文件。
脚本如果**在写这个文件之前**就崩了/被 kill/超时，
文件里留的还是**上一次成功运行**的结果 → 处理器读到「无故障」→ **告警被静默吞掉**。

> 恰恰发生在系统最坏的时候 —— 而且**看起来一切正常**。

**岔路口**：
1. 注入崩溃 → 手动触发 OnFailure → 看告警单元说了什么
2. 观察它读的是**哪一次**运行的结果 → 定位到「时间错位」
3. 修复要两层：
   - **新鲜度校验**（结果文件超过 N 分钟 → 不信，自己重跑）
   - **running 标记**（开跑前写标记，跑完删掉；标记还在 = 没跑完 = 失败）

**关键**：只用「新鲜度」**不够** —— 崩溃发生在写文件前时，
旧文件可能只有 1 分钟前写的，看起来很新鲜。
必须靠 running 标记才能区分「刚成功」和「崩了」。

**成果**：
- 修好后 4 条路径全部验证：正常成功 / 检查项失败 / 崩溃在写文件前 / 文件陈旧
- 端到端走真实 systemd OnFailure 链路验证：`code=0 msg=success` ✅

**延伸**：这条其实是 E12「落盘 ≠ 送达」的**镜像版** ——
E12 讲「执行了不等于送达了」，E26 讲「读取了不等于读的是对的东西」。
两者都是**中间产物被误当作结论**。

### E27：两处结论同时错，根因通常是「测量环境不同」

> 本条讲：**两处结论同时错，根因通常是「测量环境不同」—— 先问是不是在测同一个东西**

**场景**：复核另一个会话（或过去的自己）写在共享文档里的实测结论。

**陷阱**：两边都「测过了」，数看起来也有依据，但**测的不是同一个东西**。
这次的实例：
- A 会话测「`--log-level warn` flag 有没有效」时，**环境变量还没配**
- B 会话（我）复核时，**环境变量已经配上了**
- 于是 flag 的效果被环境变量**盖住** → 看起来像「flag 无效」
- 而在**裸环境**单独测 flag，它完全有效（-100%）

同样地，「每次 CLI 调用都会重新注册全部插件」这个归因也是错的 ——
实测 CLI 调用产生 **0 行**，真实来源是 **agent session 启动**（同一秒成簇 16 行）。

**岔路口**：
1. 发现结论冲突时，**先问「两边测的是同一个环境吗」**，而不是先判断谁对
2. **构造「裸环境」单独测**：`env -u OPENCLAW_LOG_LEVEL ...`
3. 对照表要分维度量（动作 × 产生量），不要只测一个动作
4. 跨会话共享的文档（TOOLS.md / 运维笔记）**必须复核** ——
   写错的结论会一直复制下去

**证据**：2026-10-26 21:35，裸环境 3 次 CLI 调用：
默认 60630 字节 → 带 `--log-level warn` = 0 字节；
`openclaw cron list` × 5 → 0 条 Registered 行；
agent session 启动 → 同一秒 16 条。

**关键判断**：环境变量的价值不在于「比 flag 强」，
而在于**它能作用于非 CLI 的进程** —— 也就是 agent session 启动、systemd 单元这些
真正产生噪音的地方。flag 只在显式带 flag 的那一次调用里有效。

### E28：长期项和真故障混在一起，等于让信号失效

> 本条讲：**长期项和真故障混在一起，等于让「今天有没有故障」这个信号彻底失效**

**场景**：巡检里加了一条「客观存在、但要等别人才能解决」的断言。

**陷阱**：那条断言每天都会 FAIL →
1. 巡检从此**永久 exit 1** → 告警链路每次都触发 → 每次都被去重抑制 → 纯消耗
2. 更糟：**真故障出现时，它和长期项并列在同一个列表里** → 报告里两个 FAIL 并列，
   长期项把真故障的注意力带走了
3. 「今天有没有故障」这个信号**彻底失效** —— 永远是「有」

**岔路口**：
1. 给失败项**分类**：「可处理 — 现在就该修」 vs 「等用户 — 长期项」
2. 分类后：长期项**仍然全部报出来**（信息不丢），但
   - **退出码只看可处理项** → 服务该 success 就 success
   - **告警只对可处理项触发** → 长期项静默
   - 报告里两组分开显示，一眼看出哪些要动、哪些在等
3. 关键：**别把长期项「静音」成看不见** —— 那是另一种形式的信号失效。
   要静默的只是**通知**，不是**记录**

**证据**：2026-10-26 22:35，加了【M】Provider 韧性断言后：
只有长期项 → exit 0、不告警 ✅；注入真故障 → exit 1、告警发出 ✅；
每日报告分成「可处理 / 等牛哥哥」两组 ✅

**延伸**：这是 E6「状态字段 ≠ 用户得到的结果」的**变体** ——
E6 讲「状态绿着但功能死了」，E28 讲「状态红着但这个红不代表你的动作」，
两者都是**信号与含义脱节**。

### E29：断言的第一版阈值很可能是假警报 —— 先问「正常时它长什么样」

   - 当前真实状态 → 全 PASS（不假警报）

**同时修掉的真实问题**：
今天笔记里有一段 748 行的**原始茶馆摘录**，而那些内容**已经完整存在**于

已删除（105KB → 64KB，索引 215 块 → 179 块），只留蒸馏结论 + 指针。

**延伸**：这是 E28 的**反面教材** —— E28 讲「别把长期项静音成看不见」，
E29 讲「别把正常状态报成故障」。两者是同一件事的两面：
**信号必须和它要表达的含义对齐**，多报和少报一样有害。

### E30：队列型状态只加不减 = 每次运行都在重复劳动

> 本条讲：**队列型状态只加不减 = 每次运行都在重复劳动**

**场景**：茶馆监控每 4 小时跑一次，拉取新讨论 → 写入「待蒸馏清单」→ agent 蒸馏成知识。
看起来是完整的流水线。

**陷阱**：2026-10-27 凌晨发现，`memory/teahouse-todo.json` 的 `pending` 队列里
**永远躺着同样 4 条**（#135/#138/#134/#154）—— 它们在 11:30 就已经蒸馏完了。

根因：`prompt_distillation()` **只追加，从不移除**。
```
for i in fresh:
    if n in known: continue
    existing["pending"].append(...)     # 只加
# 全函数没有一句从 pending 里删东西
```
→ 蒸馏完成后**没有任何机制**把条目移出队列 → 每 4 小时重新蒸馏同样 4 条。

**为什么巡检没发现**：健康巡检的【I】组是**间接**判定的 ——
它查「编号是否出现在某篇 memory 笔记里」，出现就报 PASS。
但它**从不检查队列本身**，所以：
- 巡检报「茶馆内容已全部蒸馏」✅
- 而队列里明明还挂着 4 条 ❌
**两个状态互相矛盾，巡检只信了对自己有利的那个。**

**岔路口**：
1. 任何「待处理队列」必须配一个**出队**路径，且出队和入队一样显式
2. 蒸馏完成的条目 → 移到 `distilled` 列表（保留编号/标题，便于追溯）
3. **`distilled` 列表也要限量**（默认 50）—— 否则只是把「只增不减」换了个字段
4. 巡检要查**队列本身的自洽性**：
   `pending ∩ distilled == ∅`（同一议题不能既待处理又已蒸馏）
5. 修的时候顺手检查：**我查的字段对吗？**
   → 我一开始查 `seen_ids`（GitHub REST 的 10 位 id）以为没去重，
   实际去重键是 `seen_numbers`（议题号）→ **4 条都在里面**
   → 差点得出「修复会被 4 小时后推翻」的错误结论

**证据**：
- 修前：`pending` 恒为 4 条，每 4 小时重蒸馏一遍
- 修后：端到端跑真实监控 → 「无新内容」，`pending` 保持 0，`distilled` 4 条
- 巡检自洽性：注入「#135 同时在两个列表」→ **正确 FAIL** ✅；正常态 → PASS ✅

**延伸**：这跟 E29 是同一类问题 —— **状态字段和真实情况脱节**。
E29 讲「别把正常报成故障」，E30 讲「别让队列状态骗过自己」。
共同点：**光看一个状态字段不够，要交叉验证**。

### E31：只在指令里写「要记得做」= 把 bug 交给人的记性

> 本条讲：**只在指令里写「要记得做」= 把 bug 交给人的记性**

**场景**：2026-10-27 01:10，修完 E30（茶馆待办队列只加不减）之后，
我意识到自己的修复**留了个洞**：

```
cron 指令: "蒸馏完成后，把已蒸馏的议题编号标记掉"
           python3 scripts/teahouse_monitor.py --mark-distilled <编号>
```

**陷阱**：E30 的根因就是「**出队这一步靠人记得做**」。
我把这一步写进了 cron 指令 —— 但那**还是靠 agent 记得执行**。
指令是提示，不是机制。agent 忘了、或者跑歪了、或者指令被别的段落盖住，
bug 原样复发。

而且更糟：**巡检查不出来**。我原来的【I】组逻辑是：
```
still = [pending 里没出现在任何笔记的条目]
if still: FAIL        # 真未蒸馏 → 该报
else:      PASS        # 已出现在笔记里 → 报 PASS，但【不清理】
```
→ 「已蒸馏但没出队」这个 E30 的 bug 状态，**恰好落在 PASS 分支**里。
巡检说「一切正常」，而 bug 就在那儿。

**岔路口**：
1. **凡是「队列出队」类动作，必须有机制兜底，不能只靠指令**
   → 巡检自愈：检测到「pending 里的条目已出现在笔记里」→ **主动移出队列**
   → 出队不再依赖任何人记得做
2. **自愈和告警要分开**：
   - 「已蒸馏但没出队」→ **自愈**（本来就是对的，只差个出队动作）
   - 「真未蒸馏」→ **FAIL 告警**（真的需要人做事）
   → 自愈**绝不能掩盖真问题**：注入一个笔记里不存在的编号 → 仍必须 FAIL
3. **自愈之后要重新读盘**：自愈刚改过文件，继续用内存里的旧数据
   → 会报出「刚自愈完又说矛盾」的假 FAIL（我自己就踩了这个）

**证据**（双向都验了）：
- 注入 E30 原始 bug 状态（#135 已蒸馏但仍在 pending）
  → 「自愈：1 条已蒸馏但未出队 → 已移入 distilled [135]」，pending 归 0 ✅
- 注入真未蒸馏条目（#999，笔记里不存在）
  → **仍 FAIL**「茶馆有 1 条讨论未蒸馏」✅（自愈没掩盖真问题）
- 注入「#135 同时在两个列表」→ 正确 FAIL ✅
- 正常态 → PASS ✅

**⚠️ 我自己在这条上犯的错（值得记）**：
自愈逻辑第一版把 `still`（=**没**出现在笔记里的）当成了「已蒸馏」，
方向完全搞反 → 注入 #135 后自愈了 **0 条**。
**「still / healed」这类反直觉的命名最容易把逻辑写反** ——
变量名要能自解释，否则不如改成 `not_in_notes` / `in_notes`。

**延伸**：这是 E20「验证的对象错了」的**升级版** ——
E20 讲「验证了脚本却没验证指令」，E31 讲「**改了指令却没改机制**」。
两者共同点：**别把「正确性」寄托在某个人/某个 agent 会记得执行上**。

- 恢复后 → PASS ✅

**延伸**：这是 E31「别把正确性寄托在记得做上」的**延伸应用** ——
E31 讲的是「动作」（出队），E32 讲的是「状态」（计数）。
两者共同点：**手写的派生数据必然过期，过期的东西不能当参照系**。
真正的解法不是「记得更新」，是「**让过期可被自动发现**」。

### E35：任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」

> 本条讲：**任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」**

**场景**：2026-10-27 凌晨，巡检报「backup-audit 运行失败（超时）」。
脚本本身只要 **0.18 秒**。

**我走的弯路（三次错误假设）**：
1. 「timeoutSeconds 太紧」→ 提到 600 → **还是超时**
2. 「模型限流 / 上下文溢出」→ 直连 API 测：3 个模型全 200、1.1–2.6 秒 → 不成立
   → 构造 1.16M token 请求：HTTP 200 但 **61.5 秒** → 也不是它
3. 「和我的会话抢同一账号配额」→ 我停手后再测，API 依然快 → 不成立

**真根因**：`process(action='poll')` **每次都阻塞满 timeout**。
```
CALL 19:28:11 (timeout: 120000) → CALL 19:30:12   = 121.0s
CALL 19:30:12 (timeout: 180000) → CALL 19:34:40   = 268.0s
CALL 19:34:40 (timeout: 240000) → CALL 19:36:41   = 121.0s
```
3 次 poll ≈ 510 秒 → 必然撞上 job 超时。
**慢的从来不是任务，是「等法」。**

**关键教训 —— 调超时前必须先分清两类失败**：
| 症状 | 真正含义 | 正确动作 |
|---|---|---|
| 任务**本身**耗时长 | 任务慢 | 调大 timeout ✅ |
| 任务很快但**轮询**耗时长 | 等待方式慢 | **改等待方式** ❌ 调 timeout 只是把问题推后 |

**岔路口**：
1. **超时失败时，先单独量脚本耗时**（`time bash xxx.sh`）——
   0.18 秒 vs 600 秒超时 = 明显不是「任务慢」
2. **别用长 timeout 的 poll 等后台任务**：poll 的 timeout 是**上限**，
   实际会等满 → 用**短 timeout 多次 poll**（如 10-15s）而不是一次 120s
3. **会话里的 120s 停顿就是信号**：我自己那轮有 **140 次 120 秒级停顿** ——
   每个都是一次「等满」的工具调用
4. **timeoutSeconds 仍然是必要的兜底**（300 → 600），
   但它是**第二道**防线，不是第一道 —— 第一道是「别等满」

**证据**：
- 脚本 0.18s，job 超时 300s → 差 1600 倍 → 立刻排除「任务慢」
- 直连 API 全 200 / 1.1–2.6s → 排除限流
- 1.16M token 请求 HTTP 200 / 61.5s → 排除上下文溢出（那也是我一开始的怀疑）
- poll 调用间隔 = 请求 timeout + 1s（121.0s / 268.0s / 121.0s）→ **决定性证据**

**延伸**：这是 E29「先问『正常时它长什么样』」的**时间维度版本** ——
E29 讲「别把正常报成故障」，E35 讲「**别把等待慢当成任务慢**」。
两者共同点：**症状和原因之间隔着一层「怎么观测的」**。

### E36：最该被信任的地方，过期了最致命

**场景**：2026-10-27 05:10 收尾时看 `SESSION-STATE.md` 头部的「📋 系统状态」小节，

- L1 库里的计数过期 = 我判断「记忆系统状态」时参照错了（E32）
- **SESSION-STATE.md 头部过期 = 下一个会话被直接误导**
  → 它是 AGENTS.md 规定的「每次会话先读」的第一份文件
  → 下一个会话会据此认为「glmcode 还在，只是 key 过期，要等牛哥哥重签」
  → 而实际上那些决策项**早已不需要等了**
- 也就是说：过期数据不可怕，**过期的指令**可怕 ——
  它会让人做出**本不该做的动作**

**岔路口**：
1. **手写的「当前状态」小节 = 定时炸弹**：
   → 改成由 `scripts/gen_system_status.py` 从**真实系统**生成
   （providers / cron 任务 / plugins 全部实时读，加 `BEGIN/END` 标记）
2. **头部「最后更新」时间**也用 git 最后提交时间自动填，不手写
3. **加断言【S】持续核对**（18 → 19 组）：
   - providers 声明 == 真实 providers
   - cron 列表 == 真实 cron 列表（不漏、不多）
   - 小节里不出现任何**已删除实体**的名字
4. **历史记录不要改**：SESSION-STATE.md 里那些带日期的「巡检现状（快照）: 12 组断言」
   是**当时的事实**，保留不动 —— 只有「当前状态」才需要与现实同步

**证据（双向）**:
- 注入原始 bug（写回 glmcode/arkcode/teahouse-check）→
  **四条 FAIL 同时报出**（providers 不一致 / 列了不存在的 cron / 两个已删除实体残留）✅
- 恢复后 → PASS ✅

**延伸**：这是 E34「派生数据不手写」的**延伸应用** ——
E34 讲的是「说明清单」，E36 讲的是「**当前状态**」。
区别在于**后果的严重性**：
说明清单过期 → agent 不知道怎么解释某个失败
**当前状态过期 → agent 去做本不该做的事**
→ 所以「哪些手写内容算危险」的排序是：**状态描述 > 说明清单 > 计数**

### E37：并行不一定更快 —— 先看瓶颈是不是 CPU

> 本条讲：**并行不一定更快 —— 先看瓶颈是不是 CPU**

**场景**：2026-10-27 06:00，发现巡检要跑 **252 秒**，其中
`verify_l1_retrieval.py` 占 **174.7 秒（69%）** —— 它对 36 条 L1 经验
逐条调 `openclaw memory search`，每次起一个 Node 进程。

**直觉**：36 次独立调用 → 开 8 个线程并行 → 应该快 8 倍。

**实测（这台机器只有 2 个 CPU 核）**：
| 方式 | 数量 | 耗时 |
|---|---|---|
| 串行 | 1 个 | 6.6s |
| 并发 | 8 个 | **55s**（≈ 8×6.6s，**零加速**） |
| 并发 | 18 个 | **6m18s**（比 18 个串行的 119s **慢 3 倍**） |

→ **并行不但没加速，反而慢 3 倍。**
原因：`openclaw memory search` 的成本是 **Node 进程启动**（CPU 密集），
2 核上并发只加剧上下文切换。

**岔路口**：
1. **并行前先问「瓶颈是不是 CPU」**：
   - 瓶颈是**等待 I/O**（网络、磁盘）→ 并行有效
   - 瓶颈是 **CPU**（进程启动、计算）→ 并行只会更慢
   - 判断方法：`user` 时间 ≈ `real` 时间 → CPU 密集
   （我的实测：`user 5m21s / real 3m54s` → 纯 CPU 密集）
2. **真正的解法不是「怎么等」，是「要不要等这么多」**：
   → 拆成**两层**：
   - **第 1 层（全量、零成本）**：结构检查 ——
     独立文件存在 · 首行有「本条讲：**关键词**」· 主库里有对应条目
     → 这一层能抓到 E17 那类「写了但结构上检索不到」的绝大多数成因
   - **第 2 层（抽样、有成本）**：真实检索 ——
     最近 6 条全查 + 存量每 1/4 抽 1 条
3. **抽样必须轮转，不能固定**：
   固定抽样 → 抽不到的那 58% 可能 **21 天**才被查到
   → 改成**按天轮转起点** → 任何一条最多等 **3 轮**（3 天）
   （用 `datetime.now().strftime("%j") % SAMPLE_EVERY` 做 offset）

**证据**:
| 项 | 改前 | 改后 |
|---|---|---|
| verify_l1 耗时 | 174.7s | **67s** |
| 整个巡检 | 252s | **102s** |
| 结构检查覆盖 | 0（全靠检索） | **36/36 全量** |
| 真检索覆盖 | 36/36 | 14/36（**但轮转保证 3 天内全覆盖**） |

**注入验证**: 删掉 E30 的首行关键词 → **结构检查当场 FAIL** ✅

**延伸**：这是 E35「慢的是等法不是任务」的**下一层** ——
E35 讲「别用长 poll 等满」，E37 讲「**别以为并发就是答案**」。
两者合起来：**先问「时间花在哪」，再决定是「换等法」还是「少等」。**

### E38：只查「今天」的检查，会永远漏掉历史违规

> 本条讲：**只查「今天」的检查，会永远漏掉历史违规**

**场景**：2026-10-27 05:43 心跳。例行跑巡检 PASS=58 FAIL=3（全是长期项），
一切正常。顺手把 `memory/*.md` 全列出来逐个数「每日学习」小节 ——
发现 **`memory/2026-10-21.md` 有 2 个学习小节**，违反「每天只允许 1 个」的硬约束。

**根因（检查本身的盲区）**：【F】组只把**今天**的文件放进候选
（`cands = [f'{MEM}/{today}.md', ...]`）→ 10-21 那天的违规**永远不会被检查到**，
因为文件每天都在换，昨天就不再在 `cands` 里。
危险之处不在于漏报，而在于它给出的是 **PASS** ——
一个绿色的、什么都证明不了的 PASS；违规文件持续膨胀，而巡检每天报「结构正常」。

**修法**：候选从「今天」改成「所有 daily-note 文件」；
**同时不能矫枉过正** —— 只查**重复**（>1），不查**缺失**（==0）：
10-22/10-23 是修复前的空白、反思是**每周日**跑、今天的学习 09:00 才生成，
把「合法缺失」误判成 FAIL，巡检就变噪音源然后被忽略（E28）。

**同时修掉真实违规**：10-21 两节合并成一节 —— 保留 04:29 那条，
把 04:24 的独有洞察折进正文，**内容零丢失**。

**注入验证**：往**历史**文件 `2026-10-25.md` 追加学习小节 → **正确 FAIL** ✅
（改前这个注入完全不可见）；恢复 → PASS ✅

**证据**:
| 项 | 改前 | 改后 |
|---|---|---|
| 覆盖文件数 | 1（今天） | **8 个 daily-note 文件** |
| 能发现历史违规 | ❌ 永远不能 | ✅ 注入即报 |
| 10-21 小节数 | 2（违规） | **1（已合并，内容保留）** |
| 巡检总结果 | PASS=58 FAIL=3 | PASS=58 FAIL=3（**不变**） |

**岔路口**：
1. 写检查时先问「**我查的是活跃的那一份，还是全部？**」—— 违规会沉淀在历史里
2. **PASS 也要有覆盖面意识**：报告里带上「已查 N 个文件」，让覆盖面可见
3. **扩范围 ≠ 放宽标准**：扩范围后要重新界定什么算违规
4. **发现真实违规要修内容，不能只修检查** —— 否则变成天天报的噪音

**延伸**：E34 讲「手写说明清单必然过期」，E38 讲「**手写检查范围也会漏**」。
合起来：**凡是「只覆盖一部分」的断言，都要问「漏掉的那部分会不会出问题」。**

### E41：指令写了 ≠ 会照做 —— 尤其是「自己写的指令」

> 本条讲：**指令写了 ≠ 会照做 —— 尤其是「自己写的指令」**

**场景**：2026-10-27 09:45。09:00 的 `daily-learning` 跑了 **772.1s**
（timeout 1800s，余量只剩 43%）。查会话时间分布：

```
CALL 01:37:25 (poll timeout=120000) → CALL 01:40:49   = 120.0s
CALL 01:40:49 (poll timeout=120000) → CALL 01:44:48   = 120.0s
CALL 01:44:48 (poll timeout=150000) → CALL 01:47:25   = 150.0s
```

**正是 E35 那个模式。** 而那个 cron 指令里**明明写着**：

```
❌ process(action='poll', timeout=120000~300000) —— poll 会**等满整个 timeout**
✅ exec(..., yieldMs=10000) 转后台，然后 process(action='poll', timeout=10000)
```

**最扎人的一点**：写这条指令的**正是那个会话自己**（并行会话），
而且它**加完指令之后的几轮里，自己就用了 4 次长 poll**。

**根因（比 E31 更进一步）**：
E31 说「别把正确性寄托在记得做上」。E41 补上另一半 ——
**「自己写的规则，自己也会忘」**。
写规则的那一刻你是清醒的；执行的那一刻你在想别的问题。
规则写在**别人的指令里**，执行者是一个**带着自己习惯的 agent**。

**岔路口**：
1. **规则要放在「每次都会加载」的地方**，而不是「某几个任务里」：
   → `TOOLS.md` 是**全局注入**的 → 影响所有会话
   → cron 指令里的提醒**只在那几个任务里**生效
   → 同一个道理，**并行会话的指令对我无效**（那是给它的）
2. **说明 ≠ 约束**。所以再加一层**可观测性**：
   → 新增【V】断言：最近 3 天会话里 `poll` 的 timeout > 60s 的次数 > 5 → WARN
   → 它**不阻止**agent 用长 poll，但**让违规可见**
   → 这样我验收时立刻发现「又犯了」，而不是等某个任务撞上超时
3. **量自己的违规规模**：3 天 539 次长 poll，460 次在我自己这轮；
   timeout 分布 280s×235 / 250s×82 / 200s×52 / **≤60s 只有 9 次**
   → **这是习惯问题，不是配置问题** —— 配置再好，
   一个习惯用长 poll 的 agent 还是会用

**证据**:
- 09:00 daily-learning 实际 772.1s，4 次 120s/150s 的 poll ✅
- 指令里明确写了禁止长 poll，**同一会话自己违反** ✅
- 【V】实测输出：539 次长 poll，分布到 5 个会话 ✅

**延伸**：E31 的解法是「加机制」（出队靠自愈，不靠记得做）。
E41 的解法是**再加一层**：「把规则放到全局 + 让违规可见」。
**规则 + 机制 + 可观测性，三层才稳。**

### 补充（2026-10-27 12:50）：规则生效取决于**加载时机**

我自己的数据（这轮会话）：
```
我这轮上下文里的 TOOLS.md 快照 → 含「等长任务」段: False
TOOLS.md 那段是 09:57 加的（commit 6d11015），我这轮 01:00 就开始了
```
→ 规则是**中途**加的，我这轮上下文里根本没有它。
所以我这轮 481 次长 poll **不能全算「无视规则」**。

**但也不能全算「没看到规则」**：
cron 指令里那版提醒（07:10 加的）我这轮**是能看到的**，

### E42：断言量错了东西，就等于没有断言

> 本条讲：**断言量错了东西，就等于没有断言**

**场景**：2026-10-27 07:55。daily-learning 的 cron 跑完，巡检报
「2026-10-27.md 小节超长 2010 字（约束 100-200 字）」→ FAIL。
但我核了一下，那一节**我刚压缩过**，内容看着不长 → 先怀疑断言本身。

**第一个 bug —— 量的不是规则说的那个量**：
规则说「100-200 **字**」（中文 = 100-200 **汉字**），
断言却用「去空白后的**所有字符** > 1200」（含标点/英文/空白）
→ **口径不一致，比规则宽了 10 倍**
→ 10-21 的 568 汉字、今天的 991 汉字**全被放过**，直到凑到 2010 字符才触发
→ 修法：数汉字，上限 400（给 100-200 留一倍余量）

**第二个 bug —— 边界算错（今天才暴露）**：
小节结尾用 `(?=\n## |\Z)` —— **只认 `##` 级标题**。
今天「📚 每日学习」恰好是文件里**最后一个 `##` 级标题**
→ 后面所有 `### 心跳` 小节被算进学习正文 → 被算成 **946 汉字**（实际 177）
→ 而 `###` 是 `##` 的**子节**，本来就属于上一个 `##`
→ 修法：小节在**下一个任意级标题**（`#{1,6}`）处结束

**岔路口**：
1. **断言失败了先怀疑断言本身**，别急着改被测的东西
2. **宽的口径比严的更危险** —— 宽 = 静默放过，还报 PASS
3. **边界要用「下一个任意层级」**，`###` 属于 `##`
4. **报 PASS 时也要说清覆盖了哪些东西**（范围 + 口径）

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 长度判据 | 全字符 > 1200 | **汉字 > 400** |
| 小节边界 | `\n## ` | **`\n#{1,6} `** |
| 今天学习小节 | 被算成 946 汉字 | **实际 177** ✅ |
| 10-21 学习/反思 | 568 / 491（放过） | **252 / 227**（已压缩） |
| 抓到的真实违规 | 几乎抓不到 | **3 处（含 2 处历史）** |

**延伸**：E38 讲「只查今天的检查会漏掉历史违规」，本条讲「**查了但量错了**」——
两者都产出**绿色的、什么都不证明的 PASS**，区别是前者范围窄、后者口径错。
合起来：**断言的三要素 —— 范围、口径、边界 —— 任何一个错，PASS 都是假的。**

### E43：被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言

> 本条讲：**被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言**

**场景**：2026-10-27 08:20。给【S】组加断言时发现 shell 报
`line 1031: to_report: unbound variable` —— 一开始以为是**自己刚插的代码**搞坏的。

**真根因（pre-existing，不是我的锅）**：
```bash
PY5
)to_fail=$(echo "$to_report" | grep -oP '__TO_FAILED__=\K[0-9]+')
```
heredoc 结束符和赋值写在**同一行** → shell 把 `to_fail=...` 当成结束符的一部分
→ **`to_report` 从未被赋值** → `set -u` 报 unbound variable
→ 而该组写的是 `2>/dev/null` → **报错被吞掉**
→ 这组**输出为空**，却无条件 `PASS=$((PASS + 1))` → 巡检照样显示 PASS

→ **【R】组（cron 超时余量对比）其实一直是死的**：
它在结果里显示 PASS，只是从没真正算过任何东西。

**岔路口**：
1. **写完断言要验「它有没有真的输出」** ——
   不是看 `PASS` 计数（无条件 +1），而是看**这组名下有没有实际断言行**
   → 脚本化体检：每组至少一条 ✅/❌/⏳/⚠️
2. **`2>/dev/null` 要配「我确实没报错」的兜底**，别直接扔
3. **别把「命令没跑」和「检查通过」混为一谈** ——
   变量未赋值 → `grep` 拿不到 → `${to_fail:-0}` → **0 = 通过**
   （E26「读到上次的成功结果」的又一次）
4. **自己改脚本出的错，先分清是不是「本来就有」** ——
   `git show HEAD:文件` 对比，比凭感觉靠谱

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 【R】组 | 静默死亡（有 PASS 无输出） | **真实输出 2 条断言** |
| 巡检现状行 | 每次自增，累积 13 行 | **恒为 1 行** |
| 锚点 | 靠「长得像活行」推断 | **BEGIN/END 显式标记** |
| 全组输出体检 | 无 | **21/21 组都有实际输出** ✅ |

**延伸**：E26「读到上次的成功结果 → 静默失效」、E42「量错了 → 假 PASS」、
本条「**根本没跑 → 同样的假 PASS**」——
三个不同成因，同一症状：**PASS 不代表检查过**。
所以「PASS」这个信号本身也需要被检查（每组有没有实际输出）。

### E44：靠对话收敛的循环，收敛速度取决于模型而不是算法

> 本条讲：**靠对话收敛的循环，收敛速度取决于模型而不是算法**

**场景**：2026-10-27 09:00 那次 daily-learning 跑了 **772s**（timeout 900s，余量 14%）。
三个错误假设都排除了：任务重（否，输入反而少）、provider 慢（否，单发 0.95–1.5s）、
工具重（54 次 exec 里 **26 次是同一命令重试**，48%）。

**真根因：agent 在手工迭代字数**
```
272→259→233→232→227→225→222→222→223→221→219→190→190 = 13 轮
```
每轮 = 一次完整推理（~58K 缓存上下文），≈20-30s → 吃掉几百秒。

**为什么会这样**：指令写「写完自己数一遍，超了就砍」——
**「数汉字」是 LLM 做的，LLM 数不准** → 只能写一版、数一版、改一版…
这叫**靠对话收敛**：速度取决于**模型**，不取决于**算法**。

**修法：把「计数 + 裁剪」交给确定性脚本** `scripts/trim_learning_section.py`
- 数汉字（口径与 E42 一致）；保留「可立即执行的对策」段
- 删信息量最低的铺垫段；超标按句截断最长段
→ **1–2 次调用收敛**

**我自己的脚本也犯了同族错**：第一版只算正文段落，漏掉首行 25 字
→ 段落 181「合规」，实际 206 超标 → **口径要算全**

**岔路口**：
1. **判断该不该脚本化，看它是不是「可确定性判定」的**：
   「汉字数超了吗」可判定 → 脚本化；「这条教训值不值得记」不可判定 → 留给 LLM
2. **脚本化的收益 = 消除迭代次数的不确定性**（算法 1 次 vs 模型 13 次，且模型那次会超时）
3. **脚本要保护价值最高的部分**（显式保护「对策」段）
4. **同步指令前先确认「源文件」和「线上」是否一致** ——
   我用 `daily_learning_prompt.txt` 同步 cron，但那个文件**比线上旧**
   → 差点把好指令覆盖成差的 → 【T】组当场抓到

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 字数收敛轮数 | **13 轮** | **1–2 次** |
| 耗时 | 772s（86% 超时） | 待定时跑验证（预期 ~200-300s） |
| 工具调用重复率 | 48% | 应降到个位数 |
| 合规率 | 靠模型自觉 | **确定性 100%** |

**延伸**：E32「软约束等于没有约束」、E42「口径不一致 = 断言失效」，
本条讲软约束的**代价有多具体**：不是效果差一点，
而是 **13 倍推理成本 + 86% 超时余量**。

### E45：修完根因后，监控还在量修复前的那次测量

> 本条讲：**修完根因后，监控还在量修复前的那次测量**

**场景**：2026-10-27 10:00 巡检报 `daily-learning` 耗时 772s / timeout 900s = 86%，余量告急。
但根因（E44：13 轮手工迭代字数）**在 09:24 就已修复**——加了确定性裁剪脚本，
指令也重写成「1-2 次调用收敛」。也就是说：**修复已经生效，告警却在拿修复前的旧数据报警。**

**陷阱**：这类断言不会自己知道自己的信号已经过期。
- 修复前：`lastDurationMs = 772s` 是**真实**信号 → 断言正确
- 修复后：同一个 `lastDurationMs = 772s` 变成**历史遗留** → 断言变成"永远红"
- 两者在数据库里长得一模一样，断言无法分辨

**岔路口**（两个都做，别只做一半）：
1. **判定信号本身是否还有效**——先问"这个数是修复前测的还是修复后测的"
2. **给修复留冗余，而不是等下一次运行来证明**——
   直接把 timeout 从 900s 提到 1800s（772/1800 = 43%），而不是"下次跑快了就绿了"

**证据**：
| 项 | 修复前 | 修复后 |
|---|---|---|
| timeout | 900s | 1800s |
| 772s 占比 | 86%（告急） | 43%（余量充足） |
| 【U】组判定 | ❌ FAIL | ✅ PASS |
| 裁剪脚本耗时 | — | **0.057s**（实测） |

**延伸**：E33「机制缺口比单点故障更值得修」、E42「断言量错了东西就等于没有断言」，
本条讲第三种：**断言量对了东西，但量的是历史**——
它比"量错"更隐蔽，因为它看起来一直很勤奋。

**一句话**：断言红了，先别急着修任务，先确认它量的是不是「现在」。

### E46：慢的第三个层次 —— 有时候根本不该跑那个任务

> 本条讲：**慢的第三个层次 —— 有时候根本不该跑那个任务**

**场景**：2026-10-27 11:05。E35 之后我加了「短 poll」提醒、又加了【V】断言
检测长 poll。V 报出 26 次长 poll，我第一反应是「poll timeout 还是太长」。

**但把【V】改成按 cron 任务维度报告后**，一眼看出：
```
daily-learning×12, backup-audit×9, healthcheck×5
```
顺着查下去 —— **真根因根本不是 poll**：

- `daily-learning` 09:00 那次，**447s（171+78+120+78）全在等 `healthcheck.sh`**
- `backup-audit` 也有 **3 次 120s 的 poll**，等的是同一个脚本
- **而 `daily-learning` 的指令里根本没要求它跑巡检** —— 它是**自己跑去跑的**

**三层递进**（这一串是今晚最值钱的东西）：
| 层 | 命题 | 出处 |
|---|---|---|
| 1 | 慢的是**等法**不是任务（poll 会等满 timeout） | E35 |
| 2 | **指令说了也不照做**（自己写的规则自己也忘） | E41 |
| 3 | **有时候根本不该跑那个任务** | E46 ← 本条 |

**第 3 层为什么最值钱**：
- 第 1 层 → 改等法（poll timeout 调小）
- 第 2 层 → 加规则和检测
- 第 3 层 → **少做** —— 那 447s **根本不该存在**
  → 每日巡检是 07:00 那个 cron 的职责，学习任务顺手也跑一遍 =
    白白多等 + 挤占 2 核 CPU（实测 8 并发零加速、18 个慢 3 倍）

**岔路口**：
1. **看到「等很久」时，先问「这个等待有必要吗」**，再问「怎么等得快」
   —— 顺序反了就会一直在优化一个不该存在的东西
2. **断言要按「行动单元」分组**，不按会话/总量：
   - 按会话 → 「0d127a42×460」→ 不知道该改什么
   - 按 cron 任务 → 「daily-learning×12」→ 立刻知道动哪里
3. 修的时候要区分**两个不同的问题**：
   - 「怎么等」（技术）→ 短 poll / sessions_spawn
   - 「该不该等」（范围）→ **这条任务不需要跑那个脚本**
   → 后者收益大得多

**证据**:
- daily-learning 09:00 实测 772.1s，其中 447s 在等 healthcheck.sh ✅
- backup-audit 3 次 120s poll 同样在等它 ✅
- 3 条 cron 指令已加【别跑不必要的巡检】✅

**延伸**：这是 E7「修完根因后监控还在量修复前的那次测量」的**行为侧版本** ——
E7 讲「别量已经不存在的问题」，E46 讲「**别做不该存在的工作**」。

### E47：断言只看「最近一次」，就等于没在看历史

> 本条讲：**断言只看「最近一次」，就等于没在看历史**

**场景**：2026-10-27 11:28 心跳。巡检全绿（PASS=63 / FAIL=3 / WARN=2），
5 个 cron 的 `lastRunStatus` 全是 `ok`，3 个 announce 任务的 `lastDelivered` 全是 `True`。
**但我去翻 `cron runs` 历史时，看见了巡检完全看不见的东西**：

```
daily-reflection  总 43 次 = ok 3 次 + error 40 次
  └ 其中 2 次「status=ok 但 delivered=false」（10-26 00:35、10-21 04:27）
healthcheck      6 次里 1 次 ok-but-not-delivered（10-26 10:44）
daily-learning  20 次里 3 次 ok-but-not-delivered（10-26 09:00 / 00:36、10-21 04:29）
```

**为什么巡检看不见**：`check_cron_delivery.py` 读的是 `cron list --json` 里的
`state.lastRunStatus` / `state.lastDelivered` —— **只有最近一次**。
历史失败在那个字段里**根本不存在**。

**最毒的一点**：`ok-but-not-delivered` 的语义是
「**任务成功跑完了，但结果没送到牛哥哥手上**」。
这正是 AGENTS.md 里那句「**状态字段描述的是『任务跑完了』，不是『用户得到了结果』**」
的**反面**：断言自己就犯了这个错 —— 它断言的是「任务跑完了」，
而用户要的是「**结果送到了**」。

**⚠️ 取证时踩的一个坑（差点得出相反结论）**：
`cron runs` 的输出里，`not-delivered` 对两种完全不同的任务都出现：
- `mode=none` 的任务（teahouse-monitor / backup-audit）—— **设计上就不投递**，不是故障
- `mode=announce` 的任务 —— **是真的没送出去**
→ **看 `not-delivered` 之前，必须先看 `delivery.mode`**。
不分清就会把「正常」报成「故障」，或者反过来。

**✅ 修法**：断言从「看 lastRun」改成「**看 history**」：
```
for 每个 mode==announce 的 job:
    runs = openclaw cron runs --id <id> --limit 20
    undelivered = [r for r in runs if r.status=='ok' and r.delivered is False]
    ├ 最近一次仍未投递 → FAIL
    └ 历史有、最近已好   → WARN（带时间点，便于定位）
```
→ **一次就把 6 个之前完全看不见的静默失败抓了出来。**

**教训**：
1. **「当前值正常」不能推出「历史正常」** —— 断言要问对时间维度
   （最近一次 / 近 N 次 / 全部历史，是三个不同的问题）
2. **断言的字段要和「用户得到的结果」对齐**，而不是和「任务跑完了」对齐
3. **同一个状态码在不同 mode 下含义不同**（`not-delivered` 对 none 是正常、对 announce 是故障）
   → 判定前**必须先分组**，不能只看字段值
4. **新增断言必须做注入故障验证** —— 我把「最近一次」强制改成未投递，
   确认它会 FAIL（`__FAILED__=3`），不是只会 WARN；然后恢复

**延伸**：E7「修完根因后监控还在量修复前的测量」讲的是**时间上的滞后**；
E47 讲的是**维度上的遗漏** —— 前者是没看到「旧数据」，后者是**根本没在看那一列**。

#### 🔗 与既有条目的关系

| 条目 | 命题 | 与 E47 的关系 |
|---|---|---|
| E7 | 修完根因后监控还在量修复前的测量 | **时间维度**的滞后 |
| E33 | 机制缺口比单点故障更值得修 | E47 正是机制缺口：**断言只看了一个点** |
| E42 | 口径不一致 = 断言失效 | E47 是「**采样口径**不一致」（只看 lastRun） |
| E46 | 有时候根本不该跑那个任务 | E46 减少「不该做的事」，E47 扩大「该看的东西」 |

**一句话**：
> **别只盯着「现在怎么样」，也要问「我到底在看多少个点」。**

### E48：分类不该等于过滤 —— 「分组」顺手造出来的盲区

> 本条讲：**分类不该等于过滤 —— 「分组」顺手造出来的盲区**

**场景**：2026-10-27 12:00 心跳。巡检【V】组（检测会话里的长 poll）报
`12h 内 309 次长 poll`。我按自己的规则复核，发现**这个会话自己就用了 3 次长 poll**
（180s / 200s / 220s）—— 违反 TOOLS.md 里「poll ≤10~15s」那条规则。

但【V】组**一次都没报我**。

**根因**：【V】组的判据是
```python
job = task_of(head)          # 按 cron 任务标记分类
if not job:
    continue                 # ← 匹配不上就整段跳过
```
`task_of()` 只认 5 个 cron 任务的标记（`scripts/healthcheck.sh`、
`每日学习（精简版）`…）。**普通心跳会话没有任务标记** → 返回 `None`
→ **整个会话被跳过** → 它的 poll 一次都不计数。

而这个盲区是**上一轮刚引入的**：
11:45 那次我为了「按任务维度报告」（daily-learning×12 / backup-audit×9），
把统计从「按会话」改成了「按任务」——
**分组是为了更好的展示，却顺手变成了只统计「认得出来」的那几类**。

**教训（两层）**：
1. **分类不该等于过滤**。分组的目的是展示，不是排除未知类别。
   「匹配不上」应该是「归入『未分类』」，不是「不算」。
2. **断言自己的覆盖面也是断言**。
   一个只统计「已知类别」的断言，等于**对未知情况完全失明**——
   而未知恰恰是最需要被看见的那部分。

**同日还查出【V】的两个隐性错误**（都是「看起来很合理」的那种）：
| 错误 | 表现 | 真因 |
|---|---|---|
| 窗口写着「12 小时」，代码是 3 天 | 说的和做的不一致 | 手写常量漂移 |
| 用文件 mtime 过滤窗口 | 3 天前的违规被算进「12 小时」 | 一个**一直在追加**的会话，mtime 永远是「现在」 |

第三个错最隐蔽：会话文件会持续追加，所以 `mtime` 判龄**永远等于现在**，
导致窗口过滤**完全失效**。必须按**每条记录的 timestamp** 过滤。

**✅ 已做**：
1. 【V】不再跳过任何会话 → 匹配不到归入 `heartbeat/其他`
   → **一次抓出 267 次以前完全不可见的违规**
2. 窗口改用**每条 poll 的时间戳**（不再用文件 mtime）
3. 报告加**按会话归属 + 最后一次违规时间**
   → 一眼分清「还在犯」和「已经停了」
4. `task_of()` 同时匹配**转义形式**（JSON 里非 ASCII 可能变成 `\uXXXX`）
5. **新增【W】组：判据自身的单测**（`scripts/test_v_poll_assertion.py`，9 个用例）

**【W】是这轮最值钱的一条**：
【V】今天连修三个 bug，而【V】报的是「长 poll 数量」——
**判据坏了，它照样输出一个看起来正常的数字**。
典型的自指陷阱：**坏掉的断言看起来和好断言一样正常**。
所以判据逻辑必须有独立单测，而且单测要**直接跑真身代码**：
`test_v_poll_assertion.py` 从 `healthcheck.sh` 的 PY9 块里**抽取真身**来跑
（不是抄一份）→ 判据改了单测立刻跟着变，**物理上无法漂移**。

> 第一版单测就是「抄了一份判据」，
> 而真身已经改成两行写法（`if not job: job = ...`）—— 抄版和真版**悄悄漂移**了。
> 抄一份判据来测 = 测的是「我以为的判据」，不是「在跑的判据」。

**岔路口**：
- ❌ 「把规则写进 TOOLS.md 就行」—— 那是**说明**，不是**约束**（E41/E31 老问题）
- ✅ 让违规**自动可见**：断言负责「发现」，单测负责「保证发现能力没坏」
- ✅ 更进一步：让**约束可执行**（工具层直接拒绝长 poll），但那要改 OpenClaw 本身，
  成本高 —— 先把「可见性」做扎实

**验证**（双向）：
- 真身单测 9/9 通过（现在 / 13 小时前 / 短 poll / 无标记会话 / 转义标记 / 原始中文 / 缺时间戳）
- 全量巡检 PASS=65 FAIL=3（3 项全是长期项）
- 【Q】组当场抓到「新组【W】没同步进 cron 指令」→ 同步后修复 ✅
  （**新加一组断言必然要同步说明文档** —— 这正是【Q】存在的意义）


**同族的三个「断言看起来在干活」**：
E42 讲**数据源**错了 · E45 讲**时间**上是旧数据 · E48 讲**覆盖面**漏了一类
→ 三条都不报错，都给出一个合理的数字 —— **最危险的失败模式**。

**判据本身也要有单测**：坏掉的断言看起来和好断言一样正常。

**延伸**：E42「断言量错了东西」讲的是**数据源**；
E45「监控还在量修复前的那次测量」讲的是**时间**；
E48 讲的是**覆盖面** —— 三条都是「断言看起来在干活，其实没在看该看的东西」。
共同点：**它们都不报错，都给出一个合理的数字。**

#### 🔗 与既有条目的关系

| 条目 | 命题 | 与 E48 的关系 |
|---|---|---|
| E42 | 断言量错了东西 = 没有断言 | E42 是**数据源**错了，E48 是**覆盖面**漏了 |
| E45 | 监控还在量修复前的那次测量 | E45 是**时间**维度，E48 是**类别**维度 |
| E47 | 断言只看「最近一次」 | E47 是**采样点**太少，E48 是**采样对象**漏了一类 |
| E31/E41 | 指令是说明，不是约束 | E48 把「可见性」做成机制，不再依赖「记得做」 |

**一句话**：
> **分组是为了看清，不是为了排除。** 判据自己漏掉的那一类，
> 往往正是最该被看见的那一类。
