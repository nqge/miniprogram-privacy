## 🔧 排查方法论

### E1：区分「失败」和「没触发」

> 本条讲：**区分「失败」和「没触发」**

**场景**：定时任务没产出结果。
**陷阱**：看到没产出就归因为「任务失败了」→ 去查日志、查错误码 → 什么都查不到 → 记为「已知残留项」。
**岔路口**：先查 **cron runs 历史**（有没有触发记录）→ 有记录 = 失败（查日志）；没记录 = 没被调度（改频率/查调度器）。
**证据**：2026-10-26，`daily-learning` 10-24/10-25 零产出。查 runs 历史发现
**10-19 之后到 10-26 之间零次触发** —— 不是失败，是根本没跑。

### E2：口径不一致的对比会产生假告警

> 本条讲：**口径不一致的对比会产生假告警**

**场景**：比对「本地 vs 远端」文件数。
**陷阱**：一边用 `find`（含运行时垃圾如 `__pycache__`），另一边用 `git ls-tree`（只含被追踪文件）→ 报「漏文件」。
**岔路口**：**先确认两边用同一口径**，再判断差异是否真实。
**证据**：2026-10-26，`backup_audit` 报「scripts/ 远端 8 < 本地 9」，实测 `git ls-files` 两边完全一致。

### E3：清理想删旧文件，先确认判龄信号本身有效

> 本条讲：**清理想删旧文件，先确认判龄信号本身有效**

**场景**：清理按时间轮转的日志。
**陷阱**：用 `mtime` 判断「文件多旧」→ 规则永不触发，而且**看起来一直在正常工作**。
**岔路口**：先验证判龄信号本身（打印每个文件的实际年龄）；轮转方式与文件系统行为不符时，
**唯一可靠信号通常是文件名里的槽位标识**。
**证据**：2026-10-26，OpenClaw 日志轮转**按大小不按天** → 同一槽位跨天追加 → `mtime` 永远新鲜
→ `-mtime +7` 规则一次都没触发过。

### E4：涉及「默认值/协议/常量」的结论，必须查源码或实测

> 本条讲：**涉及「默认值/协议/常量」的结论，必须查源码或实测**

**场景**：判断某个配置项的默认行为。
**陷阱**：读文档或凭印象 → 写进记忆文件 → 下个会话当成已验证事实继承。
**岔路口**：`grep` 源码里的常量定义 / 直接实测。
**证据**：2026-10-26 两次栽在这上面 ——
① 「agentTurn 型 cron 默认 timeout 是 30s」实为 **360s**（30s 是 `apply.runtime` 搜索路径的值）
② 「远端提交已添加 `bin/requirements.txt`」实为**文件根本没提交**。

### E5：提交说明 ≠ 文件真的存在

> 本条讲：**提交说明 ≠ 文件真的存在**

**场景**：判断某个修复是否生效。
**陷阱**：读 commit message 里的「已添加/已修复」就当作事实。
**岔路口**：`git ls-tree` / `git show --stat` 落到**文件层面**核实。
**证据**：2026-10-26，远端 `ad8098d` 声称「添加 bin/requirements.txt」→ `git ls-tree origin/main bin/` 只有脚本。

## 📏 工程取舍

### E6：状态字段 ≠ 用户得到的结果

> 本条讲：**状态字段 ≠ 用户得到的结果**

**场景**：任何「自动化是否正常工作」的判断。
**陷阱**：只看 `status=ok` / `enabled` / `consecutiveErrors=0` → 绿色一片，实际功能全死。
**岔路口**：沿着 **触发 → 执行 → 落盘 → 投递 → 用户看到** 逐段取证，每段单独断言。
**证据**：2026-10-26 一天内四个例子——
① 记忆检索 `enabled` 但 Embeddings unavailable（**从 3 月起就没工作过**）
② 飞书投递 `status=ok` 但结果从未送达
③ 学习笔记不报错但周频让 4/8 天根本不触发
④ 茶馆摘要稳定落盘但 4/15 讨论从未被提炼

### E7：定时器保证触发频率，不保证信息增量

> 本条讲：**定时器保证触发频率，不保证信息增量**

**场景**：设计周期性任务。
**陷阱**：把「每 4 小时跑一次」当成「每 4 小时有新东西」→ 重复产出、浪费存储。
**岔路口**：落盘前与上一份比对，内容相同则跳过。
**证据**：2026-10-26，茶馆 0039 与 0040 两份摘要**全文 1671 行、diff 仅 4 行**（99.8% 相同）。

### E8：纯脚本任务不该用 agent 型 cron

> 本条讲：**纯脚本任务不该用 agent 型 cron**

**场景**：让定时器执行一个 shell 脚本。
**陷阱**：agent 型 cron 为了跑一个 20ms 的脚本，消耗 261 秒的模型往返。
**岔路口**：需要判断的用 agent 型；纯脚本用 systemd timer。
**证据**：2026-10-26，`log-cleanup` 改成 systemd oneshot → **261s → 21ms**。

### E9：收集、存储、加工是三件事

> 本条讲：**收集、存储、加工是三件事**

**场景**：构建「信息采集」类系统。
**陷阱**：把「收集」当成终点 → 数据进磁盘，但从未影响判断。
**岔路口**：加工环节要独立存在（待办清单 + 进度断言），否则收集系统只是**浪费磁盘的订阅服务**。
**证据**：2026-10-26，茶馆 monitor 忠实收集 95 条讨论，**4/15 未被提炼**。

### E10：同一文件里的多个同类小节会指数膨胀

> 本条讲：**同一文件里的多个同类小节会指数膨胀**

**场景**：让 agent「在已有小节内追加」而非覆盖。
**陷阱**：频繁触发 + 追加语义 = 每次跑一次多一节。
**岔路口**：明确规定「每天只允许 1 个小节，已有则**替换/精炼**」；长度写成硬约束并自检。
**证据**：2026-10-26，一天堆出 **6 个学习小节、单节 3365 字**（约束是 100-200 字）——
典型的「反刍」。

### E11：新增断言必须做注入故障验证

> 本条讲：**新增断言必须做注入故障验证**

**场景**：写检查脚本（巡检、校验器）。
**陷阱**：脚本跑出 PASS=20 就认为它有效 —— 它可能内含一个**永远抓不到故障**的分支。
**岔路口**：注入故障（停服务 / 造分歧 / 造未蒸馏）→ 确认它真会 FAIL → 恢复。
**证据**：2026-10-26，9 组断言里 **4 组写完后自己坏过**；
且第一版【I】组把蒸馏稿也算进搜索范围，一直**误判 PASS** ——
**检查自己产出的文件，等于没检查**。

## 🧭 认知与判断

### E39：共享账号就是共享配额 —— provider 变慢比 provider 挂掉更隐蔽

> 本条讲：**共享账号就是共享配额**

**场景**：2026-10-27 06:30 心跳。查 `daily-learning` 为何 362s / timeout 420s（余量仅 16%），
翻会话时间分布发现**有一次单次 LLM 调用等了 353 秒** —— 不是在等工具。

**陷阱**：把「只有一个 provider」只理解成一重后果（**挂了兜底无效**）。
真实还有第二重后果：**provider 变慢 → 所有任务一起变慢**。
而且这一重**不报错、不告警**，只表现为「时间莫名变长」，
最难归因 —— 因为每个任务单独看都「没超时」。

**根因**：所有任务共用**同一个 MiniMax 账号**。
关键线索：353 秒那段时间（19:05–19:11 UTC）**正是 backup-audit 超时失败的时段**，
两者是**互相抢同一个配额**，不是各自慢。

**实测（同账号 6 并发，256 token 输出）**：

| 场景 | 延迟 |
|---|---|
| 单个请求 | 1.8s |
| 6 个并发 | 最慢 **7.0s（3.9 倍）** |

**岔路口**：
1. **第二个 key 的价值不是「容灾冗余」，是「拆开共享配额」** ——
   两把 key 指向两个独立配额桶，慢的那把只拖慢用它的那批任务。
   把它记成「兜底」会低估价值，记成「冗余」会误以为有 key 就不挤了。
2. **退化分两类，优先级不同**：
   - **挂掉** → 有 error、有 timeout → 容易发现 → 排查成本低
   - **变慢** → 无 error、只是慢 → **最难发现** → 而它恰恰先吃掉超时余量
   → 所以要给「慢」配观测（单次调用耗时分布），不能只配错误率
3. **并发变慢要区分两种成因，别混为一谈**：
   - **E37**：瓶颈是 **CPU**（本地进程启动）→ 并行只会更慢
   - **本条**：瓶颈是**远端配额**（共享账号）→ 并行请求彼此排队
   → 判据：本地 `user ≈ real` 是 CPU 密集；本地很快但远端慢 = 远端排队
4. **发现长尾耗时先查「时间重叠」**：把慢调用区间和其他任务失败区间叠在一起，
   若重叠 → 不是那个任务自己慢，是**它们在抢同一份资源**。

**证据**：
| 项 | 值 |
|---|---|
| 单次 LLM 调用最长等待 | **353s**（daily-learning 会话内） |
| 同账号 6 并发最慢延迟 | **7.0s**（单发 1.8s，**3.9 倍**） |
| 巡检超时余量 | 420s 预算里只剩 16% |

**已做**：把并发实测数字（1.8s→7.0s，3.9 倍）与 353 秒那次等待的关联，
写进【M】长期项断言的注释 —— 让「等牛哥哥给第二个 key」这件长期项
**带上具体代价**，而不只是一句「兜底无效」。

**延伸**：E28 讲「长期项和真故障混在一起会让信号失效」，
E39 讲「**同账号多任务是隐形的长期项**」——
它在系统里表现为「大家都变慢了」，而不是「某一项坏了」，
所以永远排不进「故障」列表，只能靠实测并发延迟才能看见。

### E40：验收用的测量，必须跑在真实负载上

> 本条讲：**验收用的测量，必须跑在真实负载上**

**场景**：2026-10-27 07:00。今晚所有改动第一次**无人值守**验收。
跑之前的前置检查写「巡检 ~102s / timeout 600s，余量充足 ✅」，
但 07:00 真实 cron 跑完实测 **298.4s** —— **差了近 3 倍**。
前置检查没测错东西，它测的是**另一个工作负载**。

**陷阱**：用「我手动跑一次」的数字给**定时任务**定超时预算。
两者的负载不同，差多少事先不知道：
- 我的手动跑：交互会话里跑，缓存热、抽样轮转到轻的一天、我在旁边盯着
- 真实 cron：无人值守、缓存冷、按 `%j % 4` 轮转到不同抽样位置、还要和别的任务抢配额
→ **手动测出的耗时是定时任务耗时的下界，不是它的估计值。**
更糟的是它**给出一个自信的具体数字**（102s），比不给数字更危险。

**根因**：`verify_l1_retrieval.py` 的抽样量**按天轮转**
（`offset = %j % SAMPLE_EVERY`，存量每 4 条抽 1 条 + 最近 6 条全查）。
轮转设计的初衷是「保证任何一条最多等 3 轮就被真检索一次」——
**它保证了覆盖的公平，却让每天的负载不一样**。
于是「昨天测的耗时」根本不能代表「今天这一轮」的耗时。

**岔路口**：
1. **别拿手动测的耗时给定时任务定预算** —— 要么在**最重的一轮**上测，
   要么直接看**真实 cron run 的历史耗时**（run 记录里有真实值）
2. **抽样/轮转的设计要同时管「覆盖」和「负载」** —— 覆盖公平 ≠ 负载恒定；
   如果轮转让工作量浮动，就得给预算留**最坏情况的余量**，而不是平均情况
3. **最重的负载要能被识别出来** —— 抽样量随天变化时，
   「今天这轮为什么慢」需要能从数据里看出来，不能靠人记得今天轮转到哪
4. **验收要验收「被验收的那一份」** —— 手测的样本 ≠ 线上跑的样本，
   这和 E23「担心要用实测替代想象」、E26「读到上次的成功结果」同族：
   **验证的对象错了，结论就全错（E20）**

**证据**：前置检查记录「~102s，余量充足」；同一套脚本 07:00 真实 cron 实测
**298.4s**（timeout 600s，余量 50%）。差 2.9 倍，**同一天、同一套脚本**。

**延伸**：E35 讲「任务超时 ≠ 任务慢 —— 先量等待方式再调超时值」，
E37 讲「并行不一定更快」，本条讲**测量的样本本身**——
E35/E37 都在追问「时间花在哪」，本条追问的是「**你测的是哪一次运行**」。

### E15：对外收敛 ≠ 对内收敛

> 本条讲：**对外收敛 ≠ 对内收敛**

**场景**：判断某件事该不该做。
**陷阱**：把「用户不在场」当成「可以无限期做」→ 内部学习、笔记、维护一起停掉。

### E16：低触发频率的机制没有容错

> 本条讲：**低触发频率的机制没有容错**

**场景**：把某个每日任务调成每周/每月以「省资源」。
**陷阱**：低频 = 每次失败就是整周空白，且**空白期往往正是无人注意的时候**。
**岔路口**：频率是**容错参数**，不是省钱旋钮。
**证据**：2026-10-26，daily-learning 周频 → 10-24/10-25 零文件。

### E17：检索的最小单位是「块」，不是「条」——短章节会被切碎稀释

> 本条讲：**检索的最小单位是「块」，不是「条」——短章节会被切碎稀释**

**场景**：新建知识库 / 经验库 / 笔记体系；任何「写下来了但搜不到」的现象（沉淀一条新经验时）。
**陷阱**：验证「文件存在、条目数对、mtime 新」就宣布完成 → 内容**写完即死**。
更隐蔽的一层：检索按 token 切块（`chunking.tokens=200`），**切在条目中间时标题和「场景」被切走**；
短小节夹在两个长小节之间时，标题与正文分处两块，**两块都不以这条内容开头** → 向量被邻段平均掉，
搜原文措辞也排不进去。检索到的是**语义残片**，不是你的条目。
**岔路口**：① 建完立刻拿**原文措辞**检索一次，排不进前列就重写标题/措辞（命中分数是硬指标，不是感觉）；
② 关键条目**首行重复标题关键词**（本文件的 `> 本条讲：` 约定即为锚点），让条目在任意切块下都自洽；
③ 独立条目**拆成独立文件**，彻底摆脱邻段稀释（最有效，见下方证据）。
**证据**：2026-10-26 建立 L1 库（16 条）→ 用原文措辞搜「区分『失败』和『没触发』」，
L1 排第 1（**0.6554**）→ 但新增 E17 后搜「沉淀 验收标准 检索命中」，**E17 所在块没进前 6**；
查库见其被切成 20-45（开头是反思）与 41-57（开头无标题）两块 →

### E18：记住了 ≠ 不再踩，要改结构

> 本条讲：**记住了 ≠ 不再踩，要改结构**

**场景**：任何「我刚犯过这个错」「我刚记录过这条教训」的场合。
**陷阱**：把教训写进笔记 / 记忆文件就当解决了 → 同样的错误换个场景再来，
而且因为「我已经记过了」，反而不会再警惕。
**岔路口**：凡是**已经踩过一次**的错误，要改的不是记忆而是**结构**：
- 长文本（尤其含反引号、`>`、`$`）→ 写进文件，用 `--message "$(cat file)"` 引用，不要裸放命令行
- 危险字符 → 用 heredoc（`<< 'EOF'`）而非拼接字符串
- 路径 → 提取成变量，不重复手写
**证据**：2026-10-26 12:15，我给 cron 改指令时在命令行里写了反引号和 `>`：
- 反引号 → **命令替换** → `memory/YYYY-MM-DD.md` 被当命令执行
- `>` → **输出重定向** → `memory/daily-notes-index.md` 被当输出目标

→ **记教训是最弱的改进步骤，改结构才是。**

### E19：bash 里嵌套 heredoc + 命令替换会吞掉变量

> 本条讲：**bash 里嵌套 heredoc + 命令替换会吞掉变量**

**场景**：在 shell 脚本里用 `$(...)` 包一个 heredoc（python 代码），再把结果放进变量。
**陷阱**：变量**静默变成空串**，不报错、不中断。表现是「写进去了，但值是 0/空」。

**证据**：2026-10-26 12:20，给 healthcheck.sh 加「自动更新 SESSION-STATE 巡检现状行」时：

```bash
...

)
NEWLINE="... ${GROUPS} 组断言 ..."
```
`bash -x` 显示 `GROUPS=12` 紧接着 `NEWLINE='... 0 组断言 ...'` —— **变量被吞**。
我试了固定路径（怀疑 BASH_SOURCE 空）、花括号、多字节字符、heredoc 改写，
**换了四种写法都是 0**，直到把 python 抽成独立脚本 `scripts/update_state_status.py` 才通。

### E20：验证的对象错了，结论就全错

> 本条讲：**验证的对象错了，结论就全错**

**场景**：想证明「某个机制能工作」。
**陷阱**：验证了**你想验证的东西**，而不是**实际生效的东西**。
**岔路口**：先问「**真正生效的是哪个？**」，再去验证它。

**同一类问题的三种形态**（2026-10-26 一天内连中三次）：

| 我验证的 | 实际生效的 | 症状 |
|---|---|---|
| 手动 `cron run` 成功 | 定时调度 | 从没真正无人值守跑过 |
| 交互 shell 里跑通 | systemd 环境 | PATH 缺 pnpm、`systemctl --user` 报 unknown |
| 文件里有 `OnFailure=` 这行字 | 指令真的生效 | 注释里也有这行字，grep 看着正常 |

**证据**：2026-10-26
1. 08:00 巡检我以为是自动跑过，实际是我自己手动触发的，还写成「无人值守下真实生效」
2. 30 分钟巡检第一版在 shell 里测过，systemd 下直接挂两项（PATH + XDG_RUNTIME_DIR）
3. 为了加一行 `ExecStartPost` 重写了整个 `.service`，把 `OnFailure=` 真实指令弄丢 ——
   **但注释里还留着这行文字**，所以 grep 能搜到，看起来一切正常，
   而故障时告警单元**完全不被触发**。

**怎么破**：验证时先确认「**我看到的东西就是系统用的东西**」。
- 指令是否生效 → `systemctl show -p <Prop> --value`（不是 grep 文件）
- 定时是否触发 → 找**真实的定时运行样本**（看 sessionId、时间和手动触发区分开）
- 状态是否正常 → 问「**实际运行的是谁**」（`/proc/<pid>/environ` 的 PATH）

**延伸**：**时间线是因果的证据**。09:02 失败 / 09:19 修 / 09:19 之后全成功 ——
这三条排在一起，因果关系不需要解释。如果只看「现在是 ok」，无法排除是偶然。

### E21：修症状 ≠ 修类

> 本条讲：**修症状 ≠ 修类**

**场景**：修完一个 bug。
**陷阱**：把「这个具体问题」修好就收工 → 同一类的下一个问题照样会静默发生。
**岔路口**：修完立刻问「**这一类风险还有哪些地方没覆盖？**」，
用一个检查**覆盖整类**，而不是每次出一处补一处。

**证据**：2026-10-26
我修了「重写 .service 把 `OnFailure=` 弄丢」这个**症状**（恢复指令 + 加一条断言），
但没问「『配置文件里的东西 ≠ 实际生效的东西』这一类风险覆盖到了吗」——
换个单元、改个路径，同样会静默失效。
于是又做了 `scripts/check_unit_drift.py`，把这一类系统性覆盖：
单元 enabled / 脚本存在 / 关键指令生效 / 解释器存在 / 定时器调度 / 敏感文件权限。

**怎么破**：
1. 修完先问「这是**个案**还是**一类**？」
2. 是类 → 找一个能**同时覆盖多个实例**的检查点
3. 新检查点**必须做注入故障验证**（否则它自己可能有盲区）

**代价对比**：个案修复 = 一次；类覆盖 = 一次 + 一个检查脚本，
但**同类问题再也不会复发**。

**陷阱**：以为「我已经知道这条了」→ 写东西时**根本没想起它** → 犯了刚学过的错。

### E24：跑两遍不只是浪费，是会引入竞态

> 本条讲：**跑两遍不只是浪费，是会引入竞态**

**场景**：某个脚本被调用了两次（自己调自己，或两个入口各跑一次）。
**陷阱**：只是「慢一点」→ 忽略了两次读到的**是不同时间点的状态**。
**岔路口**：两次执行之间状态可能已经变了 → **结果可能不一致**。

**证据**：2026-10-26
`alert_dedup.py` 会自己再跑一遍 `quick_health.py`，
导致每次成功巡检实际跑两遍（8 秒 → 16 秒）。
**更要紧的是竞态**：
「第一次 FAIL、第二次 PASS」会让 dedup 误判为**已恢复** →
**发一条假的恢复通知，同时丢掉真实的故障**。

**修法**：`quick_health.py` 把结果写到 `logs/quick-health-result.json`，dedup **读它**。
效果：~14 秒 → ~7 秒，且状态与实际**严格一致**。

**怎么破**：修性能问题时顺手问一句「**这两次跑的结果可能不一致吗**」——
答案是「会」，那就不只是性能问题了。

### E26：告警链路自身的失败模式，是「读到了上次的成功结果」

> 本条讲：**告警链路读到的可能是上次的成功结果 —— 故障时告警被静默吞掉**

**场景**：想证明「故障时告警真的会发出去」。

**陷阱**：OnFailure 处理器读巡检结果文件。
脚本如果**在写这个文件之前**就崩了/被 kill/超时，
文件里留的还是**上一次成功运行**的结果 → 处理器读到「无故障」→ **告警被静默吞掉**。

> 恰恰发生在系统最坏的时候 —— 而且**看起来一切正常**。

**岔路口**：
1. 注入崩溃 → 手动触发 OnFailure → 看告警单元说了什么
2. 观察它读的是**哪一次**运行的结果 → 定位到「时间错位」
3. 修复要两层：
   - **新鲜度校验**（结果文件超过 N 分钟 → 不信，自己重跑）
   - **running 标记**（开跑前写标记，跑完删掉；标记还在 = 没跑完 = 失败）

**关键**：只用「新鲜度」**不够** —— 崩溃发生在写文件前时，
旧文件可能只有 1 分钟前写的，看起来很新鲜。
必须靠 running 标记才能区分「刚成功」和「崩了」。

**成果**：
- 修好后 4 条路径全部验证：正常成功 / 检查项失败 / 崩溃在写文件前 / 文件陈旧
- 端到端走真实 systemd OnFailure 链路验证：`code=0 msg=success` ✅

**延伸**：这条其实是 E12「落盘 ≠ 送达」的**镜像版** ——
E12 讲「执行了不等于送达了」，E26 讲「读取了不等于读的是对的东西」。
两者都是**中间产物被误当作结论**。

### E27：两处结论同时错，根因通常是「测量环境不同」

> 本条讲：**两处结论同时错，根因通常是「测量环境不同」—— 先问是不是在测同一个东西**

**场景**：复核另一个会话（或过去的自己）写在共享文档里的实测结论。

**陷阱**：两边都「测过了」，数看起来也有依据，但**测的不是同一个东西**。
这次的实例：
- A 会话测「`--log-level warn` flag 有没有效」时，**环境变量还没配**
- B 会话（我）复核时，**环境变量已经配上了**
- 于是 flag 的效果被环境变量**盖住** → 看起来像「flag 无效」
- 而在**裸环境**单独测 flag，它完全有效（-100%）

同样地，「每次 CLI 调用都会重新注册全部插件」这个归因也是错的 ——
实测 CLI 调用产生 **0 行**，真实来源是 **agent session 启动**（同一秒成簇 16 行）。

**岔路口**：
1. 发现结论冲突时，**先问「两边测的是同一个环境吗」**，而不是先判断谁对
2. **构造「裸环境」单独测**：`env -u OPENCLAW_LOG_LEVEL ...`
3. 对照表要分维度量（动作 × 产生量），不要只测一个动作
4. 跨会话共享的文档（TOOLS.md / 运维笔记）**必须复核** ——
   写错的结论会一直复制下去

**证据**：2026-10-26 21:35，裸环境 3 次 CLI 调用：
默认 60630 字节 → 带 `--log-level warn` = 0 字节；
`openclaw cron list` × 5 → 0 条 Registered 行；
agent session 启动 → 同一秒 16 条。

**关键判断**：环境变量的价值不在于「比 flag 强」，
而在于**它能作用于非 CLI 的进程** —— 也就是 agent session 启动、systemd 单元这些
真正产生噪音的地方。flag 只在显式带 flag 的那一次调用里有效。

### E28：长期项和真故障混在一起，等于让信号失效

> 本条讲：**长期项和真故障混在一起，等于让「今天有没有故障」这个信号彻底失效**

**场景**：巡检里加了一条「客观存在、但要等别人才能解决」的断言。

**陷阱**：那条断言每天都会 FAIL →
1. 巡检从此**永久 exit 1** → 告警链路每次都触发 → 每次都被去重抑制 → 纯消耗
2. 更糟：**真故障出现时，它和长期项并列在同一个列表里** → 报告里两个 FAIL 并列，
   长期项把真故障的注意力带走了
3. 「今天有没有故障」这个信号**彻底失效** —— 永远是「有」

**岔路口**：
1. 给失败项**分类**：「可处理 — 现在就该修」 vs 「等用户 — 长期项」
2. 分类后：长期项**仍然全部报出来**（信息不丢），但
   - **退出码只看可处理项** → 服务该 success 就 success
   - **告警只对可处理项触发** → 长期项静默
   - 报告里两组分开显示，一眼看出哪些要动、哪些在等
3. 关键：**别把长期项「静音」成看不见** —— 那是另一种形式的信号失效。
   要静默的只是**通知**，不是**记录**

**证据**：2026-10-26 22:35，加了【M】Provider 韧性断言后：
只有长期项 → exit 0、不告警 ✅；注入真故障 → exit 1、告警发出 ✅；
每日报告分成「可处理 / 等牛哥哥」两组 ✅

**延伸**：这是 E6「状态字段 ≠ 用户得到的结果」的**变体** ——
E6 讲「状态绿着但功能死了」，E28 讲「状态红着但这个红不代表你的动作」，
两者都是**信号与含义脱节**。

那个文件是 15 小时连续工作的产物，里面是**真实且唯一的操作知识**
（日志清理脚本失效、技能仓库停滞、茶馆摘要去重…）—— 它**合法地**就该占 30-40%。

→ 我差点把「忙碌的一天」当成「故障」来报。

**岔路口**：
1. 加任何「规模类」断言前，先问：**「正常时它长什么样？」**
   - 样本：其他天分别是 1-8 块 → 今天的 35-46% 是**离群值，但不是错误**
   - 一个离群值不等于一个故障
2. 阈值要对着**真实故障**设，不是对着**我的不适感**设
3. 真故障长什么样？→ **两个可验证的特征**：
   - ① **没有上限**（memory/ 目录原本**完全没有任何体积限制**，
     而 `/tmp/openclaw` 日志有 50MB/200MB 上限 —— 对比才看得出缺口）
   - ② **开始垄断检索**（把别的文件挤掉）
   → 据此重设：单文件 > 300KB FAIL、占比 > 60% FAIL、目录 > 200MB WARN
4. **双方向验证**（这是必须的）：
   - 当前真实状态 → 全 PASS（不假警报）
   - 注入 400KB 文件 → 正确 FAIL（不漏报）

**证据**：重写后
- 真实状态（35% 占比、64KB 笔记）→ **3 项全 PASS** ✅
- 注入 400KB 文件 → **正确 FAIL** ✅
- 25% 阈值已废弃，并在注释里写明**为什么废弃**（防止以后有人「优化」回去）

**同时修掉的真实问题**：
今天笔记里有一段 748 行的**原始茶馆摘录**，而那些内容**已经完整存在**于
`memory/teahouse-digest-2026-10-26.md` → 纯重复存储。
已删除（105KB → 64KB，索引 215 块 → 179 块），只留蒸馏结论 + 指针。

**延伸**：这是 E28 的**反面教材** —— E28 讲「别把长期项静音成看不见」，
E29 讲「别把正常状态报成故障」。两者是同一件事的两面：
**信号必须和它要表达的含义对齐**，多报和少报一样有害。

### E30：队列型状态只加不减 = 每次运行都在重复劳动

> 本条讲：**队列型状态只加不减 = 每次运行都在重复劳动**

**场景**：茶馆监控每 4 小时跑一次，拉取新讨论 → 写入「待蒸馏清单」→ agent 蒸馏成知识。
看起来是完整的流水线。

**陷阱**：2026-10-27 凌晨发现，`memory/teahouse-todo.json` 的 `pending` 队列里
**永远躺着同样 4 条**（#135/#138/#134/#154）—— 它们在 11:30 就已经蒸馏完了。

根因：`prompt_distillation()` **只追加，从不移除**。
```
for i in fresh:
    if n in known: continue
    existing["pending"].append(...)     # 只加
# 全函数没有一句从 pending 里删东西
```
→ 蒸馏完成后**没有任何机制**把条目移出队列 → 每 4 小时重新蒸馏同样 4 条。

**为什么巡检没发现**：健康巡检的【I】组是**间接**判定的 ——
它查「编号是否出现在某篇 memory 笔记里」，出现就报 PASS。
但它**从不检查队列本身**，所以：
- 巡检报「茶馆内容已全部蒸馏」✅
- 而队列里明明还挂着 4 条 ❌
**两个状态互相矛盾，巡检只信了对自己有利的那个。**

**岔路口**：
1. 任何「待处理队列」必须配一个**出队**路径，且出队和入队一样显式
2. 蒸馏完成的条目 → 移到 `distilled` 列表（保留编号/标题，便于追溯）
3. **`distilled` 列表也要限量**（默认 50）—— 否则只是把「只增不减」换了个字段
4. 巡检要查**队列本身的自洽性**：
   `pending ∩ distilled == ∅`（同一议题不能既待处理又已蒸馏）
5. 修的时候顺手检查：**我查的字段对吗？**
   → 我一开始查 `seen_ids`（GitHub REST 的 10 位 id）以为没去重，
   实际去重键是 `seen_numbers`（议题号）→ **4 条都在里面**
   → 差点得出「修复会被 4 小时后推翻」的错误结论

**证据**：
- 修前：`pending` 恒为 4 条，每 4 小时重蒸馏一遍
- 修后：端到端跑真实监控 → 「无新内容」，`pending` 保持 0，`distilled` 4 条
- 巡检自洽性：注入「#135 同时在两个列表」→ **正确 FAIL** ✅；正常态 → PASS ✅

**延伸**：这跟 E29 是同一类问题 —— **状态字段和真实情况脱节**。
E29 讲「别把正常报成故障」，E30 讲「别让队列状态骗过自己」。
共同点：**光看一个状态字段不够，要交叉验证**。

### E31：只在指令里写「要记得做」= 把 bug 交给人的记性

> 本条讲：**只在指令里写「要记得做」= 把 bug 交给人的记性**

**场景**：2026-10-27 01:10，修完 E30（茶馆待办队列只加不减）之后，
我意识到自己的修复**留了个洞**：

```
cron 指令: "蒸馏完成后，把已蒸馏的议题编号标记掉"
           python3 scripts/teahouse_monitor.py --mark-distilled <编号>
```

**陷阱**：E30 的根因就是「**出队这一步靠人记得做**」。
我把这一步写进了 cron 指令 —— 但那**还是靠 agent 记得执行**。
指令是提示，不是机制。agent 忘了、或者跑歪了、或者指令被别的段落盖住，
bug 原样复发。

而且更糟：**巡检查不出来**。我原来的【I】组逻辑是：
```
still = [pending 里没出现在任何笔记的条目]
if still: FAIL        # 真未蒸馏 → 该报
else:      PASS        # 已出现在笔记里 → 报 PASS，但【不清理】
```
→ 「已蒸馏但没出队」这个 E30 的 bug 状态，**恰好落在 PASS 分支**里。
巡检说「一切正常」，而 bug 就在那儿。

**岔路口**：
1. **凡是「队列出队」类动作，必须有机制兜底，不能只靠指令**
   → 巡检自愈：检测到「pending 里的条目已出现在笔记里」→ **主动移出队列**
   → 出队不再依赖任何人记得做
2. **自愈和告警要分开**：
   - 「已蒸馏但没出队」→ **自愈**（本来就是对的，只差个出队动作）
   - 「真未蒸馏」→ **FAIL 告警**（真的需要人做事）
   → 自愈**绝不能掩盖真问题**：注入一个笔记里不存在的编号 → 仍必须 FAIL
3. **自愈之后要重新读盘**：自愈刚改过文件，继续用内存里的旧数据
   → 会报出「刚自愈完又说矛盾」的假 FAIL（我自己就踩了这个）

**证据**（双向都验了）：
- 注入 E30 原始 bug 状态（#135 已蒸馏但仍在 pending）
  → 「自愈：1 条已蒸馏但未出队 → 已移入 distilled [135]」，pending 归 0 ✅
- 注入真未蒸馏条目（#999，笔记里不存在）
  → **仍 FAIL**「茶馆有 1 条讨论未蒸馏」✅（自愈没掩盖真问题）
- 注入「#135 同时在两个列表」→ 正确 FAIL ✅
- 正常态 → PASS ✅

**⚠️ 我自己在这条上犯的错（值得记）**：
自愈逻辑第一版把 `still`（=**没**出现在笔记里的）当成了「已蒸馏」，
方向完全搞反 → 注入 #135 后自愈了 **0 条**。
**「still / healed」这类反直觉的命名最容易把逻辑写反** ——
变量名要能自解释，否则不如改成 `not_in_notes` / `in_notes`。

**延伸**：这是 E20「验证的对象错了」的**升级版** ——
E20 讲「验证了脚本却没验证指令」，E31 讲「**改了指令却没改机制**」。
两者共同点：**别把「正确性」寄托在某个人/某个 agent 会记得执行上**。

### E32：手写的「参照数字」会过期，而它是判断依据

> 本条讲：**手写的「参照数字」会过期，而它是判断依据**

**场景**：2026-10-27 02:10 收尾做一致性检查，发现 `MEMORY.md` 里写着
「我学到的方法论（**29 条**，E1–E29）」，而实际已经有 **31 条** ——
E30/E31 是我当晚加的，加完忘了同步文档。

**陷阱**：「一条过期的计数」看起来无害 —— 只是个数字。
但它是**参照系**：
- 我用「L1 库有多少条」来判断「我的记忆系统在不在正常生长」
- 数字停在 29，而真实值是 31 → **我以为没长，其实是长了但记错了**
- 更坏的情况：数字停在 31 而真实值掉到 25 → 我会以为「一切正常」
  → **参照错了，判断就错了**

**岔路口**：
1. 任何**被当作判断依据的数字**，要么**自动生成**，要么**自动校验**
   —— 不能只是「手写在那儿」
2. 本次做法：新增【O】断言（14 → 15 组），自动核对**四处**声明：
   - `memory/L1-entries/` 实际文件数 vs 主库 `### E<N>` 条目数
   - `MEMORY.md` 的「N 条，E1–E<N>」
   - `MEMORY.md` 的「检索自检（必须 N/N）」
   - L1 主库头部的「当前条目数」
   → 任何一处对不上就 FAIL
3. **验证方式**：不是「改完看一眼」，而是**注入 bug 确认能抓到**
   → 把 MEMORY.md 改回 29 → 两条 FAIL 同时报出 → 再恢复

**证据**：
- 注入陈旧计数 → 「MEMORY.md 声明 29 条/E1–E29，实际 31 条/E1–E31」
  +「MEMORY.md 自检声明 29/29，实际应为 31/31」**两条同时报出** ✅
- 恢复后 → PASS ✅

**延伸**：这是 E31「别把正确性寄托在记得做上」的**延伸应用** ——
E31 讲的是「动作」（出队），E32 讲的是「状态」（计数）。
两者共同点：**手写的派生数据必然过期，过期的东西不能当参照系**。
真正的解法不是「记得更新」，是「**让过期可被自动发现**」。

### E33：跨过零点还在写昨天 —— 时间线失真比丢内容更隐蔽

> 本条讲：**跨过零点还在写昨天 —— 时间线失真比丢内容更隐蔽**

**场景**：2026-10-27 凌晨 02:30 收尾检查时，发现 `memory/2026-10-26.md`
里混着 **10-27 的内容** —— E29 到 E32 五个小节（00:35–02:16 写的）
全都追加在 10-26 那个文件里。

**为什么隐蔽**：内容**一点没丢**，检索也**完全正常**（搜到的还是对的），
Git 历史也**连续**。没有任何一个「失败」信号。
但：
- 「10-26 的日志」里写着 10-27 的事 → **时间线失真**

- 拆分：10-26.md 1331 → 1139 行（68K），新建 10-27.md 196 行（12K）

E32 讲「数字会过期」，E33 讲「**日期会过期**」。
共同点：**会话里的隐含上下文（今天几号、写到哪个文件）会随时间漂移**，

```
**当前 FAIL 的 14 类含义**（2026-10-26 实测整理，共 13 组断言 A–M）：
```

### E35：任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」

> 本条讲：**任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」**

**场景**：2026-10-27 凌晨，巡检报「backup-audit 运行失败（超时）」。
脚本本身只要 **0.18 秒**。

**我走的弯路（三次错误假设）**：
1. 「timeoutSeconds 太紧」→ 提到 600 → **还是超时**
2. 「模型限流 / 上下文溢出」→ 直连 API 测：3 个模型全 200、1.1–2.6 秒 → 不成立
   → 构造 1.16M token 请求：HTTP 200 但 **61.5 秒** → 也不是它
3. 「和我的会话抢同一账号配额」→ 我停手后再测，API 依然快 → 不成立

**真根因**：`process(action='poll')` **每次都阻塞满 timeout**。
```
CALL 19:28:11 (timeout: 120000) → CALL 19:30:12   = 121.0s
CALL 19:30:12 (timeout: 180000) → CALL 19:34:40   = 268.0s
CALL 19:34:40 (timeout: 240000) → CALL 19:36:41   = 121.0s
```
3 次 poll ≈ 510 秒 → 必然撞上 job 超时。
**慢的从来不是任务，是「等法」。**

**关键教训 —— 调超时前必须先分清两类失败**：
| 症状 | 真正含义 | 正确动作 |
|---|---|---|
| 任务**本身**耗时长 | 任务慢 | 调大 timeout ✅ |
| 任务很快但**轮询**耗时长 | 等待方式慢 | **改等待方式** ❌ 调 timeout 只是把问题推后 |

**岔路口**：
1. **超时失败时，先单独量脚本耗时**（`time bash xxx.sh`）——
   0.18 秒 vs 600 秒超时 = 明显不是「任务慢」
2. **别用长 timeout 的 poll 等后台任务**：poll 的 timeout 是**上限**，
   实际会等满 → 用**短 timeout 多次 poll**（如 10-15s）而不是一次 120s
3. **会话里的 120s 停顿就是信号**：我自己那轮有 **140 次 120 秒级停顿** ——
   每个都是一次「等满」的工具调用
4. **timeoutSeconds 仍然是必要的兜底**（300 → 600），
   但它是**第二道**防线，不是第一道 —— 第一道是「别等满」

**证据**：
- 脚本 0.18s，job 超时 300s → 差 1600 倍 → 立刻排除「任务慢」
- 直连 API 全 200 / 1.1–2.6s → 排除限流
- 1.16M token 请求 HTTP 200 / 61.5s → 排除上下文溢出（那也是我一开始的怀疑）
- poll 调用间隔 = 请求 timeout + 1s（121.0s / 268.0s / 121.0s）→ **决定性证据**

**延伸**：这是 E29「先问『正常时它长什么样』」的**时间维度版本** ——
E29 讲「别把正常报成故障」，E35 讲「**别把等待慢当成任务慢**」。
两者共同点：**症状和原因之间隔着一层「怎么观测的」**。

### E36：最该被信任的地方，过期了最致命

> 本条讲：**最该被信任的地方，过期了最致命**

**场景**：2026-10-27 05:10 收尾时看 `SESSION-STATE.md` 头部的「📋 系统状态」小节，
发现里面**几乎每一条都是过期的**：
- provider 写着 `minimax, glmcode, arkcode` —— 后两个**早就删了**（实际只剩 minimax）
- cron 列表里有 `teahouse-check` / `dream-cycle-v3` —— **任务早就删了**
- plugin 里有 `qqbot` / `ddingtalk` —— **早就移除了**
- 「首次自动调度验证待 10-26」—— 早就过了

**陷阱 —— 为什么这条比 L1 库里的过期计数更严重**：
- L1 库里的计数过期 = 我判断「记忆系统状态」时参照错了（E32）
- **SESSION-STATE.md 头部过期 = 下一个会话被直接误导**
  → 它是 AGENTS.md 规定的「每次会话先读」的第一份文件
  → 下一个会话会据此认为「glmcode 还在，只是 key 过期，要等牛哥哥重签」
  → 而实际上那些决策项**早已不需要等了**
- 也就是说：过期数据不可怕，**过期的指令**可怕 ——
  它会让人做出**本不该做的动作**

**岔路口**：
1. **手写的「当前状态」小节 = 定时炸弹**：
   → 改成由 `scripts/gen_system_status.py` 从**真实系统**生成
   （providers / cron 任务 / plugins 全部实时读，加 `BEGIN/END` 标记）
2. **头部「最后更新」时间**也用 git 最后提交时间自动填，不手写
3. **加断言【S】持续核对**（18 → 19 组）：
   - providers 声明 == 真实 providers
   - cron 列表 == 真实 cron 列表（不漏、不多）
   - 小节里不出现任何**已删除实体**的名字
4. **历史记录不要改**：SESSION-STATE.md 里那些带日期的「巡检现状（快照）: 12 组断言」
   是**当时的事实**，保留不动 —— 只有「当前状态」才需要与现实同步

**证据（双向）**:
- 注入原始 bug（写回 glmcode/arkcode/teahouse-check）→
  **四条 FAIL 同时报出**（providers 不一致 / 列了不存在的 cron / 两个已删除实体残留）✅
- 恢复后 → PASS ✅

**延伸**：这是 E34「派生数据不手写」的**延伸应用** ——
E34 讲的是「说明清单」，E36 讲的是「**当前状态**」。
区别在于**后果的严重性**：
说明清单过期 → agent 不知道怎么解释某个失败
**当前状态过期 → agent 去做本不该做的事**
→ 所以「哪些手写内容算危险」的排序是：**状态描述 > 说明清单 > 计数**

### E37：并行不一定更快 —— 先看瓶颈是不是 CPU

> 本条讲：**并行不一定更快 —— 先看瓶颈是不是 CPU**

**场景**：2026-10-27 06:00，发现巡检要跑 **252 秒**，其中
`verify_l1_retrieval.py` 占 **174.7 秒（69%）** —— 它对 36 条 L1 经验
逐条调 `openclaw memory search`，每次起一个 Node 进程。

**直觉**：36 次独立调用 → 开 8 个线程并行 → 应该快 8 倍。

**实测（这台机器只有 2 个 CPU 核）**：
| 方式 | 数量 | 耗时 |
|---|---|---|
| 串行 | 1 个 | 6.6s |
| 并发 | 8 个 | **55s**（≈ 8×6.6s，**零加速**） |
| 并发 | 18 个 | **6m18s**（比 18 个串行的 119s **慢 3 倍**） |

→ **并行不但没加速，反而慢 3 倍。**
原因：`openclaw memory search` 的成本是 **Node 进程启动**（CPU 密集），
2 核上并发只加剧上下文切换。

**岔路口**：
1. **并行前先问「瓶颈是不是 CPU」**：
   - 瓶颈是**等待 I/O**（网络、磁盘）→ 并行有效
   - 瓶颈是 **CPU**（进程启动、计算）→ 并行只会更慢
   - 判断方法：`user` 时间 ≈ `real` 时间 → CPU 密集
   （我的实测：`user 5m21s / real 3m54s` → 纯 CPU 密集）
2. **真正的解法不是「怎么等」，是「要不要等这么多」**：
   → 拆成**两层**：
   - **第 1 层（全量、零成本）**：结构检查 ——
     独立文件存在 · 首行有「本条讲：**关键词**」· 主库里有对应条目
     → 这一层能抓到 E17 那类「写了但结构上检索不到」的绝大多数成因
   - **第 2 层（抽样、有成本）**：真实检索 ——
     最近 6 条全查 + 存量每 1/4 抽 1 条
3. **抽样必须轮转，不能固定**：
   固定抽样 → 抽不到的那 58% 可能 **21 天**才被查到
   → 改成**按天轮转起点** → 任何一条最多等 **3 轮**（3 天）
   （用 `datetime.now().strftime("%j") % SAMPLE_EVERY` 做 offset）

**证据**:
| 项 | 改前 | 改后 |
|---|---|---|
| verify_l1 耗时 | 174.7s | **67s** |
| 整个巡检 | 252s | **102s** |
| 结构检查覆盖 | 0（全靠检索） | **36/36 全量** |
| 真检索覆盖 | 36/36 | 14/36（**但轮转保证 3 天内全覆盖**） |

**注入验证**: 删掉 E30 的首行关键词 → **结构检查当场 FAIL** ✅

**延伸**：这是 E35「慢的是等法不是任务」的**下一层** ——
E35 讲「别用长 poll 等满」，E37 讲「**别以为并发就是答案**」。
两者合起来：**先问「时间花在哪」，再决定是「换等法」还是「少等」。**

### E38：只查「今天」的检查，会永远漏掉历史违规

> 本条讲：**只查「今天」的检查，会永远漏掉历史违规**

**场景**：2026-10-27 05:43 心跳。例行跑巡检，PASS=58 FAIL=3（全是长期项），
一切正常。但顺手做了一件巡检**本来该做**的事：把 `memory/*.md` 全列出来，
逐个统计「📚 每日学习」小节数量 —— 发现 **`memory/2026-10-21.md` 有 2 个学习小节**，
违反「每天只允许 1 个学习小节」的硬约束。

**根因（检查本身的盲区）**：
【F】组的实现只把**今天**的文件放进候选：
```python
today = datetime.date.today().isoformat()
cands = [f'{MEM}/{today}.md', ...]   # ← 只看今天
```
→ 10-21 那天确实有 2 个（04:24 和 04:29 两次手动 `cron run` 留下的），
但因为**每天都在换文件**，这个违规**永远不会被检查到** ——
等 10-21 变成「历史」后，`cands` 里就不再有它。

**这个盲区为什么危险**：
- 检查项本身是对的（「每天只允许 1 个」），**逻辑没问题，作用域错了**
- 而且它给出的是 **PASS** —— 一个绿色的、什么都证明不了的 PASS
- 更糟的是：**违规文件会持续膨胀**，而巡检每天报「记忆笔记结构正常」
  → 「今天结构正常」被当成了「结构一直正常」
- 这跟 E34（cron 指令过期）、E32/E36（手写的数字会过期）是**同一个家族**：
  **派生状态只查活跃的那一份，历史那份没人看**

**修法**：把候选从「今天」改成「所有 daily-note 文件」
```python
daily_files = sorted(glob.glob(f'{MEM}/20??-??-??.md'))
cands = daily_files + ['/root/.openclaw/workspace/SESSION-STATE.md']
```
**但要小心不能矫枉过正**：只查**重复**（>1），**不查缺失**（==0）：
| 情况 | 是否违规 | 原因 |
|---|---|---|
| 学习小节 = 2 | ❌ 违规 | 重复，违反硬约束 |
| 学习小节 = 0（修复前的 10-22/10-23） | ✅ 正常 | 那时 cron 还没修好 |
| 反思 = 0（工作日） | ✅ 正常 | 反思是**每周日** 22:00 跑 |
| 学习小节 = 0（今天 05:43） | ✅ 正常 | 今天的 cron 09:00 才跑 |
→ **把「合法缺失」误判成 FAIL，巡检就会变成噪音源，然后被忽略**（E28 的教训）

**同时修掉真实违规**：把 10-21 的两节合并成一节 ——
保留 04:29 那条（更可复用：「先确认故障发生在哪一层」），
把 04:24 那条的独有洞察（「收敛的对象是对外动作，不是对内学习」）
作为「同日另一条」折进正文，**内容零丢失**。

**注入验证**（双向）：
- 往**历史**文件 `2026-10-25.md` 追加一个学习小节 → **正确 FAIL** ✅
  （改前这个注入是**完全不可见**的 —— 这正是本次修的东西）
- 恢复 → PASS ✅

**证据**:
| 项 | 改前 | 改后 |
|---|---|---|
| 覆盖文件数 | 1（今天） | **8 个 daily-note 文件** |
| 能发现历史违规 | ❌ 永远不能 | ✅ 注入即报 |
| 10-21 小节数 | 2（违规） | **1（已合并，内容保留）** |
| 巡检总结果 | PASS=58 FAIL=3 | PASS=58 FAIL=3（**不变**） |

**岔路口**：
1. **写检查时先问「我查的是活跃的那一份，还是全部？」**
   —— 状态类断言默认只查「当前」，但**违规会沉淀在历史里**
2. **PASS 也要有覆盖面意识**：「今天的结构正常」≠「结构一直正常」
   → 报告里带上「已查 N 个文件」，让覆盖面**可见**
3. **扩范围 ≠ 放宽标准**：扩到全部文件后要**重新界定什么算违规**，
   否则「合法缺失」会被当成 FAIL → 巡检变噪音 → 被忽略（E28）
4. **发现真实违规要修内容，不能只修检查** —— 否则下次巡检照样 FAIL，
   变成天天报的噪音

**延伸**：E34 讲「手写说明清单必然过期」，E38 讲「**手写检查范围也会漏**」。
两者合起来：**凡是「只覆盖一部分」的断言，都要问「漏掉的那部分会不会出问题」。**

### E41：指令写了 ≠ 会照做 —— 尤其是「自己写的指令」

> 本条讲：**指令写了 ≠ 会照做 —— 尤其是「自己写的指令」**

**场景**：2026-10-27 09:45。09:00 的 `daily-learning` 跑了 **772.1s**
（timeout 1800s，余量只剩 43%）。查会话时间分布：

```
CALL 01:37:25 (poll timeout=120000) → CALL 01:40:49   = 120.0s
CALL 01:40:49 (poll timeout=120000) → CALL 01:44:48   = 120.0s
CALL 01:44:48 (poll timeout=150000) → CALL 01:47:25   = 150.0s
```

**正是 E35 那个模式。** 而那个 cron 指令里**明明写着**：

```
❌ process(action='poll', timeout=120000~300000) —— poll 会**等满整个 timeout**
✅ exec(..., yieldMs=10000) 转后台，然后 process(action='poll', timeout=10000)
```

**最扎人的一点**：写这条指令的**正是那个会话自己**（并行会话），
而且它**加完指令之后的几轮里，自己就用了 4 次长 poll**。

**根因（比 E31 更进一步）**：
E31 说「别把正确性寄托在记得做上」。E41 补上另一半 ——
**「自己写的规则，自己也会忘」**。
写规则的那一刻你是清醒的；执行的那一刻你在想别的问题。
规则写在**别人的指令里**，执行者是一个**带着自己习惯的 agent**。

**岔路口**：
1. **规则要放在「每次都会加载」的地方**，而不是「某几个任务里」：
   → `TOOLS.md` 是**全局注入**的 → 影响所有会话
   → cron 指令里的提醒**只在那几个任务里**生效
   → 同一个道理，**并行会话的指令对我无效**（那是给它的）
2. **说明 ≠ 约束**。所以再加一层**可观测性**：
   → 新增【V】断言：最近 3 天会话里 `poll` 的 timeout > 60s 的次数 > 5 → WARN
   → 它**不阻止**agent 用长 poll，但**让违规可见**
   → 这样我验收时立刻发现「又犯了」，而不是等某个任务撞上超时
3. **量自己的违规规模**：3 天 539 次长 poll，460 次在我自己这轮；
   timeout 分布 280s×235 / 250s×82 / 200s×52 / **≤60s 只有 9 次**
   → **这是习惯问题，不是配置问题** —— 配置再好，
   一个习惯用长 poll 的 agent 还是会用

**证据**:
- 09:00 daily-learning 实际 772.1s，4 次 120s/150s 的 poll ✅
- 指令里明确写了禁止长 poll，**同一会话自己违反** ✅
- 【V】实测输出：539 次长 poll，分布到 5 个会话 ✅

**延伸**：E31 的解法是「加机制」（出队靠自愈，不靠记得做）。
E41 的解法是**再加一层**：「把规则放到全局 + 让违规可见」。
**规则 + 机制 + 可观测性，三层才稳。**

### 补充（2026-10-27 12:50）：规则生效取决于**加载时机**

我自己的数据（这轮会话）：
```
我这轮上下文里的 TOOLS.md 快照 → 含「等长任务」段: False
TOOLS.md 那段是 09:57 加的（commit 6d11015），我这轮 01:00 就开始了
```
→ 规则是**中途**加的，我这轮上下文里根本没有它。
所以我这轮 481 次长 poll **不能全算「无视规则」**。

**但也不能全算「没看到规则」**：
cron 指令里那版提醒（07:10 加的）我这轮**是能看到的**，
而我 09:00 之后仍然用了 4 次 120s+ 的 poll。

**cron 任务那边的对照（规则确实有效）**：
| | 加提醒前 | 加提醒后 |
|---|---|---|

| backup-audit 长 poll | 9 次 | **3-4 次** |
| teahouse-monitor（11:30 那次） | — | **0 次** |

**因此，巡检发现「某会话违规」时，要先看两件事**：
1. 那个会话的**启动时间** vs 规则的**加入时间**

### E42：断言量错了东西，就等于没有断言

> 本条讲：**断言量错了东西，就等于没有断言**

**场景**：2026-10-27 07:55。daily-learning 的 cron 跑完，巡检报
「2026-10-27.md 小节超长 2010 字（约束 100-200 字）」→ FAIL。
但我核了一下，那一节**我刚压缩过**，内容看着不长 → 先怀疑断言本身。

**第一个 bug —— 量的不是规则说的那个量**：
规则说「100-200 **字**」（中文 = 100-200 **汉字**），
断言却用「去空白后的**所有字符** > 1200」（含标点/英文/空白）
→ **口径不一致，比规则宽了 10 倍**
→ 10-21 的 568 汉字、今天的 991 汉字**全被放过**，直到凑到 2010 字符才触发
→ 修法：数汉字，上限 400（给 100-200 留一倍余量）

**第二个 bug —— 边界算错（今天才暴露）**：
小节结尾用 `(?=\n## |\Z)` —— **只认 `##` 级标题**。
今天「📚 每日学习」恰好是文件里**最后一个 `##` 级标题**
→ 后面所有 `### 心跳` 小节被算进学习正文 → 被算成 **946 汉字**（实际 177）
→ 而 `###` 是 `##` 的**子节**，本来就属于上一个 `##`
→ 修法：小节在**下一个任意级标题**（`#{1,6}`）处结束

**岔路口**：
1. **断言失败了先怀疑断言本身**，别急着改被测的东西
2. **宽的口径比严的更危险** —— 宽 = 静默放过，还报 PASS
3. **边界要用「下一个任意层级」**，`###` 属于 `##`
4. **报 PASS 时也要说清覆盖了哪些东西**（范围 + 口径）

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 长度判据 | 全字符 > 1200 | **汉字 > 400** |
| 小节边界 | `\n## ` | **`\n#{1,6} `** |
| 今天学习小节 | 被算成 946 汉字 | **实际 177** ✅ |
| 10-21 学习/反思 | 568 / 491（放过） | **252 / 227**（已压缩） |
| 抓到的真实违规 | 几乎抓不到 | **3 处（含 2 处历史）** |

**延伸**：E38 讲「只查今天的检查会漏掉历史违规」，本条讲「**查了但量错了**」——
两者都产出**绿色的、什么都不证明的 PASS**，区别是前者范围窄、后者口径错。
合起来：**断言的三要素 —— 范围、口径、边界 —— 任何一个错，PASS 都是假的。**

### E43：被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言

> 本条讲：**被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言**

**场景**：2026-10-27 08:20。给【S】组加断言时发现 shell 报
`line 1031: to_report: unbound variable` —— 一开始以为是**自己刚插的代码**搞坏的。

**真根因（pre-existing，不是我的锅）**：
```bash
PY5
)to_fail=$(echo "$to_report" | grep -oP '__TO_FAILED__=\K[0-9]+')
```
heredoc 结束符和赋值写在**同一行** → shell 把 `to_fail=...` 当成结束符的一部分
→ **`to_report` 从未被赋值** → `set -u` 报 unbound variable
→ 而该组写的是 `2>/dev/null` → **报错被吞掉**
→ 这组**输出为空**，却无条件 `PASS=$((PASS + 1))` → 巡检照样显示 PASS

→ **【R】组（cron 超时余量对比）其实一直是死的**：
它在结果里显示 PASS，只是从没真正算过任何东西。

**岔路口**：
1. **写完断言要验「它有没有真的输出」** ——
   不是看 `PASS` 计数（无条件 +1），而是看**这组名下有没有实际断言行**
   → 脚本化体检：每组至少一条 ✅/❌/⏳/⚠️
2. **`2>/dev/null` 要配「我确实没报错」的兜底**，别直接扔
3. **别把「命令没跑」和「检查通过」混为一谈** ——
   变量未赋值 → `grep` 拿不到 → `${to_fail:-0}` → **0 = 通过**
   （E26「读到上次的成功结果」的又一次）
4. **自己改脚本出的错，先分清是不是「本来就有」** ——
   `git show HEAD:文件` 对比，比凭感觉靠谱

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 【R】组 | 静默死亡（有 PASS 无输出） | **真实输出 2 条断言** |
| 巡检现状行 | 每次自增，累积 13 行 | **恒为 1 行** |
| 锚点 | 靠「长得像活行」推断 | **BEGIN/END 显式标记** |
| 全组输出体检 | 无 | **21/21 组都有实际输出** ✅ |

**延伸**：E26「读到上次的成功结果 → 静默失效」、E42「量错了 → 假 PASS」、
本条「**根本没跑 → 同样的假 PASS**」——
三个不同成因，同一症状：**PASS 不代表检查过**。
所以「PASS」这个信号本身也需要被检查（每组有没有实际输出）。

### E44：靠对话收敛的循环，收敛速度取决于模型而不是算法

> 本条讲：**靠对话收敛的循环，收敛速度取决于模型而不是算法**

**场景**：2026-10-27 09:00 那次 daily-learning 跑了 **772s**（timeout 900s，余量只剩 14%）。
我先怀疑三件事，都排除了：
1. 「任务变重了」→ 否，输入 60K tokens，比昨天还少
2. 「provider 慢」→ 否，单发实测 0.95–1.5s，HTTP 200
3. 「工具调用多」→ 54 次 exec 看着多，但**其中 26 次是同一个命令的重试**（48%）

**真根因：agent 在手工迭代字数**。翻会话里的长度序列：
```
272 → 259 → 233 → 232 → 227 → 225 → 222 → 222 → 223 → 221 → 219 → 190 → 190
```
**13 轮**。每一轮 = 一次完整推理（上下文带缓存 ~58K tokens），≈ 20–30s。
→ 光这一件事就吃掉了几百秒。

**为什么它会这样**：
任务指令写的是「长度 100-200 字……**写完自己数一遍，超了就砍**」。
问题在于 —— **「数汉字」这件事是 LLM 做的**，而 LLM 数不准中文汉字数。
于是它只能：写一版 → 数一遍 → 不对 → 改一版 → 再数 → …
这叫**靠对话收敛**：收敛速度取决于**模型**，不取决于**算法**。

**陷阱**：
- 「13 轮是我写得不好」→ 不是，**是机制把收敛成本推给了模型**
- 「多几次 exec 说明工具重」→ 先看**命令去重**：
  26/54 次是同一条命令重试 —— 真正的信号是「同一件事做了很多遍」
- 「每次迭代只花 20s，不算什么」→ 但**迭代次数没有上限**：
  模型不收敛、或者收敛得慢，代价就线性放大
- 「约束写得越详细越好」→ **软约束在 LLM 任务里等于没有约束**（E32）

**修法：把「计数 + 裁剪」交给确定性脚本**
新增 `scripts/trim_learning_section.py`：
- 数**汉字**（口径与 E42 一致），学习 100–200 / 反思 100–400
- **保留「可立即执行的对策」段**（这是小节的价值所在）
- 删信息量最低的铺垫段（最短的非对策段）
- 仍超标 → 对**最长**段按句截断
- agent 流程：写草稿 → `--from` 裁剪 → `--check` 确认 → 写入
→ **1–2 次调用收敛**

**踩坑（我自己写的脚本也犯了同族错）**：
第一版只算**正文段落**的汉字，漏掉首行「> 本条讲：**关键词**」的 25 字
→ 段落 181 字「合规」，实际 206 字超标
→ **口径要算全**（E42：口径不一致 = 断言失效）

**岔路口**：
1. **判断一段 LLM 工作该不该脚本化，看它是不是「可确定性判定」的**：
   - 「这段汉字数超了吗」→ **可确定性判定** → 该脚本化
   - 「这条教训值不值得记」→ 不可判定 → 该留给 LLM
2. **脚本化的收益 = 消除迭代次数的不确定性**：
   算法收敛在 1 次，模型收敛在 13 次 —— 而且模型那次**还会超时**
3. **脚本要保护「价值最高的部分」**：
   自动裁剪最怕把核心论点当铺垫删掉
   → 显式保护「可立即执行的对策」段，其余按信息量排
4. **同步指令前，先确认「源文件」和「线上」是否一致**：
   我这次用 `scripts/daily_learning_prompt.txt` 同步 cron，
   但那个文件**比线上旧**（缺【跨日提醒】/【等待方式】）
   → 同步差点把好的指令覆盖成差的
   → 【T】组当场抓到（这正是它存在的意义）

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 字数收敛轮数 | **13 轮**（对话式） | **1–2 次**（脚本式） |
| daily-learning 耗时 | 772s（86% 超时） | 待 10-28 定时跑验证（预期 ~200-300s） |
| 工具调用重复率 | 48% | 应降到个位数 |
| 裁剪后合规率 | 靠模型自觉 | **确定性 100%** |

**延伸**：E32 讲「软约束在 LLM 任务里等于没有约束」，
E42 讲「断言口径不一致 = 断言失效」，
本条讲**软约束的代价有多具体**：
不是「效果差一点」，而是 **13 倍的推理成本 + 86% 的超时余量**。

### E45：修完根因后，监控还在量修复前的那次测量

> 本条讲：**修完根因后，监控还在量修复前的那次测量**

**场景**：2026-10-27 10:00 巡检报 `daily-learning` 耗时 772s / timeout 900s = 86%，余量告急。
但根因（E44：13 轮手工迭代字数）**在 09:24 就已修复**——加了确定性裁剪脚本，
指令也重写成「1-2 次调用收敛」。也就是说：**修复已经生效，告警却在拿修复前的旧数据报警。**

**陷阱**：这类断言不会自己知道自己的信号已经过期。
- 修复前：`lastDurationMs = 772s` 是**真实**信号 → 断言正确
- 修复后：同一个 `lastDurationMs = 772s` 变成**历史遗留** → 断言变成"永远红"
- 两者在数据库里长得一模一样，断言无法分辨

**岔路口**（两个都做，别只做一半）：
1. **判定信号本身是否还有效**——先问"这个数是修复前测的还是修复后测的"
2. **给修复留冗余，而不是等下一次运行来证明**——
   直接把 timeout 从 900s 提到 1800s（772/1800 = 43%），而不是"下次跑快了就绿了"

**证据**：
| 项 | 修复前 | 修复后 |
|---|---|---|
| timeout | 900s | 1800s |
| 772s 占比 | 86%（告急） | 43%（余量充足） |
| 【U】组判定 | ❌ FAIL | ✅ PASS |
| 裁剪脚本耗时 | — | **0.057s**（实测） |

**延伸**：E33「机制缺口比单点故障更值得修」、E42「断言量错了东西就等于没有断言」，
本条讲第三种：**断言量对了东西，但量的是历史**——
它比"量错"更隐蔽，因为它看起来一直很勤奋。

**一句话**：断言红了，先别急着修任务，先确认它量的是不是「现在」。

### E46：慢的第三个层次 —— 有时候根本不该跑那个任务

> 本条讲：**慢的第三个层次 —— 有时候根本不该跑那个任务**

**场景**：2026-10-27 11:05。E35 之后我加了「短 poll」提醒、又加了【V】断言
检测长 poll。V 报出 26 次长 poll，我第一反应是「poll timeout 还是太长」。

**但把【V】改成按 cron 任务维度报告后**，一眼看出：
```
daily-learning×12, backup-audit×9, healthcheck×5
```
顺着查下去 —— **真根因根本不是 poll**：

- `daily-learning` 09:00 那次，**447s（171+78+120+78）全在等 `healthcheck.sh`**
- `backup-audit` 也有 **3 次 120s 的 poll**，等的是同一个脚本
- **而 `daily-learning` 的指令里根本没要求它跑巡检** —— 它是**自己跑去跑的**

**三层递进**（这一串是今晚最值钱的东西）：
| 层 | 命题 | 出处 |
|---|---|---|
| 1 | 慢的是**等法**不是任务（poll 会等满 timeout） | E35 |
| 2 | **指令说了也不照做**（自己写的规则自己也忘） | E41 |
| 3 | **有时候根本不该跑那个任务** | E46 ← 本条 |

**第 3 层为什么最值钱**：
- 第 1 层 → 改等法（poll timeout 调小）
- 第 2 层 → 加规则和检测
- 第 3 层 → **少做** —— 那 447s **根本不该存在**
  → 每日巡检是 07:00 那个 cron 的职责，学习任务顺手也跑一遍 =
    白白多等 + 挤占 2 核 CPU（实测 8 并发零加速、18 个慢 3 倍）

**岔路口**：
1. **看到「等很久」时，先问「这个等待有必要吗」**，再问「怎么等得快」
   —— 顺序反了就会一直在优化一个不该存在的东西
2. **断言要按「行动单元」分组**，不按会话/总量：
   - 按会话 → 「0d127a42×460」→ 不知道该改什么
   - 按 cron 任务 → 「daily-learning×12」→ 立刻知道动哪里
3. 修的时候要区分**两个不同的问题**：
   - 「怎么等」（技术）→ 短 poll / sessions_spawn
   - 「该不该等」（范围）→ **这条任务不需要跑那个脚本**
   → 后者收益大得多

**证据**:
- daily-learning 09:00 实测 772.1s，其中 447s 在等 healthcheck.sh ✅
- backup-audit 3 次 120s poll 同样在等它 ✅
- 3 条 cron 指令已加【别跑不必要的巡检】✅

**延伸**：这是 E7「修完根因后监控还在量修复前的那次测量」的**行为侧版本** ——
E7 讲「别量已经不存在的问题」，E46 讲「**别做不该存在的工作**」。

### E47：断言只看「最近一次」，就等于没在看历史

> 本条讲：**断言只看「最近一次」，就等于没在看历史**

**场景**：2026-10-27 11:28 心跳。巡检全绿（PASS=63 / FAIL=3 / WARN=2），
5 个 cron 的 `lastRunStatus` 全是 `ok`，3 个 announce 任务的 `lastDelivered` 全是 `True`。
**但我去翻 `cron runs` 历史时，看见了巡检完全看不见的东西**：

```
daily-reflection  总 43 次 = ok 3 次 + error 40 次
  └ 其中 2 次「status=ok 但 delivered=false」（10-26 00:35、10-21 04:27）
healthcheck      6 次里 1 次 ok-but-not-delivered（10-26 10:44）
daily-learning  20 次里 3 次 ok-but-not-delivered（10-26 09:00 / 00:36、10-21 04:29）
```

**为什么巡检看不见**：`check_cron_delivery.py` 读的是 `cron list --json` 里的
`state.lastRunStatus` / `state.lastDelivered` —— **只有最近一次**。
历史失败在那个字段里**根本不存在**。

**最毒的一点**：`ok-but-not-delivered` 的语义是
「**任务成功跑完了，但结果没送到牛哥哥手上**」。
这正是 AGENTS.md 里那句「**状态字段描述的是『任务跑完了』，不是『用户得到了结果』**」
的**反面**：断言自己就犯了这个错 —— 它断言的是「任务跑完了」，
而用户要的是「**结果送到了**」。

**⚠️ 取证时踩的一个坑（差点得出相反结论）**：
`cron runs` 的输出里，`not-delivered` 对两种完全不同的任务都出现：
- `mode=none` 的任务（teahouse-monitor / backup-audit）—— **设计上就不投递**，不是故障
- `mode=announce` 的任务 —— **是真的没送出去**
→ **看 `not-delivered` 之前，必须先看 `delivery.mode`**。
不分清就会把「正常」报成「故障」，或者反过来。

**✅ 修法**：断言从「看 lastRun」改成「**看 history**」：
```
for 每个 mode==announce 的 job:
    runs = openclaw cron runs --id <id> --limit 20
    undelivered = [r for r in runs if r.status=='ok' and r.delivered is False]
    ├ 最近一次仍未投递 → FAIL
    └ 历史有、最近已好   → WARN（带时间点，便于定位）
```
→ **一次就把 6 个之前完全看不见的静默失败抓了出来。**

**教训**：
1. **「当前值正常」不能推出「历史正常」** —— 断言要问对时间维度
   （最近一次 / 近 N 次 / 全部历史，是三个不同的问题）
2. **断言的字段要和「用户得到的结果」对齐**，而不是和「任务跑完了」对齐
3. **同一个状态码在不同 mode 下含义不同**（`not-delivered` 对 none 是正常、对 announce 是故障）
   → 判定前**必须先分组**，不能只看字段值
4. **新增断言必须做注入故障验证** —— 我把「最近一次」强制改成未投递，
   确认它会 FAIL（`__FAILED__=3`），不是只会 WARN；然后恢复

**延伸**：E7「修完根因后监控还在量修复前的测量」讲的是**时间上的滞后**；
E47 讲的是**维度上的遗漏** —— 前者是没看到「旧数据」，后者是**根本没在看那一列**。

### E48：分类不该等于过滤 —— 「分组」顺手造出来的盲区

> 本条讲：**分类不该等于过滤 —— 「分组」顺手造出来的盲区**

**场景**：2026-10-27 12:00 心跳。巡检【V】组（检测会话里的长 poll）报
`12h 内 309 次长 poll`。我按自己的规则复核，发现**这个会话自己就用了 3 次长 poll**
（180s / 200s / 220s）—— 违反 TOOLS.md 里「poll ≤10~15s」那条规则。

但【V】组**一次都没报我**。

**根因**：【V】组的判据是
```python
job = task_of(head)          # 按 cron 任务标记分类
if not job:
    continue                 # ← 匹配不上就整段跳过
```
`task_of()` 只认 5 个 cron 任务的标记（`scripts/healthcheck.sh`、
`每日学习（精简版）`…）。**普通心跳会话没有任务标记** → 返回 `None`
→ **整个会话被跳过** → 它的 poll 一次都不计数。

而这个盲区是**上一轮刚引入的**：
11:45 那次我为了「按任务维度报告」（daily-learning×12 / backup-audit×9），
把统计从「按会话」改成了「按任务」——
**分组是为了更好的展示，却顺手变成了只统计「认得出来」的那几类**。

**教训（两层）**：
1. **分类不该等于过滤**。分组的目的是展示，不是排除未知类别。
   「匹配不上」应该是「归入『未分类』」，不是「不算」。
2. **断言自己的覆盖面也是断言**。
   一个只统计「已知类别」的断言，等于**对未知情况完全失明**——
   而未知恰恰是最需要被看见的那部分。

**同日还查出【V】的两个隐性错误**（都是「看起来很合理」的那种）：
| 错误 | 表现 | 真因 |
|---|---|---|
| 窗口写着「12 小时」，代码是 3 天 | 说的和做的不一致 | 手写常量漂移 |
| 用文件 mtime 过滤窗口 | 3 天前的违规被算进「12 小时」 | 一个**一直在追加**的会话，mtime 永远是「现在」 |

第三个错最隐蔽：会话文件会持续追加，所以 `mtime` 判龄**永远等于现在**，
导致窗口过滤**完全失效**。必须按**每条记录的 timestamp** 过滤。

**✅ 已做**：
1. 【V】不再跳过任何会话 → 匹配不到归入 `heartbeat/其他`
   → **一次抓出 267 次以前完全不可见的违规**
2. 窗口改用**每条 poll 的时间戳**（不再用文件 mtime）
3. 报告加**按会话归属 + 最后一次违规时间**
   → 一眼分清「还在犯」和「已经停了」
4. `task_of()` 同时匹配**转义形式**（JSON 里非 ASCII 可能变成 `\uXXXX`）
5. **新增【W】组：判据自身的单测**（`scripts/test_v_poll_assertion.py`，9 个用例）

**【W】是这轮最值钱的一条**：
【V】今天连修三个 bug，而【V】报的是「长 poll 数量」——
**判据坏了，它照样输出一个看起来正常的数字**。
典型的自指陷阱：**坏掉的断言看起来和好断言一样正常**。
所以判据逻辑必须有独立单测，而且单测要**直接跑真身代码**：
`test_v_poll_assertion.py` 从 `healthcheck.sh` 的 PY9 块里**抽取真身**来跑
（不是抄一份）→ 判据改了单测立刻跟着变，**物理上无法漂移**。

> 第一版单测就是「抄了一份判据」，
> 而真身已经改成两行写法（`if not job: job = ...`）—— 抄版和真版**悄悄漂移**了。
> 抄一份判据来测 = 测的是「我以为的判据」，不是「在跑的判据」。

**岔路口**：
- ❌ 「把规则写进 TOOLS.md 就行」—— 那是**说明**，不是**约束**（E41/E31 老问题）
- ✅ 让违规**自动可见**：断言负责「发现」，单测负责「保证发现能力没坏」
- ✅ 更进一步：让**约束可执行**（工具层直接拒绝长 poll），但那要改 OpenClaw 本身，
  成本高 —— 先把「可见性」做扎实

**验证**（双向）：
- 真身单测 9/9 通过（现在 / 13 小时前 / 短 poll / 无标记会话 / 转义标记 / 原始中文 / 缺时间戳）
- 全量巡检 PASS=65 FAIL=3（3 项全是长期项）
- 【Q】组当场抓到「新组【W】没同步进 cron 指令」→ 同步后修复 ✅
  （**新加一组断言必然要同步说明文档** —— 这正是【Q】存在的意义）

**同族的三个「断言看起来在干活」**：
E42 讲**数据源**错了 · E45 讲**时间**上是旧数据 · E48 讲**覆盖面**漏了一类
→ 三条都不报错，都给出一个合理的数字 —— **最危险的失败模式**。

**判据本身也要有单测**：坏掉的断言看起来和好断言一样正常。

**延伸**：E42「断言量错了东西」讲的是**数据源**；
E45「监控还在量修复前的那次测量」讲的是**时间**；

**延伸**：E35「poll 会等满」→ E49「规则可见性」→ E50「任务归属」。
三层叠加起来才看得清：**等法 → 规则 → 归属**，缺一层就会优化错地方。

### E51：常亮的告警会训练你忽略它 —— 真故障反而看不见

> 本条讲：**常亮的告警会训练你忽略它**

**发现时间**: 2026-10-27 20:45

## 现象

备份审计每次都报：
```
[⚠️  WARN] 工作区有 1 个未提交改动
```
追查发现来源是 `memory/teahouse_state.json` —— **纯运行时状态**
（`seen_ids` + `last_check` 时间戳），每 2 小时的 `teahouse-monitor` cron 都会改它。

→ **每次跑完工作区必然是脏的** → **每次备份审计必然 WARN**。

## 为什么这是个问题

不是「多一条噪音」那么轻 —— 它是 **E28（长期项和真故障混在一起）** 的变种：

> **一个永远不会安静的告警，会训练你忽略它。**
> 当「改代码忘了提交」这种**真问题**出现时，
> 它和这条常亮的噪音长得一模一样 → **你不会注意到**。

告警的价值不在于「报了多少」，在于「**真出事时能不能一眼看见**」。

## ⚠️ 但不能简单 gitignore

`seen_ids` 是**有价值的数据**：丢了 → 换机/重装后 96 条 issue 被重复蒸馏。
它**必须随远端一起备份**。

→ 所以要改的是「**判定**」，不是「入库与否」。

## ✅ 正确解法：区分「运行时状态」与「真实改动」

```bash
RUNTIME_STATE_FILES="memory/teahouse_state.json"
DIRTY=$(... | grep -vF -f <(printf '%s
' $RUNTIME_STATE_FILES) | grep -c .)
```
- 剔除后 = 0 → **PASS**（附注「N 个运行时状态文件有变动，属正常」）
- 剔除后 > 0 → **WARN**（真改动，该提交了）

效果：`PASS=19 FAIL=0 WARN=0` **且能保持** —— 下次 cron 跑完仍是 PASS。

## 通用判据

> **问「这个告警会不会永远亮着」。**
> 会永远亮着 → 它不是告警，是**状态** → 要么改成 PASS，要么改成「实时查询」，
> 绝不能让它占据 WARN 位。

## 关联

- E28 长期项和真故障混在一起
- E42 断言量错了东西，就等于没断言
- E45 修完根因后，监控还在量修复前的指标

### E52：快照管不住退化 —— 递增是趋势，快照看不见

> 本条讲：**快照管不住退化 —— 递增是趋势，快照看不见**

**发现时间**: 2026-10-28 08:0x

## 现象

今晨巡检后手查 healthcheck 的 run history，发现耗时在**无修改**地爬升：

| 时间 | 耗时 |
|---|---|
| 10-26 10:52 | **27s** |
| 10-26 17:10 | 214s |
| 10-27 07:00 | 298s |
| 10-28 07:00 | **378s** |

不到两天涨了 **13.9 倍**。按每次 +80s 的斜率外推，**10-31 前后撞 600s timeout**。

## 陷阱一：把「我加的」和「它自己变的」混成一条线

我最初的归因是「provider 变慢」或「CPU 争抢」。查 run history 才发现——
**10-26 那两次跑的根本不是同一份代码**：27s 那次是我手动跑的旧版本，
214s 那次是当天下午加完断言组之后的 cron。

所以曲线里混着**两种增长**：

1. **我加组**（有意为之）：断言组从 20 组加到 26 组 → 每组都要跑 → 自然更慢
2. **每组自身变慢**（退化）：这才是真正要盯的

**混成一条线去外推，就会得出「再调高 timeout 就行」的错误结论** ——
那只是把退化藏起来，等下一次「变化」重新解释曲线。

> **通用判据**：看到一条单调递增的曲线，先问
> **「这几次运行之间，代码变了吗？」**
> 变了 → 是我加的（可接受）；没变 → 是它自己退化（要查）。

## 陷阱二：占用率断言是快照，递增是趋势

【U】组管的是「最近一次耗时 / timeout 是多少」——那是**快照**。
快照在 50% 时是 PASS，趋势到 100% 才是 FAIL。

**中间这 3 天完全没人看见。**

| | 问的问题 | 能在什么时候发现问题 |
|---|---|---|
| 快照 | 最近一次占比多少 | 已经撞上时 |
| 趋势 | 最近 N 次是不是在涨 | **涨的过程中** |

> **快照只能在终点报警，趋势才能在途中报警。**
> 一个只会看「当前值」的监控，对**渐进式退化是盲的**。

## ✅ 解法：给【U】组加一条趋势判定

判据：最近 3 次耗时**单调递增**且最新一次 > 50% timeout → WARN。

- 单调性要求：避免「抖动」被误判成趋势
- 涨幅门槛：避免日常 ±10% 的正常波动刷屏
- 报 WARN 而非 FAIL：退化还不致命，但**值得现在看一眼**

### E53：上次全绿不等于现在还好，上一轮巡检的 PASS 只是快照不是状态

> 本条讲：**「上次全绿」不等于「现在还好」 —— 巡检的 PASS 是快照，不是状态**

**发现时间**: 2026-10-29 00:0x

## 现象

10-28 03:00 的 `backup-audit` cron 报告 **「all PASS (PASS=19, FAIL=0, WARN=0)」**。
我 00:00 手跑**同一个脚本**，得到 **PASS=16 FAIL=1 WARN=2**：

```
❌ FAIL  本地领先远端 13 个 commit（未推送）
```

13 个 commit 是 10-28 白天/晚间的工作 —— **cron 那次跑完之后才产生的**。

## 为什么会这样

**「全绿」描述的是任务跑完那一刻的世界，不是现在的世界。**

任何「周期性执行的巡检」都有这个性质：
- 巡检跑完 → 写一份快照 → 快照不会自己更新
- 快照与现实之间的差距**只增不减**（除非有人改）

所以：
> **引用上一轮巡检结论 = 在用过期数据判断现在。**

## 三个层次的同一个病

| 层 | 表现 |
|---|---|
| 巡检结果 | 「上次全绿」被当成「现在还好」 |
| cron 状态字段 | `status=ok` 只说明 agent 那轮没崩，**不代表脚本输出是什么** |
| 记忆里的结论 | 「已修复 / 已了结」让下个会话直接跳过 |

第 3 层尤其阴险 —— 它连「复查」的动作都省了。

## 怎么破

1. **想知道当下状态 → 当场重跑**，别引用上一轮结论
2. **「cron 报 ok」与「脚本报 FAIL」矛盾 → 以脚本为准**，并去查 `cron runs` 历史
   （矛盾本身就是信号，说明快照已经过期）
3. **重要状态写进「当前状态」类文件 → 要么自动生成，要么定期刷新 + 写完实测校验**

## 附带收获：巡检的历史比巡检的结论更有信息量

查 `openclaw cron runs --id <id>` 时，发现 `backup-audit` 在 10-27 **连续 3 次超时**
（300s / 600s / 600s），而**最后一次却是 ok**。

如果只看最新一条（ok），根本不知道前面崩过 3 次。
**历史里的异常模式，只有翻历史才看得见。**

## 关联

- 教训 4 属于「状态字段 ≠ 用户得到的结果」的第三个实例（前两次见 TOOLS.md / SESSION-STATE）
- 与 E52 互补：E52 讲「快照看不见递增」，本条讲「快照会被后续变化推翻」

### E54：瓶颈在「进程启动」时，堆并发只会更慢 —— 先 profile，再优化

> 本条讲：**瓶颈在「进程启动」时，堆并发只会更慢 —— 先 profile，再优化**

**发现时间**: 2026-10-29 00:3x

## 现象

`healthcheck.sh` 耗时在无修改地爬升（207s → 298s → 378s），逼近 600s 超时。
我先认定瓶颈是「循环里调 `openclaw cron runs`」（21s），改完发现**只快了 6%**。

## 真正的瓶颈

profile 25 个 python 块之后：

```
verify_l1_retrieval.py   77 秒   ← 占体检 80%
```

它要做 **17 次真实检索**，每次：

```
openclaw memory search  →  4.85 秒/次
其中 embedding 请求      →  0.36 秒
                            ─────────
差值 4.5 秒 = Node 进程启动 + 插件注册
```

**要优化的是「起进程」，不是「发请求」。**

## 试过并否决的方案

**并行 4 路**：

| 方式 | 17 次查询耗时 |
|---|---|
| 串行 | 78.4s |
| 并行 4 路 | **86.9s（更慢）** |

2 核机上并发只抢 CPU —— 这与 TOOLS.md 里既有的
「8 并发零加速、18 个慢 3 倍」记录**一致**。

> **并发只在「等待外部 I/O」时划算。**
> 瓶颈若是 CPU 或进程启动开销，并行 = 负优化。

## 落地方案：一次启动，复用同一个运行时

`openclaw` 的 memory search manager 可以**在同一个 Node 进程里复用**，
不必走 CLI（CLI 每次都重新拉起进程）：

```
17 次 CLI 调用  78s  →  一次进程内批量检索  8.3s   （9.4×）
```

## 四个坑（都实测踩过）

1. **打包后 export 名被压成单字母** —— `n`/`r`/`t` 里哪个是
   `getMemorySearchManager`？**不能靠名字猜**，只能挨个调、看返回对象有没有 `.search`
2. **`new URL('file://' + 绝对路径)`** 会把路径当 host → 报
   "Cannot find package 'undefined'"（和真正的错误毫无关系）
3. **自己写的 URL helper 返回字符串时，别再 `.href`** —— 字符串的 `.href` 是 `undefined`
   → `import(undefined)` → **同一个诡异报错**（最迷惑的一个）
4. **遍历导入 dist 下所有 .js 来找导出** → 触发 CLI 副作用 + **dump core**
   → 只能按文件名精确匹配导入

## 两条不能省的验证

**① 等价性自检**（优化后必须与原路径结果一致，否则断言装死）：

```
node scripts/memory_batch_search.mjs --self-test
→ PASS batch 与 CLI 一致（6 条）   # 逐条比对 path + score
```

**② 故障注入**（优化路径挂掉时，必须自动回落且结果不变）：

```bash
mv scripts/memory_batch_search.mjs /tmp/     # 移走优化脚本
python3 scripts/verify_l1_retrieval.py        # 应自动回落逐条 CLI
→ 结果仍是 52/52，耗时 91s（回落路径），没有静默失效 ✅
```

> **只测「快路径能跑」是不够的 —— 要测「快路径挂掉时会不会静默给错答案」。**

## 关联

- 与 E43 同族：**断言装死**（拿到空数据却看起来通过）
- 与 TOOLS.md「2 核机并发只会更慢」互为印证
- 教训：**先 profile 再优化** —— 我自己在这条上犯了半次（以为 21s 是大头）

### E55：没内容就不该投递 —— 同一状态码，正常与故障要问「本该发什么」

> 本条讲：**没内容就不该投递 —— 同一状态码，正常与故障要问「本该发什么」**

**发现时间**: 2026-10-29 08:01

## 现象

今早 08:00 茶馆 cron 跑完，`delivered=false / not-delivered`。
按 E47 的判据（`mode=announce` + `delivered=false` = 真故障），
这**应该**是一条 FAIL。但它不是。

## 为什么不是故障

那一次 cron 的实际输出是：

```
[teahouse] 拉取 issue 共 96 条 / 新增 0 条 / 无新内容
```

**没有新内容 → 没什么值得打扰牛哥哥的 → 不投递是正确的。**

而 10-28 那批「运行成功但未投递」是**真的故障**：任务有内容，
结果没送到手上。两者字段一模一样，性质完全相反。

## 真正的洞：字段本身没有「本该发什么」这个维度

`check_cron_delivery.py` 现在的判据链是：

```
mode == "none"     → 跳过（设计如此）
mode == "announce" → delivered=false 就是 FAIL/WARN
```

**它在 `mode=announce` 这一层里不再往下分。**
可「announce 型的任务」里，既可能有内容，也可能本来就无事可报 ——
判据缺了「本该发什么」这一维，就只能靠人肉读输出。

## 岔路口

**先确定「本次是否真的有东西要发」，再判 delivered。**

可行的判据按成本从低到高：

| 判据 | 怎么取 | 适用 |
|---|---|---|
| 产出物计数 | 任务写出的产物文件数 / 队列长度 | 茶馆类（`teahouse_state.json` 的 `pending`） |
| 输出摘要 | run 记录里的 summary / 输出文本 | 任何 announce 任务 |
| 产出新鲜度 | 产物 mtime vs 本次 run 时间 | 有产物但可能为空的文件型任务 |

> **判据要看「本该发什么」，不能只看 `delivered` 字段。**

## 陷阱

- **别把「没告警」当「没做事」** —— 今天 08:00 那次跑完全程正确，只是**正确地决定不打扰**。
  反过来更危险：为了「留点痕迹」硬写一篇笔记，把空内容包装成洞察
  （同一条的另一面，10-29 00:00 茶馆巡检也踩过）。
- **别为了消告警而放宽断言** —— 正确做法是**加一个维度**（本该发什么），
  不是把 `delivered=false` 一律放过（那样 E47 抓出的 6 次真故障会重新被吞掉）。

## 关联

- 与 **E47** 同族且更深一层：E47 说「先按 `delivery.mode` 分组再判」；
  本条说「**分组还不够，同一 mode 内部还要按『本该发什么』再分一层**」。
- 与 **E53** 同族：都是「**状态字段 ≠ 用户得到的结果**」——
  E53 讲时间维（快照 vs 现在），本条讲内容维（发了什么 vs 该不该发）。

## 关联断言（待落地）

`scripts/check_cron_delivery.py` 的 announce 分支应补：
**取该次 run 的产出摘要 → 无产出则标为「有意不投递」而非 FAIL**。
改动前必须做注入验证：构造「有产出但未投递」→ 仍须 FAIL ✅

### E56：刷新哈希基线时，「相对路径」会静默失效

> 本条讲：**哈希基线刷新必须用绝对路径**

## 场景

配置基线不匹配（backup-audit 报 FAIL），需要刷新基线文件。

## 陷阱

在 `~/.openclaw/` 目录下执行：

```bash
sha256sum openclaw.json > .config-baseline.sha256
```

看起来对（校验和一致、文件权限 600、hash 没变），但 **backup-audit 仍然报 FAIL**。

**原因**：`sha256sum -c` 是按**当前工作目录**解析文件名的。
基线里存的是 `openclaw.json`（相对路径），而校验脚本的 cwd 是 workspace
（`/root/.openclaw/workspace`）→ 那里根本没有 `openclaw.json` → 校验失败。

**最阴的地方**：
- 用同一个目录校验 → 通过（假象）
- 换一个目录校验 → 失败
- 而 baseline 文件里到底存的是相对还是绝对路径，**肉眼要去看文件内容才知道**

旧基线（Oct 26 建的）用的是绝对路径 `/root/.openclaw/openclaw.json`，
所以一直好好的 —— 这次「刷新」把它降级成了相对路径，**反而制造了新故障**。

## 岔路口

发现「基线不匹配」时的判断顺序：

1. **先确认改动是合法的吗？** → 是合法变更（如改了 heartbeat 配置）→ 才该刷新基线
2. **先看旧基线文件里存的是绝对还是相对路径** → `cat .config-baseline.sha256`
3. **刷新时用绝对路径** → `sha256sum /root/.openclaw/openclaw.json > .config-baseline.sha256`
4. **在【与校验脚本不同的 cwd】下验证** → `cd <别处> && sha256sum -c <基线>`
5. **最后再跑一遍真正的审计脚本** → `bash scripts/backup_audit.sh`，看结果是不是真的变绿

## 为什么值得记

「我刷新了基线」和「基线真的生效了」是**两件事**。
只做第 1 步就宣布修好，等于用「自检通过」骗自己。

**通用化**：任何「写入一个路径、之后在别的目录读它」的机制，
都必须**跨目录验证**。同一个目录下验证成功 = 什么都没证明。

**配套判据**：backup-audit 的基线校验，本质上就是在测「cwd 无关性」。
以后任何基线/清单类机制，都该有一个「换个目录还能用吗」的断言。

### E57：看门狗和被看守对象共用一个依赖 —— 它会先死，而且死得静悄悄

> 本条讲：**巡检和被巡检任务共用同一份额度时，额度耗尽会先掐死巡检自己**

## 场景

给一批定时任务配监控/告警，监控本身也由同一套调度系统执行。

## 陷阱

MiniMax Token Plan 用量上限（429「已达到 Token Plan 用量上限」），
2026-10-30 至 11-01 连着 3 天，所有 `agentTurn` 型 cron 全部失败 ——
**其中就包括 07:00 的体检任务**。

体检本来就是那道发现「定时任务全挂」的保险，结果它自己被同一个额度桶掐死，
而且**死得毫无声响**：

- cron 列表里只有 `lastRunStatus=error`，没有任何一条告警发出去
- 「体检没跑」这件事本身没人监控 → 三天里没有任何人知道系统全挂了
- 交互式会话却不受影响（小请求能过）→ 手动 curl 测 HTTP 200，
  看起来「provider 是好的」→ 误判成任务自身的问题

关键结构问题：**监控路径与被监控路径共用同一份稀缺依赖**。
额度一耗尽，被监控对象和监控者同时死 —— 而监控者的死，
在告警系统里表现为「没有告警」，和「一切正常」无法区分。

E8（纯脚本任务不该用 agent 型 cron）早就写下来了，但**没有执行**；
规则写在纸上而架构没改，额度一耗尽，连「体检」自己都先死。

## 岔路口

发现「整批定时任务同时失败且报错一致」时，判断顺序：

1. **先看报错是不是同一句话** → 429 / 配额类报错 = 依赖耗尽，不是任务 bug
2. **再看依赖关系**：这个任务依赖模型额度吗？监控任务也依赖吗？
   → 两者共用 = 监控是假的安全网
3. **拆依赖路径**：把纯脚本任务（体检、审计、备份、日志清理）
   迁到 **systemd timer** —— 不消耗模型额度，模型挂了它们照跑
4. **给「监控没跑」本身加断言**：产出物（今日巡检日志）是否真的落地，
   没落地 = 可告警事件，不能默认「没消息就是好消息」
5. **控制消耗方**：心跳频率 30 分钟 → 60 分钟，且限定活跃时段
   （08:00–22:00）—— 心跳每次注入 ~60k token 上下文，48 次/天 ≈ 2.9M input token/天
6. **配额型依赖要区分两种形态**：「变慢」（共享配额被抢，无 error，难归因）
   vs 「耗尽」（明确 429 + 明确报错文案）→ **见 429 就立刻查额度，别继续试模型**

## 为什么值得记

「我配了监控」和「监控真的能在我出事时报警」是**两件事**。
第二件事的前提是：**监控不能和被监控对象共用同一个会死的东西**。

**通用化**：任何「监控 / 告警 / 巡检」机制，都必须问一句
**「它和被监控对象共用哪些依赖？」** ——
凡是共用的依赖一旦耗尽，监控会**先于**被监控对象失效，
且它的失效形态（没有告警）与「一切正常」**无法区分**。

**配套判据**：任何巡检类机制都该有一条「产出物是否存在」的断言 ——
「巡检没产出」必须是一个**可告警的失败**，而不是「无事发生」。

**关联**：E8（纯脚本任务不该用 agent 型 cron，规则未执行）·
E39（共享配额被抢 → 变慢）· E47（状态字段 ≠ 用户得到的结果）·
E56（基线「刷新了」≠「生效了」）

### E58：「最近一次是 ok」不能代表「最近一直 ok」—— 连续失败次数必须单独断言

> 本条讲：**lastRunStatus 是单点快照，用它判断健康度等于用一个样本推断趋势**

## 场景

给一批定时任务配巡检断言。巡检读 `cron list --json` 里的 `state.lastRunStatus`，
以及 `state.lastDelivered`，据此判断任务健不健康。

## 陷阱

2026-11-03 心跳巡检实测：**`daily-reflection` 连续 4 个月没成功过，计划槽位成功率 0%**。

- `cron/runs/b7a0aca1-*.jsonl` 全部 44 条记录里，**只有 3 次 `ok`**
- 而这 3 次**全是手动补跑**（10-21 04:27 Wed、10-26 00:35 Mon、10-26 09:21 Mon）
- **周日 22:00 的计划槽位，15 次全挂**（2026-05-14 → 2026-11-01）

但巡检报告只写了一句：
> `FAIL daily-reflection 运行失败（lastRunStatus=error，原因：接口限流）`

—— 读起来像「昨天挂了一次」。**4 个月的停摆在报告里只有一行。**

根因分三个时代，每换一个原因就以为「修好了」，从没从「历史上到底成功过几次」的角度看过：

| 时期 | provider / model | 错误 | 真实原因 |
|---|---|---|---|
| 05-14 ~ 07-05 | glmcode/GLM-5、kimicode | HTTP 400 | **provider 已死**（后来删了） |
| 07-12 ~ 10-18 | minimax/MiniMax-M3 | HTTP 400 / 超时(180s) | **timeout 默认值太短**，后来才改 900s |
| 10-25 ~ 11-01 | minimax | rate_limit | **Token Plan 额度耗尽** |

同期 `daily-learning` 也有 **7 次 error**（含 10-30/10-31/11-01 **连续 3 天全挂**），
巡检报「投递正常（delivered=True）」—— 因为最近一次（11-02）确实成功了。

## 岔路口

**症状**：任务「时好时坏」，但状态字段看起来正常。

**判断顺序**：

1. **别看 `lastRunStatus`，看历史分布**
   → 拉 `openclaw cron runs --id <id> --limit 20`，统计 `status` 的历史构成
2. **区分「零散失败」和「连续失败」** —— 这两件事的运维含义完全不同：
   - 零散 N 次 = 偶发抖动
   - **连续 N 次 = 静默中断 N 天，用户完全无感**
   → 所以要单独算 **最长连续失败次数**，而不是只算失败总数
3. **区分「计划槽位失败」和「手动补跑成功」**
   → 手动补跑成功会掩盖「计划任务从没成功过」的真相
   → 按 `runAtMs` 对齐 cron 表达式，**只统计符合调度规律的那些 run**
4. **失败原因要分类**：`rate_limit`（依赖耗尽）/ `timeout`（配置太紧）/
   `HTTP 400`（参数或 provider 已死）/ `auth 403`（凭证过期）——
   每类的修法完全不同，混在一起看就是「时好时坏」
5. **修完之后必须实跑验证**
   → 11-03 08:51 补跑：80s，`ok` + `delivered=True` → 证明 900s timeout 的修法有效
   → 注意：**900s timeout 的修法从来没在「额度健康」条件下被验证过**，
     11-01 那次失败是配额问题，不是超时问题 → 修法有效性是**未验证状态**

## 为什么值得记

**「我配了监控」和「监控真的能在我出事时报警」是两件事**（E57 讲的是依赖共用，这里讲的是**样本量**）。

状态字段的设计初衷是「当前如何」，但健康度判断需要的是「**一直如何**」。
拿单点快照当趋势用，会系统性地**低估**故障时长：

- 一个任务挂了 1 天 → 看不出来
- 一个任务挂了 4 个月 → **也只看出来一行**，读起来像「昨天的事」

更隐蔽的是：**手动补跑会把「计划任务从没成功过」这个事实擦掉**。
3 次成功看起来像「它偶尔能跑」，实际上 3 次全是手动救火。

**通用化**：任何「状态字段 + 巡检断言」的组合，都必须问一句
**「我断言的是瞬时状态，还是历史趋势？」**
只断言瞬时状态的巡检，**结构上无法发现长期停摆** —— 它只会把
「停了 4 个月」报成「昨天挂了一次」。

**配套判据**：
1. 断言「最近 N 次里有 M 次 error」
2. 断言「**最长连续失败次数** ≤ 阈值」
3. 断言「**符合调度规律的那些 run** 里成功过几次」（排除手动补跑）
4. 失败原因**分类计数**，而不是只统计总数

**关联**：E57（监控与被监控共用会死的依赖）· E47（状态字段 ≠ 用户得到的结果）·
E34（靠「记得做」补的漏洞 → 这次是判据本身的盲区，同源）·
E8（规则写下来没执行；这次是**判据写下来有盲区**，同源）·
E55（本该发什么：先问有没有产出，再判投递）

### E59：长期项混进 FAIL 计数，会把真故障淹在假警报里

> 本条讲：**汇总行和退出码必须表达「可处理的故障数」，而不是「所有非 PASS 项数」**

## 场景

给巡检脚本加「⏳ 等你处理」的分类 —— 一些故障需要用户本人操作
（充值、吊销 PAT、决定博客方向），脚本改不了，只能列出。

为了让这类项显示得更温和，文案写成「⏳ 等你」而不是「❌ FAIL」。

## 陷阱

2026-11-03 07:00 巡检输出：

```
 结果: PASS=73  FAIL=1  WARN=6
 ✅ 没有可处理的失败(1 项长期项在等你处理)。
```

**自相矛盾**：计数行说 `FAIL=1`，下一行说「没有可处理的失败」。
而且脚本**退出码返回 1**。

根因在 `scripts/healthcheck.sh`：

```bash
bad() {
  FAIL=$((FAIL+1))          # ← 无条件加一
  ...
}
# 后面渲染时：文案命中 WAITING_PATTERNS → 打印成「⏳ 等你」
```

→ **计数按「非 PASS 的总数」算，显示按「是不是真故障」分**，
两者口径不一致 → 汇总行把「长期项」也算成了 FAIL。

**为什么这条比「报错了」值钱**：

危害不是「吵」，是**驯化**。一个每天都会出现、连续出现很多天、
谁都看得见但没人细看的假失败，会训练出「扫一眼就划走」的阅读习惯。
等真正的故障来的时候，同样被划走 —— 假警报的成本不是它自己，
是它**消耗掉的注意力额度**。

而且这个假警报会**持续消耗**：长期项是设计上的常态，
它会一直报、一直混在 FAIL 里，直到有人主动清理。

**还有一个隐蔽副作用**：退出码 1 → systemd 判红。
虽然配了 `SuccessExitStatus=1` 兜住噪音，但**信号语义已经错了** ——
下游脚本/CI/告警规则读退出码时，收到的是「有故障」，而实际是「有个长期项」。

## 岔路口

**触发条件**：只要报告里存在「需要人操作、我改不了」这一类项，
就要立刻检查它的**计数口径**和**退出码口径**。

**修法**（本次已落地，`healthcheck.sh` 第 2592 / 2618 行）：

1. **拆开计数、拆开显示**
   - 汇总行 → `PASS=73  FAIL=0  WARN=6  等你=1（长期项，不计入 FAIL）`
   - 「等你」是**独立维度**，不混进 FAIL
2. **退出码按「可处理失败数」决定**
   - 长期项**不该**让 systemd 判红 —— 判红的应该是「我现在能修但没修」
3. **判定用文案模式**：`WAITING_PATTERNS` 命中的项，在计数时就要分流，
   而不是只在渲染时换个词

**配套判据**（每条巡检脚本都该自查）：

- 汇总行里出现的每个数字，读者能不能**照着它行动**？
  → 「FAIL=1」但正文说不用处理 = 读者无所适从
- **退出码表达的是不是「可处理故障数」**？还是「非 PASS 项数」？
- 长期项有没有**单独维度**显示，而不是换个文案词混在 FAIL 里？
- 有没有**清理机制**？长期项堆积到几十条时，FAIL 计数就彻底失去意义了

**通用化**：
> 任何把「我修不了」和「我该修」放进同一个桶的系统，
> 桶里的水位就不再代表「我该干的活有多少」。
>
> 汇报类系统（巡检、告警、CI、待办看板）里，
> **「需要人决策」和「需要人执行」必须分桶** ——
> 否则前者会稀释后者的信噪比。

## 为什么值得记

E47 讲「状态字段 ≠ 用户得到的结果」，E55 讲「先问该发什么」。
E59 讲的是**第三个维度**：**指标本身的口径**。

前两个都在讨论「测的东西对不对」，E59 讨论的是**「报出来的数字代表什么」**——
一个数字如果不能用它来指导行动，它就是噪声，而噪声比没有更糟。

值得注意的是：**这次的假警报不是因为数据错，是因为文案和计数用了两套口径**。
数据本身完全正确（确实有 1 项长期项），错的是**这个 1 该不该叫 FAIL**。

这比「测错了」更难发现 —— 因为每个数字单看都对，
只有把**计数行 + 结论行 + 退出码**三个出口放一起看，才看得出它们在说不同的事。

**关联**：E47（状态字段 ≠ 用户得到的结果）· E29（断言的第一版阈值很可能是假警报）·
E55（先问「本该发什么」）· E57（看门狗和被看守对象共用依赖）·
E58（连续失败次数必须单独断言 —— 同样在修「单一数字表达不了真实状态」）

### E60：把「预计会自愈」写进状态字段 —— 预言没有失效时间，就会被当成事实继承

> 本条讲：**「预计会自愈」是预言不是观测 —— 写进状态字段就等于把未验证的猜测当事实继承**

> 预测写进状态字段时，必须同时写下证伪条件。

## 场景

心跳巡检在**事件发生之前**给下一个计划槽位下判断，然后把这个判断写进
「下次会话先读」的状态字段。

2026-11-04 08:42 心跳的 SESSION-STATE 头部（同一个「状态」行里）：

```
**状态**: ✅ 07:00 巡检 PASS=72 FAIL=1 WARN=6 … 配额预检通过（~15k 真实负载探测 1.27s ✅）
→ 11-04 09:00 daily-learning 预计自愈。context 4%（无危险区）。
```

这一行里混着三种不同性质的东西：

| 内容 | 性质 | 有没有证据 |
|---|---|---|
| 巡检 PASS=72 FAIL=1 WARN=6 | **观测** | 有日志 `memory/healthcheck-logs/` |
| 配额预检通过（探测 1.27s） | **观测** | 有脚本退出码 |
| 11-04 09:00 daily-learning 预计自愈 | **预言** | 只有两个推断 |

09:00 那次跑成功时，看不出任何问题。
**但如果它又失败了呢？**

## 陷阱

**预言和观测在文本格式上完全一样** —— 都是陈述句、都带时间戳、
都出现在「**状态**」这个看起来只装事实的字段里、都由同一套生成逻辑写出。
下个会话读头部时，**没有任何机制能区分它们**。

更要命的是这条预言**有两个缺失**：

1. **没有失效时间** —— 「预计自愈」没有「截至 09:15」
2. **没有证伪条件** —— 没有写「若 09:00 后 cron delivered≠true 则本条作废」

→ 于是预言一旦写进去就**永久有效**，哪怕它早已被现实推翻。
09:00 真挂了，头部依然写着「预计自愈」，
下个会话读到时**无从分辨**，只会当成「已知自愈中，不用管」。

**为什么这条特别危险**：

前面 E57/E58/E59 修的都是「**测错**」或「**报歪**」——
数据本身是对的，只是维度不够、口径不对。
这条修的是**「把还没发生的事写成了已查明的结论」** ——
它是**分类错误**：一个推断被放进了事实区。

而且它比 E58 更难被发现：E58 的「单点快照当趋势」，
数据来源是真的、只是推论过头；这条的**数据来源根本不存在**，
只有一个「额度够 + 距上次失败 24 小时」的合理推断。

**还有一个隐蔽的自强化**：

新加的 `scripts/quota_preflight.py` 护栏会**提高预言成真的概率**，
于是「预检通过」更容易被当成「那 09:00 就稳了」的证据 →
护栏越有效，人越容易把概率当确定性。
**一个提高成功率的工具，会诱导人把概率写成结论。**

## 岔路口

**触发条件**：只要你要把**尚未发生**的判断写进任何会被后续会话读取的地方
（状态字段、交接文档、下次会话先读段），就必须问三个问题：

1. **这是观测还是推断？** —— 观测有日志/命令输出可回查，推断只有理由
2. **它什么时候失效？** —— 要么给个截止时间，要么给个证伪条件
3. **被推翻后谁来清理？** —— 谁会把它改写掉，还是它就烂在那儿

**修法**（本次已落地）：

1. **预测词单独标记**：状态字段里凡是出现「预计／应该／大概率／估计」
   这类**预测词**的行，单独归为「待验证」类，与观测类**分行/分列**，
   不混在同一条「状态」句子里
2. **每条预测必须带证伪条件**：
   - 写法：`「待验证」09:00 daily-learning 预计自愈 —— 证伪条件：09:00 后查 cron delivered≠true 即作废`
   - 证伪条件必须是**可执行的命令或检查**，不是「如果失败就说明」
3. **验证后必须回写**：验证完成后把这条改写成观测结论
   （`→ 11-04 09:00 daily-learning 已恢复，delivered=True`），
   **不能只删不写** —— 删掉会让下个会话失去「它曾经失败过」这条线索
4. **过期即作废**：没有任何后续动作会来清理的预言，
   等同于**没有失效时间的永久断言**

**配套判据**（写状态字段前自查）：

- 头部这一句，读者能不能**逐字判断它是观测还是推断**？
- 里面的每个「预计」，有没有配一条**能跑的证伪检查**？
- 如果它明天被现实推翻，**谁会发现？** 没有答案 = 它会被当成事实继承
- 预检/护栏类工具的输出，是**观测**（额度够）还是**结论**（任务会成功）？
  → 前者不能直接写成后者

**通用化**：
> 任何「跨会话传递的状态」都是**接口**，接口必须区分
> **「已确认」和「待确认」两种类型** ——
> 只声明一种类型的接口，等于让下游把两者一视同仁地信任。
>
> 概率、推断、预期、直觉 —— 这些在**对话里**是自然的，
> 但一旦写进**持久状态**，就必须升级成
> 「待验证 + 证伪条件 + 失效时间」三件套，
> 否则它就完成了从「想法」到「事实」的**静默升格**。

## 为什么值得记

E47 讲「状态字段 ≠ 用户得到的结果」，
E58 讲「单点快照当趋势」，
E59 讲「长期项混进 FAIL 计数会淹掉真故障」。

E60 补的是**第四个维度：状态字段里的内容本身有类型**。

前三个都在讨论「**同一个数字/字段表达不了真实状态**」，
E60 讨论的是「**不同性质的内容被放进了同一个字段**」——
观测和推断在字节层面无法区分，但它们的**可信度差着一个数量级**。

而且它有一个前三条都没有的性质：

> **前三条的错误会自己暴露**（计数矛盾、连续失败、单点快照过期），
> E60 的错误**只在预言被推翻时才暴露** ——
> 而那正是你已经没有余力再去纠正它的时刻。

**关联**：E47（状态字段 ≠ 用户得到的结果）·
E55（先问「本该发什么」）·
E57（看门狗和被看守对象共用依赖）·
E58（连续失败次数必须单独断言）·
E59（指标口径必须能指导行动）·
E33（跨日写入会让时间线失真 —— 同样是「写入时机」带来的内容腐化）

### E61：入库脚本的「剥」和「装」必须用同一个真相源 —— 否则作者原话会被静默改写

> 本条讲：**入库脚本先剥掉关键词、组装时又拿不到它，就会退回用标题覆盖作者原话**

## 场景

写「把一条经验写进两个地方（独立文件 + 主库）」的入库脚本时，
流程天然分两步：**从源文件剥出正文** → **组装成目标块**。

2026-11-04 实测（`scripts/add_l1_entry.py`）：主库 60 条里有 **5 条**
（E55/E56/E57/E59/E60）出现了**重复的「本条讲」行**，E60 甚至有 **3 行**。

## 陷阱

两个独立缺陷叠在一起，互相掩护：

**缺陷 A —— 组装端无条件注入**
```python
block = f"{heading}\n\n> 本条讲：**{title}**\n\n{body}\n"   # ← 注入
```
但 `body` 里**本来就带作者的「本条讲」行** → 主库变成 2 行。
E60 的源文件有 2 行 → 变成 3 行。

**缺陷 B —— 剥除端只剥一行**
```python
re.sub(r"^###\s*E\d+[：:].*$\n+\s*^> 本条讲：\*\*.+?\*\*\s*$", "", text, ...)
```
这个模式**锚定在标题行之后**，只能命中标题后**紧邻**的那一行。
作者若写了第二行（E60 就是这样），第二行**残留进 body** → 叠加缺陷 A → 3 行。

**更隐蔽的一层（差点自己踩进去）**：
我第一版修法是「剥掉所有本条讲行」+「body 里有就沿用作者的，没有才用标题补」。
但流程是**先剥后装** —— 剥掉的关键词**没传给组装函数**，
组装时发现 body 里没有 → 退回用**标题** →
**E58 的作者原话「lastRunStatus 是单点快照…」被静默改写成标题**。

> **一个工具「修好了重复」，同时「改掉了内容」——
> 而重复是看得见的，改写是看不见的。**

## 岔路口

剥与装之间**必须有一个显式的真相传递**：

```
peel_body(text, eid) -> (body, kw)      # 剥下来的关键词一起返回
build_block(eid, title, body, kw)        # kw 优先，没有才用 title 兜底
```

配套三步：
1. **剥**：剥掉**所有**「本条讲」行（不只一行），同时记住第一行内容
2. **装**：优先用传下来的 `kw`（作者原话）→ body 里残留的（兜底）→ 都没有才用标题
3. **断言**：每条主库条目必须**恰好 1 行**「本条讲」——多于 1 行和 0 行都是坏数据

本条是**第 4 次**「入库脚本自己的替换逻辑与它写入的结构不一致」：
- E52：stub 标题重复

**规律**：入库脚本是「渲染源」—— 它写错的内容会被下一个会话**直接当成事实继承**，
所以它的判据必须和它写入的结构**同源**，不能各写一份。

### E62：派生副本的漂移不产生错误信号 —— 「自动生成的」比「手工维护的」更不值得检查

> 本条讲：**派生副本的漂移不产生错误信号 —— 自动生成的东西没人检查**

**核心断言**：派生副本（渲染出来的汇总文件）漂移到旧版时，
**不产生任何错误信号** —— 主库合法、断言全 PASS、检索全命中，
只是**内容是旧的**。而「自动生成」会让人**降低警惕**，却**不降低腐烂概率**。

## 场景

2026-11-04 修 L1 入库脚本（E61）时顺手做了一次**全量重跑**，
捞出一条 8 天前就该同步的旧条目：**E39 的独立文件在 `346a32b`(10-27) 就改过，
主库 `memory/L1-experience-library.md` 里的 E39 却从未重新同步**。

这 8 天里：主库是合法 Markdown、每条恰好一行「本条讲」、巡检全 PASS、检索自检 61/61 PASS。
**没有任何一个信号说「主库过期了」。**

## 陷阱

### 陷阱一：把「主库由脚本渲染」误当成「单一真相源」

自动生成听起来比「两份手工维护」更可靠。
但**自动生成 ≠ 自动同步**：入库脚本只在**新增**时跑，
一条经验被**修改**时（改独立文件），**没人会想起去重跑渲染**。

→ 派生副本就变成了**第二份真相**，而且是「需要人记得触发同步」的第二份。

### 陷阱二：自动生成的东西反而更不会被检查

人的检查直觉是「盯手写的地方」——手写的东西显然会腐烂。
可**自动生成的**东西也有腐烂路径：**生成器只被部分触发**。
偏偏因为「它自动生成」，**没人会想去检查它**。

| | 手写副本 | 自动渲染副本 |
|---|---|---|
| 腐烂原因 | 忘了改 | **改了源，忘了重跑** |
| 谁会发现 | 有人定期看 | **没人看一个自动生成的东西** |
| 有无信号 | 通常读着就不对 | **完全无信号（合法但旧）** |

→ **「自动生成」让人降低了警惕，却不降低腐烂概率。**

### 陷阱三：全量重跑的双重身份被低估

这次全量重跑**同时干了两件事**：修复缺陷（E61 三个缺陷），
**以及把漂移的 E39 拉齐**（副作用）。

这不是巧合——**「重跑」和「同步」本就是同一个动作的两面**。
所以「修派生副本落后」的最优解不是手工补那一条，而是**跑一次全量**。

## 岔路口

1. **发现派生副本落后 → 跑全量，不要手工补**

单点探测失败 → 「可能是它坏了」。

**信号越整齐，越容易被当成结论，而越不容易被当成探针故障。**

### 陷阱三：已知可用的对象就是天然的对照组

讽刺的是，**系统里本来就有正确答案的样本**——正在跑的 minimax。

## 场景

2026-11-06 15:54 的一次心跳，把「MiniMax 额度耗尽会污染 FAIL 计数」这段巡检观测

## 陷阱

### 陷阱一：错的是「归属」，不是「长度」

446 汉字里，约 270 字是巡检观测，**学习笔记本身只有 178 字**——
本来就在 100-200 区间内，**一个字都不用删**。

真正的问题是**归属**：巡检观测挂在学习小节下，
于是正文被算进了「100-200 汉字」的账上。
**判据说的不是「这一节太长」，而是「这一节不该包含那些字」——
但错误信息只报了长度，把「越界」讲成了「过量」。**

### 陷阱二：读者的眼睛看不出边界错误，解析器能量出来

小节边界是**纯结构**信息：
在 Markdown 渲染里，「学习」和它下面的「### 心跳观测」是**同一个视觉块**，
只有按 `^## ` 切分的正则才知道两者是**不同层级**。

→ **人 review 只会看「读起来顺不顺」，永远不会发现放错层级；
只有巡检能发现，而巡检的报错语言（"超长"）指向了错误的方向。**

### 陷阱三：追加内容是默认动作，"另起小节"要额外决定

往当天笔记里补一段观测，是最自然、最无脑的操作——
**不另起小节几乎不需要理由，另起反而要多想一步**。
所以这个错会**稳定复现**，而不是偶发手误。

## 岔路口

1. **追加内容前先回答一个问题：这段属于哪一类小节？**

2. **「超长」的报错要读根因，不要直接按字面修**。

3. **拆小节优于压缩小节**，当被误挂的内容本身是有价值的事实记录时。

   拆小节**只改结构，不改内容**。
4. **结构错误要有独立断言**。

> 本条讲：**失败计数是原始计数，不含调度频率与错误种类 —— 别用「连续 N 次失败」直接推「已停摆」**

**核心断言**：巡检里的「最近 20 次里有 N 次 error、最长连续 M 次失败」
**只统计次数，不统计上下文**——它不知道这个 job 多久跑一次，
也不知道**每一次失败是不是同一个原因**。
→ 于是「连续 14 次失败」这句话，既可能是「服务彻底死了」，
也可能是「**周频 job 在 20 周里撞了 14 次同一个已修好的 bug**」——
**两者在数字上完全无法区分**。

## 场景

2026-11-07 09:54，我读到 07:00 巡检的【D】组 WARN：

```
daily-reflection 最近 20 次里有 16 次 error，其中最多【连续 14 次】失败
```

我据此判断「这个任务大概率已经实际停摆，而不是偶发抖动」，
并把它列为**需要牛哥哥单独查运行日志**的事项。

查完整 45 次运行历史后，**结论几乎完全相反**：

| 项 | 巡检 WARN 说的 | 实际 |
|---|---|---|
| 调度 | 描述写「每天22点每日反思」 | `0 22 * * 0` = **每周日**一次 |
| 「连续 14 次失败」 | 14 个连续失败 | 其中 **11 次是 `AxiosError: 400`**（05-14 → 10-18） |
| 最近一次 | 11-01 22:00 失败 | **11-03 08:51 补跑：ok / delivered / 80.9s** |
| 当前状态 | 疑似停摆 | `consecutiveErrors: 0`、`lastRunStatus: ok` |

**任务完全健康**，最近一次成功投递。

## 陷阱

### 陷阱一：计数没有「频率」这个维度

`最近 20 次` 对**日频 job** 是 20 天，对**周频 job** 是 **20 周**。
同一个「20 次里失败 16 次」，日频是 80% 失效率（很严重），
周频是 5 个月里的 16 次（可能全集中在某个已修复的历史 bug 上）。

→ **读计数前必须先知道 job 的调度表达式**（`cron list` 里就有）。

### 陷阱二：计数没有「错误种类」这个维度

那 14 次连续失败里，其实是**三种不同的病**：

1. `AxiosError: status code 400` —— 11 次。持续 1.7s–167s 不等、**没消耗 token**
   → 是请求本身被拒（格式/参数），不是「跑太久被砍」。
2. `cron: job execution timed out` —— 恰好卡在 **180.1s**（180193 / 180146 / 180384 ms）
   → 是当时的 timeout 上限。timeout 后来提到 900s → **这类绝迹**。
3. `All models failed (3): rate_limit` —— MiniMax 429 额度耗尽，与已知长期项同源。

**把它们合并成一个数字「连续失败 14 次」，等于把三个独立的因果链压成一条**——
然后我就会去查一个「不存在的、正在持续的系统性故障」。

### 陷阱三：失败 ≠ 没干活

有一次运行（10-11）`status: error`，但 `summary` 完整存在、
`memory/2026-10-11.md` 确实写入了、32k tokens 也真的消耗了——
**只是响应尾部的 HTTP 400 让整个 turn 记成了 error**。
→ 「error」是**状态字段**，不是**事实**（这跟 E62 的「漂移不产生错误信号」是同一族）。

### 陷阱四：失败的时间分布本身就是答案

45 次运行按时间一排，「连续失败」是 **05-14 → 10-18 一整段**，
10-21 起开始出现 ok。**「连续」这个词只在窗口内成立，
出了某个时间点它就断了**——不画出时间线，只看聚合计数就会漏掉这个断点。

## 岔路口

1. **看调度表达式** → `openclaw cron list`：

2. **看错误种类分布** → `openclaw cron runs --id <id> --limit 45`：

我独立查了 `cron/runs/*.jsonl` 原始记录，实际情况是：

```
11-08 09:03 | error | dur=215598 | ⚠️ API rate limit reached (rate_limit)
```

三个候选模型 **3/3 同时中招**，且额度探测（~15k token 真实负载）在 23 小时后**通过**。

→ 根因是 **MiniMax 账号级额度耗尽**（计费周期），**只能靠牛哥哥充值解决**，
我改代码改不了 —— **它是个长期项，不是我现在就该修的故障**。

而分类器为什么判错？因为它写的是：

```python
if "Token Plan" in err:          # ← 认字面量
    reason = "，原因：Token Plan 用量上限(需充值)"
elif "rate limit" in err.lower():
    reason = "，原因：接口限流"   # ← 落进「可处理」组
```

而 `WAITING_PATTERNS` 里只有 `"Token Plan"`。
**11-08 的报错里已经没有「Token Plan」这四个字了**（11-02 时还有）——
措辞一变，匹配器就静默漏判，长期项被误报成「可处理」。

**三个模型同时挂**才是区分两种限流的关键特征：

| 现象 | 根因 | 谁能修 |
|---|---|---|
| **全部**候选模型同时报限流 | 账号级额度耗尽（计费周期） | **只能等牛哥哥充值** |
| 只挂一两个模型、很快恢复 | 每分钟/并发限流 | 能自愈，不用管 |

## 岔路口

判根因时的岔路口：**报错里写了什么词** → **几个对象同时中招**。

判据写成「特征」而不是「字面量」：

```python
m = re.search(r"All models failed \((\d+)\)", err)
if m and int(m.group(1)) >= 2 and 有额度语义:
    return True   # 全部候选模型一起挂 = 账号级额度耗尽
```

这样明天上游把 `rate limit` 改成 `quota exhausted`，判定依然成立。

## 代价

**假警报的代价不是它自己，是它训练出来的阅读习惯。**
一个每天额度一耗尽就出现一次的「可处理 - 现在就该修」，
会训练出「扫一眼就划走」的习惯 —— 等真正的故障来的时候，同样被划走。

（这正是 E59 的老病根：长期项混进 FAIL 计数，会把真故障淹在假警报里。
E59 解决的是「分类」，E66 补的是「分类依据不能认字面量」——
**分类对了，但依据是脆的，一样会漏判。**）

## 修法

1. 分类依据从「报错关键字」改成「故障结构特征」
2. 分类器与故障形态之间**必须有单测**（否则措辞一变就没人发现）
3. 修完复跑一次全量巡检，确认 FAIL 计数真的变了（不是「看起来对」）

## 关联

- E59 —— 长期项混进 FAIL 计数，会把真故障淹在假警报里
- E65 —— 失败计数是原始计数，不含调度频率与错误种类
- E62 —— 派生副本的漂移不产生错误信号（**分类器 = 派生副本**）
- E63 —— 先拿已知可用的对象校准探针（探针错了会被误报成「全挂了」）
- E64 —— 内容合规 ≠ 位置合规
- E57 —— 额度耗尽时小请求照样 HTTP 200（小请求是反向指标）

### E67：自愈机制会自己制造新错 —— 补记写进哪一天的文件，决定了它会不会挤掉当天真正的笔记
> 本条讲：**自愈机制会自己制造新错 —— 补记写进哪一天的文件，决定了它会不会挤掉当天真正的笔记**

**核心断言**：一个用来**修复缺失**的机制，如果**落点选错**，
它会把「缺一个文件」换成一个**结构违规**——而且**全程不报错**。
修复动作本身看起来是对的（内容补上了、字读着通顺），
只有当**下一条正事**要占用同一个位置时，冲突才显形。

## 场景

2026-11-08 的 `daily-learning` 因 MiniMax 额度耗尽失败，
`memory/2026-11-08.md` **根本没生成**（那天的学习笔记丢了）。

11-09 08:08 的心跳按 cron 指令里的【自愈要求】做补记：
把 11-08 那条学习笔记写进了 **`memory/2026-11-09.md`**，
而不是新建 `memory/2026-11-08.md`。

小节标题写的是 `## 📚 每日学习（补记：11-08）`——
一眼看过去完全合理：**确实是在补 11-08，日期也没写错**。

## 陷阱

### 陷阱一：补记的「落点」和「内容归属」是两件事

内容属于 11-08，落点却在 11-09 的文件里 → **归属与位置不一致**。
更麻烦的是，巡检的**按小节计数**断言只看**文件**，不看**小节标题里的日期**：

```python
learn = re.findall(r'^## 📚 每日学习.*$', s_nofence, re.M)
if len(learn) > 1:
    print(f"FAIL {name} 有 {len(learn)} 个「每日学习」小节(应只有 1 个)")
```

→ `2026-11-09.md` 的**唯一名额**被「补记：11-08」占了。
等 09:00 真要写**今天**这条时，再加一节就变成 2 节 → **巡检【F】项立刻 FAIL**。

**修复机制没有制造任何新信息，它只是挪动了「一个位置」**，
而位置是有**配额**的（每天 1 个）。

### 陷阱二：自愈动作发生在「正事」之前，冲突被推迟到下一轮

08:08 的补记当时**看不出任何问题**：
文件存在、有学习小节、164 汉字、长度合规、`--check` 退出码 0。
真正的冲突要到 **09:00 正事写入时**才暴露——而那已经是**另一个会话**了。

→ 这类错误**不可能在修复当场被发现**，
因为它的**受害者是下一个写同一文件的人**。
（这跟 E64 的「结构错误隐形」同族，但机制不同：
E64 是**放错层级**，E67 是**放错文件**。）

### 陷阱三：修「缺失」的动作本身有落点规则，而指令里没写

cron 指令的【自愈要求】说：
「若有缺失日期 → 补写那一天的（同样 100-200 字，每天只 1 个小节），注明『补记：MM-DD』」
「不要为补记单独开新小节」

—— **它规定了「写什么」「多长」「小节数量」，但没规定「写进哪个文件」**。
而「写进哪个文件」恰恰是唯一会造成结构性冲突的那个决策。

### 陷阱四：落点选错的产物看起来是「正确」的

`2026-11-08.md` 不存在 → 我写进了 `2026-11-09.md`，
再给它起了个带日期的标题 `（补记：11-08）`。
**从内容、标题、日期标注上看都无可挑剔**——所以任何「读一遍」的 review 都不会发现。
只有**结构断言**（文件里有几个学习小节）会抓到它。

## 岔路口

补记/回填/迁移类动作落下时，岔路口是：

> **「内容属于谁」** → **「写进哪个容器」**

具体判法：

1. **补记 = 新建那一天的日期文件**，不要往当前文件里塞。
   `memory/2026-11-08.md` 不存在 → **新建它**，把补记放进去。
2. **标题里的日期 ≠ 内容的归属**。
   判据数的是「这个文件里有几个学习小节」，
   所以**容器必须与日期一一对应**。
3. **「不要为补记单独开新小节」的正确读法**：
   不要在**同一个文件**里给补记开第二个学习小节——
   它的意思是「那一天的**那个**小节里写，别再开第二个」，
   而不是「写进今天的小节里」。
4. **配额型位置（每天 1 个小节）要先算占用，再决定落点**。
   落点选择 = **资源分配**，不是排版选择。

## 代价

如果没发现：今天的笔记**写不进去**（或写进去就触发 FAIL），
而修复动作**看起来已经成功**（164 汉字、`--check` 通过、文件存在）。
→ 代价是**下一次运行被迫做二次修复**，且**失败原因指向「重复小节」而不是「补记落点错了」**——
错误信息又一次只描述症状（E66 的同族病）。

## 修法

1. 补记一律**新建那一天的日期文件**（`memory/YYYY-MM-DD.md`），不混装进当前文件
2. 落点判断写成显式规则：**内容日期 → 目标文件名**，一一映射，不允许「就近放」
3. 自愈类动作**必须做一次落点自检**：目标文件是否已存在学习小节？
   已存在 → 说明落点错了
4. 若补记当天确实来不及建文件，**宁可不写**，也不要占用当天的名额

## 关联

- E64 —— 内容合规 ≠ 位置合规（放错层级）
- E66 —— 故障根因会换措辞（报错语言只描述症状）
- E65 —— 失败计数是原始计数，不含调度频率
- E62 —— 派生副本的漂移不产生错误信号
- E60 —— 预测必须改写成观测结论
- E17 —— 检索按 token 切块，短小节夹在长文档中间会被切碎稀释

### E68：先落盘再总结 —— 限流掐死的是「生成总结」，不是「已经做完的活」
> 本条讲：**先落盘再总结 —— 限流掐死的是「生成总结」，不是「已经做完的活」**

**核心断言**：当会话可能**中途被掐死**（限流、超时、进程被杀）时，
**产出必须先落盘，再生成总结**。
因为限流掐死的是**会话的后半段**——如果正文只存在于会话里，
它会跟着会话一起消失。

## 场景

2026-11-09 排查 `daily-reflection`（周日 22:00，跑了 46 次、**0 次在计划槽位成功**）时，
翻历史运行记录发现一个之前没人注意的事实：

- 46 次运行里，**16 次的 `summary` 里「声称已写入 memory/YYYY-MM-DD.md」**
- 但去 `memory/` 下核对文件 —— **真实存在的只有 3 次**
- **13 次的正文凭空消失了**

再看那 13 次的运行特征：`durationMs` 在 **148s~312s**，
而 4 次成功的手动补跑只要 **9.4s~80.9s**。

## 陷阱

这 13 次不是「什么都没做」。它们的 `summary` 写得**非常完整**——
甚至包含「已写入 memory/2026-10-11.md（约 1KB…）」这种**连文件名都说了**的话。

**但文件就是不存在。**

根因是**顺序错了**：

```
❌ 错的顺序：干活 → 生成总结 → （会话在写文件前被限流掐死）→ 正文丢失
✅ 对的顺序：干活 → 落盘 → 生成总结 → （掐死也只丢总结）
```

限流是**会话级**的。它不会阻止你写文件，
它只会让你**没机会走到写文件那一步**（如果你把写文件排在总结之后）。

## 岔路口

「任务失败了」的判断上，岔路口是：**产出落在哪里**。

- 产出只在**会话/总结**里 → 会话一死，产出归零 → **状态显示 error，实质是「白干」**
- 产出已经**落盘** → 会话一死，只丢总结 → **实质是「做成了，只是没报」**

于是「error」这个词其实盖住了两种完全不同的情况：
**没做成** vs **做成了但没报出来**。区分它们只需要核对**文件是否真的存在**。

## 为什么值得记

**「任务状态=error」和「活白干了」不是一回事**，但状态字段分不出来。

E47 讲的是「状态字段 ≠ 用户得到的结果」，
E58 讲的是「单点快照 ≠ 趋势」，
**E68 讲的是「error 这个词本身盖住了两种状态」** ——
它没说你是没做，还是做了没落盘。

而且这次的危害是**双重叠加**：

1. 反思内容**从来没真正存下来过**（6 个月，46 次，0 份产出）
2. 但报告里只写「昨天运行失败（接口限流）」—— 看起来像偶发故障

**一个从没产出的任务，被当成偶尔抖动的任务 —— 没人会去修它。**

## 修法

1. **先落盘，再生成总结**；写完立刻确认文件真的存在
2. **核对产出，别信自述**：agent 的 summary 说「我写了」不等于文件在
   → 判据应该查**文件系统**，而不是读 run 记录里的 summary
3. **一次写完，别反复改写同一个文件** —— 反复试错会拉长运行时间，
   撞上更多限流（E35 的同一机制）

## 配套：把「从没成功过」的任务修好

E58 在 2026-11-03 就已经诊断出「`daily-reflection` 计划槽位成功率 0%，
4 个月没成功过」—— **但只改了巡检的报告口径，没改任务本身**，
所以它又继续挂了 5 天、6 次。

**诊断不是修复。** 这次的落地动作：
- 改时段：周日 **22:00 → 07:00**
  （依据：4 次手动补跑全在 05:00~10:00 窗口成功；且 07:00 在心跳活跃时段 08:00 之前）
- 改顺序：加「先落盘再总结」段
- 验证：等 11-15 07:00 那次真跑，再确认文件落地

## 关联

- E58 —— 「最近一次是 ok」不能代表「最近一直 ok」（同一次排查的前半段）
- E47 —— 状态字段 ≠ 用户得到的结果
- E35 —— 反复试错拉长运行时间，撞上更多限流
- E55 —— 本该发什么：先问有没有产出，再判投递
- E57 —— 额度耗尽时小请求照样 HTTP 200
- E66 —— 故障根因会换措辞，认字面量的分类器会静默漏判

### E69：健康端点返回的是硬编码的 ok —— 探针没坏，被探的对象在撒谎

> 本条讲：**健康端点返回的是硬编码的 ok —— 探针没坏，被探的对象在撒谎**

**核心断言**：当探针调用的端点**不真正走通被检查的依赖**时，
探针报出的 PASS **只证明「进程在」「端点会返回 200」**，不证明「功能能用」——
而且这个错误信号**不会以失败的形式出现**，它长得和真 PASS 一模一样。

## 场景

2026-11-10 07:00 巡检，同一份报告里同时出现：

```
【A3】✅ PASS  嵌入代理健康（记忆检索依赖）
【C】 ❌ FAIL  Embeddings: unavailable - 记忆检索不可用
【H】 ❌ FAIL  记忆检索执行异常
```

A3 说代理健康，C/H 说记忆检索是死的。**两者都不矛盾** ——
它们看的是同一台代理的**两条不同路径**。

## 陷阱

### 陷阱一：端点是写死的，不碰上游

`tools/minimax_embed_proxy.mjs` 的健康分支：

```js
if (req.method === "GET" && req.url === "/health") {
  return send(200, { ok: true, model: MINIMAX_MODEL });
}
```

**返回的是字面量**。它不向 MiniMax 发任何请求，不问余额，不问模型在不在。

于是当上游真实返回
`{"status_code":1008,"status_msg":"insufficient balance"}` 时，
这个端点**依然返回 `{"ok":true}`**。

### 陷阱二：探针本身完全正常，所以没人怀疑探针

这是 E63（「先拿已知可用的对象校准探针」）**没覆盖到的反面**：

- E63 的场景是**探针坏了** → 探了一个不存在的东西 → 误报「全挂了」
- 本条的场景是**探针完全正确，目标在撒谎** → 探针问「进程活着吗」，
  进程确实活着 → 报 PASS → **依赖其实是死的**

E63 的自检（拿已知可用的对象校准探针）在这里**照常通过** ——
因为探针真的没坏。**探针的自检无法发现「对方在自我认证」。**

### 陷阱三：真错在日志里，但不在任何断言的读取路径上

`journalctl -u openclaw-embed-proxy.service` 里明明白白写着
`upstream error: insufficient balance`，
**但没有任何一条断言去读它** → 断言读的是那个写死的 `ok:true`。

实测这次错误只出现在 **07:00:37–07:01:52**（正是巡检自己探测的那几分钟），
之后 10:35 的 3 次真实检索全部成功 → 说明当时是**额度瞬时耗尽**，
而巡检把瞬时状态**固化成了 FAIL**，又因为探针撒谎而**没能区分「额度耗尽」和「代理坏了」**。

## 岔路口

1. **探针要穿过被检查的那条依赖，不能停在它的门口**。
   「进程在」+「端点返回 ok」是**存活检查**；
   「真发一次请求，看上游返回码」才是**功能检查**。
2. **自建服务时，健康端点必须真打一次上游**（哪怕带缓存或降级），
   否则这个端点就等于**让被检查方自己给自己盖章**。
3. **断言报告里，同一个对象出现 PASS 和 FAIL 并存时，先问「这两条查的是不是同一条路径」**，
   而不是急着判其中一条是误报。
4. **故障日志要有一条断言去读它** ——
   「错误躺在 journal 里没人看」和「错误不存在」在效果上是同一件事。

## 为什么值得记

这是「**判据 / 真身 / 失败形态三者不一致**」系列的新变种：

- E42 —— 断言量错了东西
- E63 —— 探针本身坏了
- E66 —— 根因换措辞，认字面量的分类器静默漏判
- **E69 —— 探针没坏，但被探对象返回的是硬编码的 PASS**

前三种都会产生**可见的失败信号**；
只有本条产生的是**和真 PASS 无法区分的假 PASS** ——
**故障被伪装成了健康**，这正是 2026-10-26 立 healthcheck 的初衷
（「状态字段描述的是『任务跑完了』，不是『用户得到了结果』」）的翻版。

## 关联

- E63 —— 先拿已知可用的对象校准探针（本条是它的反面：探针对，对象在撒谎）
- E26 —— 告警链路自身的失败模式，是「读到了上次的成功结果」
- E42 —— 断言量错了东西，就等于没有断言
- E4 —— 涉及「默认值 / 协议 / 常量」的结论，必须查源码或实测
- E57 —— 看门狗和被看守对象共用一个依赖 → 它会先死，而且死得静悄悄

### E70：复跑一次再动手修，巡检 FAIL 是快照不是状态

> 本条讲：**复跑一次再动手修，巡检 FAIL 是快照不是状态**

**核心断言**：巡检报告里的 FAIL 只证明「**在某个时刻**探测失败」，
不证明「**现在**功能是死的」。**会自愈的故障**（额度耗尽 / 限流 / 余额不足 /
上游抖动）报出来的 FAIL 和真故障**长得一模一样** —— 都只是「❌ FAIL」一行。
**区别只有时间**，而报告**不记录时间维度**。
**对策：巡检报出 FAIL 后，先原样复跑一次再动手修** ——
复跑还红 = 真故障；复跑变绿 = 波动。

## 场景

2026-11-11 07:00 巡检：

```
【C】 ❌ FAIL  Embeddings: unavailable - 记忆检索不可用
【H】 ❌ FAIL  记忆检索执行异常
【A】 ⏳ 等你  嵌入上游额度耗尽（HTTP 502）- insufficient balance
```

我 10:48 原样复跑同一份巡检 → **PASS=75 FAIL=0 等你=3**。

**两次之间什么都没改**：没改配置、没重启服务、没动任何代码。
唯一的差别是**时间**：上游额度在 07:00 那一刻是空的，在 10:48 又有了。

如果 07:00 看到 FAIL 就开始「修」——改代理、改配置、改判据 ——
那是在修一个**已经自己好了的东西**，而且每改一次就多引入一个
「改坏了」的机会。

## 陷阱

### 陷阱一：把「额度类」错误当成「可处理」

07:00 的报告把两个 FAIL 放进了「【可处理 — 现在就该修】」，
而额度耗尽在同一份报告里是「等你」。**同一件事（额度）被分到了两个档**，
原因是：额度信号只出现在**某一行**的文本里，分类器按**行**匹配，
没匹配上的就落进「可处理」。

→ 这和 E69 是同一个病根的变种：
**E69** 是探针端点撒谎（对象在骗你），
**E70** 是报告的时间维度缺失（快照被当成状态）。

### 陷阱二：FAIL 数量会制造「多问题」的错觉

07:00 报 FAIL=2（C 和 H），看起来像**两个独立的故障**。
实际上它们是**同一个根因**（额度）沿两条路径各投影了一次 ——
C 走 `memory status --deep` 的 Embeddings 字段，H 走端到端检索。
**根因只有一个，投影有两个。**

→ 修的时候按**根因**修，不要按 **FAIL 条数**修 ——
否则会出现「修好了 C，H 还在」的错觉，然后误判成「我修的方向不对」。

## 岔路口

```
看到巡检 FAIL
    │
    ├─ 报错里有「额度 / 限流 / 余额 / insufficient balance / rate_limit」
    │       → 【别改代码】先复跑一次
    │            ├─ 复跑还红  → 真故障，去查（可能上游确实在挂）
    │            └─ 复跑变绿  → 波动，记一笔「窗口期」，不修
    │
    └─ 报错里没有额度特征
            → 按真故障处理
```

**「复跑一次」不是敷衍，是最便宜的一步**：
它花一次巡检的时间（约 60~100s），
却能区分「要动手改」和「不用动手改」这两个**代价差几个数量级**的决定。

## 对策

1. **巡检报出 FAIL 后，先原样复跑一次再动手。**
   复跑还红 = 真故障；复跑变绿 = 波动。
2. **额度类错误在分类上归「等你」**（需牛哥哥充值），不归「可处理」。
3. **按根因计数，不按 FAIL 条数计数** —— 多个 FAIL 可能是一根因的多个投影。

## 关联

- **E69**（健康端点返回硬编码的 ok）：探针正常但被探对象在撒谎 —— 本条是**报告的时间维度**出问题。
- **E57**（额度耗尽时小请求照样 HTTP 200）：额度问题的另一个伪装形态。
- **E66**（故障根因会换措辞，认字面量的分类器会静默漏判）：分类器读哪条路径的问题。

## 边界

- 本条**不是**说「不要修 FAIL」——真故障该修还是要修。
  本条说的是**顺序**：先花 60s 分清「波动 vs 故障」，再决定要不要动手。
- 判据：**报错的特征**是额度类 → 先复跑；
  否则 → 直接按真故障查。
  这是**启发式**，不是绝对 —— 若连续多次同一 FAIL 复跑都红，那它就是真故障。

### E71：连续失败的任务被判成 WARN，监控看见了但没人动

> 本条讲：**连续失败的任务被判成 WARN，监控看见了但没人动**

**核心断言**：巡检把「**连续失败 ≥3 次的定时任务**」归进 **WARN** 区，
于是它既不进「现在就该修」，也不进「等你」——
**它变成了一条每天都在刷的背景噪音**。
**测量是准的，分类把它降级了**，结果就是：一个已经死了 6 天的任务，
在报告里看起来和一次偶发失败一样重。

**对策：给巡检加一条断言 —— 「连续失败 ≥3 次的定时任务」直接记 FAIL**，
别留在 WARN 里当背景噪音。

## 场景

2026-11-16 07:00 巡检：

```
[⚠️  WARN]  daily-learning 最近 20 次里有 11 次 error，
            其中最多【连续 6 次】失败（最近一次正常）：11-15 09:00, 11-14 09:00, ...
[⚠️  WARN]  daily-reflection 最近 20 次里有 16 次 error，其中最多【连续 12 次】失败
[❌  FAIL]  SESSION-STATE.md 已 5 天未更新
结果: PASS=74  FAIL=1  WARN=5  等你=3
```

daily-learning 从 **11-10 起连续 6 天**每天 09:00 失败，
cron 记录里每次都是 `All models failed (3): ... rate_limit`。
**11-10 和 11-11 的笔记是心跳补的**，11-12 ~ 11-16 这 5 天的
`memory/YYYY-MM-DD.md` 全部不存在 —— 也就是说
**这条「已经死了 6 天」的信息，每天早上都被算出来、写进报告，然后归档**。

## 陷阱

### 陷阱一：WARN 是「不严重」的意思吗？不是

WARN 在报告里的实际效果是**「看到了，但不需要动作」**。
而「连续 13 次失败」和「一次偶发」在 WARN 区里**排在一起**，
读的时候无法区分「上次刚失败一次」和「已经死了两周」。

→ **持续性（连续 N 次）是一个独立维度，不能和「单次严重度」混在一个档里。**

### 陷阱二：监控「看见了」不等于「有人会处理」

巡检把这条写进报告 → 报告进 `memory/healthcheck-logs/` → 归档。
链路完整、信号准确、**没有任何一步会触发动作**。
如果没人主动去读日志里那行 WARN，它就等于不存在。

→ 这和 E68/E69/E70 是同一个病根的另一个切面：
**信号存在，但不在能驱动动作的那条路径上**。
E69 是探针端点撒谎，E70 是报告没有时间维度，
**E71 是报告有时间维度（连续 N 次）却没有把它接到「该修」上**。

### 陷阱三：失败次数是唯一的健康指标吗？不是

「连续失败 6 次」说明的是**产出断了**。
但根因（MiniMax Token Plan 额度周期性耗尽）**不归这条 job 管** ——
job 本身没坏，它只是撞上了上游额度窗口。

→ 所以正确做法不是「让 job 重试到成功」，
而是把「**连续失败 ≥3 次**」升格成 **FAIL**，
让它进入「可处理」通道去推动真正的修复（充值 / 加 key / 加 fallback），
而不是永远躺在 WARN 里。

## 岔路口

```
巡检报出某任务「连续 N 次失败」
    │
    ├─ N ≥ 3
    │     → 这是**持续故障**，不是波动
    │        → 应该被记 FAIL 并进「现在就该修」
    │        → 同时查根因是不是「上游额度」这类外部依赖
    │           （是的话 → 归「等你」，但仍要 FAIL，不能只 WARN）
    │
    └─ N = 1
          → 单次失败，先看有没有「最近一次正常：」
             有 → 可能是波动（E70：先复跑）
             无 → 按真故障查
```

**关键分界**：WARN 留给「**信息性**」的观察项（比如「agent 级目录另有 4 个 provider」），
FAIL 留给「**必须有人做点什么**」的项。
「连续 6 次失败」显然属于后者。

## 对策

1. **给巡检加断言：连续失败 ≥3 次的定时任务 → 记 FAIL**（不是 WARN）。
2. **同时保留「最近一次正常：时间戳」**（巡检已经在输出）——
   它让人能区分「自愈型波动」和「持续性死亡」。
3. 失败次数**按根因计数**（E70）：同一 provider 额度耗尽导致的连续失败
   算**一个**根因，但**在任务维度仍然算持续失败** —— 两个维度分别计数。

## 关联

- **E70**（FAIL 是快照不是状态）：本条是它的**反面**——
  E70 说「单次 FAIL 可能只是波动」，本条说「**持续失败再稳也可能是坏事**」。
  两条合起来才是完整判据：**单次看时间维度，连续看次数维度**。
- **E69**（探针没坏但对象在撒谎）：信号不在能被读取的路径上。
- **E68**（先落盘再总结）：产出断了就不会有落盘 —— 本条是它的「症状侧」。
- **E59 / E57**（额度预检与额度耗尽的伪装）：本条根因的上游。

## 边界

- 本条**不是说所有 WARN 都该升级成 FAIL**。
  「连续失败 ≥3 次」是**具体触发条件**，不是「把 WARN 全变 FAIL」。
- 本条也**不是说 task 自己能修好** —— 根因在额度，
  task 侧只能做「如实暴露、别藏」。
- 判据要看的是**连续失败次数**，不是累计 error 数：
  20 次里失败 11 次（断断续续）和**连续 6 次**，不是一回事。

### E72：超时余量要看基线不要看最近一次，单次异常负载会把基线带偏

> 本条讲：**超时余量要看基线不要看最近一次，单次异常负载会把基线带偏**

**核心断言**：巡检【U】组用「**最近一次成功运行的耗时 / timeout**」判断余量，
一旦某次运行因为**当天的额外工作量**变慢，这个值就**不再是基线**，
而是**那一天的负载快照** —— 判据会把「今天特别忙」误报成「这个任务快撞超时了」。

**判据修法**：余量看**中位数/分位数**（或「最近 N 次里超过 P75 的那些」），
把单次异常值从「基线」里剔除；同时**保留**「最近一次」作为**事实**展示，
但不让它单独决定 FAIL。

## 场景

2026-11-16 09:22 心跳。巡检报：

```
[❌  FAIL]  daily-learning 最近一次耗时 1276s / 超时 1800s = 71% -- 余量告急,下次可能撞超时
```

实测这个任务的历史（全部成功运行）：

| 日期 | 耗时 | 占用率 |
|---|---|---|
| 10-27 | 181s / 772s | 10% / 43% |
| 10-29 | 736s | 41% |
| 11-05 | 673s | 37% |
| 11-07 | 317s | 18% |
| 11-09 | 822s | 46% |
| **11-16** | **1276s** | **71%** |

**近 10 次成功运行的中位数 = 673s = 37%**。
1276s 是 **1.9 倍中位数** —— 明显是异常值，不是趋势。

## 陷阱

### 陷阱一：耗时反映的是「那天的负载」，不是「任务的基线」

翻 11-16 那次会话的时间线（185 条记录 / 69 个 assistant 回合），
它那天干的是**平时不会干的事**：

- 补写 11-12～11-15 **四天**缺失笔记（平时 0 天）
- 新增 L1 条目 E71（平时 0 条）
- 为修 E53 检索失效，**重建索引 3 次**（01:08 / 01:10 / 01:16，每次 ~28s）
- 单独调试 E53 检索措辞，跑了 **6 次** `openclaw memory search`（每次 ~10-30s）
- 跑 5 套回归单测

耗时拆解：**工具执行 377s（30%）+ 模型推理 899s（70%）**，
70% 来自**回合数**（69 轮小步调用），不是单个步骤变慢。

→ **同一条任务，不同的日子，负载可以差一个数量级。**
「最近一次」恰好抽中了负载最重的那天。

### 陷阱二：【U】的规则 1 是单点判据，规则 2 的「趋势」也救不了它

【U】现有两条规则：

1. `最近一次耗时 / timeout > 0.7` → FAIL
2. `最近 3 次耗时呈上升趋势且已 > 0.5` → WARN

规则 2 看着能交叉验证，但**它比的是「最近 3 次成功运行」**，
而这 3 次在日历上**相隔 317s(11-07) / 822s(11-09) / 1276s(11-16) ——
中间隔了 7 天**。稀疏样本上的「上升」不是趋势，是**三个不同负载下的三个点**。

→ 两条规则**共用同一个假设**：耗时序列里各次是可比的。
一旦某次负载异常，**两条规则会一起被带偏**。

### 陷阱三：FAIL 会消耗「可处理」通道的注意力

11-16 这条 FAIL 出现在「【可处理 — 现在就该修】」栏里，
和真正需要动手的项**并列**。而这条 FAIL **明天就会自己消失**（下次正常负载 ≈ 37%）。
→ **假警报不只是噪音，它会占掉「现在就该修」这一格的真实信号**。

这正是 E66 的老问题：**故障根因会换措辞，认字面量的分类器会静默漏判** ——
反过来，**判据不看数据分布，就会静默误判**。

## 岔路口

```
看到「某任务超时余量告急」
    │
    ├─ 先看：这个值是「最近一次」还是「基线」？
    │     │
    │     ├─ 只有「最近一次」
    │     │     → **不能直接当风险** —— 去算中位数 / P75
    │     │        · 中位数 ≤ 60% → 这次是异常负载 → WARN「单次异常」或直接不报
    │     │        · 中位数 > 60% → 真的偏高 → 才该 FAIL
    │     │
    │     └─ 有基线（中位数 / P75）
    │           → 用基线判 FAIL，用「最近一次」补充展示
    │
    └─ 再问：这次运行干了「平时不会干的事」吗？
          （补记多天 / 新增 L1 / 重建索引 / 调试检索 / 跑回归）
          · 有 → 这是**负载异常**，不是**任务变慢**
            → 修法是「拆任务」或「给这次额外留余量」，不是「加 timeout」
          · 无 → 那就是任务真的变慢了 → 查哪一步变慢
```

**关键分界**：**「任务变慢了」和「今天任务变重了」是两件事**，
前者要优化，后者要**要么拆要么容忍**。用「最近一次」当基线，会把后者误判成前者。

## 对策

1. **【U】规则 1 改用基线**：算最近 N 次（建议 N=8～10）成功运行的**中位数**，
   `中位数 / timeout > 0.7` 才 FAIL。
2. **保留「最近一次」但降级为展示项**：它作为**事实**写在报告里，
   不单独决定 FAIL —— 避免「明天自己好了」造成的信号抖动。
3. **异常值单独标注**：若「最近一次 / 中位数 ≥ 1.5」，
   报一句「本次为异常负载（中位数 X s，最近一次 Y s）」，
   把「负载异常」和「余量告急」**分成两句话** —— 它们的修法完全不同。
4. **趋势规则要按日历密度看**：相邻样本间隔 > 2 天时不算「趋势」。

## 关联

- **E70**（FAIL 是快照不是状态）：本条是它的**第三种形态** ——
  E70 说的是「**单次** FAIL 不代表现在坏了」，本条说的是
  「**单次**耗时不代表基线」。同一个病根：**快照 ≠ 状态**，
  一个用在故障判定上，一个用在余量判定上。
- **E71**（连续失败被判成 WARN）：本条是它在**性能维度**的对应物 ——
  E71 修的是「持续故障被降级」，本条修的是「单次异常被当成趋势」。
- **E65**（失败计数不含调度频率）：本条同源 ——
  **聚合统计丢掉关键维度，其聚合值就无法支撑结论**。
  E65 丢掉的是「调度频率」，本条丢掉的是「负载分布」。
- **E66**（根因换措辞，认字面量会漏判）：反向 ——
  **判据不看数据分布，就会误判**。

## 边界

- 本条**不是说「最近一次」没价值** —— 它是**事实**，只是**不能单独当基线**。
- 本条**不是说所有异常负载都该忽略** —— 如果**连续多次**都超 70%，
  那就是任务真的变重了，该拆。
- 中位数 vs P75：**中位数更稳**（抗单点异常），
  P75 更保守（提前预警）。【U】的用途是「防明天撞超时」，
  取**中位数判 FAIL、P75 判 WARN** 是折中。
- 本条**不适用于失败运行**：失败跑的耗时是「烧满 timeout」，
  不反映真实负载 —— 现有判据已经只取成功运行，本条沿用。

### E73：算故障持续了多久，终点必须是故障本身，不能是「现在」

> 本条讲：**算故障持续了多久，终点必须是故障本身，不能是「现在」**

**核心断言**：任何统计「持续了多久 / 断了多久」的判据，
终点**不能取「当前时间」或「最新一条记录」** ——
因为故障一恢复，最新那条就变成成功，跨度被缩到最短，
**最该留痕的那段历史正好被抹掉**。
正确做法是**独立地找出最近一段连续失败**，
量「该段之前最后一次成功 → 该段最后一次失败」，
并保留**历史维度**：恢复后仍要能报出「历史上曾连续失败 N 次（约 M 天，现已恢复）」。

## 场景

2026-11-16 09:45 心跳。同一天早上刚修完 E71（连续失败 ≥3 次升级为 FAIL），
新增的 `_outage_span_days()`（按**日历跨度**算中断天数，而非按次数）初版写成了：

```
跨度 = 最新一次运行时间 − 最后一次成功时间
```

daily-learning 11-10～11-15 连挂 6 天、11-16 恢复 `ok` ——
**最新那次就是 ok** → 「最后一次成功」= 11-16 → 跨度 = **约 1 天**，
**6 天的真实中断被报成 1 天**。

## 陷阱

### 陷阱一：终点取「现在」，恢复即归零

用 `now - 上次成功` 计算：
- 故障还在 → 数字**随时间持续增长**（看着还挺准）
- 故障修好 → 数字**瞬间缩回 0**，报告里再查不到「它曾经连挂 6 天」

**恢复的那一刻是监控价值最高的时刻**（可以结案、可以复盘），
而这个算法**恰好在最需要证据的时刻把证据擦了**。

### 陷阱二：终点取「最新一条记录」，被恢复的那条自己抹掉自己

更隐蔽的版本：终点不取 `now`，取「最新一条运行记录」。
直觉上「取最新」比「取现在」更保险 —— 它是**确定的**数据点。
但**最新那条本身可能就是那条恢复记录**，
于是「最后一次成功」被推到了故障段的**末尾之后** → 跨度被压缩到最小值。

### 陷阱三：日历天跨度还有个 off-by-one

「从 X 日到 Y 日」按日历天算应为 `Y - X + 1`。
初版漏了 `+1`，报「连续失败 12 次」时跨度显示「11 天」。
**次数和天数是两个口径**，必须一致 —— 否则报告会自相矛盾。

## 岔路口

1. **终点取自哪里？**
   - 从**故障序列本身**取（该段最后一次失败）→ ✅ 正确
   - 从 `now` 取 → ❌ 恢复即归零
   - 从「最新一条运行记录」取 → ❌ 恢复记录会自己抹掉自己
2. **恢复后还查得到历史吗？**
   - 查得到（「曾连续失败 N 次 / 约 M 天，现已恢复」）→ ✅
   - 查不到 → ❌ 失败痕迹被当成「没发生过」
3. **历史段要不要保留？**
   - 保留**最近一段**连续失败 + 之前最后一次成功作为起点 → ✅
   - 只看「当前这一段」 → ⚠️ 会丢掉更早的历史
4. **全程无成功过怎么办？**
   - 单独分支处理（起点回退到**首次运行**时间）→ ✅
   - 让 `last_success = None` 直接参与减法 → ❌ TypeError

## 对策

```python
def _outage_span_days(runs):
    # 1) 找出「最近一段连续失败」：从后往前扫，遇到第一个 ok 就停
    consecutive = []
    for r in reversed(runs):
        if r.status == 'ok':
            break
        consecutive.append(r)
    if not consecutive:
        return 0
    last_fail = max(r.at for r in consecutive)          # 终点取自故障本身
    before = [r for r in runs if r.at < min(x.at for x in consecutive)]
    start = max((r.at for r in before if r.status == 'ok'), default=None)
    if start is None:
        start = min(r.at for r in runs)                 # 全程无成功 → 回退首次运行
    return (last_fail - start).days + 1                 # 日历天跨度，+1
```

配套自测（**必须包含「刚恢复」这个场景**）——
只测「正在失败」的话，这个 bug **测不出来**：
- 正在连续失败 → 跨度 = N 天
- **刚恢复**（末条 ok）→ 跨度仍应是 N 天，**不是 1 天**
- 全程无成功 → 起点回退到首次运行
- 单次失败 → 1 天

## 关联

- **E70**（FAIL 是快照不是状态）：本条是它在**时间跨度维度**的延伸 ——
  E70 说「单次 FAIL 可能只是波动」，本条说
  「**要算多长，得从故障序列里取，不能从『现在』取**」。
- **E71**（连续失败被判成 WARN）：本条是它的**配套修正** ——
  E71 把「连续失败 ≥3 次」升级为 FAIL，**但如果跨度算法在恢复时归零**，
  这条刚升级的断言就会在**任务恢复的当天**自己失去证据。
- **E72**（余量看基线不看最近一次）：本条同源 ——
  E72 是「**基线**别用最近一次」，本条是「**终点**别用现在/最新一条」。
  两者都是**单点数据被当成了基线或边界**。
- **E65**（失败计数不含调度频率）：本条是它的**同类** ——
  同样是「聚合统计必须带着正确的维度」，E65 丢的是调度频率，本条丢的是故障段边界。

## 边界

- 本条**不是说「跨度」不重要** —— 恰恰相反，E71 的 FAIL 判定**依赖**它。
- 本条**不适用于「最近一次耗时」这类单点量** —— 那本来就没有故障段。
- 本条**不要求永久保留全部历史段** —— 保留**最近一段**即可，
  但**恢复后必须仍能报出来**。
- 若任务**频繁失败又频繁恢复**，本条会让 FAIL 长期亮着 —— 这是**事实**，
  不该用「恢复就归零」去掩盖（E71 同理）。

### E74：闸门太安静就没人在乎，连续跳过必须有人读

> 本条讲：**闸门太安静就没人在乎，连续跳过必须有人读**

**核心断言**：一个**只在故障时动作**的机制，如果它的动作**没有接到「该修」的那根线上**，
就会变成一台**安静地坏掉的机器** —— 它工作正常、它忠实报告，
但**没人读它的报告**，于是「每天都在跳过」这件事永远不会变成「该修」。

**判据修法**：给闸门加一条巡检断言 —— **「连续跳过 ≥3 次」直接记 FAIL**，
并把「跳过」和「失败」**当成两种不同的信号**分别呈现。

## 场景

2026-11-16 14:20 心跳。同一天刚上了一套**额度闸门**架构：

```
systemd timer（09:00 / 周日 07:00）
   └─ daily_learning_gate.py（纯脚本 · 不烧模型额度）
         ├─ 预检不通过 → GATE_RESULT=skipped，**不启动 agentTurn**
         └─ 预检通过   → openclaw cron run <job>
```

这套架构解决的是一个真问题：**闸门装在了它要守的东西里面** ——
原来 preflight 是写在 cron 指令里的，而 cron 指令**只在 agent 已经跑起来之后才生效**；
额度耗尽时 agent 连第一个工具调用都发不出去 → preflight **一次都没跑到** →
照样烧 180~316s、零产出。搬到 systemd 之后，闸门本身不受额度影响。✅

**但当天下午复查时发现**：闸门把 `GATE_RESULT=skipped reason=quota`
写进 `memory/healthcheck-logs/daily-learning-gate-*.txt`，
而**巡检从来不读那些文件**。

→ 如果额度**长期**枯竭，闸门会一天一天地跳过，
**巡检一条都不会提** —— 额度问题又退化成「背景噪音」。

## 陷阱

### 陷阱一：把「修好故障」当成「修好观测」

闸门让「额度耗尽」从「烧 300s 空转」变成「秒级跳过」—— **故障本身修好了**。
但**故障修好的同时，信号也跟着消失了**：以前失败会进 cron 记录、进巡检报告；
现在跳过只写进一个没人读的日志文件。

→ **降噪的同时可能顺手把告警降没了。**
一个只输出「一切正常」的组件，比一个会报警的组件更难被发现它坏了。

### 陷阱二：这正是 E71 的翻版

E71：「**连续失败**被判成 WARN，监控看见了但没人动」。
E74：「**连续跳过**连日志都没人读」。

两个是同一个病根的两副面孔：**信号算出来了、写下来了，但没接到「该修」的那根线上**。
E71 的信号在**巡检报告里但被降级**，E74 的信号在**日志文件里但根本没进巡检**。

→ 往系统里加一个新机制时，要问：**「它出问题时，谁会发现？」**
答不上来的机制，就是一台安静地坏掉的机器。

### 陷阱三：「跳过」和「失败」不是同一件事，别混着报

闸门跳过 = **额度不够，主动不跑**（这不是故障，是正确行为）。
agentTurn 失败 = **该跑但没跑成**。

两者的**修法完全不同**：
- 跳过 → 充值 / 加 key 拆配额（**等牛哥哥**，长期项）
- 失败 → 可能是我这边的 bug（**我能修**）

→ 混在一栏里，要么把「额度问题」误报成「可处理」（天天假警报），
要么把「真 bug」藏进「等你」栏（E71 的老坑）。

## 岔路口

```
某个机制「只在故障时动作」（闸门 / 熔断 / 重试 / 降级）
    │
    ├─ 它的「故障信号」写在哪？
    │     ├─ 巡检报告会读的字段 → ✅ 已被接住
    │     ├─ 独立的日志文件 → ⚠️ **要专门加断言去读**（本条）
    │     └─ 只在内存里 / 只打 stderr → ❌ 等于不存在
    │
    └─ 它的「正常信号」会不会淹没故障信号？
          ├─ 会 → 要用**结构化标记**（本例的 `GATE_RESULT=`），
          │        别指望从自然语言日志里 grep
          └─ 不会 → 保持
```

**关键分界**：**故障被修好** 和 **故障被看见** 是两件事。
闸门让第一个成立，但如果第二个没跟上，**修得越好越危险** ——
因为它把「一直在坏」变成了「安静地不坏」。

## 对策

1. **新增巡检【G2】组**：读闸门日志 → 统计**最近连续跳过次数** →
   连续 ≥3 次 → **FAIL**；1-2 次 → WARN。
2. **判据真身抽到 `scripts/check_gate_skips.py`**（E11：不抄判据），
   单测 **11 用例全 PASS**，**含真实故障注入**。
3. **用结构化标记** `GATE_RESULT=<ok|skipped|blocked|triggered|error>`，
   不靠 grep 自然语言。
4. **跳过与失败分列**：闸门跳过归「额度不足（等牛哥哥）」，
   agentTurn 失败才进「可处理」—— 两者的修法不同，混报等于制造噪音。

## 关联

- **E71**（连续失败被判成 WARN）：本条是它在「新增机制」上的对应版本 ——
  E71 修的是「已有的信号被降级」，本条修的是「**新加的机制没接线**」。
- **E69**（探针没坏但对象在撒谎）：探针正常但被探对象在自我认证；
  本条是**探针正常、探针自己产出的是故障、但没人看探针**。
- **E66**（根因换措辞，字面量分类器会漏判）：本条用**结构化标记**
  代替自然语言 grep，正是这条教训的应用。
- **E58 / E68**（诊断不是修复）：**修好故障不等于修好观测** —— 本条是它的新变体。
- **E8**（纯脚本任务不该用 agent 型 cron）：闸门本身是纯脚本，
  所以它不受额度影响 —— 这条架构决策直接催生了本条的需求。

## 边界

- 本条**不是说闸门不该跳过** —— 跳过是正确的（有闸可下总比空转好）。
  本条说的是**跳过的次数要能被别人看见**。
- 本条**不是说连续跳过就该 FAIL** —— 阈值 3 是「额度长期枯竭」的信号，
  1-2 次属于正常波动（WARN）。**阈值本身要按任务的合理频率定**。
- 本条**不覆盖「闸门根本没被触发」** —— 那属于
  systemd timer 层面的问题，由漂移检查（57 项）覆盖。
- 本条的判据**只读闸门自己的日志**，
  不去推断「额度到底够不够」—— 那是 preflight 的职责，
  巡检只负责**「它说了跳过，说的次数是多少」**。

### E75：手写内容会被自动清理吃掉，验证必须跑真正删它的那个脚本

> 本条讲：**手写内容会被自动清理吃掉，验证必须跑真正删它的那个脚本**

**核心断言**：**「自动生成」和「自动清理」一样，都会吃掉你手写的东西。**
一个文件里如果存在「保留前缀」机制（脚本按行首匹配来识别机器产物），
那么**你手写的行只要撞上那个前缀，就会被静默删除** ——
没有任何报错、没有痕迹，只剩下「我明明写过了，怎么不见了」。

**配套的第二个错误**：声称「已验证稳定」时，**跑的是你怀疑的那个脚本，
而不是真正会删你的那个脚本**。验证的不是会发生的那件事 = 没验证。

**对策**：写进有自动维护逻辑的文件前，先确认这行的开头不会被当成机器标记；
声称「稳定」时跑**完整触发链**（把真正执行删除的那个脚本也跑一遍），不是只跑一个。

## 场景

2026-11-16 15:00 心跳。14:47 写进 `SESSION-STATE.md` 的一行
`**巡检现状**：PASS=80 ...`「又不见了」—— 一小时内被删了两次，
所以一度以为是某个并发会话在改文件。

查实：`scripts/update_state_status.py` 第 100–114 行有一段
**「清理遗留的旧格式行」** 逻辑：

```python
for ln in out:
    ...
    # 块外的旧格式行：丢掉
    if ln.startswith("**巡检现状"):
        continue
```

那行 `**巡检现状` 是它用来**定位自己生成的活行**的锚点，
它同时也是**自增机制**（防止每次巡检多插一行）的实现方式。
→ 我手写的那行**恰好也以 `**巡检现状` 开头**，于是被当成「上一轮的旧机器产物」删掉。

**同一天犯的配套错误**：14:47 那次我写「恢复后验证稳定」，实际只跑了
`gen_system_status.py --update`（**没删**），
**没跑 `update_state_status.py`（真正删它的是这个）**。
→ 验证的对象错了，所以「稳定」这个结论是空的。

## 陷阱

### 陷阱一：把「消失」当成「并发冲突」

两个会话同时写同一个文件 → 确实可能互相覆盖。
但这次的两个会话**根本没冲突**：一个在写、一个在按前缀删。
→ 症状是「我写的行不见了」时，**先查有没有按前缀删除的逻辑**，
再查并发。前者命中率远高于后者。

### 陷阱二：修法只改措辞，不改可发现性

当时的修法是「手写状态换措辞（不用保留前缀）」——
但**下一个人**还会撞上同样的坑，除非报错信息本身会教人。
→ 修法要包含**让错误可被发现**：把报错改成
「这个前缀是保留的、块外的行会被删除、换个措辞」，
否则下个会话只会看到「我的行凭空消失」而查不出原因。

### 陷阱三：只跑自己怀疑的那一个脚本

「我怀疑是 A 删的 → 我跑 A → A 没删 → 结论：稳定」——
但真正删的是 B。**验证必须覆盖完整的触发链**，
即「什么机制会删这行」的**全部候选**，而不是「我最怀疑的那个」。

## 岔路口

**岔路口 A：报错要不要改？**
选择「改报错措辞」而不是「只在错误日志里加一句」。
→ 理由：报错**就是**下个会话的地图。加了措辞，下个会话 5 秒定位；
只加日志，下个会话还得重新推一遍。

**岔路口 B：验证范围到哪？**
选择「跑完整触发链」而不是「跑真正删我的那个脚本」。
→ 理由：完整触发链才是**将来**会发生的事；
真正删我的那个脚本只是**当前**的一个候选 ——
今天删我的是 `update_state_status.py`，明天可能是别的脚本。

## 对策

1. **往有自动维护逻辑的文件写手写内容前**，先确认这行的开头
   不会被当成机器标记（看脚本里有没有 `startswith(...)` 之类的清理逻辑）。
2. **声称「稳定 / 已恢复」时**，跑完整触发链 ——
   把「所有可能删掉这行的机制」都触发一遍，而不只是你怀疑的那一个。
3. **报错信息要带修复指引**（换个措辞 / 换个位置），
   让下一个遇到同样症状的人不用重新推一遍。

## 关联

- **E70**（巡检 FAIL 是快照不是状态）：本条是它在「文件写入」上的对应版本 ——
  E70 修的是「报告反映的是某个时刻」，本条修的是「**报告/文件反映的不是你以为的那次写入**」。
- **E69**（探针没坏但对象在撒谎）：**「我写过了」和「我写的还在」是两件事** ——
  本条是它在「自己写的记录」上的版本。
- **E73**（算故障持续了多久，终点取自故障本身）：
  本条是它的**观测侧孪生** —— E73 说「算跨度不要用『现在』当终点」，
  本条说「**验证不要用『我跑的那个』当终点**」。两处都是同一个错误形状：
  **用一个方便但不对的终点，代替了真正相关的那一点**。
- **E74**（闸门太安静就没人在乎）：E74 说「机制的动作要接上『该修』的那根线」，
  本条说「**机制的清理要接上『我写的』的那根线**」——
  都是「一个自动化组件对某类内容有生杀权，而另一方不知情」。
- **E71**（连续失败被判成 WARN）：本条是「**信号被降级**」的另一种 ——
  这次连信号都没有：删除是**静默**的，被删的行也不会出现在任何报告里。

## 边界

- 本条**不是说自动清理机制不该有** —— 它防「每次巡检多插一行」是必要的。
  本条说的是**被它清理的那一方要有办法知道**。
- 本条**不覆盖并发写同一文件的冲突** —— 那是另一类问题，
  要靠锁或原子写解决。本条针对的是「**按内容前缀删除**」这类语义性清理。
- 本条的判据是「**该行会不会被某个 `startswith` 命中**」，
  不是「这个脚本会不会报错」—— 静默删除**不报错**。

### E76：检查产出物别只检查执行状态，被跳过和跑了没产出在下游无法区分

> 本条讲：**检查产出物别只检查执行状态，被跳过和跑了没产出在下游无法区分**

**核心断言**：**「任务没跑」和「任务跑了但什么都没产出」是两种完全不同的故障，
但在只检查执行状态的监控里长得一模一样。**
一旦某层「抑制/跳过」机制（闸门、熔断、重试上限、限流）存在，
就必须在**产出物**这一侧另设一道断言 ——
否则「被正确地拦下来了」和「默默地什么都没干」在报告里无法区分。

**核心断言（第二个）**：**「检查重复」的断言，不能替代「检查缺失」的断言。**
「小节 > 1 就报错」的检查，对「小节 == 0」是**结构性沉默**——
它不但不报，还会在注释里写下「缺失是正常的，等它自己来」，
把这个盲区**当成设计固化下来**。

**对策**：断言要问「**该有的东西在不在**」，而不只是「**多出来的东西有没有**」；
报告缺失时先查抑制层的记录（该次是「被拦的」还是「真没产出」），
**措辞要区分这两种**，别把「被正确拦下」报成「任务坏了」。

## 场景

2026-11-17 09:38。早上 09:00 的 daily-learning 被闸门拦下
（上游 HTTP 529 过载，`reason=upstream_busy`）—— **这是闸门按设计工作**，
拦对了。09:38 补跑成功，当天笔记正常产出。

回头查断言链时发现一个盲区：

- 【F】组（记忆笔记结构）只查**重复**：`if len(learn) > 1: FAIL`，
  **从不查缺失**（`len(learn) == 0` 一个字都没有）。
  代码注释里还明写着「今天的学习小节要等 09:00 的 cron 才会生成」——
  于是「缺失」被**当成正常状态**固化下来了。
- 【G】组只查**连续跳过次数**：跳 1 次 = WARN，且措辞是「最近一次被闸门跳过」。

→ 两者叠加的后果：**某天学习笔记缺失时，全链路零报错、零 FAIL。**
唯一可能的发现途径是「等自愈补记」或「人工翻日志」。

更要命的是**措辞的反向风险**：如果将来给「今日笔记缺失」加断言，
却不去查抑制层记录，就会把「被闸门正确拦下」（上游抖了，正常）
报成「任务坏了」—— 这是 E66 的同族病：**根因换了措辞，分类器还按老样子判**。

## 陷阱

### 陷阱一：把「抑制层拦下了」当成「一切正常」

闸门存在的前提就是「它拦下的都是不该跑的」。
**拦对了 = 系统按预期工作**，但它同时意味着**产出物不存在**。
→ 抑制层和产出层必须**各有各的断言**，
抑制层只回答「该不该跑」，产出层才回答「跑没跑出东西」。

### 陷阱二：只查重复、不查缺失

「重复」是**增量**问题，「缺失」是**存量**问题，
两者的检测逻辑和数据源都不同：
- 重复：数同一个文件里有几个
- 缺失：**去产出物本身里看有没有** —— 需要知道「正常应该有几个」

只写重复检查的断言，对缺失是**沉默**，而不是「假阴性」——
它连报错的机会都没有，因为它压根没去看那个维度。

### 陷阱三：报告缺失时不做根因分流

「今天没有学习小节」这一个事实，至少对应三种完全不同的根因：
1. 闸门拦了（上游/额度问题）—— **系统按设计工作**
2. 任务跑了但没产出（写盘失败、被限流掐死）—— **真故障**
3. 任务压根没被调度（timer 没触发）—— **真故障**

三者都报同一句话 = 把「正常」和「故障」混进同一档，
和 E59（长期项混进 FAIL 计数）是同一个病：
**假警报会消耗掉真警报的注意力**。

## 岔路口

在「产出缺失」这类断言上，有三条路，**别默认选第一条**：

### 岔路口一：直接报 FAIL（默认走法）

最省事。但会把「被正确拦下」也报成故障 → 假警报。
**只有在确认该产出物「本该存在且不该被拦」时**才走这条。

### 岔路口二：查抑制层记录再分流（推荐）

断言先读**抑制层的历史**（如 `memory/gate-history.jsonl`）：
- 当天有 `triggered` → 任务跑过了，产出缺失 = **真故障** → FAIL
- 当天全是 `skipped` → **被拦的** → 按「闸门拦截（非故障）」措辞，且**不计入 FAIL**
- 当天没有任何记录 → 压根没调度 → **真故障** → FAIL

分流的关键是**两种结果用不同措辞、且不进同一个计数桶**。

### 岔路口三：把「产出物」当成一等公民来断言

更强的做法：给每个有产出物的任务配一条
「**当天该产出物存在且内容达标**」的断言，
让它和「任务执行状态」的断言**平行存在**。
这样即使抑制层、调度层、日志层全都改版了，
产出侧的断言仍然独立成立。

> E73 的观测侧教训在这里再次显形：
> **「当前状态」和「历史事实」要分开判** ——
> 「现在还缺吗」和「它是不是被跳过过」是两个问题，
> 只问前一个，就让**抑制层的一个正确决策把产出侧的缺失盖住了**。

### E77：次数和跨度必须来自同一段，否则拼出来的是假消息

> 本条讲：**次数和跨度必须来自同一段，否则拼出来的是假消息**

**核心断言**：当一条告警**同时报「连续 N 次」和「已中断 N 天」**时，
这两个数字**必须来自同一段失败**。
它们各取各的，就会拼出一句**事实正确但整体荒谬**的话 ——
而这种话比明显的错更危险，因为**它读起来完全合理**。

**真实翻车（2026-11-17 实测，daily-reflection）**：

巡检报出来的是：
> `daily-reflection 连续失败 12 次，任务已中断约 12 天！`

真实数据（`openclaw cron runs --limit 20`，时间倒序）：
```
11-15 E / 11-08 E / 11-03 o / 11-01 E / 10-26 o / 10-26 o / 10-25 E / 10-21 o
/ … / 09-01 E … 08-02 E          ← 窗口末尾是一长段 8 月的旧账
```
拆开看：
- **「连续失败 12 次」** ← 来自 **08-02 → 09-01** 那段**早已恢复**的旧账
- **「已中断约 12 天」** ← 来自 **11-03 成功 → 11-15 失败** 的**真实跨度**
- 而**当前**实际只连挂 **2 次**（11-08、11-15）

→ 次数说「12 次」，跨度说「12 天」，**两个 12 纯属巧合**，
放在一起却让人以为「连挂 12 次、每次一天」—— **全是编的**。

**根因**：`_max_consecutive_errors()` 取的是**窗口内最长的一段**（含历史旧账），
`_outage_span_days()` 取的是**当前这段的跨度**。
两个函数**各答各的问题**，却被拼进**同一句话**。

**修法**：把「当前是否还在持续失败」和「历史上曾挂过多长」**拆成两个函数**：
- `_max_consecutive_errors()` —— 只数**从最新一次往回数、还没被成功打断的那一段**
- `_max_consecutive_errors_history()` —— 窗口内**历史**最长段

→ **当前段**用于「还在挂吗？挂了多久？」（要 FAIL 就 FAIL 当下的事）
→ **历史段**用于「曾经挂过多长？」（WARN 留痕即可）

**更深一层的教训**：**「连续失败」这个词本身有歧义** ——
是「现在正在连挂」（当前段）还是「历史上最长连挂过」（历史段）？
判据写的时候**必须先定义清楚问的是哪一个**，否则两个消费者会各自取自己那套语义，
拼起来就成了假消息。

**配套的检查动作**：报告警之前，**把每个数字单独回溯到它的来源** ——
「12 次」是哪一段的？「12 天」是哪一段的？
**两个数字指向同一段吗？** 不指向同一段，就说明有一半是编的。

**怎么防止再犯**：
① 每个数字都问一句「它来自哪一段」；
② 单测里**造一段「早已恢复的旧账」放在窗口里**，断言当前段**不受它污染**
（`test_cron_delivery_output.py` 8.8c 就是这个用例）；
③ 修判据时**单测会先红** —— 这次就是 W2 抓到了我（它断言的是旧语义，
   我改了语义它立刻 FAIL → 逼我把「为什么改」写清楚，而不是偷偷改测试）。

_已提升至 L1：E77_

### E78：连续计数器只数条数不看跨度，一次事故能被数成三天

> 本条讲：**连续计数器只数条数不看跨度，一次事故能被数成三天**

**核心断言**：任何以「**连续 N 次**」为阈值的判据，都必须同时检查
**这 N 次跨越了多长时间**。
只数条数不看跨度 → **一次事故的 N 次重试**和**N 天的持续故障**会撞进同一个阈值。

**真实翻车（2026-11-18 07:00 实测，额度闸门）**：

巡检【G2】组报出来的是：
> `daily-learning-gate 最近曾连续 3 次被闸门跳过（截至 2026-11-17-092823，现已恢复）`

这句话的措辞暗示「**额度枯竭了 3 天**」。但查 `memory/gate-history.jsonl` 的真实数据：
```
2026-11-17T09:01:52 | skipped | upstream_busy
2026-11-17T09:20:39 | skipped | upstream_busy
2026-11-17T09:28:23 | skipped | upstream_busy
2026-11-17T09:38:31 | triggered
```
→ 这 3 次是**同一天早上、27 分钟内**的**同一起上游 529 过载**，
被 systemd timer 重试了 3 遍而已 —— **一起事故，不是三天**。

**根因**：`check_gate_skips.py` 的 `FAIL_CONSECUTIVE = 3`，
它的**设计语义是「连着 3 天额度枯竭」** ——
证据在它**自己的单测**里：三条假数据被写成 `2026-11-16` / `11-17` / `11-18`，
**跨 3 个自然日**。
但判据的实现**只数条数**（`cur += 1`），**从不看时间跨度** →
**半小时里重试 3 次 = 连续 3 次 = 触发阈值**。
**次数是「行数」，却被当成了「天数」。**

**更危险的一层**：这条 FAIL 会进 `is_waiting()` 的分栏。
虽然 reason 分类正确（`upstream_busy` → 措辞已带「**无需处理**」，E66/E77 的修复生效了），
但**阈值语义被触发**这件事本身是假的 ——
它占用了「连续 3 次 = 该充值」这个**额度告警名额**。
当真正连续 3 天枯竭时，读报告的人已经见过一次「连续 3 次」→ **信号被稀释**。

**修法**：判据加一道**跨度下限** —— 连续跳过那段
**跨越 ≥2 个自然日**（或首末条间隔 **>6 小时**）才算「持续枯竭」；
同一天内的多次跳过归类为「**上游过载重试**」，
只报 **WARN** 并附上首末时间戳，不占用额度告警名额。

**怎么防止再犯**：
① 阈值旁边**必须写清楚它的单位**（「3 次 = 3 **天**」还是「3 次 = 3 **条记录**」）——
   写不清楚就是 bug 温床；
② 单测里**同时造两种形态**：跨 3 天的 3 条（应 FAIL）
   和**同一天 27 分钟内的 3 条**（应只 WARN）——
   只造前一种，判据就会一直装死；
③ 报「连续 N 次」时**把首末时间戳一起打出来** ——
   让读的人一眼能看出这是「三天」还是「27 分钟」。

**与 E77 的区别**：E77 讲的是「次数和跨度来自**不同的段**，拼出假消息」；
本条讲的是「**同一个段内**，跨度从未被检查，段被当成了天」。
前者是拼错，后者是**没量**。

_已提升至 L1：E78_

### E79：修好一个判据不会修好它的兄弟，修完要横向扫同族

> 本条讲：**修完一个判据的假信号，兄弟判据里同一类假信号还留着**

**核心断言**：修掉某个判据里的**一类假信号**后，
**同族的其他判据几乎一定还带着同一类病灶**——
因为它们通常是**同一个错误模式被复制了几遍**，而不是独立写出来的。
→ **修完一个，必须横向扫一遍同族**（同一个巡检脚本里的其他组、
同一类问题的其他判据），而不是只确认「原来那条不报了」。

**真实翻车（2026-11-19 09:00 实测，巡检【D】组投递判据）**：

今早 E78 落地：给「连续跳过」判据（`check_gate_skips.py`）补了跨度下限，
同一起上游 529 重试不再被报成「额度枯竭三天」。
顺手查同族判据，发现**投递判据**（`check_cron_delivery.py`）
里还有同一类病灶，而且是在**第三条路径**上：

`scripts/check_cron_delivery.py:491-493`（已恢复任务的 WARN 分支）：
```python
consec    = _max_consecutive_errors_history(runs)   # ← 窗口内「最长的一段」
span_days = _outage_span_days(runs)                # ← 「最近的一段」
```
→ 报出：`WARN {name} 历史上曾连续失败 {consec} 次（约 {span_days} 天，现已恢复）`

**构造数据实测**（早期 5 次连挂跨 4 天 + 近期 2 次连挂跨 1 天）：
```
consec    = 5     ← 来自「窗口内最长段」
span_days = 11    ← 来自「最近段」，但它的起点是「最近段前一次成功」
→ 报出：「历史上曾连续失败 5 次（约 11 天，现已恢复）」
```
**那 5 次真实只跨 4 天**；「11 天」是拿**另一段**的起点量的。
**两个数字指向不同的段** —— 拼出来的话**事实正确、整体荒谬**。

**为什么 E77 修过却还在**：
E77（2026-11-17）修的是 **FAIL 路径**（任务还在挂时那条），
把「当前段」与「历史段」**拆成了两个函数**。
但 **WARN 路径**（任务已恢复时那条）是**第三种组合**：
它拿「**历史最长段**」的次数，配「**最近段**」的天数 ——
E77 的拆分只保证了两个函数各自正确，**没保证调用方把它们配对**。
→ **函数拆对了 ≠ 配对对了。**

**为什么 36/36 单测全绿**：
`test_cron_delivery_output.py` 36 个用例全过，
但**没有任何一个用例覆盖这条 WARN 的数字配对**——
单测测的是「`_max_consecutive_errors_history()` 返回几」，
**不是**「报出来的那句话里，两个数字是否来自同一段」。
→ **单测覆盖了函数，没覆盖配对。**

**修法**：
① 给 `_outage_span_days` 加一个「**指定段**」参数，
   让**次数和天数从同一段取**（要么都用历史最长段，要么都用最近段）；
② 补一条单测 —— 造「**早期长段 + 近期短段**」，
   断言报出的天数 **等于那段自己的首末跨度**，不是任何别的段的值；
③ 修好后，报告文案里带上**首末时间戳**，
   让读的人能自己核对「这几次到底跨了多久」。

**怎么防止再犯（横向扫描清单）**：
① 修判据 A 时，主动问一句：**「同类问题的判据 B、C 有没有同一个毛病？」**
   —— 同族判据通常是**复制粘贴**出来的，错误也一起被复制；
② 每条告警里的**每个数字**都要能回答「**它来自哪一段**」；
   指向不同段的数字凑在一句话里 → **有一半是编的**；
③ 「**已恢复**」分支最容易被漏测 ——
   FAIL 路径有大量用例，WARN 路径常常一条都没有，
   而 **WARN 路径恰恰是唯一会长期留在报告里的那段**。

**与 E77 / E78 的区别**：
- E77：两个数字来自**不同的段**，拼出假消息（**错配**）；
- E78：**同一个段内**，跨度从未被检查，段被当成了天（**没量**）；
- E79：修好了一条路径（FAIL），**另一条路径（WARN）仍错配**，
  而且**单测没覆盖配对** → **修一个是局部修，不是同类问题修完**。

眼里被销账（不再被报出来）。判据通常用**固定的销账词表**（`已落地`/`已修复`/
`✅ 落地状态`）来判定 —— 你自己写的**语义等价**措辞，判据**不认识**。
→ 账没销 → 下次巡检照报 → **多出一条假信号**。

**真实翻车（2026-11-20 08:45 实测，【V2】「待落地」标记扫描组）**：

今早把 E65 落地，我在 L1 条目里写下：
```
✅ 已于 2026-11-20 落地
```
而判据的 `DONE_PAT` 只认：
`✅ 落地状态` / `已落地` / `修法（已做）` / `已修复`
→ 「已于…落地」**一个都不匹配** → 巡检**仍然报**「E65 仍带未完成声明」。
→ **代码确实修了，账没销** —— 这是 P13「条目写完 ≠ 修好了」的**镜像版**。

**陷阱：为了消 WARN 而改文案 = 把判据的缺陷藏进文案里**：
一看到 WARN 就去把「修法（还没做）」改成别的说法 →
判据不再报，但**没人知道判据有毛病**；换个措辞、换个场景就复现。
→ **判据有毛病 → 修判据 + 加单测**；**真待办 → 修代码 + 用判据认得的措辞销账**。

**岔路口（第二个更隐蔽的坑）：给判据加过滤 = 把判据改弱**：
今天为修「元引用被当成真待办」的假警报，加了引号/「这类/标记」过滤。
→ 过滤写宽了 → **真待办不再被报** → 报告全绿 → **比原来的假警报更危险**
（假警报只是噪音；漏报是真的漏）。
→ **凡是加过滤的判据，单测必须双向覆盖**：
① 真待办**仍要报**；② 假警报**要消失** —— **两边同时断言，缺一边就是装死**。

**对策**：
① 销账前先查判据的**销账词表**，只用词表里的**原话**；
② 判据有缺陷时改判据，不要改文案去迎合判据；
③ 加过滤的判据，单测**双向**覆盖（真阳性 + 真阴性）；
④ 断言本身要有**注入自检** —— 断言「注入前后结果必须不同」，
专门防「注入空转、测试全绿但什么都没测」。

**与 E79 / P13 的区别**：
- P13：条目写完 ≠ 修好了（**代码层面**没真修）；
- E79：修好一个判据 ≠ 修好它的兄弟（**覆盖面**不够）；
- E80：代码真修好了 ≠ 账销了（**措辞/销账**这一层没对上）。

_已提升至 L1：E80_

### E81：数据源迁移后断言还在读旧源，报的是假故障

> 本条讲：**数据源迁移后断言还在读旧源，报的是假故障**

**核心断言**：一个判据的**数据源被换掉**（job 从 cron 迁到 systemd、字段改名、
文件搬迁）之后，判据如果**没跟着换**，它报出来的就不是「现在的事实」，
而是**旧源的最后一个快照** —— 而且往往**报得比真故障还像故障**
（因为快照里恰好存着一个 `error`）。

→ 判据输出的**时间戳**必须能对上「现在」，对不上就是在读历史。

**真实翻车（2026-11-21 08:10 实测，【D】组定时任务投递组）**：

07:00 巡检 `PASS=86 FAIL=0`，但有一条「等你」项：

```
⏳ daily-reflection 运行失败（lastRunStatus=error，原因：额度耗尽(API rate limit，需充值)）
```

它被列为**当前故障**。实际是**6 天前的陈旧快照**：

| 证据 | 值 |
|---|---|
| 最后一次 cron 运行 | 2026-11-15 07:03（status=error，额度耗尽，耗时 217s） |
| 迁移到 systemd 的日子 | 2026-11-16 |
| cron 里的 `nextRunAtMs` | 2026-11-22 07:00 —— 但 `enabled=False` → **永远不会触发** |
| systemd timer | `OnCalendar=Sun *-*-* 07:00` → 首跑 **明天 07:00** |

→ 这条「故障」既**过期 6 天**，又**还没到新路径的首次执行**。

**为什么会漏**：判据里的守卫是

```python
if run_status is None and not st.get("lastRunAtMs"):
    print("... 尚未运行过 ...")
    continue
```

`run_status` 是**陈旧的 `error`**（不是 `None`）→ 守卫**永远不触发** →
判据把 6 天前的失败当成「刚发生」。

**最扎眼的一点：同一个 job，两个组读的是两套真相源**：

- 【G2】组读 `memory/gate-history.jsonl`（**活的**）→ 报的是真实闸门行为
- 【D】组读 `cron/jobs.json`（**冻的**）→ 报的是历史残留

→ **同一个对象，两组用不同真相源** → 一组准、一组假，而且**没人发现**，
因为「有一组准」会让整个巡检显得可信。

**岔路口：怎么区分「陈旧快照」和「真故障」**：

判据报错前先问一句 —— **这个状态是「现在发生的」还是「上次写入的」**。
三种可靠的判别法（可叠加）：

1. **时间戳对齐**：判据要用的时间戳必须落在合理窗口内
   （比如「最近 24 小时」），否则只当**历史**展示，不当**故障**告警。
2. **写入方对齐**：数据源迁移了，**写入方和读取方必须一起换** ——
   读旧源的那组要**显式标注「本组读的是历史快照」**，而不是照报。
3. **下一次调度对齐**：`nextRunAtMs` 存在但 `enabled=False` →
   这个「下次运行」**是假的** → 不能用它推断「系统正在等它跑」。

**附带坑：`LAST = -` 不等于定时器坏了**：
`systemctl list-timers` 里 `LAST=-`（从未跑过）看起来像故障，
但如果该 timer 是**周频**（`OnCalendar=Sun *-*-* 07:00`）且**刚建**、
而**今天不是那个星期几** → `LAST=-` 完全是正常的。
→ 看 `LAST=-` 之前**必须先读 `OnCalendar` 表达式**，
   再看 timer 的启用时间 —— 否则会把「还没到点」误判成「坏了」。

**对策**：
① 判据的每个数据源都要标注**「谁在写它」**；写入方换了，读取方必须跟着换；
② 同一对象**只能有一个真相源** —— 多个组读不同源 = 迟早一组假；
③ 判据输出**必须带时间戳**，让「陈旧」和「当前」肉眼可分；
④ 「从没见过这个状态」有两种含义（没跑过 / 跑了但没写回来）——
   **区分它们**，别默认前者；
⑤ 迁移期最容易出这种错 —— **迁移完成的那天，就要重新验一遍所有断言的读源**。

**与 E26 / E78 / E80 的区别**：
- E26：告警链路读到了**上次的成功** → 故障被静默吞掉（漏报）；
- E80：代码真修好了 ≠ 账销了（**措辞**没对上 → 多报一条假信号）；
- E81：**数据源换了但断言没换** → 报的是**旧源的最后一个快照**（假故障）。

_已提升至 L1：E81_

### E82：缓存指纹只盖住新建那一个文件，陈旧结果就被无限期缓存

> 本条讲：**缓存指纹要覆盖所有能改变结论的文件，只盖住新建那一个就等于没盖**

**核心断言**：缓存的**失效指纹**必须覆盖**所有能改变结论的文件**。
如果指纹只盖住「新建的那一个」，那么后续所有**只改动其他文件**的修正
（同步、迁移、补充）**都不会让缓存失效** → 陈旧结果被**无限期缓存**。

→ 指纹的范围 = **结论的依赖集**，不是「这次新建的文件」。

**真实翻车（2026-11-21 08:10 实测，L1 经验库检索组）**：

修完 E81（陈旧快照）之后，巡检**仍然**报：

```
FAIL L1 经验库有经验检索不到 -- 结果: 81/81 条经验可被检索
```

**两个事实自己打架**：一行说「全通过」，另一行说「有 FAIL」。
查缓存 `/tmp/openclaw/l1_verify_cache.json`：

```json
{"fp": "dcb443...", "rc": 1, "line": " 结果: 81/81 ...", "fails": ["❌ FAIL E81 不在主库里"]}
```

→ 缓存的是**中间状态**（E81 独立文件已建、**主库还没同步那一刻**）的 FAIL。
→ 而**指纹只覆盖 `memory/L1-entries/E*.md`**。
→ 同步主库**只改主库文件**，独立文件**一个字节没动** → 指纹不变 → 陈旧 FAIL 无限期缓存。

→ 这条本身就是 E81 的**第二个实例**：派生数据会过期，**缓存也会过期**，
  而且**过期的方式很隐蔽**（指纹没覆盖到真正会变的那部分）。

**陷阱一：指纹范围跟着「这次改了什么」划，而不是跟着「结论依赖什么」划**

最自然的想法是「我这次新建了 E82.md → 那就把 E*.md 纳入指纹」。
但结论依赖的是**三处**：独立文件（能被检索到）+ 主库（条目在不在）+ MEMORY.md（声明）。
**缺一个，那个维度就会静默过期。**

**陷阱二：结果行只数「通过的」，不扣「失败的」**

原来 hits 只统计结构通过数 → 才会出现「81/81 可被检索」+「FAIL E81 不在主库里」
**同时出现**。
→ 一个计数必须**扣掉失败项**才有意义；否则「全通过」是假的。

**岔路口：怎么判定一个缓存该不该失效**：

不要问「我改了哪些文件」，要问 **「哪些文件的任意变化都会改变结论」**。
三个检查动作：
1. 列出结论的**全部输入**（这次是 3 个文件），逐一纳入指纹；
2. 改完任何输入后，**指纹必须变**（否则缓存不会失效）；
3. 缓存里的结论行**必须与实际失败项一致**（计数要扣 miss）。

**附带坑：自检脚本的计数与主判据的计数口径可能不一致** ——
`trim_learning_section.py` 的 `--from` 口径（不含首行与尾部元信息）与
`--check` 口径（整段全算）**差着几十字**：
`--from` 报「189 汉字，无需裁剪」→ 直接写入 → `--check` 报「228 汉字，超标」。
→ **以 `--check` 的退出码为准**（它是任务指令指定的验收口径）；
  `--from` 的字数只是**裁剪前的估算**，两者不是同一个尺子。

**对策**：
① 缓存指纹的范围 = **结论的依赖集**，不是「这次新建的文件」；
② 依赖集里的文件，**改任何一个**都必须让指纹变化；
③ 计数/结果行必须**扣掉失败项**，否则「全通过」和「有 FAIL」会并存；
④ 自检工具之间**口径要一致**，或明确以哪个为准（本项目以 `--check` 退出码为准）；
⑤ 缓存条目要能看出**它是什么时候写的**（至少带指纹），否则陈旧结果无法自证新鲜。

**与 E80 / E81 的区别**：
- E80：代码真修好了 ≠ 账销了（**措辞**没对上 → 多报一条假信号）；
- E81：**数据源换了但断言没换** → 报的是**旧源的最后一个快照**（假故障）；
- E82：**缓存指纹没覆盖依赖集** → 陈旧结论被**无限期缓存**（假故障的第二种成因）。

_已提升至 L1：E82_

### E83：闸门跳过的日子不留痕，巡检查「声称写了」查不出「本该有却没有」

> 本条讲：**闸门跳过的日子不留痕，所有巡检都看不见时间线上的空洞**

**场景**：给额度敏感的 agentTurn 任务加**额度闸门**（systemd timer 在 OpenClaw 之外预检，
额度够才 `cron run` 触发）。闸门判定额度不足时跳过 → 这是**机制正常工作**，不是故障。

**陷阱**：被跳过的日子**在时间线上留下一个静默的洞**，而所有巡检组**都看不见它**。
2026-11-22 实测：闸门 `skipped/quota` → `memory/2026-11-22.md` **压根没建**，
但 11-23 07:00 的巡检 **PASS=91 FAIL=0**，一条都没报。三层都漏了：

1. 【A2-1】「声称写了但文件不存在」—— 只扫 `status != "ok"` 的 run 摘要里的日期；
   **闸门跳过压根没进 cron** → 没有 run 记录 → 没有摘要 → **结构上不可能被抓到**；
2. 【A2-3】「索引漏写了某天的笔记」—— **只遍历 `memory/` 下已存在的文件**，
   再和索引比 → 「本该有却没有」**天然不在它的视野里**（它只查「有但没进索引」）；
3. 【D】「投递是否正常」—— 看的是 **cron 投递记录**，闸门跳过的那天**压根没有投递**，
   于是「没投递」和「投递失败」长得一样，但前者不是故障。

→ 结果：**闸门守住了额度，却让「当天没产出」变成了一个不会报警的正常状态**。
→ 一句话：**「健康地跳过」和「悄悄地没跑」在信号上无法区分**。

**岔路口**：判「这段时间该有产出却没产出」，数据源不能只用**产出侧**，
必须用**决策侧**（闸门历史）交叉算：

- 数据源 = `memory/gate-history.jsonl`（记了 `triggered` / `skipped` + `reason`）
- 算式：对最近 N 天，每天应有一个 triggered；若当天是 `skipped` →
  **不是故障，但必须在时间线上留痕**（补记 / 占位），否则洞会一直静默；
- 关键分界：`skipped` = **闸门正常工作**（不算故障，E81 口径），
  但 `skipped` 且**没有补记** = **产出缺失**（该报）；
  → 这两件事必须**分开判**，否则修一个就会吞掉另一个（E81 的教训）。

**为什么值得记**：闸门类机制（限流闸、审批闸、配额闸）**天然会跳过任务**，
而「跳过」在下游看起来像「没运行」，在产出侧看起来像「正常（没报错）」。
→ **每加一个会跳过任务的闸门，就要同时加一条「产出连续性」的判据**，
  否则闸门越可靠，时间线上的洞越多。

**关联**：E81（数据源换了但断言没换）、E82（缓存指纹范围 = 结论依赖集）、
E16（低触发频率的机制没有容错）、E1（区分「失败」和「没触发」——
本条是 E1 的**反向版本**：这次是「没触发」被当成了「没触发」，
问题不在归因，而在**没人要求产出必须存在**）。


**✅ 落地状态（2026-11-23 补）**

- 判据真身：`scripts/check_note_gaps.py`（自检 10 用例全过）
- 接入：【A2】组第 4 条 + 新增【W8】单测组（35 → **36 组**）
- 数据源换成**决策侧**（`memory/gate-history.jsonl`），带宽限期 1 天

落地时踩到两个坑（已固化为单测用例）：

1. **「没有记录」≠「被跳过」** —— 第一版把闸门上线前（11-16 之前）的日子全判成了洞，
   闸门历史里根本没那一天 → **不判**（否则天天误报 = E66 假警报驯化，
   **比不写更糟**：真洞出现时会被无视）；
2. **宽限期边界差一天** —— 补记发生在**下一个 09:00**，
   `age < grace` 会把「昨天被跳过（还能被补）」误判成洞 → 改成 `age <= grace`。

→ 自检当场抓出了第一版的假阳性 —— **判据本身要先证明自己是对的**
（与 E81「断言读旧源」、E82「指纹没盖住依赖集」一脉相承）。
