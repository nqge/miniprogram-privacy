## 2026-10-27 — provider 变慢比 provider 挂掉更隐蔽：共享账号就是共享配额

> 本条讲：**provider 变慢比 provider 挂掉更隐蔽 —— 共享账号就是共享配额**

昨晚以为「单 provider」只有一重后果：挂了兜底无效。今晨查 daily-learning 为何 362s/420s，发现**一次单次 LLM 调用等了 353 秒**，不是等工具。那段时间正是 backup-audit 超时的时段，两者共用同一 MiniMax 账号。实测同账号 6 并发：单发 1.8s，最慢 7.0s，**慢 3.9 倍**。

所以第二个 key 的价值不是容灾冗余，而是**拆开共享配额**。这类退化不报错、只变慢：所有任务一起挤牙膏，巡检 50% 的超时余量被吃掉。

**可立即执行的对策**：给长期项补上并发实测数字（1.8s→7.0s），让「等第二个 key」带上代价而非一句「兜底无效」。

## 2026-10-27（补记）— 验收用的测量，必须跑在真实负载上

> 本条讲：**验收用的测量，必须跑在真实负载上**

今晚改动首次无人值守验收。跑之前的前置检查写「巡检 ~102s / timeout 600s，余量充足」，但 07:00 真实 cron 实测 **298.4s**——同一天、同一套脚本，差了近 3 倍。

前置检查没测错东西，它测的是**另一个工作负载**：手动跑缓存热、抽样轮转到轻的一天；真实 cron 无人值守、缓存冷、轮转位置不同、还要和别的任务抢配额。手动耗时只是定时耗时的**下界**，比不给数字更危险——它给了一个自信的值。

根因在 `verify_l1_retrieval.py` 按 `%j % 4` 轮转抽样：保证了覆盖公平，却让每天负载浮动。**覆盖公平 ≠ 负载恒定**。

**可立即执行的对策**：给巡检超时预算按**最重的一轮**留余量，别拿手动测的耗时定预算。

_已提升至 L1：E40_

## 2026-10-27 — 被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言

> 本条讲：**被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言**

今晨 shell 报 `to_report: unbound variable`，真根因却是 pre-existing：heredoc 结束符与赋值同行，变量从未赋值；那组带 `2>/dev/null`，报错被吞掉、**输出为空**，却无条件 `PASS=$((PASS+1))`。【R】组一直显示 PASS，从没真正算过。

它**死得像个健康检查**。`PASS` 计数无条件 +1，不是证据；证据是**这组名下有没有实际断言行**。`2>/dev/null` 是最常见的静默失败制造机：本意是「这组失败别炸掉巡检」，副作用是把这组自己的 bug 一起吞，于是「这组坏了」和「这组查出真问题」一模一样。

**可立即执行的对策**：给巡检加元断言——每组至少一条 ✅/❌/⏳/⚠️ 输出，缺失即 FAIL。

_已提升至 L1：E43_

## 2026-10-28 — 快照管不住退化：递增是趋势，快照看不见

> 本条讲：**巡检器自己在退化，而没有任何断言在看它**

今晨查 healthcheck 耗时：10-26 上午 27s，傍晚 214s，10-27 是 298s，10-28 是 378s，两天涨 13.9 倍，外推 10-31 撞 600s timeout。关键不在「会超时」，而在**我原来的归因是错的**。我以为是 provider 变慢，查 run history 才发现，那两次跑**不是同一份代码**，那天我正往巡检里加断言组。**更关键的盲区是耗时递增没有任何断言在看**：【U】组问「最近一次占比」，那是快照，而递增是趋势——快照 50% 是 PASS，趋势 100% 才 FAIL，中间三天没人看见。

**可立即执行的对策**：给【U】组加趋势判定，最近 3 次耗时递增且涨幅超 50% 就 WARN，让退化在撞 timeout 前被看见。

_已提升至 L1：E52_

## 📚 每日学习（2026-10-29）

> 本条讲：**没内容就不该投递 —— 同一状态码，正常与故障要问「本该发什么」**

今早 08:00 茶馆 cron 是 `delivered=false`。按 E47 判据该报 FAIL，但它不是故障 —— 那次输出「新增 0 条 / 无新内容」，**没内容就不该打扰牛哥哥，不投递才是正确的**；10-28 那批「跑完了没送到手上」才是真故障，字段一样，性质相反。洞在 `check_cron_delivery.py` 只按 `delivery.mode` 分组，**同一 mode 内没再往下分** —— 字段没有「本该发什么」这一维，只能靠人肉读输出。补法不是放宽断言，而是**加一维**：取 run 产出摘要，无产出则标「有意不发」。

**可立即执行的对策**：给 `check_cron_delivery.py` 的 announce 分支补产出判据 —— 无产出则不判 FAIL，注入「有产出但未投递」验证它仍 FAIL。

## 📚 每日学习（2026-10-30）

> 本条讲：**错误信息里的「3 个模型都失败」本身就是一条线索**

今天 9 次调度全部 `All models failed (3)`，三个模型报的是**同一句** `API rate limit reached`。这个「3/3 同时同因失败」的形态，和「模型 A 挂了、切到 B 成功」是完全不同的两件事——后者是 provider 级故障，前者是**账号级配额耗尽**：三个模型在同一个 MiniMax 账号、同一个额度桶里，fallback 只是换了三个名字的同一张卡。

**可立即执行的对策**：解析 cron 错误串，统计「同一错误文案出现在多个模型名上」的次数，出现即告警提示「配额级耗尽，请充值或加第二把 key」，而不是继续轮换模型重试。

_已提升至 L1：E57_

## 📚 每日学习（2026-10-31）

> 本条讲：**手动探测成功，不等于故障不存在——小请求能过只是额度还没见底**

## 📚 每日学习（2026-11-01）

> 本条讲：**恢复是「自己发生的」不等于「被修好了」——两者要分开记账**

停摆第三天，16:02 那次调度 `status=ok`，额度自己回来了。但翻回这三天，**没有一次是我的动作修好的**：没充值、没改配置、没加 key —— 纯粹是配额周期重置。这件事如果记成「已修复」，下一轮额度耗尽时就会以为「上次也自己好了，不用管」。真正的区分是：谁能让故障不再复发，谁只是让这一次症状消失。

**可立即执行的对策**：给「恢复」单独记一笔账 —— 恢复事件必须写明「恢复原因：自动/人工」+「复发风险是否已消除」，只有后者为真才允许把该故障标记为已解决。

## 📚 每日学习（2026-11-02）

> 本条讲：**看门狗和被看守对象共用一个额度，额度耗尽时看门狗先死**

MiniMax Token Plan 用量上限，10-30 到 11-01 连着 3 天，所有 agentTurn 型 cron 全挂——其中就包括 07:00 的体检。可笑之处在于：体检本来是发现「定时任务全挂」的那道保险，而它自己被同一个额度桶掐死，还死得毫无声响——cron 列表里只有 `lastRunStatus=error`，没有一条告警发到牛哥哥手上。真正漏掉三天的是「体检没跑」这件事本身没人监控。

**可立即执行的对策**：把所有巡检与告警类任务迁到不消耗模型额度的 systemd timer，并在断言里加一条「今日巡检日志是否真的产出」——巡检没产出本身必须可告警。

## 📚 巡检发现（2026-11-03）

> 本条讲：**「最近一次是 ok」不能代表「最近一直 ok」—— 连续失败次数必须单独断言**

`daily-reflection` 的 44 条运行记录里只有 3 次成功，而这 3 次全是手动补跑——**周日 22:00 的计划槽位 15 次全挂，跨 4 个月，成功率 0%**。但巡检只报了一行「昨天运行失败（接口限流）」，读起来像偶发故障。根因分三个时代换过：glmcode/kimicode 已死（HTTP 400）→ timeout 默认 180s 太短 → Token Plan 额度耗尽。每次都以为「修好了」，从没从「历史上到底成功过几次」的角度看过。

更深一层：`check_cron_delivery.py` 把 error 统计写在 `else:` 分支里，只要历史上存在任何一次「ok 但没投递」就永远走不到 → **daily-learning 那 3 天连续全挂被完全吞掉**。修法是让 error 统计与未投递统计正交，并新增「最长连续失败次数」维度。

**可立即执行的对策**：任何健康度判断都不能只看 `lastRunStatus` 单点快照。要同时断言「最近 N 次里 M 次 error」「最长连续失败次数 ≤ 阈值」「符合调度规律的 run 里成功过几次（排除手动补跑）」「失败原因分类计数」。连续 N 次失败 ≠ 零散 N 次失败——前者是静默中断 N 天，用户完全无感。

_已提升至 L1：E58_

## 📚 每日学习（2026-11-03）
> 本条讲：**长期项混进 FAIL 计数，会把真故障淹在假警报里**

今天巡检打印 `FAIL=1`，下一行却写「✅ 没有可处理的失败」，退出码还返回 1。根因是 `bad()` 对每一项都加一，可文案命中 `WAITING_PATTERNS` 时却渲染成「⏳ 等你」——「等我充值的长期项」和「真坏了」在计数行里长得一模一样。危害不是吵，是**驯化**：一个每天都报、没人细看的假失败，会让人养成扫一眼就划走的习惯，等真故障来时同样被划走。

**可立即执行的对策**：把「可处理失败」和「等你的长期项」拆开计数、拆开显示，退出码只按可处理失败数决定——长期项不该让 systemd 判红。

_已提升至 L1：E59_

## 📚 每日学习（2026-11-04）

> 本条讲：**「预计会自愈」是预言不是观测 —— 写进状态字段就等于把未验证的猜测当事实继承**

今天 08:42 心跳把两条**观测**（巡检 PASS=72、配额探测通过）和一条**预言**（「09:00 daily-learning 预计自愈」）写进 SESSION-STATE 头部同一行，格式完全一样。可前两条有日志为证，第三条只有「额度够 + 距上次失败 24 小时」两个推断，且**无失效时间、无证伪触发器**：09:00 真挂了，头部仍写「预计自愈」，下个会话无从分辨。

## 📚 每日学习（2026-11-05）
> 本条讲：**派生副本漂移不报错 —— 「自动生成的」比「手工维护的」更不值得检查**

昨天修入库脚本时顺手全量重跑，捞出 8 天前就该同步的旧条目：E39 独立文件 10-27 就改过，主库却从没重新同步，8 天里巡检全 PASS，只是**内容是旧的**。

**可立即执行的对策**：给「独立文件 → 主库」渲染链加一条巡检断言，比对正文哈希——不同步就不该算绿灯。

## 📚 每日学习（2026-11-06）

> 本条讲：**先拿已知可用的对象校准探针 —— 探针错了会被误报成「全挂了」**

昨天实测残留 provider 凭证，第一轮直接探 `models.json` 里的 key，**正在用的 minimax 也 401**——差点得出「凭证全死」。根因不是凭证坏，是 `models.json` 存旧 key、`openclaw.json` 存当前 key，靠 `models.mode=merge` 覆盖，**探针读的不是生效配置**；改探合并后的有效配置，minimax 立刻 200。教训不在「合并」这个细节：**任何批量健康探针，第一步都该拿一个「已知活着」的对象试跑**。

**可立即执行的对策**：批量探活脚本先对已知可用对象做自检，不通过就中止并报「探针失效」，而不是输出结果。
