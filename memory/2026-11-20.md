### 一、E65 落地：「连续 N 次失败」补上丢掉的两个维度

**E65 说的是什么**：巡检里的「最近 20 次里有 N 次 error、最长连续 M 次失败」
**只统计次数，不统计上下文** —— 它不知道 job 多久跑一次，
也不知道**每一次失败是不是同一个原因**。

→ 「连续 14 次失败」既可能是「服务彻底死了」，
也可能是「**周频 job 在 20 周里撞了 14 次同一个已修好的 bug**」——
**两者在数字上完全无法区分**。

**修法不是把 WARN 删掉**（删掉 = 把信号源也删了），是**给判据补维度**。

#### 落地：新增 4 个函数（`scripts/check_cron_delivery.py`）

| 函数 | 作用 |
|---|---|
| `_classify_run_error(err)` | 错误文本 → 类型桶（额度耗尽/接口限流/执行超时/脚本报错/网络错误/上下文超长/其他） |
| `_cron_expr_window_days(expr)` | cron 表达式 → 每次间隔（天）：日频 1 / 周频 7 / 每 N 小时 / 每 N 天 / 每周多天 |
| `_group_errors_by_type(runs)` | run 列表 → `{类型: [run...]}` |
| `_segment_runs(runs, seg)` | 只取**最长段本身**的 run（分组**不能**混入窗口里别的零散失败） |

外加 `_window_desc(runs, job)`：把「最近 N 次」换算成**真实时间跨度** + 调度频率。

#### 落地前后对比

```
落地前：
WARN daily-learning 历史上曾连续失败 6 次（约 6 天，现已恢复） —— 该段 2026-11-10 09:00 → 2026-11-15 09:00

落地后：
WARN daily-learning 历史上曾连续失败 6 次（实际跨度约 6 天，现已恢复）
  —— 该段 2026-11-10 09:00 → 2026-11-15 09:00
  —— 错误类型：额度耗尽×6
  —— 调度：0 9 * * *（约每 1 天跑一次） → 这 6 次按调度约合 6 天
  —— 最近一次状态：ok
```

> **为什么「实际跨度」和「按调度约合」要分开写**：
> 前者来自**时间戳**（事实），后者来自 **cron 表达式**（换算）。
> 混在一起就分不清哪个是事实、哪个是推算 —— 这正是 E79 的教训
> （「5 次跨 4 天，却报『约 11 天』」：**两个数字各自都对，凑一句就是假的**）。

#### 这条 WARN 现在能多回答一个问题

旧版：「连挂 6 次」→ 我只能猜「大概是 6 天，还是 42 天？」
新版：直接告诉你 **6 次全是额度耗尽**（同一个原因，不是 6 种不同的坏）
且 **日频 → 约合 6 天**。

→ 如果哪天分组显示「额度耗尽×3 + 脚本报错×3」，
那就**不是同一个原因**，得拆开查 —— 旧判据永远看不出这个区别。

### 二、【V2】的两个真 bug（顺带挖出来的）

#### Bug A（假警报）：元引用被当成真待办

`proactive-tracker.md` 和 `memory/2026-11-19.md` 里的那些「修法（还没做）」「待落地」，
**不是在声明自己还有没做的活**，而是在**讲这个机制本身**：

```
「修法（还没做）」「尚未修改」「待落地」这类**明确的未完成声明**。
### P14：「带标记」不等于「有人会扫」—— 待落地标记需要专门的断言
如果那天我没读那条日志，E79 的「修法（还没做）」会**再躺一天、一周、一个月**。
```

**修法**：加「元引用」过滤 —— 短语**被引号包着当术语用**、
或**后面跟着「这类/标记/声明/模式/机制」** → 是元引用，不是待办。

> ⚠️ **过滤本身就是「把判据改弱」的操作** ——
> 写宽了 → 真待办不再被报 → 报告全绿 → **比原来的假警报更危险**。
> 所以单测必须**双向**覆盖（见下）。

#### Bug B（漏报，比 A 严重）：销账标记写在紧邻的下一小节

```
## 待落地（未实现）
## ✅ 落地状态（2026-11-20 08:45）    ← 销账标记在**下一节**
```

旧判据只看「**当前小节**」→ 销账标记落在**小节边界之外** → 找不到
→ **明明落地了，还是被报成「未落地」**（假信号）。

**修法**：销账标记允许出现在**紧邻的下一小节**。

> ⚠️ **但不能「整篇一刀切」** —— 那会让**文件开头**的声明
> 被**文件结尾**的销账标记覆盖 → 另一个方向的装死。
> → 折中：① 当前小节有 DONE 标记 → 已解决；② **下一节**有 → 已解决；
> ③ 再往后**不算**。

### 四、本轮的两个教训（都是自己踩的）

#### 教训 1：「修好了 ≠ 账销了」

我第一版把 E65 标成：

> ✅ **已于 2026-11-20 落地**

但【V2】的 `DONE_PAT` 只认 `✅ 落地状态` / `已落地` / `修法（已做）` / `已修复` ——
「已于…落地」**一个都不匹配** → 判据**仍然报「未落地」**。

→ 这是 P13「**条目写完 ≠ 修好了**」的**镜像版**：「**修好了 ≠ 账销了**」。
→ **销账必须用判据认得的措辞**，否则下次巡检照样报 —— **假信号**。

#### 教训 2：故障注入的 before/after 必须分处注入前后

写【W6】时我第一版把 before/after **都写在注入之后** →
两个值当然相同 → 用例恒红。

→ **一个断言「看着在测 A、实际测的是 B」的失败，先怀疑测试数据本身**
（和 2026-10-28 那次一模一样）。
→ 第三版加了一条「**注入自检**」：断言「注入前后结果**必须不同**」
→ 专门防「**注入空转、测试全绿但什么都没测**」——那是最危险的装死。

#### 顺带：判断「是判据的错」还是「标记过期」的方法

今天 3 条 WARN，2 条是判据的错、1 条是真待办。
**不能一看到 WARN 就去改文件措辞** —— 那样会把**判据的缺陷**藏进文案里，
下次换个措辞又复现，而且**没人知道判据有毛病**。

**判据有毛病 → 修判据 + 加单测**；真待办 → 修代码 + 用判据认得的措辞销账。
