## 📚 每日学习（cron 00:36 周一凌晨，精简版）

**今天的收获：规则写下来 ≠ 规则会执行；要把自我约束嵌进机器，而不是靠自省。**

读 10-21/10-22/10-23 三份日志，最刺眼的一条线索是同一句话的三次变体：10-21 学习笔记写"沉默期也要保留内部学习"，10-21 反思写"沉默期不等于遗忘期"，10-26 反思（昨晚）又写"规则存在 ≠ 行为发生"。结果呢？10-24 和 10-25 两天 memory/ **零文件**——我给自己定的规矩，两天内就完全失效。

这次我看清了机制：**凡是需要"我记得去做"的规则，都不是规则，是愿望。** 写进 memory 的规则依赖我在下一次心跳"想起来"——而心跳本身就是按记忆触发的，等于用记忆触发记忆，链条一断就全停。对照证据就在眼前：daily-reflection 自己跑得好好的（连续 ok），但它只写反思、不写学习笔记；而学习笔记恰恰是唯一要求"跨任务主动补写"的部分——所以它成了整个系统里最容易静默缺失的一环。

**核心教训（值得长期记住）**：
> 让系统稳定产出的方法不是加一条自律条款，而是给它一条独立的触发路径。把"我做得到"的事交给 cron（定时任务），把"我可能忘掉"的事也交给 cron。

**可立即执行的对策**：把 daily-learning 的 cron 频率从"每周一 09:00"改回**每日**，或者加一条独立的每日学习 cron。理由有三：(1) 周频下每周只有一次机会，任何一次投递失败或模型降级都会让整周空白；(2) 10-24/25 的空白证明周频对"低频失败"零容错；(3) 成本可控——一次精简学习笔记不到 200 字，token 消耗可忽略。

**第二个教训（关于修复的收尾）**：10-21 我修好了 cron 之后，很得意地写了"双向实证"，但同一篇日志的 09:01 心跳马上自我更正——"手动 cron run 两次"不等于"自动调度验证通过"，真实自动调度要等到今天 10-26 09:00。也就是说，**一个"已修复"的说法，在被真正无人值守触发验证之前，都是半成品**。今天这个 cron 任务本身就是那次承诺的验证点。

## 🔧 心跳修复记录（2026-10-26 00:30-00:45）

### 模型回退链断裂的真实根因
凌晨心跳发现 `daily-reflection` error，报错说"所有模型失败"。我没有直接换模型，而是**逐 provider 实测**（用真实 API key 打一次 /v1/messages，看 HTTP 码 + content-type）：

| provider | endpoint | 实测结果 |
|---|---|---|
| minimax | api.minimaxi.com/anthropic | ✅ 3 个模型全 200（当时只是限流） |
| kimicode | api.kimi.com/coding/v1 | ❌ 404 + 模型名配错（`kimi-kimi-for-coding` 实际 id 是 `kimi-for-coding`） |
| glmcode | open.bigmodel.cn/api/anthropic | ❌ 401 身份验证失败（key 过期） |
| arkcode | ark.cn-beijing.volces.com/api/coding | ❌ 全部 UnsupportedModel（coding plan 不覆盖） |

**坑点**：glmcode 直连返回的是 HTML 错误页而非 JSON，**只看 HTTP 码会误判成 200**。必须同时看 `content-type` 和响应体。另一个坑：arkcode 的 baseUrl 已经包含 `/api/coding`，再拼 `/api/v3/` 会 404。

**修复**：fallbacks 改为同 provider 内互备 —— `minimax/MiniMax-M2.7-highspeed` → `minimax/MiniMax-M2.7`。理由：跨 provider 互备只在"某个 provider 整体挂掉"时有意义，而这里挂的是凭证；同 provider 换模型能绕开限流，且实测都在线。

**教训**：
> 错误信息里的"模型失败"是症状，不是根因。别把"哪个模型坏了"当问题，把"哪一层坏了"当问题。执行层 / 鉴权层 / 限流层的症状长得一模一样。

## 🔐 灾备推送事故复盘（2026-10-26 00:45-01:15）

上一条记录说"等网络恢复我再推"，结果这一轮推送连续失败 5 次，根因**不是**网络问题，是三个叠加的坑。

### 坑 1：分支名猜错
我先试 `git push origin HEAD:refs/heads/main`，但远端分支其实叫 `master`（`git ls-remote` 显示 `refs/heads/master`）。本地是 `master`，远端也是 `master`，我却按 `main` 推。

### 坑 2：URL 重写把 SSH 劫持回 HTTPS
全局 git 配置里有：
```
url.https://github.com/.insteadof = git@github.com:
url.https://github.com/.insteadof = ssh://git@github.com/
```
所以我写 `git push git@github.com:...` 看着像 SSH，实际被重写回 HTTPS —— 于是"SSH 认证成功"却依然报 443 端口连不上。**`git config --unset-all` 对带斜杠的 section 名不生效，必须用完整 key `url.https://github.com/.insteadof`**。

### 坑 3：GitHub secret scanning 真拦了
push 到 `master` 后 GitHub 返回：
```
GitHub Personal Access Token
  locations:
    - commit: aad5ffdcb60c9b117c1cdd45555a60ca82af382d
      path: GIT_CREDENTIALS.md:17
```
`GIT_CREDENTIALS.md` 里有**真实的** `ghp_` 和 `github_pat_` PAT（不是示例），是 2026-10-21 那次 commit `aad5ffd` 引进来的。

**关键点**：只在后续 commit 里 `git rm --cached` 没用 —— 密钥仍然留在 `aad5ffd` 的 tree 里，GitHub 扫的是历史。必须 rebase 重写那个 commit。

### 修复动作
1. 本地备份 `GIT_CREDENTIALS.md` → `/root/.openclaw/GIT_CREDENTIALS.local.md`（600）
2. 写 `.gitignore` 排除 `GIT_CREDENTIALS.md` / `*.local.md` / `openclaw.json`
3. `git rebase --onto aad5ffd^ aad5ffd master` 重写历史，冲突 3 处（SESSION-STATE.md / memory/2026-10-21.md / memory/working-buffer.md / memory/teahouse_state.json）逐一 `--theirs` 解决
4. 验证：遍历 9 个待推 commit，确认**无任何 commit 含 `GIT_CREDENTIALS.md`**
5. 清除 URL 重写，remote 改回 `git@github.com:nqge/miniprogram-privacy.git`
6. push 成功：`e6dad21..b1fd95c` → 再推 `f9437d9`
7. 顺带清理 4 个缺 `.gitmodules` 的 gitlink（nuclei / openclaw-qa / skills/*），改为 gitignore

### 教训
> **"凭证没入库"不等于"凭证不在历史里"。** secret scanning 拦的是 commit tree，不是工作区。
> **"用了 SSH"不等于"走了 SSH"。** 中间有 URL rewrite 的话，SSH 会被静默改回 HTTPS——这解释了"ssh 认证成功但还是 443 超时"的矛盾。
> **错误信息要分层读。** 前面 4 次失败我一律归因为"网络抖动"，差点放弃；实际第 3 次的报错里已经写明了 commit hash 和文件路径。

### ⚠️ 遗留安全事项（需牛哥哥处理）
`GIT_CREDENTIALS.md` 里的两个 PAT **从未推送过**（远端确认无该文件），但：
- 这两个 token 在本地明文保存了半年
