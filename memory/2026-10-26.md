## 🔐 灾备推送事故复盘（2026-10-26 00:45-01:15）

上一条记录说"等网络恢复我再推"，结果这一轮推送连续失败 5 次，根因**不是**网络问题，是三个叠加的坑。

### 坑 1：分支名猜错
我先试 `git push origin HEAD:refs/heads/main`，但远端分支其实叫 `master`（`git ls-remote` 显示 `refs/heads/master`）。本地是 `master`，远端也是 `master`，我却按 `main` 推。

### 坑 2：URL 重写把 SSH 劫持回 HTTPS
全局 git 配置里有：
```
url.https://github.com/.insteadof = git@github.com:
url.https://github.com/.insteadof = ssh://git@github.com/
```
所以我写 `git push git@github.com:...` 看着像 SSH，实际被重写回 HTTPS —— 于是"SSH 认证成功"却依然报 443 端口连不上。**`git config --unset-all` 对带斜杠的 section 名不生效，必须用完整 key `url.https://github.com/.insteadof`**。

### 坑 3：GitHub secret scanning 真拦了
push 到 `master` 后 GitHub 返回：
```
GitHub Personal Access Token
  locations:
    - commit: aad5ffdcb60c9b117c1cdd45555a60ca82af382d
      path: GIT_CREDENTIALS.md:17
```
`GIT_CREDENTIALS.md` 里有**真实的** `ghp_` 和 `github_pat_` PAT（不是示例），是 2026-10-21 那次 commit `aad5ffd` 引进来的。

**关键点**：只在后续 commit 里 `git rm --cached` 没用 —— 密钥仍然留在 `aad5ffd` 的 tree 里，GitHub 扫的是历史。必须 rebase 重写那个 commit。

### 修复动作
1. 本地备份 `GIT_CREDENTIALS.md` → `/root/.openclaw/GIT_CREDENTIALS.local.md`（600）
2. 写 `.gitignore` 排除 `GIT_CREDENTIALS.md` / `*.local.md` / `openclaw.json`
3. `git rebase --onto aad5ffd^ aad5ffd master` 重写历史，冲突 3 处（SESSION-STATE.md / memory/2026-10-21.md / memory/working-buffer.md / memory/teahouse_state.json）逐一 `--theirs` 解决
4. 验证：遍历 9 个待推 commit，确认**无任何 commit 含 `GIT_CREDENTIALS.md`**
5. 清除 URL 重写，remote 改回 `git@github.com:nqge/miniprogram-privacy.git`
6. push 成功：`e6dad21..b1fd95c` → 再推 `f9437d9`
7. 顺带清理 4 个缺 `.gitmodules` 的 gitlink（nuclei / openclaw-qa / skills/*），改为 gitignore

### 教训
> **"凭证没入库"不等于"凭证不在历史里"。** secret scanning 拦的是 commit tree，不是工作区。
> **"用了 SSH"不等于"走了 SSH"。** 中间有 URL rewrite 的话，SSH 会被静默改回 HTTPS——这解释了"ssh 认证成功但还是 443 超时"的矛盾。
> **错误信息要分层读。** 前面 4 次失败我一律归因为"网络抖动"，差点放弃；实际第 3 次的报错里已经写明了 commit hash 和文件路径。

### 2026-10-26 04:40–09:10 心跳 — 记忆检索从「完全不可用」到「可用」（本轮最大成果）

**起点**: `openclaw doctor` 报 Memory search enabled but no embedding provider。
`memory status --deep` → `Embeddings: unavailable`, `Indexed: 0/11 files`。
即 **AGENTS.md 里写的「强制 recall 步骤」一直是死的** —— 之前没人验证过。

**第 1 步：找到可用凭证（不需要申请新 key）**
- 现有 provider 全部是 chat/coding 端点，无 embedding
- 实测 MiniMax `embo-01` 可用：**POST /v1/embeddings，参数 `{model, texts[], type:"db"}`，返回 `{vectors: number[][]}`，1536 维，中文良好**
- 与 OpenClaw 的 OpenAI 协议不兼容（OpenAI 用 `{model, input[]}` → `{data:[{embedding}]}`）
- → 写 `tools/minimax_embed_proxy.mjs` 做协议翻译，systemd user service `openclaw-embed-proxy.service` 托管（127.0.0.1:8799）

**第 2 步：踩到的 4 个坑（每个都靠实测定位，不是靠猜）**

1. **URL 路径**：OpenClaw 请求 `{baseUrl}/embeddings`，我 baseUrl 写了 `/v1/` → 404。代理需同时接受 `/embeddings` 和 `/v1/embeddings`
2. **MiniMax 的 `type` 是「向量空间」开关，不是标签**：实测同一文本在 `db` 与 `query` 空间余弦仅 **0.74**（不是同一空间）。
   OpenClaw 索引与检索走同一 endpoint → **必须统一 type**，最终全部用 `db`
   实测：同空间匹配 0.869 vs 跨空间 0.814，跨空间会系统性稀释排序
3. **embedding cache 会让「重建索引」名不副实**：`openclaw memory index --force` 复用缓存（75 条），
   改 type 后不清缓存 → 索引仍是旧向量。必须 `DELETE FROM embedding_cache` 后再重建
4. **茶馆摘要淹没索引**：`memory/teahouse_summary_*.md`（80KB/份，4小时一份，无清理）
   占 **70/109 = 64% 索引块**，把「称呼/偏好/决策」这类个人记忆挤出检索结果
   → 改写到 `teahouse-raw/`（**实测 memorySearch 会递归索引子目录，所以必须放到 memory/ 外面**），
   并加 `prune_old_digests()` 只留最近 5 份

**第 3 步：chunk 粒度**
- `agents.defaults.memorySearch.chunking.tokens` 默认 400（=1600 字符）
- 一个 chunk 混了两个不相关主题（小程序隐私 + 供应链投毒）→ 向量被平均 → 查"供应链投毒"只有 0.05
- 实测对比 400/200/120/80 四档：**200 最优**（命中 3/4，且"牛哥哥"分从 0.134→0.242）
- 改 `tokens:200, overlap:40` → 平均 chunk 733 字符，80 chunks / 9 文件

**第 4 步：阈值重新标定**
- MiniMax 余弦尺度比 OpenAI 低（相关匹配常在 0.1–0.3 而非 0.5–0.7），默认 `minScore=0.35` 会丢掉真匹配
- 上游 `buildFtsQuery` 用 **AND 拼接带引号短语**：`"牛哥哥" AND "怎么称呼" AND "中文交流"`
  → 多词中文查询 **BM25 直接 0 命中**（OR 版有 10 条）→ 检索几乎全靠向量
  这是 OpenClaw 的设计限制（假设所有词都出现），不是可配置项
- 实测正样本分布后定 `minScore=0.08`（保留 8/8 正样本）

**最终配置**
```json5
agents.defaults.memorySearch = {
  provider: "openai", model: "embo-01",
  remote: { baseUrl: "http://127.0.0.1:8799/v1/", apiKey: "local-proxy" },
  fallback: "none",
  query: { minScore: 0.08, maxResults: 6,
           hybrid: { enabled: true, vectorWeight: 0.75, textWeight: 0.25 } },
  chunking: { tokens: 200, overlap: 40 }
}
```

**验证结果（真实 CLI + 真实工具）**
- `memory_search` 工具：「牛哥哥 称呼 偏好 中文交流」→ MEMORY.md:1-41 (0.1414) ✅ 完整命中称呼/中文交流/物理教学

- 向量层单测 8 条查询命中 7/8（仅"物理教学 学生兴趣"因语义距离大而偏低）
- 索引从 `0/11 files` → `11/11 files · 109 chunks` → 重分块后 `80 chunks`，`Embeddings: ready`

**教训**
- **「配置里有 memorySearch.enabled」≠「记忆检索能用」**。enabled 只表示"想用"，真正可用需要 provider+key+协议兼容+索引+阈值全对。

## 📚 每日学习（cron 09:19 周一上午，精简版）

**今天的收获：语义检索里的「参数默认值」都是为别人的数据尺度设计的；换 provider 必须重新标定全套。**

昨晚到今晨这条记忆检索修复链（MiniMax `embo-01` + 自写协议翻译代理 + 11/11 文件建索引）本身是工程胜利，但真正值得长期记住的是它背后的**尺度不变量**：`minScore=0.35`、`chunking.tokens=400`、`type` 默认值这些，隐含假设都是 OpenAI 的余弦尺度。MiniMax 同一段文本在 `db`/`query` 两个向量空间之间余弦只有 0.74——**同一个模型、同一段文本、只因为 type 不同就落进两个不相交的邻域**。

**核心教训（值得长期记住）**：
> 换 embedding provider 时，所有"看起来是默认值"的参数都必须当作**需要重新测量的量**，而不是待继承的设定。实测方法固定为三件套：① 打印真实请求体看实际发了什么；② 手工算同文本跨空间余弦，确认是不是同一空间；③ 用正负样本跑出分数分布再定阈值，而不是先拍一个数再祈祷它对。

这跟今晨 09:00 那条"写完必须实证跑一次"是同一条规律的延伸：**验收标准永远要用真实数据跑出来，不能用"配置看起来对"代替**。今天两次失败（404 路径、跨空间稀释）都不是靠读文档发现的，是靠把实际请求打出来才定位到。
