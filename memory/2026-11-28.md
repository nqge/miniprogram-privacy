## 10:05 心跳 —— E92：改了判据就要重算历史结论

**背景**：E91（09:00 daily-learning）诊断出「额度耗尽结论是被标签推出来的，不是被证据推出来的」，
但**光诊断不重算，错误结论会一直挂着**。今早 07:00 巡检仍在报：
> ⏳ 最近 7 天里有 3 天额度耗尽（11-22、11-23、11-27）—— 需要牛哥哥充值

**落地**：改判据真身 `scripts/check_quota_sustained.py`，加**证据分级**：

| 级别 | 判据 | 计入确认耗尽？ |
|---|---|---|
| L3 确认耗尽 | Token Plan 上限措辞 **且** 含 `request_id` | ✅ 是 |
| L2 疑似耗尽 | 有额度措辞但无 request_id | ❌ 分开计数 |
| L1 未证实 | 「额度特征命中」等字符串匹配 | ❌ 分开计数 |
| L0 矛盾信号 | 「没有任何可用 provider」（与实测矛盾） | ❌ 单独归类并 WARN |

**实测前后**：巡检 `等你 2 → 1` —— 那条充值请求**消失了**。
**不是故障消失了，是结论本来就不成立。**

**逐条核对真实数据**（防止只改了汇总数字、分级本身错了）：
- L3 = 2 次，**全在 11-27 同一天** → 确认耗尽 **1 天**
- L1 = 11 次，散在 11-14～11-23 → 7 天窗口内 **2 天**
- L0 = 13 次，**全在 10-30～11-09** → 窗口外（**这说明不能只看窗口内数据，
  否则会误以为 L0 从未出现过而删掉那套分级逻辑**）

**踩到的三个坑**：
1. **分级顺序**：L1 的「额度特征命中」含「额度」二字，先被 L2 的 `QUOTA_MARKERS` 命中 → 归错级。
   → **L1 必须先于 L2 判**。
2. **形态不一致**：分类器 `m in d` 对 tuple 不生效，而真实落盘是**拼成一段字符串**，
   我自测里却传了 tuple → 判据得**同时容忍两种形态**。
3. **测试写错 ≠ 判据写错**：L0 那条我用了 3 个不同日期却断言「1 天」——
   先分清是测试错还是判据错，再动手。
