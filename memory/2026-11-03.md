### 更正 5：小节长度判据的**正则盲区** —— 注释是对的，代码是错的

**症状**：`trim_learning_section.py --check memory/2026-11-03.md` 报
「⚠️ 偏短 19 汉字（约束 100-400）」，但那篇反思小节我明明写得很长。

**根因**：终止符 `(?=\n#{1,6} |\Z)` 会在**第一个 `###` 子标题**处截断。
而「每日反思（三问）」天然就是三段式：
```
## 🪞 每日反思（<括号里是什么文字不重要>）
### 1. 今天是否浪费了用户的时间？
### 2. 在哪个决策点提供了关键异议？
### 3. 从用户的决策偏好中学到了什么？
```
→ 只量到第一个 `###` 之前的引言块 = **19 汉字**（真实 844）
→ 报「偏短」，而实际**超长一倍** → 这条断言在反思小节上基本没生效。

**最扎眼的地方**：healthcheck 里那条断言的**注释**写的是
「小节在**下一个任意级标题**(## 或 ###)处结束 —— `###` 是 `##` 的子节,
本来就属于上一个 `##`」
→ **注释描述的意图和代码实现完全相反**，而**注释才是对的**。
注释写了正确意图，代码没跟上，而且没人发现 —— 因为「报偏短」看起来像个小问题。

**修法：双终止符**
| 终止符 | 挡什么 |
|---|---|
| `^## ` | 下一个同级小节 |
| `^### ` + 日期 | 「另一个顶层记录」伪装的子标题 |

- 不带日期的 `### 1. / ### 📌 待牛哥哥决策` → 算**本节内部**，保留
- 带日期的 `### 2026-10-27 07:09 …` → 是**新记录**，截断
  （10-27 那种「学习小节下挂了 30 多条 ### 心跳记录」必须在这里断，
    否则把别人的内容算进来 → 报 12095 汉字）

**顺带修的两个**：
1. `gen_healthcheck_instruction.py` 的组名正则 `[A-Z]` → `[A-Z][0-9]*`
   → 【W2】【W3】原本被漏掉，「巡检说明与脚本同步(26 组)」报的 26
   实际是 **28** → 又一次「单点快照当全貌」的同类错误
2. 新增【W3】组 + `scripts/test_section_length_checker.py`（10 个用例），
   核心是**故障注入**：证明旧正则量到 0、新正则量到 939

**真实违规**：修好判据后，11-03 的反思小节暴露为 **844 汉字（上限 400）**
→ 确实超长 → 已精简到 **393** ✅（保留了三个问题的实质，压掉了
「待牛哥哥决策/今日自修/一句话自省」三个**任务没要求的**附加小节）

**教训**：
> **注释里的意图和代码的实现可以长期背离，而没人发现。**
> 因为「报偏短」看起来像个小问题，不值得追。
> → **判据的注释和实现不一致时，要有一条测试把两者对齐**——
>   不然注释就只是「写了个愿望」。

**另一个教训**：
> **同一条正则被两个地方复制使用（脚本 + 巡检），就必然有两处盲区。**
> → 修的时候要一起修；更根本的是**应该 import 同一份真身**，

### 更正 3：巡检汇总行的 FAIL 计数**混进了「等你」的长期项** → 假警报

**症状**：巡检跑完打印
```
 结果: PASS=73  FAIL=1  WARN=6
 ✅ 没有可处理的失败(1 项长期项在等你处理)。
```
**自相矛盾**：计数说 FAIL=1，下面说没有可处理的失败 —— 而且退出码是 1。

**根因**：`bad()` 对每一项都 `FAIL+=1`，但如果文案命中 `WAITING_PATTERNS`
就打印成「⏳ 等你」而不是「❌ FAIL」。→ **汇总行把「长期项」也算成了 FAIL**。

**为什么有害**：只读计数行或只看退出码的人/脚本，会得到**假警报**；
退出码 1 还会让 systemd 判红（虽然 `SuccessExitStatus=1` 兜住了噪音）。
→ 这是 **E47「状态字段 ≠ 实际结论」换个马甲**：计数行是给人看的结论，
退出码是给脚本看的信号，两者都该表达**可处理的故障数**，而不是**所有非 PASS 项数**。

**修法**：把「可处理失败」和「等牛哥哥的长期项」**拆开计数、拆开显示**：
- 汇总行 → `PASS=73  FAIL=0  WARN=6  等你=1（长期项，不计入 FAIL）`
- 退出码 → 按**可处理失败数**决定（长期项不该让 systemd 判红）

**教训**：一个长期存在、每天都在报、但没人细看的告警，
**它的危害不是「吵」，是「真故障来了的时候被淹没在假故障里」**。

### 更正 2：巡检判据有盲区 —— `error` 次数会被完全吞掉

**bug 位置**：`scripts/check_cron_delivery.py`
**症状**：daily-learning 有 **7 次 error**（含 10-30/10-31/11-01 **连续 3 天全挂**），
巡检却报「daily-learning 投递正常（delivered=True）」，**只字未提那 3 天中断**。

**根因**：error 统计被写在 `else:` 分支里（`undelivered` 为空时才走到）。
只要历史上存在任何一次「ok 但没投递」，就**永远走不到 else** → error 次数被吞掉。
daily-learning 恰好有 3 次 ok-but-not-delivered（10-26 09:00、10-26 00:36、10-21 04:29）→ 触发这个盲区。

**修法**：error 统计与 undelivered 统计**正交**，两边都要无条件报告；
新增 `_max_consecutive_errors()` 维度 —— 连续 N 次失败 ≠ 零散 N 次失败
（前者 = 静默中断 N 天，用户完全无感）。

**教训**（这条比 bug 本身值钱）：
> **「最近一次是 ok」不能代表「最近一直 ok」。**
> lastRunStatus 是**单点快照**，用它判断健康度 = 用一个样本推断趋势。
> 我给巡检写了 26 组断言，却从没断言过「**连续失败次数**」——
> 而这恰恰是抓「长期静默停摆」唯一有效的指标。

## 📚 每日学习（2026-11-03）
> 本条讲：**长期项混进 FAIL 计数，会把真故障淹在假警报里**
