### 更正 3：巡检汇总行的 FAIL 计数**混进了「等你」的长期项** → 假警报

**症状**：巡检跑完打印
```
 结果: PASS=73  FAIL=1  WARN=6
 ✅ 没有可处理的失败(1 项长期项在等你处理)。
```
**自相矛盾**：计数说 FAIL=1，下面说没有可处理的失败 —— 而且退出码是 1。

**根因**：`bad()` 对每一项都 `FAIL+=1`，但如果文案命中 `WAITING_PATTERNS`
就打印成「⏳ 等你」而不是「❌ FAIL」。→ **汇总行把「长期项」也算成了 FAIL**。

**为什么有害**：只读计数行或只看退出码的人/脚本，会得到**假警报**；
退出码 1 还会让 systemd 判红（虽然 `SuccessExitStatus=1` 兜住了噪音）。
→ 这是 **E47「状态字段 ≠ 实际结论」换个马甲**：计数行是给人看的结论，
退出码是给脚本看的信号，两者都该表达**可处理的故障数**，而不是**所有非 PASS 项数**。

**修法**：把「可处理失败」和「等牛哥哥的长期项」**拆开计数、拆开显示**：
- 汇总行 → `PASS=73  FAIL=0  WARN=6  等你=1（长期项，不计入 FAIL）`
- 退出码 → 按**可处理失败数**决定（长期项不该让 systemd 判红）

**教训**：一个长期存在、每天都在报、但没人细看的告警，
**它的危害不是「吵」，是「真故障来了的时候被淹没在假故障里」**。

### 更正 2：巡检判据有盲区 —— `error` 次数会被完全吞掉

**bug 位置**：`scripts/check_cron_delivery.py`
**症状**：daily-learning 有 **7 次 error**（含 10-30/10-31/11-01 **连续 3 天全挂**），
巡检却报「daily-learning 投递正常（delivered=True）」，**只字未提那 3 天中断**。

**根因**：error 统计被写在 `else:` 分支里（`undelivered` 为空时才走到）。
只要历史上存在任何一次「ok 但没投递」，就**永远走不到 else** → error 次数被吞掉。
daily-learning 恰好有 3 次 ok-but-not-delivered（10-26 09:00、10-26 00:36、10-21 04:29）→ 触发这个盲区。

**修法**：error 统计与 undelivered 统计**正交**，两边都要无条件报告；
新增 `_max_consecutive_errors()` 维度 —— 连续 N 次失败 ≠ 零散 N 次失败
（前者 = 静默中断 N 天，用户完全无感）。

**教训**（这条比 bug 本身值钱）：
> **「最近一次是 ok」不能代表「最近一直 ok」。**
> lastRunStatus 是**单点快照**，用它判断健康度 = 用一个样本推断趋势。
> 我给巡检写了 26 组断言，却从没断言过「**连续失败次数**」——
> 而这恰恰是抓「长期静默停摆」唯一有效的指标。
