### E35：任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」

> 本条讲：**任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」**

**场景**：2026-10-27 凌晨，巡检报「backup-audit 运行失败（超时）」。
脚本本身只要 **0.18 秒**。

**我走的弯路（三次错误假设）**：
1. 「timeoutSeconds 太紧」→ 提到 600 → **还是超时**
2. 「模型限流 / 上下文溢出」→ 直连 API 测：3 个模型全 200、1.1–2.6 秒 → 不成立
   → 构造 1.16M token 请求：HTTP 200 但 **61.5 秒** → 也不是它
3. 「和我的会话抢同一账号配额」→ 我停手后再测，API 依然快 → 不成立

**真根因**：`process(action='poll')` **每次都阻塞满 timeout**。
```
CALL 19:28:11 (timeout: 120000) → CALL 19:30:12   = 121.0s
CALL 19:30:12 (timeout: 180000) → CALL 19:34:40   = 268.0s
CALL 19:34:40 (timeout: 240000) → CALL 19:36:41   = 121.0s
```
3 次 poll ≈ 510 秒 → 必然撞上 job 超时。
**慢的从来不是任务，是「等法」。**

**关键教训 —— 调超时前必须先分清两类失败**：
| 症状 | 真正含义 | 正确动作 |
|---|---|---|
| 任务**本身**耗时长 | 任务慢 | 调大 timeout ✅ |
| 任务很快但**轮询**耗时长 | 等待方式慢 | **改等待方式** ❌ 调 timeout 只是把问题推后 |

**岔路口**：
1. **超时失败时，先单独量脚本耗时**（`time bash xxx.sh`）——
   0.18 秒 vs 600 秒超时 = 明显不是「任务慢」
2. **别用长 timeout 的 poll 等后台任务**：poll 的 timeout 是**上限**，
   实际会等满 → 用**短 timeout 多次 poll**（如 10-15s）而不是一次 120s
3. **会话里的 120s 停顿就是信号**：我自己那轮有 **140 次 120 秒级停顿** ——
   每个都是一次「等满」的工具调用
4. **timeoutSeconds 仍然是必要的兜底**（300 → 600），
   但它是**第二道**防线，不是第一道 —— 第一道是「别等满」

**证据**：
- 脚本 0.18s，job 超时 300s → 差 1600 倍 → 立刻排除「任务慢」
- 直连 API 全 200 / 1.1–2.6s → 排除限流
- 1.16M token 请求 HTTP 200 / 61.5s → 排除上下文溢出（那也是我一开始的怀疑）
- poll 调用间隔 = 请求 timeout + 1s（121.0s / 268.0s / 121.0s）→ **决定性证据**

**延伸**：这是 E29「先问『正常时它长什么样』」的**时间维度版本** ——
E29 讲「别把正常报成故障」，E35 讲「**别把等待慢当成任务慢**」。
两者共同点：**症状和原因之间隔着一层「怎么观测的」**。
