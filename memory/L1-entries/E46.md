### E46：慢的第三个层次 —— 有时候根本不该跑那个任务

> 本条讲：**慢的第三个层次 —— 有时候根本不该跑那个任务**

**场景**：2026-10-27 11:05。E35 之后我加了「短 poll」提醒、又加了【V】断言
检测长 poll。V 报出 26 次长 poll，我第一反应是「poll timeout 还是太长」。

**但把【V】改成按 cron 任务维度报告后**，一眼看出：
```
daily-learning×12, backup-audit×9, healthcheck×5
```
顺着查下去 —— **真根因根本不是 poll**：

- `daily-learning` 09:00 那次，**447s（171+78+120+78）全在等 `healthcheck.sh`**
- `backup-audit` 也有 **3 次 120s 的 poll**，等的是同一个脚本
- **而 `daily-learning` 的指令里根本没要求它跑巡检** —— 它是**自己跑去跑的**

**三层递进**（这一串是今晚最值钱的东西）：
| 层 | 命题 | 出处 |
|---|---|---|
| 1 | 慢的是**等法**不是任务（poll 会等满 timeout） | E35 |
| 2 | **指令说了也不照做**（自己写的规则自己也忘） | E41 |
| 3 | **有时候根本不该跑那个任务** | E46 ← 本条 |

**第 3 层为什么最值钱**：
- 第 1 层 → 改等法（poll timeout 调小）
- 第 2 层 → 加规则和检测
- 第 3 层 → **少做** —— 那 447s **根本不该存在**
  → 每日巡检是 07:00 那个 cron 的职责，学习任务顺手也跑一遍 =
    白白多等 + 挤占 2 核 CPU（实测 8 并发零加速、18 个慢 3 倍）

**岔路口**：
1. **看到「等很久」时，先问「这个等待有必要吗」**，再问「怎么等得快」
   —— 顺序反了就会一直在优化一个不该存在的东西
2. **断言要按「行动单元」分组**，不按会话/总量：
   - 按会话 → 「0d127a42×460」→ 不知道该改什么
   - 按 cron 任务 → 「daily-learning×12」→ 立刻知道动哪里
3. 修的时候要区分**两个不同的问题**：
   - 「怎么等」（技术）→ 短 poll / sessions_spawn
   - 「该不该等」（范围）→ **这条任务不需要跑那个脚本**
   → 后者收益大得多

**证据**:
- daily-learning 09:00 实测 772.1s，其中 447s 在等 healthcheck.sh ✅
- backup-audit 3 次 120s poll 同样在等它 ✅
- 3 条 cron 指令已加【别跑不必要的巡检】✅

**延伸**：这是 E7「修完根因后监控还在量修复前的那次测量」的**行为侧版本** ——
E7 讲「别量已经不存在的问题」，E46 讲「**别做不该存在的工作**」。
