### E54：瓶颈在「进程启动」时，堆并发只会更慢 —— 先 profile，再优化

> 本条讲：**瓶颈在「进程启动」时，堆并发只会更慢 —— 先 profile，再优化**

**发现时间**: 2026-10-29 00:3x

## 现象

`healthcheck.sh` 耗时在无修改地爬升（207s → 298s → 378s），逼近 600s 超时。
我先认定瓶颈是「循环里调 `openclaw cron runs`」（21s），改完发现**只快了 6%**。

## 真正的瓶颈

profile 25 个 python 块之后：

```
verify_l1_retrieval.py   77 秒   ← 占体检 80%
```

它要做 **17 次真实检索**，每次：

```
openclaw memory search  →  4.85 秒/次
其中 embedding 请求      →  0.36 秒
                            ─────────
差值 4.5 秒 = Node 进程启动 + 插件注册
```

**要优化的是「起进程」，不是「发请求」。**

## 试过并否决的方案

**并行 4 路**：

| 方式 | 17 次查询耗时 |
|---|---|
| 串行 | 78.4s |
| 并行 4 路 | **86.9s（更慢）** |

2 核机上并发只抢 CPU —— 这与 TOOLS.md 里既有的
「8 并发零加速、18 个慢 3 倍」记录**一致**。

> **并发只在「等待外部 I/O」时划算。**
> 瓶颈若是 CPU 或进程启动开销，并行 = 负优化。

## 落地方案：一次启动，复用同一个运行时

`openclaw` 的 memory search manager 可以**在同一个 Node 进程里复用**，
不必走 CLI（CLI 每次都重新拉起进程）：

```
17 次 CLI 调用  78s  →  一次进程内批量检索  8.3s   （9.4×）
```

## 四个坑（都实测踩过）

1. **打包后 export 名被压成单字母** —— `n`/`r`/`t` 里哪个是
   `getMemorySearchManager`？**不能靠名字猜**，只能挨个调、看返回对象有没有 `.search`
2. **`new URL('file://' + 绝对路径)`** 会把路径当 host → 报
   "Cannot find package 'undefined'"（和真正的错误毫无关系）
3. **自己写的 URL helper 返回字符串时，别再 `.href`** —— 字符串的 `.href` 是 `undefined`
   → `import(undefined)` → **同一个诡异报错**（最迷惑的一个）
4. **遍历导入 dist 下所有 .js 来找导出** → 触发 CLI 副作用 + **dump core**
   → 只能按文件名精确匹配导入

## 两条不能省的验证

**① 等价性自检**（优化后必须与原路径结果一致，否则断言装死）：

```
node scripts/memory_batch_search.mjs --self-test
→ PASS batch 与 CLI 一致（6 条）   # 逐条比对 path + score
```

**② 故障注入**（优化路径挂掉时，必须自动回落且结果不变）：

```bash
mv scripts/memory_batch_search.mjs /tmp/     # 移走优化脚本
python3 scripts/verify_l1_retrieval.py        # 应自动回落逐条 CLI
→ 结果仍是 52/52，耗时 91s（回落路径），没有静默失效 ✅
```

> **只测「快路径能跑」是不够的 —— 要测「快路径挂掉时会不会静默给错答案」。**

## 关联

- 教训：**先 profile 再优化** —— 我自己在这条上犯了半次（以为 21s 是大头）
