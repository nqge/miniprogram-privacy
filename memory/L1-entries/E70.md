### E70：复跑一次再动手修，巡检 FAIL 是快照不是状态
> 本条讲：**复跑一次再动手修，巡检 FAIL 是快照不是状态**

**核心断言**：巡检报告里的 FAIL 只证明「**在某个时刻**探测失败」，
不证明「**现在**功能是死的」。**会自愈的故障**（额度耗尽 / 限流 / 余额不足 /
上游抖动）报出来的 FAIL 和真故障**长得一模一样** —— 都只是「❌ FAIL」一行。
**区别只有时间**，而报告**不记录时间维度**。
**对策：巡检报出 FAIL 后，先原样复跑一次再动手修** ——
复跑还红 = 真故障；复跑变绿 = 波动。

## 场景

2026-11-11 07:00 巡检：

```
【C】 ❌ FAIL  Embeddings: unavailable - 记忆检索不可用
【H】 ❌ FAIL  记忆检索执行异常
【A】 ⏳ 等你  嵌入上游额度耗尽（HTTP 502）- insufficient balance
```

我 10:48 原样复跑同一份巡检 → **PASS=75 FAIL=0 等你=3**。

**两次之间什么都没改**：没改配置、没重启服务、没动任何代码。
唯一的差别是**时间**：上游额度在 07:00 那一刻是空的，在 10:48 又有了。

如果 07:00 看到 FAIL 就开始「修」——改代理、改配置、改判据 ——
那是在修一个**已经自己好了的东西**，而且每改一次就多引入一个
「改坏了」的机会。

## 陷阱

### 陷阱一：把「额度类」错误当成「可处理」

07:00 的报告把两个 FAIL 放进了「【可处理 — 现在就该修】」，
而额度耗尽在同一份报告里是「等你」。**同一件事（额度）被分到了两个档**，
原因是：额度信号只出现在**某一行**的文本里，分类器按**行**匹配，
没匹配上的就落进「可处理」。

→ 这和 E69 是同一个病根的变种：
**E69** 是探针端点撒谎（对象在骗你），
**E70** 是报告的时间维度缺失（快照被当成状态）。

### 陷阱二：FAIL 数量会制造「多问题」的错觉

07:00 报 FAIL=2（C 和 H），看起来像**两个独立的故障**。
实际上它们是**同一个根因**（额度）沿两条路径各投影了一次 ——
C 走 `memory status --deep` 的 Embeddings 字段，H 走端到端检索。
**根因只有一个，投影有两个。**

→ 修的时候按**根因**修，不要按 **FAIL 条数**修 ——
否则会出现「修好了 C，H 还在」的错觉，然后误判成「我修的方向不对」。

## 岔路口

```
看到巡检 FAIL
    │
    ├─ 报错里有「额度 / 限流 / 余额 / insufficient balance / rate_limit」
    │       → 【别改代码】先复跑一次
    │            ├─ 复跑还红  → 真故障，去查（可能上游确实在挂）
    │            └─ 复跑变绿  → 波动，记一笔「窗口期」，不修
    │
    └─ 报错里没有额度特征
            → 按真故障处理
```

**「复跑一次」不是敷衍，是最便宜的一步**：
它花一次巡检的时间（约 60~100s），
却能区分「要动手改」和「不用动手改」这两个**代价差几个数量级**的决定。

## 对策

1. **巡检报出 FAIL 后，先原样复跑一次再动手。**
   复跑还红 = 真故障；复跑变绿 = 波动。
2. **额度类错误在分类上归「等你」**（需牛哥哥充值），不归「可处理」。
3. **按根因计数，不按 FAIL 条数计数** —— 多个 FAIL 可能是一根因的多个投影。

## 关联

- **E69**（健康端点返回硬编码的 ok）：探针正常但被探对象在撒谎 —— 本条是**报告的时间维度**出问题。
- **E57**（额度耗尽时小请求照样 HTTP 200）：额度问题的另一个伪装形态。
- **E66**（故障根因会换措辞，认字面量的分类器会静默漏判）：分类器读哪条路径的问题。

## 边界

- 本条**不是**说「不要修 FAIL」——真故障该修还是要修。
  本条说的是**顺序**：先花 60s 分清「波动 vs 故障」，再决定要不要动手。
- 判据：**报错的特征**是额度类 → 先复跑；
  否则 → 直接按真故障查。
  这是**启发式**，不是绝对 —— 若连续多次同一 FAIL 复跑都红，那它就是真故障。
