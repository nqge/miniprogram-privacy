### E59：长期项混进 FAIL 计数，会把真故障淹在假警报里
> 本条讲：**汇总行和退出码必须表达「可处理的故障数」，而不是「所有非 PASS 项数」**

## 场景

给巡检脚本加「⏳ 等你处理」的分类 —— 一些故障需要用户本人操作
（充值、吊销 PAT、决定博客方向），脚本改不了，只能列出。

为了让这类项显示得更温和，文案写成「⏳ 等你」而不是「❌ FAIL」。

## 陷阱

2026-11-03 07:00 巡检输出：

```
 结果: PASS=73  FAIL=1  WARN=6
 ✅ 没有可处理的失败(1 项长期项在等你处理)。
```

**自相矛盾**：计数行说 `FAIL=1`，下一行说「没有可处理的失败」。
而且脚本**退出码返回 1**。

根因在 `scripts/healthcheck.sh`：

```bash
bad() {
  FAIL=$((FAIL+1))          # ← 无条件加一
  ...
}
# 后面渲染时：文案命中 WAITING_PATTERNS → 打印成「⏳ 等你」
```

→ **计数按「非 PASS 的总数」算，显示按「是不是真故障」分**，
两者口径不一致 → 汇总行把「长期项」也算成了 FAIL。

**为什么这条比「报错了」值钱**：

危害不是「吵」，是**驯化**。一个每天都会出现、连续出现很多天、
谁都看得见但没人细看的假失败，会训练出「扫一眼就划走」的阅读习惯。
等真正的故障来的时候，同样被划走 —— 假警报的成本不是它自己，
是它**消耗掉的注意力额度**。

而且这个假警报会**持续消耗**：长期项是设计上的常态，
它会一直报、一直混在 FAIL 里，直到有人主动清理。

**还有一个隐蔽副作用**：退出码 1 → systemd 判红。
虽然配了 `SuccessExitStatus=1` 兜住噪音，但**信号语义已经错了** ——
下游脚本/CI/告警规则读退出码时，收到的是「有故障」，而实际是「有个长期项」。

## 岔路口

**触发条件**：只要报告里存在「需要人操作、我改不了」这一类项，
就要立刻检查它的**计数口径**和**退出码口径**。

**修法**（本次已落地，`healthcheck.sh` 第 2592 / 2618 行）：

1. **拆开计数、拆开显示**
   - 汇总行 → `PASS=73  FAIL=0  WARN=6  等你=1（长期项，不计入 FAIL）`
   - 「等你」是**独立维度**，不混进 FAIL
2. **退出码按「可处理失败数」决定**
   - 长期项**不该**让 systemd 判红 —— 判红的应该是「我现在能修但没修」
3. **判定用文案模式**：`WAITING_PATTERNS` 命中的项，在计数时就要分流，
   而不是只在渲染时换个词

**配套判据**（每条巡检脚本都该自查）：

- 汇总行里出现的每个数字，读者能不能**照着它行动**？
  → 「FAIL=1」但正文说不用处理 = 读者无所适从
- **退出码表达的是不是「可处理故障数」**？还是「非 PASS 项数」？
- 长期项有没有**单独维度**显示，而不是换个文案词混在 FAIL 里？
- 有没有**清理机制**？长期项堆积到几十条时，FAIL 计数就彻底失去意义了

**通用化**：
> 任何把「我修不了」和「我该修」放进同一个桶的系统，
> 桶里的水位就不再代表「我该干的活有多少」。
>
> 汇报类系统（巡检、告警、CI、待办看板）里，
> **「需要人决策」和「需要人执行」必须分桶** ——
> 否则前者会稀释后者的信噪比。

## 为什么值得记

E47 讲「状态字段 ≠ 用户得到的结果」，E55 讲「先问该发什么」。
E59 讲的是**第三个维度**：**指标本身的口径**。

前两个都在讨论「测的东西对不对」，E59 讨论的是**「报出来的数字代表什么」**——
一个数字如果不能用它来指导行动，它就是噪声，而噪声比没有更糟。

值得注意的是：**这次的假警报不是因为数据错，是因为文案和计数用了两套口径**。
数据本身完全正确（确实有 1 项长期项），错的是**这个 1 该不该叫 FAIL**。

这比「测错了」更难发现 —— 因为每个数字单看都对，
只有把**计数行 + 结论行 + 退出码**三个出口放一起看，才看得出它们在说不同的事。

**关联**：E47（状态字段 ≠ 用户得到的结果）· E29（断言的第一版阈值很可能是假警报）·
E55（先问「本该发什么」）· E57（看门狗和被看守对象共用依赖）·
E58（连续失败次数必须单独断言 —— 同样在修「单一数字表达不了真实状态」）
