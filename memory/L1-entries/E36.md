### E36：最该被信任的地方，过期了最致命

> 本条讲：**最该被信任的地方，过期了最致命**

**场景**：2026-10-27 05:10 收尾时看 `SESSION-STATE.md` 头部的「📋 系统状态」小节，
发现里面**几乎每一条都是过期的**：
- provider 写着 `minimax, glmcode, arkcode` —— 后两个**早就删了**（实际只剩 minimax）
- cron 列表里有 `teahouse-check` / `dream-cycle-v3` —— **任务早就删了**
- plugin 里有 `qqbot` / `ddingtalk` —— **早就移除了**
- 「首次自动调度验证待 10-26」—— 早就过了

**陷阱 —— 为什么这条比 L1 库里的过期计数更严重**：
- L1 库里的计数过期 = 我判断「记忆系统状态」时参照错了（E32）
- **SESSION-STATE.md 头部过期 = 下一个会话被直接误导**
  → 它是 AGENTS.md 规定的「每次会话先读」的第一份文件
  → 下一个会话会据此认为「glmcode 还在，只是 key 过期，要等牛哥哥重签」
  → 而实际上那些决策项**早已不需要等了**
- 也就是说：过期数据不可怕，**过期的指令**可怕 ——
  它会让人做出**本不该做的动作**

**岔路口**：
1. **手写的「当前状态」小节 = 定时炸弹**：
   → 改成由 `scripts/gen_system_status.py` 从**真实系统**生成
   （providers / cron 任务 / plugins 全部实时读，加 `BEGIN/END` 标记）
2. **头部「最后更新」时间**也用 git 最后提交时间自动填，不手写
3. **加断言【S】持续核对**（18 → 19 组）：
   - providers 声明 == 真实 providers
   - cron 列表 == 真实 cron 列表（不漏、不多）
   - 小节里不出现任何**已删除实体**的名字
4. **历史记录不要改**：SESSION-STATE.md 里那些带日期的「巡检现状（快照）: 12 组断言」
   是**当时的事实**，保留不动 —— 只有「当前状态」才需要与现实同步

**证据（双向）**:
- 注入原始 bug（写回 glmcode/arkcode/teahouse-check）→
  **四条 FAIL 同时报出**（providers 不一致 / 列了不存在的 cron / 两个已删除实体残留）✅
- 恢复后 → PASS ✅

**延伸**：这是 E34「派生数据不手写」的**延伸应用** ——
E34 讲的是「说明清单」，E36 讲的是「**当前状态**」。
区别在于**后果的严重性**：
说明清单过期 → agent 不知道怎么解释某个失败
**当前状态过期 → agent 去做本不该做的事**
→ 所以「哪些手写内容算危险」的排序是：**状态描述 > 说明清单 > 计数**
