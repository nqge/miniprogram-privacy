### E69：健康端点返回的是硬编码的 ok —— 探针没坏，被探的对象在撒谎
> 本条讲：**健康端点返回的是硬编码的 ok —— 探针没坏，被探的对象在撒谎**

**核心断言**：当探针调用的端点**不真正走通被检查的依赖**时，
探针报出的 PASS **只证明「进程在」「端点会返回 200」**，不证明「功能能用」——
而且这个错误信号**不会以失败的形式出现**，它长得和真 PASS 一模一样。

## 场景

2026-11-10 07:00 巡检，同一份报告里同时出现：

```
【A3】✅ PASS  嵌入代理健康（记忆检索依赖）
【C】 ❌ FAIL  Embeddings: unavailable - 记忆检索不可用
【H】 ❌ FAIL  记忆检索执行异常
```

A3 说代理健康，C/H 说记忆检索是死的。**两者都不矛盾** ——
它们看的是同一台代理的**两条不同路径**。

## 陷阱

### 陷阱一：端点是写死的，不碰上游

`tools/minimax_embed_proxy.mjs` 的健康分支：

```js
if (req.method === "GET" && req.url === "/health") {
  return send(200, { ok: true, model: MINIMAX_MODEL });
}
```

**返回的是字面量**。它不向 MiniMax 发任何请求，不问余额，不问模型在不在。

于是当上游真实返回
`{"status_code":1008,"status_msg":"insufficient balance"}` 时，
这个端点**依然返回 `{"ok":true}`**。

### 陷阱二：探针本身完全正常，所以没人怀疑探针

这是 E63（「先拿已知可用的对象校准探针」）**没覆盖到的反面**：

- E63 的场景是**探针坏了** → 探了一个不存在的东西 → 误报「全挂了」
- 本条的场景是**探针完全正确，目标在撒谎** → 探针问「进程活着吗」，
  进程确实活着 → 报 PASS → **依赖其实是死的**

E63 的自检（拿已知可用的对象校准探针）在这里**照常通过** ——
因为探针真的没坏。**探针的自检无法发现「对方在自我认证」。**

### 陷阱三：真错在日志里，但不在任何断言的读取路径上

`journalctl -u openclaw-embed-proxy.service` 里明明白白写着
`upstream error: insufficient balance`，
**但没有任何一条断言去读它** → 断言读的是那个写死的 `ok:true`。

实测这次错误只出现在 **07:00:37–07:01:52**（正是巡检自己探测的那几分钟），
之后 10:35 的 3 次真实检索全部成功 → 说明当时是**额度瞬时耗尽**，
而巡检把瞬时状态**固化成了 FAIL**，又因为探针撒谎而**没能区分「额度耗尽」和「代理坏了」**。

## 岔路口

1. **探针要穿过被检查的那条依赖，不能停在它的门口**。
   「进程在」+「端点返回 ok」是**存活检查**；
   「真发一次请求，看上游返回码」才是**功能检查**。
2. **自建服务时，健康端点必须真打一次上游**（哪怕带缓存或降级），
   否则这个端点就等于**让被检查方自己给自己盖章**。
3. **断言报告里，同一个对象出现 PASS 和 FAIL 并存时，先问「这两条查的是不是同一条路径」**，
   而不是急着判其中一条是误报。
4. **故障日志要有一条断言去读它** ——
   「错误躺在 journal 里没人看」和「错误不存在」在效果上是同一件事。

## 为什么值得记

这是「**判据 / 真身 / 失败形态三者不一致**」系列的新变种：

- E42 —— 断言量错了东西
- E63 —— 探针本身坏了
- E66 —— 根因换措辞，认字面量的分类器静默漏判
- **E69 —— 探针没坏，但被探对象返回的是硬编码的 PASS**

前三种都会产生**可见的失败信号**；
只有本条产生的是**和真 PASS 无法区分的假 PASS** ——
**故障被伪装成了健康**，这正是 2026-10-26 立 healthcheck 的初衷
（「状态字段描述的是『任务跑完了』，不是『用户得到了结果』」）的翻版。
