### E56：刷新哈希基线时，「相对路径」会静默失效
> 本条讲：**哈希基线刷新必须用绝对路径**

## 场景

配置基线不匹配（backup-audit 报 FAIL），需要刷新基线文件。

## 陷阱

在 `~/.openclaw/` 目录下执行：

```bash
sha256sum openclaw.json > .config-baseline.sha256
```

看起来对（校验和一致、文件权限 600、hash 没变），但 **backup-audit 仍然报 FAIL**。

**原因**：`sha256sum -c` 是按**当前工作目录**解析文件名的。
基线里存的是 `openclaw.json`（相对路径），而校验脚本的 cwd 是 workspace
（`/root/.openclaw/workspace`）→ 那里根本没有 `openclaw.json` → 校验失败。

**最阴的地方**：
- 用同一个目录校验 → 通过（假象）
- 换一个目录校验 → 失败
- 而 baseline 文件里到底存的是相对还是绝对路径，**肉眼要去看文件内容才知道**

旧基线（Oct 26 建的）用的是绝对路径 `/root/.openclaw/openclaw.json`，
所以一直好好的 —— 这次「刷新」把它降级成了相对路径，**反而制造了新故障**。

## 岔路口

发现「基线不匹配」时的判断顺序：

1. **先确认改动是合法的吗？** → 是合法变更（如改了 heartbeat 配置）→ 才该刷新基线
2. **先看旧基线文件里存的是绝对还是相对路径** → `cat .config-baseline.sha256`
3. **刷新时用绝对路径** → `sha256sum /root/.openclaw/openclaw.json > .config-baseline.sha256`
4. **在【与校验脚本不同的 cwd】下验证** → `cd <别处> && sha256sum -c <基线>`
5. **最后再跑一遍真正的审计脚本** → `bash scripts/backup_audit.sh`，看结果是不是真的变绿

## 为什么值得记

「我刷新了基线」和「基线真的生效了」是**两件事**。
只做第 1 步就宣布修好，等于用「自检通过」骗自己。

**通用化**：任何「写入一个路径、之后在别的目录读它」的机制，
都必须**跨目录验证**。同一个目录下验证成功 = 什么都没证明。

**配套判据**：backup-audit 的基线校验，本质上就是在测「cwd 无关性」。
以后任何基线/清单类机制，都该有一个「换个目录还能用吗」的断言。
