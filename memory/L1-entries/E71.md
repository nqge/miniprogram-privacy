### E71：连续失败的任务被判成 WARN，监控看见了但没人动
> 本条讲：**连续失败的任务被判成 WARN，监控看见了但没人动**

**核心断言**：巡检把「**连续失败 ≥3 次的定时任务**」归进 **WARN** 区，
于是它既不进「现在就该修」，也不进「等你」——
**它变成了一条每天都在刷的背景噪音**。
**测量是准的，分类把它降级了**，结果就是：一个已经死了 6 天的任务，
在报告里看起来和一次偶发失败一样重。

**对策：给巡检加一条断言 —— 「连续失败 ≥3 次的定时任务」直接记 FAIL**，
别留在 WARN 里当背景噪音。

## 场景

2026-11-16 07:00 巡检：

```
[⚠️  WARN]  daily-learning 最近 20 次里有 11 次 error，
            其中最多【连续 6 次】失败（最近一次正常）：11-15 09:00, 11-14 09:00, ...
[⚠️  WARN]  daily-reflection 最近 20 次里有 16 次 error，其中最多【连续 12 次】失败
[❌  FAIL]  SESSION-STATE.md 已 5 天未更新
结果: PASS=74  FAIL=1  WARN=5  等你=3
```

daily-learning 从 **11-10 起连续 6 天**每天 09:00 失败，
cron 记录里每次都是 `All models failed (3): ... rate_limit`。
**11-10 和 11-11 的笔记是心跳补的**，11-12 ~ 11-16 这 5 天的
`memory/YYYY-MM-DD.md` 全部不存在 —— 也就是说
**这条「已经死了 6 天」的信息，每天早上都被算出来、写进报告，然后归档**。

## 陷阱

### 陷阱一：WARN 是「不严重」的意思吗？不是

WARN 在报告里的实际效果是**「看到了，但不需要动作」**。
而「连续 13 次失败」和「一次偶发」在 WARN 区里**排在一起**，
读的时候无法区分「上次刚失败一次」和「已经死了两周」。

→ **持续性（连续 N 次）是一个独立维度，不能和「单次严重度」混在一个档里。**

### 陷阱二：监控「看见了」不等于「有人会处理」

巡检把这条写进报告 → 报告进 `memory/healthcheck-logs/` → 归档。
链路完整、信号准确、**没有任何一步会触发动作**。
如果没人主动去读日志里那行 WARN，它就等于不存在。

→ 这和 E68/E69/E70 是同一个病根的另一个切面：
**信号存在，但不在能驱动动作的那条路径上**。
E69 是探针端点撒谎，E70 是报告没有时间维度，
**E71 是报告有时间维度（连续 N 次）却没有把它接到「该修」上**。

### 陷阱三：失败次数是唯一的健康指标吗？不是

「连续失败 6 次」说明的是**产出断了**。
但根因（MiniMax Token Plan 额度周期性耗尽）**不归这条 job 管** ——
job 本身没坏，它只是撞上了上游额度窗口。

→ 所以正确做法不是「让 job 重试到成功」，
而是把「**连续失败 ≥3 次**」升格成 **FAIL**，
让它进入「可处理」通道去推动真正的修复（充值 / 加 key / 加 fallback），
而不是永远躺在 WARN 里。

## 岔路口

```
巡检报出某任务「连续 N 次失败」
    │
    ├─ N ≥ 3
    │     → 这是**持续故障**，不是波动
    │        → 应该被记 FAIL 并进「现在就该修」
    │        → 同时查根因是不是「上游额度」这类外部依赖
    │           （是的话 → 归「等你」，但仍要 FAIL，不能只 WARN）
    │
    └─ N = 1
          → 单次失败，先看有没有「最近一次正常：」
             有 → 可能是波动（E70：先复跑）
             无 → 按真故障查
```

**关键分界**：WARN 留给「**信息性**」的观察项（比如「agent 级目录另有 4 个 provider」），
FAIL 留给「**必须有人做点什么**」的项。
「连续 6 次失败」显然属于后者。

## 对策

1. **给巡检加断言：连续失败 ≥3 次的定时任务 → 记 FAIL**（不是 WARN）。
2. **同时保留「最近一次正常：时间戳」**（巡检已经在输出）——
   它让人能区分「自愈型波动」和「持续性死亡」。
3. 失败次数**按根因计数**（E70）：同一 provider 额度耗尽导致的连续失败
   算**一个**根因，但**在任务维度仍然算持续失败** —— 两个维度分别计数。

## 关联

- **E70**（FAIL 是快照不是状态）：本条是它的**反面**——
  E70 说「单次 FAIL 可能只是波动」，本条说「**持续失败再稳也可能是坏事**」。
  两条合起来才是完整判据：**单次看时间维度，连续看次数维度**。
- **E69**（探针没坏但对象在撒谎）：信号不在能被读取的路径上。
- **E68**（先落盘再总结）：产出断了就不会有落盘 —— 本条是它的「症状侧」。
- **E59 / E57**（额度预检与额度耗尽的伪装）：本条根因的上游。

## 边界

- 本条**不是说所有 WARN 都该升级成 FAIL**。
  「连续失败 ≥3 次」是**具体触发条件**，不是「把 WARN 全变 FAIL」。
- 本条也**不是说 task 自己能修好** —— 根因在额度，
  task 侧只能做「如实暴露、别藏」。
- 判据要看的是**连续失败次数**，不是累计 error 数：
  20 次里失败 11 次（断断续续）和**连续 6 次**，不是一回事。
