### E58：「最近一次是 ok」不能代表「最近一直 ok」—— 连续失败次数必须单独断言
> 本条讲：**lastRunStatus 是单点快照，用它判断健康度等于用一个样本推断趋势**

## 场景

给一批定时任务配巡检断言。巡检读 `cron list --json` 里的 `state.lastRunStatus`，
以及 `state.lastDelivered`，据此判断任务健不健康。

## 陷阱

2026-11-03 心跳巡检实测：**`daily-reflection` 连续 4 个月没成功过，计划槽位成功率 0%**。

- `cron/runs/b7a0aca1-*.jsonl` 全部 44 条记录里，**只有 3 次 `ok`**
- 而这 3 次**全是手动补跑**（10-21 04:27 Wed、10-26 00:35 Mon、10-26 09:21 Mon）
- **周日 22:00 的计划槽位，15 次全挂**（2026-05-14 → 2026-11-01）

但巡检报告只写了一句：
> `FAIL daily-reflection 运行失败（lastRunStatus=error，原因：接口限流）`

—— 读起来像「昨天挂了一次」。**4 个月的停摆在报告里只有一行。**

根因分三个时代，每换一个原因就以为「修好了」，从没从「历史上到底成功过几次」的角度看过：

| 时期 | provider / model | 错误 | 真实原因 |
|---|---|---|---|
| 05-14 ~ 07-05 | glmcode/GLM-5、kimicode | HTTP 400 | **provider 已死**（后来删了） |
| 07-12 ~ 10-18 | minimax/MiniMax-M3 | HTTP 400 / 超时(180s) | **timeout 默认值太短**，后来才改 900s |
| 10-25 ~ 11-01 | minimax | rate_limit | **Token Plan 额度耗尽** |

同期 `daily-learning` 也有 **7 次 error**（含 10-30/10-31/11-01 **连续 3 天全挂**），
巡检报「投递正常（delivered=True）」—— 因为最近一次（11-02）确实成功了。

## 岔路口

**症状**：任务「时好时坏」，但状态字段看起来正常。

**判断顺序**：

1. **别看 `lastRunStatus`，看历史分布**
   → 拉 `openclaw cron runs --id <id> --limit 20`，统计 `status` 的历史构成
2. **区分「零散失败」和「连续失败」** —— 这两件事的运维含义完全不同：
   - 零散 N 次 = 偶发抖动
   - **连续 N 次 = 静默中断 N 天，用户完全无感**
   → 所以要单独算 **最长连续失败次数**，而不是只算失败总数
3. **区分「计划槽位失败」和「手动补跑成功」**
   → 手动补跑成功会掩盖「计划任务从没成功过」的真相
   → 按 `runAtMs` 对齐 cron 表达式，**只统计符合调度规律的那些 run**
4. **失败原因要分类**：`rate_limit`（依赖耗尽）/ `timeout`（配置太紧）/
   `HTTP 400`（参数或 provider 已死）/ `auth 403`（凭证过期）——
   每类的修法完全不同，混在一起看就是「时好时坏」
5. **修完之后必须实跑验证**
   → 11-03 08:51 补跑：80s，`ok` + `delivered=True` → 证明 900s timeout 的修法有效
   → 注意：**900s timeout 的修法从来没在「额度健康」条件下被验证过**，
     11-01 那次失败是配额问题，不是超时问题 → 修法有效性是**未验证状态**

## 为什么值得记

**「我配了监控」和「监控真的能在我出事时报警」是两件事**（E57 讲的是依赖共用，这里讲的是**样本量**）。

状态字段的设计初衷是「当前如何」，但健康度判断需要的是「**一直如何**」。
拿单点快照当趋势用，会系统性地**低估**故障时长：

- 一个任务挂了 1 天 → 看不出来
- 一个任务挂了 4 个月 → **也只看出来一行**，读起来像「昨天的事」

更隐蔽的是：**手动补跑会把「计划任务从没成功过」这个事实擦掉**。
3 次成功看起来像「它偶尔能跑」，实际上 3 次全是手动救火。

**通用化**：任何「状态字段 + 巡检断言」的组合，都必须问一句
**「我断言的是瞬时状态，还是历史趋势？」**
只断言瞬时状态的巡检，**结构上无法发现长期停摆** —— 它只会把
「停了 4 个月」报成「昨天挂了一次」。

**配套判据**：
1. 断言「最近 N 次里有 M 次 error」
2. 断言「**最长连续失败次数** ≤ 阈值」
3. 断言「**符合调度规律的那些 run** 里成功过几次」（排除手动补跑）
4. 失败原因**分类计数**，而不是只统计总数

E34（靠「记得做」补的漏洞 → 这次是判据本身的盲区，同源）·
E8（规则写下来没执行；这次是**判据写下来有盲区**，同源）·
E55（本该发什么：先问有没有产出，再判投递）
