### E66：故障根因会换措辞 —— 认字面量的分类器会静默漏判
> 本条讲：**故障根因会换措辞 —— 认字面量的分类器会静默漏判，认「特征」才稳**

**核心断言**：判断故障的**根因**（进而决定「谁能修」）时，
**不能认报错文本里的关键字**，要认**故障的结构特征**——
因为上游的措辞会变，而结构特征更稳定。

## 场景

2026-11-08 `daily-learning` 失败。07:00 巡检报：

```
❌ FAIL  daily-learning 运行失败（lastRunStatus=error，原因：接口限流）
⚠️ 有 2 项可处理的失败,需要处理。
   【可处理 - 现在就该修】
```

**照字面读，这事该我修**（把脚本改好、让任务不再失败）。

## 陷阱

我独立查了 `cron/runs/*.jsonl` 原始记录，实际情况是：

```
11-08 09:03 | error | dur=215598 | ⚠️ API rate limit reached (rate_limit)
```

三个候选模型 **3/3 同时中招**，且额度探测（~15k token 真实负载）在 23 小时后**通过**。

→ 根因是 **MiniMax 账号级额度耗尽**（计费周期），**只能靠牛哥哥充值解决**，
我改代码改不了 —— **它是个长期项，不是我现在就该修的故障**。

而分类器为什么判错？因为它写的是：

```python
if "Token Plan" in err:          # ← 认字面量
    reason = "，原因：Token Plan 用量上限(需充值)"
elif "rate limit" in err.lower():
    reason = "，原因：接口限流"   # ← 落进「可处理」组
```

而 `WAITING_PATTERNS` 里只有 `"Token Plan"`。
**11-08 的报错里已经没有「Token Plan」这四个字了**（11-02 时还有）——
措辞一变，匹配器就静默漏判，长期项被误报成「可处理」。

**三个模型同时挂**才是区分两种限流的关键特征：

| 现象 | 根因 | 谁能修 |
|---|---|---|
| **全部**候选模型同时报限流 | 账号级额度耗尽（计费周期） | **只能等牛哥哥充值** |
| 只挂一两个模型、很快恢复 | 每分钟/并发限流 | 能自愈，不用管 |

## 岔路口

判根因时的岔路口：**报错里写了什么词** → **几个对象同时中招**。

判据写成「特征」而不是「字面量」：

```python
m = re.search(r"All models failed \((\d+)\)", err)
if m and int(m.group(1)) >= 2 and 有额度语义:
    return True   # 全部候选模型一起挂 = 账号级额度耗尽
```

这样明天上游把 `rate limit` 改成 `quota exhausted`，判定依然成立。

## 代价

**假警报的代价不是它自己，是它训练出来的阅读习惯。**
一个每天额度一耗尽就出现一次的「可处理 - 现在就该修」，
会训练出「扫一眼就划走」的习惯 —— 等真正的故障来的时候，同样被划走。

（这正是 E59 的老病根：长期项混进 FAIL 计数，会把真故障淹在假警报里。
E59 解决的是「分类」，E66 补的是「分类依据不能认字面量」——
**分类对了，但依据是脆的，一样会漏判。**）

## 修法

1. 分类依据从「报错关键字」改成「故障结构特征」
2. 分类器与故障形态之间**必须有单测**（否则措辞一变就没人发现）
3. 修完复跑一次全量巡检，确认 FAIL 计数真的变了（不是「看起来对」）

## 关联

- E59 —— 长期项混进 FAIL 计数，会把真故障淹在假警报里
- E65 —— 失败计数是原始计数，不含调度频率与错误种类
- E62 —— 派生副本的漂移不产生错误信号（**分类器 = 派生副本**）
- E63 —— 先拿已知可用的对象校准探针（探针错了会被误报成「全挂了」）
- E64 —— 内容合规 ≠ 位置合规
- E57 —— 额度耗尽时小请求照样 HTTP 200（小请求是反向指标）
