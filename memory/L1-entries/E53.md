### E53：「上次全绿」不等于「现在还好」 —— 巡检的 PASS 是快照，不是状态

> 本条讲：**「上次全绿」不等于「现在还好」 —— 巡检的 PASS 是快照，不是状态**

**发现时间**: 2026-10-29 00:0x

## 现象

10-28 03:00 的 `backup-audit` cron 报告 **「all PASS (PASS=19, FAIL=0, WARN=0)」**。
我 00:00 手跑**同一个脚本**，得到 **PASS=16 FAIL=1 WARN=2**：

```
❌ FAIL  本地领先远端 13 个 commit（未推送）
```

13 个 commit 是 10-28 白天/晚间的工作 —— **cron 那次跑完之后才产生的**。

## 为什么会这样

**「全绿」描述的是任务跑完那一刻的世界，不是现在的世界。**

任何「周期性执行的巡检」都有这个性质：
- 巡检跑完 → 写一份快照 → 快照不会自己更新
- 快照与现实之间的差距**只增不减**（除非有人改）

所以：
> **引用上一轮巡检结论 = 在用过期数据判断现在。**

## 三个层次的同一个病

| 层 | 表现 |
|---|---|
| 巡检结果 | 「上次全绿」被当成「现在还好」 |
| cron 状态字段 | `status=ok` 只说明 agent 那轮没崩，**不代表脚本输出是什么** |
| 记忆里的结论 | 「已修复 / 已了结」让下个会话直接跳过 |

第 3 层尤其阴险 —— 它连「复查」的动作都省了。

## 怎么破

1. **想知道当下状态 → 当场重跑**，别引用上一轮结论
2. **「cron 报 ok」与「脚本报 FAIL」矛盾 → 以脚本为准**，并去查 `cron runs` 历史
   （矛盾本身就是信号，说明快照已经过期）
3. **重要状态写进「当前状态」类文件 → 要么自动生成，要么定期刷新 + 写完实测校验**

## 附带收获：巡检的历史比巡检的结论更有信息量

查 `openclaw cron runs --id <id>` 时，发现 `backup-audit` 在 10-27 **连续 3 次超时**
（300s / 600s / 600s），而**最后一次却是 ok**。

如果只看最新一条（ok），根本不知道前面崩过 3 次。
**历史里的异常模式，只有翻历史才看得见。**
