### E52：快照管不住退化 —— 递增是趋势，快照看不见

> 本条讲：**快照管不住退化 —— 递增是趋势，快照看不见**

**发现时间**: 2026-10-28 08:0x

## 现象

今晨巡检后手查 healthcheck 的 run history，发现耗时在**无修改**地爬升：

| 时间 | 耗时 |
|---|---|
| 10-26 10:52 | **27s** |
| 10-26 17:10 | 214s |
| 10-27 07:00 | 298s |
| 10-28 07:00 | **378s** |

不到两天涨了 **13.9 倍**。按每次 +80s 的斜率外推，**10-31 前后撞 600s timeout**。

## 陷阱一：把「我加的」和「它自己变的」混成一条线

我最初的归因是「provider 变慢」或「CPU 争抢」。查 run history 才发现——
**10-26 那两次跑的根本不是同一份代码**：27s 那次是我手动跑的旧版本，
214s 那次是当天下午加完断言组之后的 cron。

所以曲线里混着**两种增长**：

1. **我加组**（有意为之）：断言组从 20 组加到 26 组 → 每组都要跑 → 自然更慢
2. **每组自身变慢**（退化）：这才是真正要盯的

**混成一条线去外推，就会得出「再调高 timeout 就行」的错误结论** ——
那只是把退化藏起来，等下一次「变化」重新解释曲线。

> **通用判据**：看到一条单调递增的曲线，先问
> **「这几次运行之间，代码变了吗？」**
> 变了 → 是我加的（可接受）；没变 → 是它自己退化（要查）。

## 陷阱二：占用率断言是快照，递增是趋势

【U】组管的是「最近一次耗时 / timeout 是多少」——那是**快照**。
快照在 50% 时是 PASS，趋势到 100% 才是 FAIL。

**中间这 3 天完全没人看见。**

| | 问的问题 | 能在什么时候发现问题 |
|---|---|---|
| 快照（【U】现状） | 最近一次占比多少 | 已经撞上时 |
| 趋势（缺的那条） | 最近 N 次是不是在涨 | **涨的过程中** |

> **快照只能在终点报警，趋势才能在途中报警。**
> 一个只会看「当前值」的监控，对**渐进式退化是盲的**。

## ✅ 解法：给【U】组加一条趋势判定

判据：最近 3 次耗时**单调递增**且累计涨幅 > 50% → WARN。

- 单调性要求：避免「抖动」被误判成趋势
- 涨幅门槛：避免日常 ±10% 的正常波动刷屏
- 报 WARN 而非 FAIL：退化还不致命，但**值得现在看一眼**
