### E57：看门狗和被看守对象共用一个依赖 —— 它会先死，而且死得静悄悄
> 本条讲：**巡检和被巡检任务共用同一份额度时，额度耗尽会先掐死巡检自己**

## 场景

给一批定时任务配监控/告警，监控本身也由同一套调度系统执行。

## 陷阱

MiniMax Token Plan 用量上限（429「已达到 Token Plan 用量上限」），
2026-10-30 至 11-01 连着 3 天，所有 `agentTurn` 型 cron 全部失败 ——
**其中就包括 07:00 的体检任务**。

体检本来就是那道发现「定时任务全挂」的保险，结果它自己被同一个额度桶掐死，
而且**死得毫无声响**：

- cron 列表里只有 `lastRunStatus=error`，没有任何一条告警发出去
- 「体检没跑」这件事本身没人监控 → 三天里没有任何人知道系统全挂了
- 交互式会话却不受影响（小请求能过）→ 手动 curl 测 HTTP 200，
  看起来「provider 是好的」→ 误判成任务自身的问题

关键结构问题：**监控路径与被监控路径共用同一份稀缺依赖**。
额度一耗尽，被监控对象和监控者同时死 —— 而监控者的死，
在告警系统里表现为「没有告警」，和「一切正常」无法区分。

E8（纯脚本任务不该用 agent 型 cron）早就写下来了，但**没有执行**；
规则写在纸上而架构没改，额度一耗尽，连「体检」自己都先死。

## 岔路口

发现「整批定时任务同时失败且报错一致」时，判断顺序：

1. **先看报错是不是同一句话** → 429 / 配额类报错 = 依赖耗尽，不是任务 bug
2. **再看依赖关系**：这个任务依赖模型额度吗？监控任务也依赖吗？
   → 两者共用 = 监控是假的安全网
3. **拆依赖路径**：把纯脚本任务（体检、审计、备份、日志清理）
   迁到 **systemd timer** —— 不消耗模型额度，模型挂了它们照跑
4. **给「监控没跑」本身加断言**：产出物（今日巡检日志）是否真的落地，
   没落地 = 可告警事件，不能默认「没消息就是好消息」
5. **控制消耗方**：心跳频率 30 分钟 → 60 分钟，且限定活跃时段
   （08:00–22:00）—— 心跳每次注入 ~60k token 上下文，48 次/天 ≈ 2.9M input token/天
6. **配额型依赖要区分两种形态**：「变慢」（共享配额被抢，无 error，难归因）
   vs 「耗尽」（明确 429 + 明确报错文案）→ **见 429 就立刻查额度，别继续试模型**

## 为什么值得记

「我配了监控」和「监控真的能在我出事时报警」是**两件事**。
第二件事的前提是：**监控不能和被监控对象共用同一个会死的东西**。

**通用化**：任何「监控 / 告警 / 巡检」机制，都必须问一句
**「它和被监控对象共用哪些依赖？」** ——
凡是共用的依赖一旦耗尽，监控会**先于**被监控对象失效，
且它的失效形态（没有告警）与「一切正常」**无法区分**。

**配套判据**：任何巡检类机制都该有一条「产出物是否存在」的断言 ——
「巡检没产出」必须是一个**可告警的失败**，而不是「无事发生」。
