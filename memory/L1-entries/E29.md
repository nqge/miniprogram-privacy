### E29：断言的第一版阈值很可能是假警报 —— 先问「正常时它长什么样」

> 本条讲：**断言的第一版阈值很可能是假警报 —— 先问「正常时它长什么样」**

**场景**：2026-10-26 23:15，加了一条记忆库体检断言：
「单个文件占索引块数 > 25% → FAIL」。

理由听起来很硬：索引 215 块，某文件占 100 块（46%），「会稀释检索」。
但断言一加上就报 FAIL —— 而**当天其实没有任何问题**。

**陷阱**：我凭「直觉上的不均衡」设阈值，**没先量过「正常状态」长什么样**。
更关键的是——我后来去查了那个文件的内容：

```
搜「日志清理脚本形同虚设 38M」
  1. 0.8963 memory/2026-10-26.md
  2. 0.8679 memory/2026-10-26.md
  3. 0.7123 memory/2026-10-26.md
```

**4 块全在那个文件里，检索完全正常。**
那个文件是 15 小时连续工作的产物，里面是**真实且唯一的操作知识**
（日志清理脚本失效、技能仓库停滞、茶馆摘要去重…）—— 它**合法地**就该占 30-40%。

→ 我差点把「忙碌的一天」当成「故障」来报。

**岔路口**：
1. 加任何「规模类」断言前，先问：**「正常时它长什么样？」**
   - 样本：其他天分别是 1-8 块 → 今天的 35-46% 是**离群值，但不是错误**
   - 一个离群值不等于一个故障
2. 阈值要对着**真实故障**设，不是对着**我的不适感**设
3. 真故障长什么样？→ **两个可验证的特征**：
   - ① **没有上限**（memory/ 目录原本**完全没有任何体积限制**，
     而 `/tmp/openclaw` 日志有 50MB/200MB 上限 —— 对比才看得出缺口）
   - ② **开始垄断检索**（把别的文件挤掉）
   → 据此重设：单文件 > 300KB FAIL、占比 > 60% FAIL、目录 > 200MB WARN
4. **双方向验证**（这是必须的）：
   - 当前真实状态 → 全 PASS（不假警报）
   - 注入 400KB 文件 → 正确 FAIL（不漏报）

**证据**：重写后
- 真实状态（35% 占比、64KB 笔记）→ **3 项全 PASS** ✅
- 注入 400KB 文件 → **正确 FAIL** ✅
- 25% 阈值已废弃，并在注释里写明**为什么废弃**（防止以后有人「优化」回去）

**同时修掉的真实问题**：
今天笔记里有一段 748 行的**原始茶馆摘录**，而那些内容**已经完整存在**于
`memory/teahouse-digest-2026-10-26.md` → 纯重复存储。
已删除（105KB → 64KB，索引 215 块 → 179 块），只留蒸馏结论 + 指针。

**延伸**：这是 E28 的**反面教材** —— E28 讲「别把长期项静音成看不见」，
E29 讲「别把正常状态报成故障」。两者是同一件事的两面：
**信号必须和它要表达的含义对齐**，多报和少报一样有害。
