### E44：靠对话收敛的循环，收敛速度取决于模型而不是算法

> 本条讲：**靠对话收敛的循环，收敛速度取决于模型而不是算法**

**场景**：2026-10-27 09:00 那次 daily-learning 跑了 **772s**（timeout 900s，余量只剩 14%）。
我先怀疑三件事，都排除了：
1. 「任务变重了」→ 否，输入 60K tokens，比昨天还少
2. 「provider 慢」→ 否，单发实测 0.95–1.5s，HTTP 200
3. 「工具调用多」→ 54 次 exec 看着多，但**其中 26 次是同一个命令的重试**（48%）

**真根因：agent 在手工迭代字数**。翻会话里的长度序列：
```
272 → 259 → 233 → 232 → 227 → 225 → 222 → 222 → 223 → 221 → 219 → 190 → 190
```
**13 轮**。每一轮 = 一次完整推理（上下文带缓存 ~58K tokens），≈ 20–30s。
→ 光这一件事就吃掉了几百秒。

**为什么它会这样**：
任务指令写的是「长度 100-200 字……**写完自己数一遍，超了就砍**」。
问题在于 —— **「数汉字」这件事是 LLM 做的**，而 LLM 数不准中文汉字数。
于是它只能：写一版 → 数一遍 → 不对 → 改一版 → 再数 → …
这叫**靠对话收敛**：收敛速度取决于**模型**，不取决于**算法**。

**陷阱**：
- 「13 轮是我写得不好」→ 不是，**是机制把收敛成本推给了模型**
- 「多几次 exec 说明工具重」→ 先看**命令去重**：
  26/54 次是同一条命令重试 —— 真正的信号是「同一件事做了很多遍」
- 「每次迭代只花 20s，不算什么」→ 但**迭代次数没有上限**：
  模型不收敛、或者收敛得慢，代价就线性放大
- 「约束写得越详细越好」→ **软约束在 LLM 任务里等于没有约束**（E32）

**修法：把「计数 + 裁剪」交给确定性脚本**
新增 `scripts/trim_learning_section.py`：
- 数**汉字**（口径与 E42 一致），学习 100–200 / 反思 100–400
- **保留「可立即执行的对策」段**（这是小节的价值所在）
- 删信息量最低的铺垫段（最短的非对策段）
- 仍超标 → 对**最长**段按句截断
- agent 流程：写草稿 → `--from` 裁剪 → `--check` 确认 → 写入
→ **1–2 次调用收敛**

**踩坑（我自己写的脚本也犯了同族错）**：
第一版只算**正文段落**的汉字，漏掉首行「> 本条讲：**关键词**」的 25 字
→ 段落 181 字「合规」，实际 206 字超标
→ **口径要算全**（E42：口径不一致 = 断言失效）

**岔路口**：
1. **判断一段 LLM 工作该不该脚本化，看它是不是「可确定性判定」的**：
   - 「这段汉字数超了吗」→ **可确定性判定** → 该脚本化
   - 「这条教训值不值得记」→ 不可判定 → 该留给 LLM
2. **脚本化的收益 = 消除迭代次数的不确定性**：
   算法收敛在 1 次，模型收敛在 13 次 —— 而且模型那次**还会超时**
3. **脚本要保护「价值最高的部分」**：
   自动裁剪最怕把核心论点当铺垫删掉
   → 显式保护「可立即执行的对策」段，其余按信息量排
4. **同步指令前，先确认「源文件」和「线上」是否一致**：
   我这次用 `scripts/daily_learning_prompt.txt` 同步 cron，
   但那个文件**比线上旧**（缺【跨日提醒】/【等待方式】）
   → 同步差点把好的指令覆盖成差的
   → 【T】组当场抓到（这正是它存在的意义）

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 字数收敛轮数 | **13 轮**（对话式） | **1–2 次**（脚本式） |
| daily-learning 耗时 | 772s（86% 超时） | 待 10-28 定时跑验证（预期 ~200-300s） |
| 工具调用重复率 | 48% | 应降到个位数 |
| 裁剪后合规率 | 靠模型自觉 | **确定性 100%** |

**延伸**：E32 讲「软约束在 LLM 任务里等于没有约束」，
E42 讲「断言口径不一致 = 断言失效」，
本条讲**软约束的代价有多具体**：
不是「效果差一点」，而是 **13 倍的推理成本 + 86% 的超时余量**。
