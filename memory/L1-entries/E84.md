# E84：「等你」类永远不告警，于是额度耗尽 589 次零通知

> 本条讲：**「等你」类永远不告警，于是额度耗尽 589 次零通知**

## 场景

2026-11-23 下午 15:16 心跳，例行查 quick-health 日志，发现 FAIL 从 1 变成了 3：
14:22 和 14:53 两次探测报「**没有任何可用 provider** —— 整个系统暂时无法推理（额度耗尽，需充值）」。

**但牛哥哥一次都没被告知。**

## 陷阱：分类对了，副作用没人接

额度耗尽在下游的归类是**「⏳ 等你」**，这是**对的**：
我改代码改不了，得牛哥哥充值 → 归「可处理 - 现在就该修」就是假警报（E66/E69 同源）。

但「等你」有个副作用，**没人想过**：

```
alert_dedup.py:  if waiting and not actionable:
                      print("只有长期项（等用户处理），不告警")
                      return [], 0        # ← 直接返回，不发任何告警
```

理由也很合理：**长期项每天都成立**（单 provider、明文凭证），
天天告警就是噪音 → 会稀释真故障的注意力。

→ 结果：**额度耗尽发生了 589 次 / 近 30 天里有 24 天，而一次通知都没有。**

## 为什么会漏得更彻底：探测是**无状态的**

`check_provider_health.py` 每次 30 分钟跑一次，每次都是**独立进程**，
每次都只看得见「此刻」。

→ 它能报「现在没额度」，但**报不出「最近一直在没额度」**。
→ 而「最近一直在没额度」才是**决策需要的信息**：
  单次额度耗尽是正常波动，连续多天就是**结构性不足**（该充值了）。

**更隐蔽的一层**：即使有历史，单点探测也答不了「代价是多少」。
真正的代价不是「报错」，是**产出被丢掉** ——
额度耗尽时闸门跳过 scheduled job → 那天的笔记压根没有。

## 岔路口

判断「这件事要不要告警」时，先分清两类：

| 类型 | 特征 | 该怎么处理 |
|---|---|---|
| **静态配置缺口** | 每天都成立（单 provider、明文凭证） | 「等你」，**不告警** ✓（原逻辑没错） |
| **动态状态** | 有起止（额度这阵子耗尽） | 「等你」**但要给你看** —— 否则就是长期沉默 |

→ **「等你」不等于「不必知道」**。
→ 正确做法不是把它改成告警（那会天天吵），而是**让巡检把它整理成一页纸给你看**。

## 修法

1. **记历史**：`scripts/record_quota_probe.py` 每次探测追加一行到
   `memory/quota-history.jsonl`（挂在 quick-health 的 `ExecStartPost`）
2. **判持续性**：`scripts/check_quota_sustained.py`
   - 最近 7 天里有多少天额度耗尽（**≥3 天 = 结构性不足**）
   - 趋势：本期 vs 上期（在变好还是变糟）
   - 代价：窗口内闸门因额度跳过多少次 scheduled job
3. **接进巡检**：新增【P2】组 + 【W9】单测组（36 → **38 组**）

### 为什么历史数据源不用 cron run

额度耗尽时**任务压根没跑** → 没有 run 记录 → 看不见（**E83 同一个坑**）。
→ 探测是**独立于任务是否执行**的，所以它能看见「本该跑但跑不了」。

## 落地时踩到的三个坑（比判据本身更值钱）

**坑 1：分类要**只扫「【Provider 凭证】」段**，不能扫整个运行日志**

整个运行 body 里【Provider 韧性】那段有句话：
> 「只有 1 个 provider，但配了 2 项 fallback —— provider 级故障(**欠费/限流**/宕机)时兜底无效」

它本身就含「欠费」「限流」等额度词 → **正常的日子被误判成耗尽日**。
实测 11-17 被误判（那天实际 47 次探测全部正常、0 次额度耗尽）。
→ **这是「误报方向」的老坑（E66）**：统计虚高 → 阈值形同虚设 → 假警报。

**坑 2：一天只要**有一次**耗尽，这天就算耗尽日**

第一版取「当天最后一次探测」：11-19 当天有 **7 次**额度耗尽，
但 23:39 那次恢复了（HTTP 200）→ 取末次 → 那天被记成 `ok` → **耗尽事实被抹掉**。
→ 判据问的是「这天系统有没有过不能工作的时候」，**不是「这天结束时什么状态」**。

**坑 3：合并历史时，「已有记录」不能直接跳过**

实时记录（当天额度恢复时写的 `ok`）会覆盖回填的 `quota_exhausted`。
→ 合并优先级：`quota_exhausted` > `other_fail` > `ok`（与同日归并同一套口径）。

## 验收

- **回填准确性**：从 journald 回填 29 天历史，与原始日志逐日核对 → **29/29 完全一致**
- **判据自检**：7 用例全过（含假阳性防护）
- **巡检**：`PASS=95 FAIL=0 等你=2`（38 组）

## 关联

- **E83**（同一根问题的另一半：闸门跳过的日子留洞）—— 本条是「额度耗尽」这条线的**持续性**视角
- **E71**（连续失败被判成 WARN）—— 本条是「持续耗尽被判成等你 → 不告警」的翻版
- **E66**（假警报驯化）—— 坑 1 就是它的变体
- **E1**（区分「失败」和「没触发」）—— 本条区分「没额度」和「额度不足」

## 最终发现（给牛哥哥）

近 30 天额度耗尽 **589 次、24 天里有 24 天**；
最近 7 天里 **6 天**耗尽，其中 11-22 闸门跳过 daily-learning 2 次 → **那天的产出被丢掉了**。

→ **这不是偶发，是结构性不足** → 充值/加第二把 key。
→ 而在充值之前，这一条**不会自动告警**（它在「等你」桶里），需要你主动看。
