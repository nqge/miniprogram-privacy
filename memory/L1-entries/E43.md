### E43：被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言

> 本条讲：**被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言**

**场景**：2026-10-27 08:20。我给【S】组加断言时，发现 shell 报
`line 1031: to_report: unbound variable`。
一开始以为是**我刚插入的代码**把脚本搞坏了 —— 查了半天。

**真根因（是 pre-existing，不是我的锅）**：
```bash
PY5
)to_fail=$(echo "$to_report" | grep -oP '__TO_FAILED__=\K[0-9]+')
```
heredoc 的结束符 `PY5` 和下一个赋值写在了**同一行**（`)` 后面直接跟内容）
→ shell 把 `to_fail=...` 当成 heredoc 结束符之后的一部分
→ **`to_report` 这个 shell 变量从来没被赋值**
→ `set -u` 触发 `unbound variable`
→ 而这一组写的是 `python3 - << 'PY5' 2>/dev/null` → **报错被吞掉**
→ 脚本继续跑，输出里这一组**什么都没有**
→ 但它最后无条件 `PASS=$((PASS + 1))` → **巡检照样显示 PASS**

→ **【R】组（cron 超时余量对比）其实一直是死的**，
而且死得很像样：它在结果里显示 PASS，只是从没真正算过任何东西。

**陷阱**：
- 「我以为它在跑」≠「它在跑」—— **有输出**才叫跑过
- `2>/dev/null` 是**最常见的静默失败制造机**：
  它的本意是「这组检查失败不要炸掉整个巡检」，
  但副作用是**把这组自己的 bug 也一起吞了**，
  于是「这组坏了」和「这组检查出真问题」长得一模一样
- shell 里「heredoc 结束符 + 紧跟内容」这种写法极隐蔽：
  `bash -n` **语法检查通过**，肉眼扫过去也像正常的闭括号

**岔路口**：
1. **写完断言要验「它有没有真的输出」** ——
   不是看 `PASS` 计数（那是无条件 +1 的），
   而是看**这一组名下有没有实际断言行**
   → 我的做法：脚本化检查每组至少有一条 ✅/❌/⏳/⚠️
2. **`2>/dev/null` 要配一个「我确实没报错」的兜底**：
   至少把 stderr 存到变量，出错时打印出来；
   而不是直接扔掉
3. **别把「命令没跑」和「检查通过」混为一谈** ——
   变量未赋值时 `grep` 拿不到内容，`to_fail` 会是空 → `${to_fail:-0}` → **0 = 通过**
   → **失败被当成通过**（E26「读到上次的成功结果」的又一次）
4. **自己改脚本时出的错，要先分清是不是「本来就有」** ——
   我一开始怪自己插错了位置，其实那个 `)to_fail=` 早就在 git 里了
   → 查 `git show HEAD:文件` 对比，比凭感觉靠谱

**证据**：
| 项 | 改前 | 改后 |
|---|---|---|
| 【R】组 | 静默死亡（有 PASS 无输出） | **真实输出 2 条断言** |
| 巡检现状行 | 每次自增，累积 13 行 | **恒为 1 行**（标记块） |
| 「巡检现状」锚点 | 靠「长得像活行」推断 | **BEGIN/END 显式标记** |
| 全组输出体检 | 无 | **21/21 组都有实际输出** ✅ |

**延伸**：E26 讲「读到上次的成功结果 → 静默失效」，
E42 讲「断言量错了东西 → 假的 PASS」，
本条讲「**断言根本没跑 → 同样的假 PASS**」——
三个不同的成因，同一个症状：**PASS 不代表检查过**。
所以「PASS」这个信号本身也需要被检查（每组有没有实际输出）。
