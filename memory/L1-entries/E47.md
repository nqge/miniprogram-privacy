### E47：断言只看「最近一次」，就等于没在看历史

> 本条讲：**断言只看「最近一次」，就等于没在看历史**

**场景**：2026-10-27 11:28 心跳。巡检全绿（PASS=63 / FAIL=3 / WARN=2），
5 个 cron 的 `lastRunStatus` 全是 `ok`，3 个 announce 任务的 `lastDelivered` 全是 `True`。
**但我去翻 `cron runs` 历史时，看见了巡检完全看不见的东西**：

```
daily-reflection  总 43 次 = ok 3 次 + error 40 次
  └ 其中 2 次「status=ok 但 delivered=false」（10-26 00:35、10-21 04:27）
healthcheck      6 次里 1 次 ok-but-not-delivered（10-26 10:44）
daily-learning  20 次里 3 次 ok-but-not-delivered（10-26 09:00 / 00:36、10-21 04:29）
```

**为什么巡检看不见**：`check_cron_delivery.py` 读的是 `cron list --json` 里的
`state.lastRunStatus` / `state.lastDelivered` —— **只有最近一次**。
历史失败在那个字段里**根本不存在**。

**最毒的一点**：`ok-but-not-delivered` 的语义是
「**任务成功跑完了，但结果没送到牛哥哥手上**」。
这正是 AGENTS.md 里那句「**状态字段描述的是『任务跑完了』，不是『用户得到了结果』**」
的**反面**：断言自己就犯了这个错 —— 它断言的是「任务跑完了」，
而用户要的是「**结果送到了**」。

**⚠️ 取证时踩的一个坑（差点得出相反结论）**：
`cron runs` 的输出里，`not-delivered` 对两种完全不同的任务都出现：
- `mode=none` 的任务（teahouse-monitor / backup-audit）—— **设计上就不投递**，不是故障
- `mode=announce` 的任务 —— **是真的没送出去**
→ **看 `not-delivered` 之前，必须先看 `delivery.mode`**。
不分清就会把「正常」报成「故障」，或者反过来。

**✅ 修法**：断言从「看 lastRun」改成「**看 history**」：
```
for 每个 mode==announce 的 job:
    runs = openclaw cron runs --id <id> --limit 20
    undelivered = [r for r in runs if r.status=='ok' and r.delivered is False]
    ├ 最近一次仍未投递 → FAIL
    └ 历史有、最近已好   → WARN（带时间点，便于定位）
```
→ **一次就把 6 个之前完全看不见的静默失败抓了出来。**

**教训**：
1. **「当前值正常」不能推出「历史正常」** —— 断言要问对时间维度
   （最近一次 / 近 N 次 / 全部历史，是三个不同的问题）
2. **断言的字段要和「用户得到的结果」对齐**，而不是和「任务跑完了」对齐
3. **同一个状态码在不同 mode 下含义不同**（`not-delivered` 对 none 是正常、对 announce 是故障）
   → 判定前**必须先分组**，不能只看字段值
4. **新增断言必须做注入故障验证** —— 我把「最近一次」强制改成未投递，
   确认它会 FAIL（`__FAILED__=3`），不是只会 WARN；然后恢复

**延伸**：E7「修完根因后监控还在量修复前的测量」讲的是**时间上的滞后**；
E47 讲的是**维度上的遗漏** —— 前者是没看到「旧数据」，后者是**根本没在看那一列**。
