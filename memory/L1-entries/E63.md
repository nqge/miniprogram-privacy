### E63：先拿已知可用的对象校准探针 —— 探针错了会被误报成「全挂了」
> 本条讲：**先拿已知可用的对象校准探针 —— 探针错了会被误报成「全挂了」**

**核心断言**：批量健康探针如果**没有先在「已知活着」的对象上自检**，
它会把**「我这边没测到」**输出成**「它坏了」**——
而且批量探测的错误信号是**整齐的全红**，比零星失败更像真结论。

## 场景

2026-11-05 实测 agent 级目录里 4 个残留 provider 凭证（arkcode/glmcode/qwen/kimicode）
是否还可用的任务。第一轮**直接探 `models.json` 里的 key**：

- minimax（**正在用的主 provider**）→ **401**
- 其余 4 个 → 401 / 404 / 400

差点就此写下结论：**「全部 provider 凭证全死」**。

## 陷阱

### 陷阱一：探针读的不是「生效配置」

根因不是凭证坏，是**配置有覆盖层**：

- `models.json` 里存的是**旧 key**
- `openclaw.json` 里才是**当前生效的 key**
- 两者通过 `models.mode=merge` 合并，`openclaw.json` 覆盖前者

→ 直接读 `models.json` = **探了一台不存在的机器**。
改用**合并后的有效配置**重探 → minimax ✅ **HTTP 200（1.0s）**，
探针这才算可信；随后逐模型探完 4 个 provider，才得出**真实结论**（全部死亡）。

### 陷阱二：批量探测的失败模式天然「像真结论」

单点探测失败 → 「可能是它坏了」。
批量探测**整齐全红** → 看起来像**一场彻底的故障**。

但「全红」同样可以是**探针整体失效**的产物——
读错文件、用错端点、漏一层合并、认证头拼错，都会一次性把所有对象打成红。
**信号越整齐，越容易被当成结论，而越不容易被当成探针故障。**

### 陷阱三：已知可用的对象就是天然的对照组

讽刺的是，**系统里本来就有正确答案的样本**——正在跑的 minimax。
探针跑在它上面是免费的、零成本的、且**有确定答案**。
不去用它，等于**放弃了唯一能证伪探针的东西**。

## 岔路口

1. **批量探活前，先拿一个「已知活着」的对象试跑**。
   通过 → 探针可信，继续；不通过 → **先修探针，不要输出任何结论**。
2. **报「探针失效」和报「对象全死」要分成两种输出**。
   自检不过时脚本应**中止并明确说「探针失效」**，而不是打印一屏红色结果——
   后者会被下游（巡检、状态字段、记忆文件）当成事实继承。
3. **「配置文件里有」≠「生效配置里有」**。
   有覆盖层（merge / env / CLI flag 优先级）时，
   **必须探合并后的结果**，不能探任一原始文件。
4. **这个自检要写进脚本，不靠临场记忆**。
   临场想起来「等等，minimax 是好的吧」—— 靠的是**当时刚好记得**，
   下一次探针作者换了、对象换了，就没了。

## 为什么值得记

这是**第 6 次**「判据 / 脚本 / 产物三者结构不一致」（E52、2026-10-29、E61 缺陷 A+B、E62 漂移、本条）。
但这次的**新东西**是：

> **探针本身是一个没有元认知的组件** ——
> 它不会说「我不确定我探的是不是真的那个」。
> 而批量探测会把探针的沉默错误**放大成整齐的全红**，
> 这种形态**比零星失败更像真结论**，因此更容易被直接继承进状态字段和记忆。

配套判据：**「探针失效」必须是一种可报出的状态，而不是一种沉默的输出形态。**
