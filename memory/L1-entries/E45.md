### E45：修完根因后，监控还在量修复前的那次测量

> 本条讲：**修完根因后，监控还在量修复前的那次测量**

**场景**：2026-10-27 10:00 巡检报 `daily-learning` 耗时 772s / timeout 900s = 86%，余量告急。
但根因（E44：13 轮手工迭代字数）**在 09:24 就已修复**——加了确定性裁剪脚本，
指令也重写成「1-2 次调用收敛」。也就是说：**修复已经生效，告警却在拿修复前的旧数据报警。**

**陷阱**：这类断言不会自己知道自己的信号已经过期。
- 修复前：`lastDurationMs = 772s` 是**真实**信号 → 断言正确
- 修复后：同一个 `lastDurationMs = 772s` 变成**历史遗留** → 断言变成"永远红"
- 两者在数据库里长得一模一样，断言无法分辨

**岔路口**（两个都做，别只做一半）：
1. **判定信号本身是否还有效**——先问"这个数是修复前测的还是修复后测的"
2. **给修复留冗余，而不是等下一次运行来证明**——
   直接把 timeout 从 900s 提到 1800s（772/1800 = 43%），而不是"下次跑快了就绿了"

**证据**：
| 项 | 修复前 | 修复后 |
|---|---|---|
| timeout | 900s | 1800s |
| 772s 占比 | 86%（告急） | 43%（余量充足） |
| 【U】组判定 | ❌ FAIL | ✅ PASS |
| 裁剪脚本耗时 | — | **0.057s**（实测） |

**延伸**：E33「机制缺口比单点故障更值得修」、E42「断言量错了东西就等于没有断言」，
本条讲第三种：**断言量对了东西，但量的是历史**——
它比"量错"更隐蔽，因为它看起来一直很勤奋。

**一句话**：断言红了，先别急着修任务，先确认它量的是不是「现在」。
