### E39：共享账号就是共享配额 —— provider 变慢比 provider 挂掉更隐蔽

> 本条讲：**共享账号就是共享配额**

**场景**：2026-10-27 06:30 心跳。查 `daily-learning` 为何 362s / timeout 420s（余量仅 16%），
翻会话时间分布发现**有一次单次 LLM 调用等了 353 秒** —— 不是在等工具。

**陷阱**：把「只有一个 provider」只理解成一重后果（**挂了兜底无效**）。
真实还有第二重后果：**provider 变慢 → 所有任务一起变慢**。
而且这一重**不报错、不告警**，只表现为「时间莫名变长」，
最难归因 —— 因为每个任务单独看都「没超时」。

**根因**：所有任务共用**同一个 MiniMax 账号**。
关键线索：353 秒那段时间（19:05–19:11 UTC）**正是 backup-audit 超时失败的时段**，
两者是**互相抢同一个配额**，不是各自慢。

**实测（同账号 6 并发，256 token 输出）**：

| 场景 | 延迟 |
|---|---|
| 单个请求 | 1.8s |
| 6 个并发 | 最慢 **7.0s（3.9 倍）** |

**岔路口**：
1. **第二个 key 的价值不是「容灾冗余」，是「拆开共享配额」** ——
   两把 key 指向两个独立配额桶，慢的那把只拖慢用它的那批任务。
   把它记成「兜底」会低估价值，记成「冗余」会误以为有 key 就不挤了。
2. **退化分两类，优先级不同**：
   - **挂掉** → 有 error、有 timeout → 容易发现 → 排查成本低
   - **变慢** → 无 error、只是慢 → **最难发现** → 而它恰恰先吃掉超时余量
   → 所以要给「慢」配观测（单次调用耗时分布），不能只配错误率
3. **并发变慢要区分两种成因，别混为一谈**：
   - **E37**：瓶颈是 **CPU**（本地进程启动）→ 并行只会更慢
   - **本条**：瓶颈是**远端配额**（共享账号）→ 并行请求彼此排队
   → 判据：本地 `user ≈ real` 是 CPU 密集；本地很快但远端慢 = 远端排队
4. **发现长尾耗时先查「时间重叠」**：把慢调用区间和其他任务失败区间叠在一起，
   若重叠 → 不是那个任务自己慢，是**它们在抢同一份资源**。

**证据**：
| 项 | 值 |
|---|---|
| 单次 LLM 调用最长等待 | **353s**（daily-learning 会话内） |
| 同账号 6 并发最慢延迟 | **7.0s**（单发 1.8s，**3.9 倍**） |
| 巡检超时余量 | 420s 预算里只剩 16% |

**已做**：把并发实测数字（1.8s→7.0s，3.9 倍）与 353 秒那次等待的关联，
写进【M】长期项断言的注释 —— 让「等牛哥哥给第二个 key」这件长期项
**带上具体代价**，而不只是一句「兜底无效」。

**延伸**：E28 讲「长期项和真故障混在一起会让信号失效」，
E39 讲「**同账号多任务是隐形的长期项**」——
它在系统里表现为「大家都变慢了」，而不是「某一项坏了」，
所以永远排不进「故障」列表，只能靠实测并发延迟才能看见。
