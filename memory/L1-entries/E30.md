### E30：队列型状态只加不减 = 每次运行都在重复劳动

> 本条讲：**队列型状态只加不减 = 每次运行都在重复劳动**

**场景**：茶馆监控每 4 小时跑一次，拉取新讨论 → 写入「待蒸馏清单」→ agent 蒸馏成知识。
看起来是完整的流水线。

**陷阱**：2026-10-27 凌晨发现，`memory/teahouse-todo.json` 的 `pending` 队列里
**永远躺着同样 4 条**（#135/#138/#134/#154）—— 它们在 11:30 就已经蒸馏完了。

根因：`prompt_distillation()` **只追加，从不移除**。
```
for i in fresh:
    if n in known: continue
    existing["pending"].append(...)     # 只加
# 全函数没有一句从 pending 里删东西
```
→ 蒸馏完成后**没有任何机制**把条目移出队列 → 每 4 小时重新蒸馏同样 4 条。

**为什么巡检没发现**：健康巡检的【I】组是**间接**判定的 ——
它查「编号是否出现在某篇 memory 笔记里」，出现就报 PASS。
但它**从不检查队列本身**，所以：
- 巡检报「茶馆内容已全部蒸馏」✅
- 而队列里明明还挂着 4 条 ❌
**两个状态互相矛盾，巡检只信了对自己有利的那个。**

**岔路口**：
1. 任何「待处理队列」必须配一个**出队**路径，且出队和入队一样显式
2. 蒸馏完成的条目 → 移到 `distilled` 列表（保留编号/标题，便于追溯）
3. **`distilled` 列表也要限量**（默认 50）—— 否则只是把「只增不减」换了个字段
4. 巡检要查**队列本身的自洽性**：
   `pending ∩ distilled == ∅`（同一议题不能既待处理又已蒸馏）
5. 修的时候顺手检查：**我查的字段对吗？**
   → 我一开始查 `seen_ids`（GitHub REST 的 10 位 id）以为没去重，
   实际去重键是 `seen_numbers`（议题号）→ **4 条都在里面**
   → 差点得出「修复会被 4 小时后推翻」的错误结论

**证据**：
- 修前：`pending` 恒为 4 条，每 4 小时重蒸馏一遍
- 修后：端到端跑真实监控 → 「无新内容」，`pending` 保持 0，`distilled` 4 条
- 巡检自洽性：注入「#135 同时在两个列表」→ **正确 FAIL** ✅；正常态 → PASS ✅

**延伸**：这跟 E29 是同一类问题 —— **状态字段和真实情况脱节**。
E29 讲「别把正常报成故障」，E30 讲「别让队列状态骗过自己」。
共同点：**光看一个状态字段不够，要交叉验证**。
