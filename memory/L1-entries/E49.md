### E49：「无视规则」和「没看到规则」是两件事 —— 别拿它们当一件事报

> 本条讲：**「无视规则」和「没看到规则」是两件事 —— 别拿它们当一件事报**

**场景**：2026-10-27 13:00。并行会话查出一件重要的事：
TOOLS.md 的「等长任务」规则是 09:57（commit 6d11015）才加的，
而那个刷了 484 次长 poll 的会话 **10-25 就启动了** ——
**它的上下文里根本不可能有那条规则**。

于是【V】组报的「265 次长 poll」里，
**绝大多数根本不是「无视规则」，是「规则还没存在」**。

**为什么这个区分要命**：
把它们混在一起报，会得出「我/它在顽固违规」的结论，
进而**优化错了地方** —— 去加强提醒（没用，它本来就看不见），
而不是去修覆盖面（规则写进 TOOLS.md，但**只对新会话生效**）。

**三层机制各不相同**（都是实测出来的，不是推测）：

| 会话类型 | 拿得到 TOOLS.md 吗 | 规则来源 |
|---|---|---|
| main 会话 | ✅ 注入 | TOOLS.md |
| isolated cron 会话 | ❌ **不注入** | **它自己的 cron 指令** |
| 规则写入前启动的会话 | ❌ 当时还不存在 | 没有 |

> 实测：14 个会话里**只有 1 个**（main 会话）的首条 user message 含 TOOLS.md。
> 其余全部要靠自己 `cat` 才能看到。

**✅ 已做**：【V】组按「规则是否可见」把违规拆成四类：
```
🔴 看得到规则却违规      → 真问题（无视）
⚪ 规则生效前启动        → 不算它的账
⚪ 隔离 cron 会话        → 它看的是自己的 cron 指令
🟡 启动晚于规则但没看到  → 值得查
```
→ 真实数据：**265 次 → 5 次真问题**（`c2513949`×3 = 我自己，`ae0adb16`×2 = 并行会话）
→ 剩下的 260 次**根本不是问题**。

**⚠️ 取证踩坑（两个）**：
1. **会话文件名 ≠ session id**。`ae0adb16.jsonl` 里的 session 记录是
   `d330c561` —— 文件名是**转录文件** id，内部 id 才是会话 id。
2. **会话文件里没有 `sessionKey`** —— 那个字段只在 `cron runs` 输出里。
   → 想从会话反查它属于哪个 cron job，**不能靠会话文件**，得靠 cron runs 建映射。

**同日翻车：我自己把 4 个断言改坏了**

为统一标点，我跑了个脚本批量替换 `healthcheck.sh` 里的全角标点，
**改坏了 4 个正则**：
| 组 | 原来的正则 | 被改成 | 后果 |
|---|---|---|---|
| 【J】 | `[：:]` | `[:]` | 匹配数 0 → 报「L1 经验库没有任何条目」 |
| 【S】 | `` ` — `` | `` ` - `` | 声明列表空 → 报「漏了全部 cron 任务」 |
| 【O】×2 | `（(\d+) 条，E1–E(\d+)）` | 半角版 | 匹配不到 → **静默跳过** |

**最毒的一点**：这 4 个里有 3 个是「**匹配不到就静默跳过**」的类型 ——
它们不报错，只是**什么都不检查** → 变成「装死的断言」。
（和 E43「被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言」同一族）

**✅ 修法**：
1. 全部改成 **unicode 转义**写法（`\uff1a` / `\u2014`）——
   标点形式再被改也认得出来
2. `task_of()` 的标记匹配加 `_norm()` 归一化（**全角/半角等价**）
   + `_unescape()` 先把 `\uXXXX` 解码再比
   → **三种形式都认**：原文全角、原文半角、转义
3. **新增【X】组：巡检脚本自己的解析器自检**（`scripts/test_healthcheck_parsers.py`，10 项）
   → 验证【J】【S】【O】的解析器**在真实数据上还能解析出东西**
4. **新增【W】组的单测扩到 13 个用例**（含「半角标记也要能归类」）

> 【W】和【X】是一对：
> 【W】测「**【V】的判据**对不对」，【X】测「**其它组的解析器还能不能解析**」。
> 两者都直接抽**真身代码**跑 → 物理上无法漂移。

**教训**：
1. **「无视规则」和「没看到规则」必须分开报** —— 混报会优化错地方
2. **规则的有效性取决于加载时机** → 判据里要问「它启动时规则存在吗」
3. **规则在哪也是机制问题**：isolated 会话拿不到工作区上下文文件
   → 想让规则到达它们，得写进**它们自己的指令**
4. **正则里的全角标点极其脆弱** —— 一次「批量格式化」就能把断言改坏，
   而且坏掉的断言**看起来和好断言一样正常**
   → 正则用 unicode 转义 + 给「解析器」本身写测试

**岔路口**：
- ❌ 「规则写进文档就行」—— 得想清楚**谁能看到那份文档**
- ✅ 每个渠道（TOOLS.md / cron 指令）各自覆盖对应的会话类型
- ✅ 断言要能区分「**做不到**」和「**不去做**」

**延伸**：E41「指令是说明不是约束」→ E49 补一刀：
**「说明」本身还要看它送到了谁那里**。
规则写进 TOOLS.md 只覆盖 main 会话；cron 会话得写进 cron 指令。
