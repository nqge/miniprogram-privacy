### E50：「等法」只是第二层问题 —— 第一层是「这活本来该谁跑」

> 本条讲：**「等法」只是第二层问题 —— 第一层是「这活本来该谁跑」**

**场景**：2026-10-27 14:48 心跳。巡检【V】组持续报「12 小时内 251 次长 poll（timeout>60s）」。
我按 E35（poll 会等满 timeout）的思路去查：把每次长 poll **前面紧邻的那条 exec 完整命令**提出来归类。

结果和预期完全不同：

| 会话 | 长 poll 次数 | 在等什么 |
|---|---|---|
| 0d127a42 | 170 | 混合（多脚本自检） |
| 1eb7251b | 46 | **42 次是 `healthcheck.sh`** |
| c2513949（我） | 3 | `healthcheck.sh` |
| 其余 | 分散 | 各自的一次性脚本 |

**84% 的长 poll 在等同一个脚本** —— `scripts/healthcheck.sh`（实测 ~3 分钟）。
而那个脚本**是 07:00 cron 的职责**。

**两层问题被混成了一层**：
1. 第一层（真根因）：**我在做本来不属于我的活** —— 反复手动全量重跑巡检
2. 第二层（表面症状）：用 250–290s 的 poll 去等一个 180s 的脚本 → **每次都等满**

E35 只说了第二层。如果我只按 E35 修（把 timeout 调小到 10s），
断言会变绿，但**重复劳动还在** —— 一个勤快的 agent 可以**合规地**做很多没价值的重复劳动。

**为什么没人发现**：
【V】组的判据只问「poll 的 timeout 是不是 > 60s」，
**没问「这个被等的脚本值不值得跑」**。
断言能查「怎么等」，查不了「该不该等」。

**教训**：
1. **先问归属，再问等待方式** —— 动手前先问「这活本来归谁管」
2. **合规 ≠ 有价值**：把 timeout 调小可以骗过断言，但没让世界变好
3. **断言要能区分「没等好」和「白等」** —— 前者改等法，后者改归属

**岔路口**：
- ❌ 「把 timeout 调小就解决了」 —— 治标，且会让断言失真
- ✅ 「这活该由 07:00 的 cron 干，我不该手动重跑」+「真要跑就用 `sessions_spawn` 推送式等」
- ✅ 断言要问两层：**「等法合规吗」** + **「这活该由谁跑」**

**延伸**：E35「poll 会等满」→ E49「规则可见性」→ E50「任务归属」。
三层叠加起来才看得清：**等法 → 规则 → 归属**，缺一层就会优化错地方。
