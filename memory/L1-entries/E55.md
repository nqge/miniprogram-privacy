### E55：没内容就不该投递 —— 同一状态码，正常与故障要问「本该发什么」
> 本条讲：**没内容就不该投递 —— 同一状态码，正常与故障要问「本该发什么」**
**发现时间**: 2026-10-29 08:01

## 现象

今早 08:00 茶馆 cron 跑完，`delivered=false / not-delivered`。
按 E47 的判据（`mode=announce` + `delivered=false` = 真故障），
这**应该**是一条 FAIL。但它不是。

## 为什么不是故障

那一次 cron 的实际输出是：

```
[teahouse] 拉取 issue 共 96 条 / 新增 0 条 / 无新内容
```

**没有新内容 → 没什么值得打扰牛哥哥的 → 不投递是正确的。**

而 10-28 那批「运行成功但未投递」是**真的故障**：任务有内容，
结果没送到手上。两者字段一模一样，性质完全相反。

## 真正的洞：字段本身没有「本该发什么」这个维度

`check_cron_delivery.py` 现在的判据链是：

```
mode == "none"     → 跳过（设计如此）
mode == "announce" → delivered=false 就是 FAIL/WARN
```

**它在 `mode=announce` 这一层里不再往下分。**
可「announce 型的任务」里，既可能有内容，也可能本来就无事可报 ——
判据缺了「本该发什么」这一维，就只能靠人肉读输出。

## 岔路口

**先确定「本次是否真的有东西要发」，再判 delivered。**

可行的判据按成本从低到高：

| 判据 | 怎么取 | 适用 |
|---|---|---|
| 产出物计数 | 任务写出的产物文件数 / 队列长度 | 茶馆类（`teahouse_state.json` 的 `pending`） |
| 输出摘要 | run 记录里的 summary / 输出文本 | 任何 announce 任务 |
| 产出新鲜度 | 产物 mtime vs 本次 run 时间 | 有产物但可能为空的文件型任务 |

> **判据要看「本该发什么」，不能只看 `delivered` 字段。**

## 陷阱

- **别把「没告警」当「没做事」** —— 今天 08:00 那次跑完全程正确，只是**正确地决定不打扰**。
  反过来更危险：为了「留点痕迹」硬写一篇笔记，把空内容包装成洞察
  （同一条的另一面，10-29 00:00 茶馆巡检也踩过）。
- **别为了消告警而放宽断言** —— 正确做法是**加一个维度**（本该发什么），
  不是把 `delivered=false` 一律放过（那样 E47 抓出的 6 次真故障会重新被吞掉）。

## 关联

- 与 **E47** 同族且更深一层：E47 说「先按 `delivery.mode` 分组再判」；
  本条说「**分组还不够，同一 mode 内部还要按『本该发什么』再分一层**」。
- 与 **E53** 同族：都是「**状态字段 ≠ 用户得到的结果**」——
  E53 讲时间维（快照 vs 现在），本条讲内容维（发了什么 vs 该不该发）。

## 关联断言（待落地）

`scripts/check_cron_delivery.py` 的 announce 分支应补：
**取该次 run 的产出摘要 → 无产出则标为「有意不投递」而非 FAIL**。
改动前必须做注入验证：构造「有产出但未投递」→ 仍须 FAIL ✅
