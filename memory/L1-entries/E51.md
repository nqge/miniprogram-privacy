### E51：常亮的告警会训练你忽略它 —— 真故障反而看不见

> 本条讲：**常亮的告警会训练你忽略它**

**发现时间**: 2026-10-27 20:45

## 现象

备份审计每次都报：
```
[⚠️  WARN] 工作区有 1 个未提交改动
```
追查发现来源是 `memory/teahouse_state.json` —— **纯运行时状态**
（`seen_ids` + `last_check` 时间戳），每 2 小时的 `teahouse-monitor` cron 都会改它。

→ **每次跑完工作区必然是脏的** → **每次备份审计必然 WARN**。

## 为什么这是个问题

不是「多一条噪音」那么轻 —— 它是 **E28（长期项和真故障混在一起）** 的变种：

> **一个永远不会安静的告警，会训练你忽略它。**
> 当「改代码忘了提交」这种**真问题**出现时，
> 它和这条常亮的噪音长得一模一样 → **你不会注意到**。

告警的价值不在于「报了多少」，在于「**真出事时能不能一眼看见**」。

## ⚠️ 但不能简单 gitignore

`seen_ids` 是**有价值的数据**：丢了 → 换机/重装后 96 条 issue 被重复蒸馏。
它**必须随远端一起备份**。

→ 所以要改的是「**判定**」，不是「入库与否」。

## ✅ 正确解法：区分「运行时状态」与「真实改动」

```bash
RUNTIME_STATE_FILES="memory/teahouse_state.json"
DIRTY=$(... | grep -vF -f <(printf '%s\n' $RUNTIME_STATE_FILES) | grep -c .)
```
- 剔除后 = 0 → **PASS**（附注「N 个运行时状态文件有变动，属正常」）
- 剔除后 > 0 → **WARN**（真改动，该提交了）

效果：`PASS=19 FAIL=0 WARN=0` **且能保持** —— 下次 cron 跑完仍是 PASS。

## 通用判据

> **问「这个告警会不会永远亮着」。**
> 会永远亮着 → 它不是告警，是**状态** → 要么改成 PASS，要么改成「实时查询」，
> 绝不能让它占据 WARN 位。
