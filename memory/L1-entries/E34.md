### E34：手写「说明清单」的文档必然过期 —— 让它从源头生成

> 本条讲：**手写「说明清单」的文档必然过期 —— 让它从源头生成**

**场景**：2026-10-27 03:20，查 `healthcheck` cron 任务的指令时发现：
```
**当前 FAIL 的 14 类含义**（2026-10-26 实测整理，共 13 组断言 A–M）：
- A ... - M
```
而脚本里实际有 **16 组（A–P）** —— 今晚新增的 N/O/P **三组不在指令里**。

**陷阱（两层）**：
1. **指令过期了**：明早 07:00 真出故障时，agent 拿到的是一份**过期的手册** ——
   N/O/P 的失败它根本不知道怎么解释，只能瞎猜或忽略
2. **而且我差点重犯同样的错**：发现时第一反应是「手动补三行」→
   那只是把「一次性修好」当成「修好了」。**手动补 = 下一个新组还会漏**

**这是 E20 的第三次翻版**：
- E20：验证了脚本，却没验证**指令**
- E31：改了指令，却没改**机制**
- E34：连「指令里的清单」本身都成了需要维护的**派生数据** ——
  和 E32（计数会过期）同源

**岔路口**：
1. **派生数据不要手写**：指令里的「FAIL 含义清单」**从 healthcheck.sh 生成**
   → 新增 `scripts/gen_healthcheck_instruction.py`
   → `extract_groups()` 从 `echo "【X】..."` 里正则提取组号和名称
   → `build_block()` 生成清单 → `--update` 用 CLI 写回 cron
2. **再加一道断言**，让「过期」可被自动发现：
   → 新增【Q】cron 指令是否与脚本同步（16 → 17 组）
   → 自动对比：脚本里的每组在 cron 指令里都有说明？组数一致？
3. **验证方式**：**注入原始 bug** —— 从 cron 指令里删掉 N/O/P 三行 →
   【Q】**正确 FAIL**「cron 指令缺 3 组说明（N, O, P）」→ 再用生成器恢复

**证据**：
- 注入原始 bug → 【Q】**正确 FAIL**，点名 N/O/P ✅
- 恢复 → PASS「cron 指令与脚本同步（17 组）」✅
- **意外收获**：加上【Q】断言后**第一次跑就报了 FAIL** ——
  「cron 指令缺 1 组说明（Q）」。因为**我刚加的 Q 组自己也忘了同步**！
  → 断言**当场抓到了我自己刚犯的同类错误**，比事后 review 可靠得多

**延伸**：E32 说「派生数据必然过期，要让过期可被自动发现」，
E34 多走一步 —— **「让派生数据不手写」比「让它可被发现」更彻底**。
两者不冲突：前者防患，后者兜底。今天两条都用上了。
