### E65：失败计数是原始计数，不含调度频率与错误种类 —— 别用「连续 N 次失败」直接推「已停摆」
> 本条讲：**失败计数是原始计数，不含调度频率与错误种类 —— 别用「连续 N 次失败」直接推「已停摆」**

**核心断言**：巡检里的「最近 20 次里有 N 次 error、最长连续 M 次失败」
**只统计次数，不统计上下文**——它不知道这个 job 多久跑一次，
也不知道**每一次失败是不是同一个原因**。
→ 于是「连续 14 次失败」这句话，既可能是「服务彻底死了」，
也可能是「**周频 job 在 20 周里撞了 14 次同一个已修好的 bug**」——
**两者在数字上完全无法区分**。

## 场景

2026-11-07 09:54，我读到 07:00 巡检的【D】组 WARN：

```
daily-reflection 最近 20 次里有 16 次 error，其中最多【连续 14 次】失败
```

我据此判断「这个任务大概率已经实际停摆，而不是偶发抖动」，
并把它列为**需要牛哥哥单独查运行日志**的事项。

查完整 45 次运行历史后，**结论几乎完全相反**：

| 项 | 巡检 WARN 说的 | 实际 |
|---|---|---|
| 调度 | 描述写「每天22点每日反思」 | `0 22 * * 0` = **每周日**一次 |
| 「连续 14 次失败」 | 14 个连续失败 | 其中 **11 次是 `AxiosError: 400`**（05-14 → 10-18） |
| 最近一次 | 11-01 22:00 失败 | **11-03 08:51 补跑：ok / delivered / 80.9s** |
| 当前状态 | 疑似停摆 | `consecutiveErrors: 0`、`lastRunStatus: ok` |

**任务完全健康**，最近一次成功投递。

## 陷阱

### 陷阱一：计数没有「频率」这个维度

`最近 20 次` 对**日频 job** 是 20 天，对**周频 job** 是 **20 周**。
同一个「20 次里失败 16 次」，日频是 80% 失效率（很严重），
周频是 5 个月里的 16 次（可能全集中在某个已修复的历史 bug 上）。

→ **读计数前必须先知道 job 的调度表达式**（`cron list` 里就有）。

### 陷阱二：计数没有「错误种类」这个维度

那 14 次连续失败里，其实是**三种不同的病**：

1. `AxiosError: status code 400` —— 11 次。持续 1.7s–167s 不等、**没消耗 token**
   → 是请求本身被拒（格式/参数），不是「跑太久被砍」。
2. `cron: job execution timed out` —— 恰好卡在 **180.1s**（180193 / 180146 / 180384 ms）
   → 是当时的 timeout 上限。timeout 后来提到 900s → **这类绝迹**。
3. `All models failed (3): rate_limit` —— MiniMax 429 额度耗尽，与已知长期项同源。

**把它们合并成一个数字「连续失败 14 次」，等于把三个独立的因果链压成一条**——
然后我就会去查一个「不存在的、正在持续的系统性故障」。

### 陷阱三：失败 ≠ 没干活

有一次运行（10-11）`status: error`，但 `summary` 完整存在、
`memory/2026-10-11.md` 确实写入了、32k tokens 也真的消耗了——
**只是响应尾部的 HTTP 400 让整个 turn 记成了 error**。
→ 「error」是**状态字段**，不是**事实**（这跟 E62 的「漂移不产生错误信号」是同一族）。

### 陷阱四：失败的时间分布本身就是答案

45 次运行按时间一排，「连续失败」是 **05-14 → 10-18 一整段**，
10-21 起开始出现 ok。**「连续」这个词只在窗口内成立，
出了某个时间点它就断了**——不画出时间线，只看聚合计数就会漏掉这个断点。

## 岔路口

看到「连续 N 次失败」时，**先做这三件事，再决定要不要报警**：

1. **看调度表达式** → `openclaw cron list`：
   算出这次窗口实际覆盖多长时间（日频？周频？月频？）。
2. **看错误种类分布** → `openclaw cron runs --id <id> --limit 45`：
   按 `error` 字段**分类计数**。一类 vs 三类，是完全不同的处置。
3. **看最近一次的真实状态** → `state.consecutiveErrors` / `lastRunStatus` /
   `lastDeliveryStatus`。**连续失败计数是历史，最近一次状态才是当下。**

补充：把时间线**打印出来**（按日期排序），不要只取聚合数——
**「连续」的边界只在时间线上才看得见**。

## 为什么值得记

这是**判据设计**层面的事，和 E61/E62/E63/E64 是同一个家族：

> **一个统计量如果丢掉了关键维度，它的聚合值就无法支撑结论。**

- E61：剥/装不同源 → 作者原话被静默改写
- E62：派生副本漂移 → 合法但旧，不产生错误信号
- E63：探针没校准 → 「全挂了」的误报
- E64：内容放错容器 → 报错语言指向错误方向
- **E65：计数丢掉维度 → 「疑似停摆」的误报**

**这次的误报代价是真实的**：我上一轮把「daily-reflection 可能已停摆」写给了牛哥哥，
而那个任务好好地在跑。**如果牛哥哥照着去排查，反而会浪费时间在一个不存在的问题上**——
**误报的代价不是「没报」，而是「让人去查不存在的东西」。**

而修法不是「把这条 WARN 删掉」（那是把信号源也删了），
是**给判据补维度**：失败计数应该**按错误类型分组**、
**按调度频率换算时间窗**，并且**永远带上最近一次的真实状态**。

## 待落地（未实现）

【D】组的判据目前输出的是聚合数字。建议后续改成三段式：
- `按错误类型分组的历史计数`（而不是一个总数）
- `这次窗口覆盖的真实时长`（用调度表达式换算）
- `最近一次的实际状态`（永远显示，不折叠进计数）
