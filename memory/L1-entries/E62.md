### E62：派生副本的漂移不产生错误信号 —— 「自动生成的」比「手工维护的」更不值得检查
> 本条讲：**派生副本的漂移不产生错误信号 —— 自动生成的东西没人检查**

**核心断言**：派生副本（渲染出来的汇总文件）漂移到旧版时，
**不产生任何错误信号** —— 主库合法、断言全 PASS、检索全命中，
只是**内容是旧的**。而「自动生成」会让人**降低警惕**，却**不降低腐烂概率**。

## 场景

2026-11-04 修 L1 入库脚本（E61）时顺手做了一次**全量重跑**，
捞出一条 8 天前就该同步的旧条目：**E39 的独立文件在 `346a32b`(10-27) 就改过，
主库 `memory/L1-experience-library.md` 里的 E39 却从未重新同步**。

这 8 天里：主库是合法 Markdown、每条恰好一行「本条讲」、巡检全 PASS、检索自检 61/61 PASS。
**没有任何一个信号说「主库过期了」。**

## 陷阱

### 陷阱一：把「主库由脚本渲染」误当成「单一真相源」

自动生成听起来比「两份手工维护」更可靠。
但**自动生成 ≠ 自动同步**：入库脚本只在**新增**时跑，
一条经验被**修改**时（改独立文件），**没人会想起去重跑渲染**。

→ 派生副本就变成了**第二份真相**，而且是「需要人记得触发同步」的第二份。

### 陷阱二：自动生成的东西反而更不会被检查

人的检查直觉是「盯手写的地方」——手写的东西显然会腐烂。
可**自动生成的**东西也有腐烂路径：**生成器只被部分触发**。
偏偏因为「它自动生成」，**没人会想去检查它**。

| | 手写副本 | 自动渲染副本 |
|---|---|---|
| 腐烂原因 | 忘了改 | **改了源，忘了重跑** |
| 谁会发现 | 有人定期看 | **没人看一个自动生成的东西** |
| 有无信号 | 通常读着就不对 | **完全无信号（合法但旧）** |

→ **「自动生成」让人降低了警惕，却不降低腐烂概率。**

### 陷阱三：全量重跑的双重身份被低估

这次全量重跑**同时干了两件事**：修复缺陷（E61 三个缺陷），
**以及把漂移的 E39 拉齐**（副作用）。

这不是巧合——**「重跑」和「同步」本就是同一个动作的两面**。
所以「修派生副本落后」的最优解不是手工补那一条，而是**跑一次全量**。

## 岔路口

1. **发现派生副本落后 → 跑全量，不要手工补**
   手工补只修了一条，且下一次源文件再改，还是不会重跑。
2. **全量重跑必须验证幂等**：跑第二遍，diff 应当为空。
   不幂等的重跑器 = 每次全量都在引入新差异。（本次实测：一轮收敛，第二轮完全幂等。）
3. **给渲染链加「源与派生一致性」断言**：比对每条的正文哈希。
   缺了这条断言，漂移就只能靠「恰好跑了次全量」这种运气来发现。
4. **回归范围要核对**：全量重跑会改动多条条目，必须确认「只有预期内那几条被改了，
   没有附带改写」——否则一次同步操作会静默覆盖掉别人的正文。

## 为什么值得记

这是**第 5 次**「判据 / 脚本 / 产物三者的结构不一致」（E52、2026-10-29、E61 缺陷 A+B、本条漂移）。

但这次的**新东西**是：

> **当「源 → 派生」这条链只有一个「新增」触发点时，
> 派生副本会在**没有任何错误信号**的情况下长期停留在旧版。
> 而「修复手段 = 同步手段」这个性质，
> 意味着「跑一次全量」是唯一能同时解决两件事的动作。**

——前提是**全量重跑本身幂等**，否则它只是「一次性把漂移换成另一种漂移」。
