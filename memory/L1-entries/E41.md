### E41：同账号并发不是「慢的那个慢」，是**全部一起慢**

> 本条讲：**同账号并发不是「慢的那个慢」，是全部一起慢**

**场景**：2026-10-27 07:30。`daily-learning` 实跑撞了 420s 超时（E35 刚修过一轮）。
我先怀疑是自己改的东西导致的（把 SESSION-STATE.md 从 43K 砍到 4K 字符），
于是去量 provider 延迟 —— 想区分「输入变多导致变慢」和「别的任务在抢」。

**三个错误假设**（每个都先做了才排除）：
1. 「是输入量的问题」→ 不对：拆分后 input 反而**降了** 37%（82.4K → 51.9K）
2. 「是 provider 挂了」→ 不对：HTTP 200，单发能通
3. 「是并发但只有慢的那个受影响」→ **也不对**，这才是重点

**实测（2026-10-27 07:35，用正确的 anthropic 协议）**：
| 场景 | 延迟 |
|---|---|
| 单发 1 | 7.94s |
| 单发 2 | 16.94s |
| 单发 3 | 15.91s |
| **并发 4 发** | **25.55s / 25.55s / 25.57s / 27.10s** |

→ **并发 4 发时，连最快的那次也只有 25.5s —— 全部落在同一个区间。**
不是「有一个慢的拖累了」，而是**所有请求的墙钟时间一起被抬高**。

而且注意：单发就已经 7.9–16.9s（比今早测的 1.8s 慢 8 倍），
说明**当时 provider 上已经有别的负载**（并行会话正在跑 E39 的检索）——
这就是 E40 说的「还要和别的任务抢配额」的机制细节。

**陷阱**：
- 「并发只是让最慢的那个变慢」→ 直觉上很合理，但**实测不成立**：
  被限的是**共享配额桶**，每个请求都得排队，排队时间对**所有人**一样
- 「任务是同时跑的，所以各自独立」→ **不独立**：共享账号 = 共享队列
- 「单发快就说明 provider 没问题」→ 只说明**那一刻**没排队

**岔路口**：
1. **看到超时先问「同时还有谁在跑」** —— 单看一个任务的耗时永远归因不了
2. **并发要实测，不要凭直觉建模**：
   直觉模型（慢者变慢）与实测模型（全部变慢）**会导出不同的应对**：
   前者只需给慢的任务加资源，后者意味着**必须减少并发**才能救所有人
3. **手写的协议/端点要先确认**：
   我第一次用 OpenAI 格式打 `api.minimaxi.com` → 0.17s 秒回 404
   —— 那不是「provider 很快」，是**认证失败秒退**
   （我自己在 10-26 踩过同一个坑，见 TOOLS.md「测 provider 必须用对协议」）
4. **拆输入 vs 抢配额是两个不同的问题**：
   拆 SESSION-STATE 让 input 降 37%、耗时降 50% ✅ 值得做
   但它**治不了**并发 —— 超时的主因是抢配额，只能靠减少并发或第二把 key

**证据**：
| 项 | 之前 | 之后 |
|---|---|---|
| daily-learning 耗时 | 362s（超时） | **180s** ✅ |
| input tokens | 82,394 | **51,921**（-37%） |
| 超时值 | 420s（余量 14%） | **900s**（余量 80%） |
| 并发 4 发延迟 | — | 全部 25.5–27.1s |

**延伸**：E39 讲「provider 变慢比 provider 挂掉更隐蔽」，
E40 讲「测量的样本本身要真实」，
本条讲**慢的机制**：
E39 说变慢难发现，E40 说样本要选对，本条给出**变慢长什么样** ——
**所有并发请求的墙钟时间被一起抬高到同一区间**。
三者合起来：
「变慢」要靠**并发实测**才看得见（不是等它自己暴露），
测的时候要**避开别的负载**（否则分不清是谁的锅），
归因要区分**输入量**和**队列等待**（两个都存在时，先看哪个）。
