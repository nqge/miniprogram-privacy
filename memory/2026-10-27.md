2. `healthcheck.sh`【I】组加**队列自洽性检查**：`pending ∩ distilled == ∅`

### 2026-10-27 04:00–05:00 心跳 — 「任务超时」其实是「等法超时」（E35）

**起因**: 巡检报「backup-audit 运行失败（超时）」。**脚本本身只要 0.18 秒**。

**我走的弯路 —— 三个错误假设**:
| 假设 | 验证方式 | 结果 |
|---|---|---|
| timeoutSeconds 太紧 | 提到 600s | **还是超时** ❌ |
| 模型限流 | 直连 API 测 3 个模型 | 全 200 / 1.1–2.6s ❌ |
| 上下文溢出 | 构造 1.16M token 请求 | HTTP 200 但 61.5s ❌ |
| 和我的会话抢配额 | 停手后再测 | API 依然快 ❌ |

**真根因**: `process(action='poll')` **每次都阻塞满 timeout**:
```
CALL 19:28:11 (timeout 120000) → CALL 19:30:12  = 121.0s
CALL 19:30:12 (timeout 180000) → CALL 19:34:40  = 268.0s
CALL 19:34:40 (timeout 240000) → CALL 19:36:41  = 121.0s
```
3 次 poll ≈ 510s → 必然撞上 job 超时。**慢的从来不是任务，是「等法」。**

**✅ 已做**:
1. **backup-audit / healthcheck / teahouse-monitor 的 cron 指令加「【等待方式】」说明**：
   - ❌ 一次长 poll 等满 → ✅ `exec(yieldMs=10000)` + **每 10 秒短 poll**
   - 判断标准：**先量脚本耗时**（`time bash xxx.sh`）
2. **【R】断言改为「脚本耗时 vs 超时」对比**（不再只看 job 状态）：
   - 脚本 < 5s 但因超时失败 → **FAIL**，并直接指出「慢的是等法不是任务」
   - timeout 余量差异过大 → WARN
3. **timeoutSeconds 300 → 600**（第二道防线，不是第一道）

**验证（端到端）**:
- 修复前：300.1s 超时 → 600.0s 超时 → 600.0s 超时
- 修复后：**47.2s ✅ 成功** —— 运行历史里 status=ok
- 【R】断言：FAIL → **转 PASS** ✅

**新增 E35** 入库（35 条，35/35 可检索）：
「任务超时 ≠ 任务慢 —— 先量「等待方式」再调「超时值」」

## 📚 每日学习（2026-10-27）

> 本条讲：**被 `2>/dev/null` 吞掉的报错 = 一个一直在装死的断言**

今晨 shell 报 `to_report: unbound variable`，真根因却是 pre-existing：heredoc 结束符与赋值同行，变量从未赋值；那组带 `2>/dev/null`，报错被吞掉、**输出为空**，却无条件 `PASS=$((PASS+1))`。【R】组一直显示 PASS，从没真正算过。

它**死得像个健康检查**。`PASS` 计数无条件 +1，不是证据；证据是**这组名下有没有实际断言行**。`2>/dev/null` 是最常见的静默失败制造机：本意是「这组失败别炸掉巡检」，副作用是把这组自己的 bug 一起吞，于是「这组坏了」和「这组查出真问题」一模一样。

**可立即执行的对策**：给巡检加元断言——每组至少一条 ✅/❌/⏳/⚠️ 输出，缺失即 FAIL。
