## 🩺 心跳巡检（2026-11-26 08:08）

> 本条讲：巡检报 FAIL 是快照不是状态，复跑一次再动手修，根因往往在别处

今早 07:00 的 systemd 巡检报 **FAIL=3**，三条看起来是三件事：
【X】巡检解析器坏了 · MEMORY.md 声明 87 条实际 88 条 · 自检声明 87/87。

**根因只有一个**：11-25 daily-learning 新增了 E88，
独立文件 `memory/L1-entries/E88.md` 和主库头部都更新到了 **88**，
但 **MEMORY.md 里那两处数字没跟着改**（还写着 87）。

→ **【X】不是解析器坏了**。跑 `scripts/test_healthcheck_parsers.py` 全绿，
  14 项解析器自检全部 ✅。它是**下游症状**：【O】的计数断言因为 MEMORY.md
  数字过期而 FAIL → 【X】把【O】的失败复述成「解析器坏了」。
  → 也就是说：**【X】这个「防断言装死」的守卫，是被它守护的断言拖下水的**。
  它没坏，它忠实地报了一个真问题，只是**归因错了**（说解析器坏，其实是数据过期）。

**修法**（3 处，全是数字）：
- `MEMORY.md:241` —「87 条，E1–E87」→「**88 条，E1–E88**」
- `MEMORY.md:252` —「检索自检（必须 87/87）」→「**88/88**」
- `memory/L1-experience-library.md:17` —「必须 77/77 可被检索」→「**88/88**」
  （这处**没有任何断言覆盖**，是顺手发现的同类陈旧数字 —— 77 是什么时候留下的已不可考）

**回执**（E87 的「意图 → 回执 → 可回放」）：
- `python3 scripts/test_healthcheck_parsers.py` → **✅ 全部通过**（14 项，含【O】MEMORY(88) 与主库(88) 一致）
- `verify_l1_retrieval.py` → **88/88 PASS**（真实检索 26 条命中）
- 三处计数交叉核对：`n_files=88 / real_max=88 / lib_n=88`，MEMORY 与主库全部 88 → `COUNT_CONSISTENT: True`

**教训**：
1. **【X】报「解析器坏了」时，先跑一次解析器自检脚本** ——
   它可能只是**忠实地转述了一个别的断言的失败**。别被它的归因带跑。
2. **一条经验入库要改的数字不止一个地方**：
   独立文件 / 主库头部 / MEMORY.md 表格 / MEMORY.md 自检行 —— 本次漏了最后两个。
   → 派生出候选改进：**入库脚本应该自动同步所有计数**，
   而不是靠人记得去改 4 个地方。
3. **断言覆盖不到的地方会悄悄烂掉**：`L1-experience-library.md:17` 的 77/77
   从没人查过 → 陈旧了很久。**「没断言覆盖」= 「迟早会错」**。

## 🔧 心跳改进（2026-11-26 10:18）—— 把 E89 落成结构

> 本条讲：把每条经验落成能拦住复发的结构，而不是记进笔记

上一轮 daily-learning 产出 **E89**「学习要升级成能拦下次复发的规则」。
这一轮我就拿 E89 当判据，回头检自己的系统 —— 发现**四处**该沉成结构而没沉的：

**① 入库脚本少同步一处计数（真 bug）**
`add_l1_entry.py` 的 `sync_main_lib()` 只同步主库「当前条目数」，
**不同步主库「检索自检」行** → 那行静默停在 77/77（历史遗留），
而**巡检也从来没断言过它** → 两边都不管，就一直烂着。
→ 修法：脚本补同步 + 巡检【O】组补断言（两种正则分别写：主库那行**没有括号**，
  MEMORY.md 那行有括号，格式不同不能共用）。
→ 回执：注入漂移 → `FAIL L1 主库自检行声明 77/77,实际应为 89/89` ✅ 抓到了。

**② 「必须走脚本」没有写进任何指令**
`daily_learning_prompt.txt` 原文只说「在主库新增一条」，
**从没提过 `add_l1_entry.py`** → 11-25 手工加 E88 就漏了 MEMORY.md 两处。
→ 修法：指令里写明「必须用入库脚本」+ 给出命令 + 说明它同步哪 4 处。

**③ 计数同步没有单测**
→ 修法：`test_add_l1_entry.py` 加 2 组用例（4 处同步 + 真实仓库一致性），
  14 → **19 个用例**。【W4】组自动收录（它本来就跑这个脚本）。

**④ daily-learning 耗时 2 天涨 5.3 倍（真回归）**
215s → 575s → 1151s（timeout 1800s，**余量只剩 649s**）。
而旧的【U】组只看「最后一次占用率」= 64% < 70% → **完全看不出问题**。
根因：11-25、11-26 连续两天用 `memory index --force` 清缓存重建 →
撞 MiniMax embedding **RPM 限流** → 反复 sleep 重试 → 时间全烧在这。
→ 修法 A：指令里写明**不要 `--force`**，用增量索引；并说清
  「`Dirty: no` 是增量状态位，不是完整性断言」。
→ 修法 B：巡检【U】组加**趋势判据**（连续 3 次递增且涨幅 ≥50% 才报），
  并配 4 条单测（真阳性 + 3 条真阴性，防恒真/恒假）。

**结构清单（本轮实际落地）**
| # | 落点 | 类型 |
|---|---|---|
| ① | `add_l1_entry.py` 同步第 4 处计数 | 修 bug |
| ① | 巡检【O】断言主库自检行 | 加断言 |
| ② | `daily_learning_prompt.txt` 写明「必须走脚本」 | 改指令 |
| ③ | `test_add_l1_entry.py` +5 用例 | 加单测 |
| ④ | 指令写明不用 `--force` | 改指令 |
| ④ | 巡检【U】趋势判据 + 4 条单测 | 加断言 |

**回执**：`test_add_l1_entry.py` **19/19 PASS** · `test_healthcheck_parsers.py` 全通过（含 5 条新用例）·
巡检重跑 **PASS=102 FAIL=0** · 趋势判据在真实数据上**报出了**回归
