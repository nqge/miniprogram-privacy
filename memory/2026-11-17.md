### 09:00 闸门按预期跳过 daily-learning（上游 529，不是额度问题）

**触发**：systemd `openclaw-daily-learning.timer` → `daily_learning_gate.py` → 额度预检。
预检连试 3 次（25s/50s 退避）全部拿到 **HTTP 529 overloaded_error**（"当前服务集群负载较高"，
错误码 2064）→ 闸门关闭，`GATE_RESULT=skipped reason=upstream_busy`。

**这一轮的判据完全按设计工作（E66 的价值在这里显形）**：
- reason 写的是 `upstream_busy` 而**不是** `quota` → 【G2】断言报的是
  「最近一次被闸门跳过（原因 upstream_busy），连续 1 次」= **WARN**，
  **不是**「额度长期枯竭，需要充值（E74）」。
  → 上游抖了 3 次，**没有**让牛哥哥为一个不是他的问题掏钱。

**实测确认的几件事**：
1. **不是我们的配置问题**：gateway 正常（pid 2514449, active）· 嵌入代理正常
   （journalctl 显示 07:01 还有成功调用）· 记忆检索正常（`openclaw memory search`
   立刻命中 E74）→ **只有 chat/completions 这条路被上游堵了**。
2. **小请求能过，大请求被拒**：直连 `api.minimaxi.com` 发 `max_tokens=5` → **HTTP 200, 1.05s**；
   但预检的 15000 token 探测 → 529。逐步降探针量：15000 ❌ / 8000 ❌ / 3000 ✅（重试后过）/ 2000 ❌
   → **是上游集群按负载排队，不是有没有额度的问题**。
3. **备用 provider 全是死的**（实测发请求，不是看配置）：
   - `arkcode` → HTTP 404「该模型不支持 coding plan」
   - `glmcode` → HTTP 401「身份验证失败」
   - `qwen` → HTTP 400「Access denied, 请确认账户状态正常」
   - `kimicode` → HTTP 403「当前订阅没有 Kimi Code 权限」
   → **fallback 链 2 项又都在 minimax 同账号下**（【M】的 WARN 是**准的**，不是误报）。
   **结论：MiniMax 是当前唯一活着的路，而它现在在上游过载中。**

**可立即执行的对策**：把 `daily_learning_gate.py` 的预检探测量做成可配置
（现在 `--probe-tokens` 只有 `quota_preflight.py` 有，闸门**没透传**，写死 15000），
并在 529 时**降档重试**而不是直接判死 —— 实测 3000 token 能过，
说明"15000 过不去"≠"这活干不了"。

**教训**：**「上游过载」和「额度枯竭」在闸门里的处置完全不同** ——
前者等几分钟，后者要充值。E66 那个修复（reason 不能写死 quota）今天**第一次在真实事故里救了场**：
如果当时写死 quota，连续 3 次 529 会被报成"额度枯竭，请充值"，
牛哥哥就会拿着一条**假警报**去给一个没问题的服务付钱。
