### 09:00 闸门按预期跳过 daily-learning（上游 529，不是额度问题）

**触发**：systemd `openclaw-daily-learning.timer` → `daily_learning_gate.py` → 额度预检。
预检连试 3 次（25s/50s 退避）全部拿到 **HTTP 529 overloaded_error**（"当前服务集群负载较高"，
错误码 2064）→ 闸门关闭，`GATE_RESULT=skipped reason=upstream_busy`。

**这一轮的判据完全按设计工作（E66 的价值在这里显形）**：
- reason 写的是 `upstream_busy` 而**不是** `quota` → 【G2】断言报的是
  「最近一次被闸门跳过（原因 upstream_busy），连续 1 次」= **WARN**，
  **不是**「额度长期枯竭，需要充值（E74）」。
  → 上游抖了 3 次，**没有**让牛哥哥为一个不是他的问题掏钱。

**实测确认的几件事**：
1. **不是我们的配置问题**：gateway 正常（pid 2514449, active）· 嵌入代理正常
   （journalctl 显示 07:01 还有成功调用）· 记忆检索正常（`openclaw memory search`
   立刻命中 E74）→ **只有 chat/completions 这条路被上游堵了**。
2. **小请求能过，大请求被拒**：直连 `api.minimaxi.com` 发 `max_tokens=5` → **HTTP 200, 1.05s**；
   但预检的 15000 token 探测 → 529。逐步降探针量：15000 ❌ / 8000 ❌ / 3000 ✅（重试后过）/ 2000 ❌
   → **是上游集群按负载排队，不是有没有额度的问题**。
3. **备用 provider 全是死的**（实测发请求，不是看配置）：
   - `arkcode` → HTTP 404「该模型不支持 coding plan」
   - `glmcode` → HTTP 401「身份验证失败」
   - `qwen` → HTTP 400「Access denied, 请确认账户状态正常」
   - `kimicode` → HTTP 403「当前订阅没有 Kimi Code 权限」
   → **fallback 链 2 项又都在 minimax 同账号下**（【M】的 WARN 是**准的**，不是误报）。
   **结论：MiniMax 是当前唯一活着的路，而它现在在上游过载中。**

**可立即执行的对策**：把 `daily_learning_gate.py` 的预检探测量做成可配置
（现在 `--probe-tokens` 只有 `quota_preflight.py` 有，闸门**没透传**，写死 15000），
并在 529 时**降档重试**而不是直接判死 —— 实测 3000 token 能过，
说明"15000 过不去"≠"这活干不了"。

**教训**：**「上游过载」和「额度枯竭」在闸门里的处置完全不同** ——
前者等几分钟，后者要充值。E66 那个修复（reason 不能写死 quota）今天**第一次在真实事故里救了场**：
如果当时写死 quota，连续 3 次 529 会被报成"额度枯竭，请充值"，
牛哥哥就会拿着一条**假警报**去给一个没问题的服务付钱。

## 🔍 10:35 心跳补记（闸门第一次真跑 —— 「一次决策两条记录」把连续段打断）

今天 09:00 闸门第一次真被 timer 唤醒 → 上游整点过载（529），跳了几轮，
09:38 上游恢复才放行 → **闸门架构的第一次真实检验**。

但【G2】一开始**漏报**（说「无连续跳过」，真实有 3 次连跳）。查到**两个叠在一起的坑**：
① **一次闸门决策写了两条记录**（`blocked` 原始文本 + `skipped` 分类 reason，同一时间戳）
→ 序列变成 `skipped, blocked, skipped, blocked…` → **`blocked` 把连续段打断** → 3 次连跳被算成 1 次；
② **两个数据源的时间戳基准不同**（日志用**启动**时刻、历史用**写入**时刻，预检跑 ~80s）
→ 同一个决策在两个源里差 80 秒 → 去重不掉 → 又数成两次。

**可立即执行的对策**：闸门侧改成「**一次决策一条记录**」且历史用**启动时刻**；
判据侧把 `blocked` 归一化成 `skipped` + 同 ts 去重 + 跨源 5 分钟窗口去重；
旧 `blocked` 的原始预检文本用 `_classify_reason_text()` 归一成结构化标签
（规则与闸门侧**一致** —— 单测当场抓到一处不一致：空 reason 时两侧返回 `""` vs `"unknown"`，
已统一为 `"unknown"`；**空 reason 绝不能当成 quota**，那是凭空指控「该充值」）。

现在实跑报的是：**3 次**（不是 1 也不是 4）· 原因如实是 `upstream_busy`
· 明确写「**不用充值**，先看上游是否恢复」。

**教训**：**「一次决策写几条记录」和「时间戳是什么基准」，都是计数类判据的前提。**
前提错了，**漏报方向恰好是最危险的那边**（额度枯竭了却不报警）。
→ **计数类判据必须先把「什么算一次」定义清楚。**


### 16:07 quick-health 失败 —— 同一个上游过载，**又**被报成了「可处理」

`openclaw-quick-health.service` exit 1，报：
```
⚠️  WARN  minimax 服务端错误（HTTP 529）{"type":"overloaded_error"}
❌ FAIL  **没有任何可用 provider** —— 整个系统无法推理
❌ FAIL  provider 检查未通过（详见上方）
结果: PASS=8  FAIL=3  (可处理 2 / 等用户 1)
```

**问题**：529 不是额度、不是配置坏了、也不是真故障 —— 上游集群过载，
**谁都不用做什么**（等 1-5 分钟自愈；实测直连 `max_tokens=5` → **200 / 1.54s**）。
但旧措辞「整个系统无法推理」**不含任何「等待」特征** → 被归「**可处理 - 现在就该修**」
→ **长期性假警报**。

**这是 E69 的同源问题**：信号在 **WARN 那行**（529），而被分类的是**另一条 FAIL**
（"没有任何可用 provider"）—— 「信号存在，但不在分类器读的那条路径上」。
今早我修了闸门【G2】的同一类问题，**但漏了 quick-health 这条路径**。

**修法**：
- `check_provider_health.py` 探针加 **529 专用分支**（此前混进「服务端错误」通用分支）
  → 措辞带「**无需处理**」；「没有可用 provider」也**三态**区分：额度 / 过载 / 真故障
- `quick_health.py` 的 `WAITING_ON_USER` 加「上游瞬时过载」「无需处理」
- 新增单测组【7】（12 断言，**故障注入跑真身 `probe()`**，不抄判据）：
  529 → warn + 带「无需处理」；**500 不带**（500 未必自愈）；真故障不被藏进「等你」(E59)

**实测前后对比**：修复前「**可处理 2** / 等用户 1」→ 修复后「**可处理 0** / 等用户 1」✅
额度分类单测 30 → **42 全 PASS**。

**教训**：
> **同一个根因会从多条路径冒出来，修了一条不等于修完了。**
> 今早修了闸门【G2】，今天 16:07 同一个 529 又从 quick-health 这条路径冒出来。
> → **修「信号分类」这类问题时，要问：「还有哪些组件会读这条信号？」**
> → 答案不能靠想，得**把 grep 一遍**（今天就该在修完闸门后顺手 grep 一下）。

**顺带**：预检的**降档阶梯**在这次实测中生效了 —— 529 → 退避 25s → 重试 → **1.08s 通过** ✅
（这正是今早加它的原因，现在有了第二次实战验证。）
