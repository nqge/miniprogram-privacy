### 二、E78 的修法落地

E78 讲的是：**任何以「连续 N 次」为阈值的判据，都必须同时检查这 N 次跨越了多长时间**。
`check_gate_skips.py` 的 `FAIL_CONSECUTIVE = 3` 语义是「连着 3 天枯竭」

但实现**只数条数**（`cur += 1`），**从不看时间跨度**。

**改法**（三处）：
1. 新增常量 `SPAN_MIN_DAYS = 2` / `SPAN_MIN_HOURS = 6`，
   并在 `FAIL_CONSECUTIVE` 旁边**写清楚单位是「3 条记录」不是「3 天」**；
2. 计算那段连续跳过的**首末时间戳 + 自然日跨度 + 小时跨度**，
   判定 `sustained`（条数够 **且** 跨度够）；
3. 报「连续 N 次」时**把首末时间戳一起打出来**（E78 教训③）。

**关键分支**：条数够但跨度不够 → `retry_only` → **只报 WARN，不占用额度告警名额**。

**单测**：新增 2 个用例 ——
2b) 同一天 27 分钟内 3 次重试 → **不应** FAIL（`retry_only=True`，`span_ok=False`），
    且措辞必须含首末时间戳 + 「E78」；
2c) 首末间隔 >6 小时 → 应算持续枯竭（`span_ok=True`）。
→ `python3 scripts/check_gate_skips.py --self-test` ✅ 全部通过。

**实测前后**（真实数据）：

### E79 是什么

巡检【D】组投递判据里，**「次数」和「天数」来自不同的段**：
```python
consec    = _max_consecutive_errors_history(runs)   # ← 窗口内「最长的一段」
span_days = _outage_span_days(runs)                # ← 「最近的一段」
```
→ 报出「历史上曾连续失败 **5** 次（约 **11** 天，现已恢复）」
—— 那 5 次其实只跨 4 天，「11 天」是拿**另一段**的起点量的。
**两个数字各自都对，凑在一句话里就是假的。**

### 改法（`scripts/check_cron_delivery.py`）

1. 新增 `_max_consecutive_errors_segment(runs)` → 返回**最长段本身**
   （count / first_ms / last_ms / success_before_ms / newest_ms）；
2. 新增 `_segment_span_days(seg)` → 天数**只从指定段**量；
3. WARN 分支：次数取 `seg["count"]`，天数取 `_segment_span_days(seg)` → **同一段**；
4. 报告里追加**该段首末时间戳** → 读的人能自己核对跨度。

### 单测 +8 个（36 → 44 全 PASS）

⭐ **故障注入证明用例真抓得住 bug**（E79 原文的核心要求）：
造「早期 5 次连挂跨 4 天 + 近期 2 次连挂跨 1 天」→
- 旧写法 `_outage_span_days` → **2 天**（取了「最近段」）
- 新写法 `_segment_span_days` → **5 天**（取了「最长段」自身）
→ 两者**结果不同** → 用例确实能区分新旧实现。

### 真实数据实测

```
修复前：WARN daily-learning 历史上曾连续失败 6 次（约 N 天，现已恢复）  ← N 来自别的段
修复后：WARN daily-learning 历史上曾连续失败 6 次（约 6 天，现已恢复）
        —— 该段 2026-11-10 09:00 → 2026-11-15 09:00
```
→ 6 次 error 跨 11-10 ~ 11-15 = **6 天**，**数字与时间戳互相印证** ✅

### 顺手踩到的坑（值得记）

`runs` 是**倒序**（最新在前）→ 一段连续失败里**先遇到的 error 是最新的一次**，
后面遇到的越来越旧 → **段首/段末的赋值顺序和直觉相反**。
我第一版把 `first_ms`/`last_ms` 装反了，**单测立刻报 3 个 FAIL** 把它抓了出来。

→ 这是 **E79 的反面教材**：E79 说「单测没覆盖配对」；
   今天单测**覆盖到了**，它就替我抓到了实现错误。
   **同一件事的两面 —— 覆盖了就值钱。**
