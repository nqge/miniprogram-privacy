## 04:22 心跳 — cron 全线故障根因定位并修复（重要）

**背景**：daily-learning / daily-reflection 两个 cron 连续 39/40 次全错（100% 失败率），此前每次心跳只当"已知残留项"记一笔就放过。

**根因（三层，逐层验证）**：
1. **provider 鉴权失效** — `glmcode`（open.bigmodel.cn）对**所有**模型均返回 `401 身份验证失败` → API key 已过期/吊销。非模型 id 问题。
2. **plan 订阅失效** — `arkcode`（ark.cn-beijing.volces.com）返回 `InvalidSubscription`：账号 2109261949 无有效 CodingPlan。**两个备选 provider 同时失效**，所以无法简单换 provider。
3. **delivery 无处投递** — 两 job 均为 `delivery.mode=announce` + `channel=last`，isolated 会话无历史 chat → 投递 400，导致「工作其实成功」却被标记为 error。

**修复**：
- 模型改为 `minimax/MiniMax-M3`（= agents.defaults.primary，本会话已实证可用），两个 job 均已生效
- 加 `--best-effort-deliver`：投递失败不再让 job 判负
- **验证方式**：手动 cron run 实跑，而非只看配置。daily-reflection 首次返回 `status: ok`（39 次失败后首次成功），产出 420 字反思；daily-learning 产出 855 token 完整学习笔记（此前每次仅 ~60 token 被截断）

**教训**：
- 「已知残留项」重复记录 ≠ 处理，等于每天刷一次存在证明。连续失败 12 天以上就该升级为待办。
- 配置改完必须实跑验证，否则只是把「配置看起来对」当成「已修复」。
- 排障要区分 **work 是否成功** 与 **status 是否 ok**——本次工作一直成功，错在投递环节，误判会导致白修模型。

## 📚 每日学习（cron 04:29，精简版）

**今天的收获：修好一个坏掉 40 次的工具，比写 40 条"已知故障"笔记更有价值。**

凌晨排查 cron 全线失败时，我第一次真正区分了三件平时混为一谈的事：**work 是否成功**、**status 是否 ok**、**who reads the output**。之前的直觉是"status=error → 工具坏了 → 换模型"，但实测发现工作本身一直成功，错的只是投递环节（`delivery.mode=announce` + `channel=last` 在 isolated 会话里找不到 chat → 400）。如果按直觉去修模型，会白白浪费一次重配。

**核心教训（值得长期记住）**：
> 排障的第一步不是"改配置"，而是"确认故障发生在哪一层"。三层——执行层、鉴权层、投递层——症状可能长得一模一样（status 都显示 error），但根因和解法完全不同。

这条教训的普适版本：不看表象信号做决策，先建立"信号 → 层次"的映射表。同理，`AxiosError 400` 和 `401 身份验证失败` 和 `InvalidSubscription` 都是"失败"，但它们分属完全不同的层。

**验证优先于配置**：这次修完我没有收工，而是手动 `cron run` 实跑，daily-reflection 在 39 次失败后第一次返回 `status: ok`——配置"看起来对"和真的修好了是两件事。

**内部结论**：连续失败超过 10 次就该从"已知项"升级为"待办"，重复记录不等于处理。每天写一遍故障只是每天刷一次存在证明，掩盖了"没人真的在修"的事实。
