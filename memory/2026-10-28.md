### 可处理失败 2：【W】【V】判据单测失败 → 已修（根因是测试自己写错了）
- 现象：场景「规则生效前启动的会话 → 不算无视规则」❌ 失败
  实际返回 `{long_total:0, poll_total:0}`，而期望 `pre_rule=1`
- 根因：测试用 `mk_session(d,'pre',[(180000,1)], pre_iso)`，
  其中 offset=**1 秒** → poll 时间戳 = 会话启动 +1 秒
  → 而规则写入时间（commit 6d11015，2026-10-27 09:57）距巡检时刻已 **21 小时**，
  远超【V】的 **12 小时窗口** → poll 落在窗口外 → 计数为 0
- **更深一层**：这个场景用「相对 offset」在结构上**根本造不出来** ——
  要么 offset 太小（窗口外），要么 offset 大到把 poll 推到未来
  （会话启动时间也跟着推后 → 不再早于规则写入时间 → 前提被破坏）
- 修法：
  1. 给 `mk_session` 加 `mk_session_abs(...)`，支持 `abs_polls=[(timeout_ms, abs_ts)]`
     —— 用**绝对 epoch 秒**精确控制「poll 在窗口内」
  2. 场景 9 改为：会话启动 = 规则写入时间 - 5 分钟（保持前提），
     poll 时间戳 = `now - 60s`（保证在 12h 窗口内）
- 结果：**13/13 全通过**，退出码 0
- 记忆：**「会话很老但 poll 发生在最近」这类用例，时间戳必须用绝对值**，
  靠相对 offset 偏移会悄悄退化成「窗口外」→ 断言看着在测 A，实际测的是 B

## 07:35 追加 - 逐个 provider 实测：为什么 fallback 无效（provider 级故障兜底 FAIL 项的根因）

### 背景
healthcheck cron 07:00 跑完：`PASS=60, FAIL=3, WARN=1`，3 个 FAIL 里有一个是
**「单一 provider 下配了 2 项同账号 fallback（provider 级故障兜底无效）」**。
配置里 `agents.defaults.model.fallbacks = ["minimax/MiniMax-M2.7-highspeed","minimax/MiniMax-M2.7"]`
—— 两个 fallback **都是 minimax**，minimax 一挂就全挂（与 10-27 17:01 余额耗尽那次同源）。

### 关键发现：另有 4 个 provider 已配置且有 key，但**全都不可用**
`agents/main/agent/models.json` 里已有 5 个 provider：`arkcode / glmcode / qwen / kimicode / minimax`。
我逐个发了真实请求（按各自 `api` 字段拼 URL：anthropic-messages → `<base>/v1/messages`，
openai-completions → `<base>/chat/completions`），结果：

| provider | endpoint | 实测结果 | 根因判定 |
|---|---|---|---|
| glmcode | open.bigmodel.cn/api/anthropic | 全部模型 **401 身份验证失败** | **API key 失效/过期**（非模型问题，7 个模型全 401） |
| qwen | dashscope .../compatible-mode/v1 | 多数 **400 Access denied / account not in good standing**；`qwen-turbo` 429 | **账号被限制/欠费**（429 说明 key 有效但被限流） |
| arkcode | ark.cn-beijing.volces.com/api/coding | 多数 **404 UnsupportedModel**；`kimi-k2-thinking` → **400 InvalidSubscription（账号 2109261949）** | **无有效订阅**（coding 端点不认这些 model id） |
| kimicode | api.kimi.com/coding/v1 | **404 resource_not_found**；换 api.anthropic.com → 403 | **coding-plan key 不能调公共 API** |
| minimax | api.minimaxi.com/anthropic | ✅ 正常（本次巡检全程在用） | ✅ 唯一可用 |

### 结论
→ FAIL 项「同账号 fallback 无效」**不是配置写错，是**「**没有第二个可用 provider**」
→ 这 4 个 key 需要**各自重新充值/换取新凭证**，不是改 `fallbacks` 数组能解决的
→ 我**没有**擅自改 `fallbacks`（换成一个同样坏的 provider 只是把失败掩盖掉）
